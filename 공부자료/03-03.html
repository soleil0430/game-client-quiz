CPU 쪽 최적화

매 프레임 드는 탐색 비용과 엔진 경계 비용을 캐싱과 매니저 순회로 걷어낸다

매 프레임 도는 코드에서 비싼 것은 계산이 아니다. 무언가를 찾는 비용과 엔진 경계를 넘나드는 비용이 먼저 쌓인다. 둘 다 답이 같은데 매번 다시 하는 일이다.

참조는 한 번만 찾아 필드에 담는다

GetComponent는 그 게임오브젝트의 컴포넌트 목록을 훑는 네이티브 호출이다. GameObject.Find는 씬 전체를 훑으며 이름을 비교한다. 결과가 안 바뀌는데 매 프레임 다시 찾을 이유가 없다.

총알이 자기 Rigidbody를 매 프레임 찾지 않게 하는 코드다: 

Rigidbody _body;                          // 참조는 필드에 담아 둔다void Awake(){_body = GetComponent<Rigidbody>();    // 탐색은 생길 때 한 번만}

가장 싼 방법은 인스펙터로 미리 넣거나 생성한 쪽에서 넘겨 주는 것이다. 그럴 수 없으면 Awake에서 한 번 찾는다. Find는 비활성 오브젝트를 못 찾으니 공용 객체는 매니저에 등록해 조회한다.

Update 하나마다 엔진 경계를 한 번씩 넘는다

Update가 있는 스크립트는 개수만큼 엔진(C++)에서 스크립트(C#)로 넘어오는 호출이 생긴다. 이 경계 비용은 본문이 비어 있어도 든다. 빈 Update를 지우라는 말이 여기서 나온다.

총알 1000개를 매니저 하나로 모은 코드다: 

public class BulletManager : MonoBehaviour{readonly List<Bullet> _list = new List<Bullet>(1024);void Update()                  // 경계를 넘는 호출은 이 하나뿐{float dt = Time.deltaTime;for (int i = 0; i < _list.Count; i++)_list[i].Tick(dt);     // Bullet에는 Update가 없다. Tick만 있다}}

매니저가 리스트를 돌면 경계를 한 번만 넘는다. 데이터도 연속으로 놓여 캐시에 유리하다. 더 밀어붙이면 Job System과 Burst로 병렬화하거나 갱신 주기를 나눈다.

Canvas는 갱신 빈도로 나눈다

UGUI는 Canvas 단위로 자식 메시를 하나로 합쳐 그린다. 요소 하나가 바뀌면 그 Canvas 전체의 레이아웃과 배치를 다시 만든다. 범위가 Canvas 단위라는 점이 핵심이다.

매 프레임 바뀌는 타이머가 정적 HUD와 같은 Canvas에 있으면 정적인 부분까지 함께 다시 만든다. 그래서 자주 바뀌는 요소를 별도 Canvas로 뗀다.

다만 Canvas가 늘면 배칭이 끊겨 드로우 콜이 는다. 기준은 갱신 빈도지 요소 개수가 아니다.

면접에서 이렇게 답한다

  • GetComponent를 왜 캐싱하나 — 컴포넌트를 찾는 탐색이 매 프레임 반복되기 때문이다. 참조가 바뀌지 않으면 Awake에서 한 번 받아 필드에 두고 재사용한다.
  • GameObject.Find를 피하는 이유와 대안 — 씬 전체를 훑고 이름을 비교해 오브젝트가 많을수록 느리다. 비활성 오브젝트는 찾지도 못한다. 인스펙터 주입이 가장 싸고, 공용 객체는 매니저에 등록해 조회한다.
  • 같은 로직의 오브젝트가 수천 개면 — 개별 Update를 없애고 매니저가 배열을 순회하며 일괄 처리한다. 그래도 모자라면 Job System과 Burst로 넘기거나 갱신 주기를 나눈다.
  • Canvas를 왜 나누나 — 요소 하나만 바뀌어도 그 Canvas 전체를 다시 구성하기 때문이다. 자주 바뀌는 UI를 떼되 드로우 콜이 늘지 않는 선에서 나눈다.

이런 오해를 한다

  • GetComponent는 내부에서 캐싱된다 — 아니다. 호출할 때마다 컴포넌트 목록을 다시 찾는다.
  • SendMessage가 간단해서 쓸 만하다 — 문자열로 메서드를 찾아 부르는 방식이라 직접 호출보다 훨씬 느리다. 오타도 컴파일러가 못 잡는다.
  • 빈 Update는 공짜다 — 본문이 비어도 엔진이 호출 목록에 넣고 매 프레임 부른다. 안 쓰면 지운다.
  • Canvas는 잘게 나눌수록 좋다 — 나눌수록 배칭이 끊겨 드로우 콜이 는다. 정적 UI와 동적 UI를 가르는 정도가 기준이다.

3줄 정리

  • 찾는 비용은 Awake에서 한 번 찾아 필드에 담아 없앤다
  • Update는 매니저 하나로 모아 엔진 경계를 한 번만 넘는다
  • Canvas는 갱신 빈도로 나눈다. 잘게 쪼개면 드로우 콜이 는다
