설계·아키텍처

객체지향

데이터와 규칙을 한 클래스에 묶고, 바뀔 자리는 인터페이스로 열어 둔다

방어력 계산 규칙이 바뀌었다. 절차지향 코드라면 그 데이터를 만지는 함수를 전부 찾아야 한다. 플레이어와 몬스터와 파괴물이 각자 계산하고 있으면 한 곳만 빠뜨려도 버그다.

객체지향은 데이터와 그 데이터를 다루는 규칙을 한 클래스에 묶는다. 고칠 곳이 한 군데로 모이는 대신, 클래스와 간접 호출이 늘어 흐름은 읽기 어려워진다.

네 가지 특징은 각각 무엇을 막아 주나

추상화·캡슐화·상속·다형성은 그냥 외울 목록이 아니다. 넷은 각각 다른 사고를 막아 준다.

특징하는 일막아 주는 사고
추상화세부를 걷어내고 쓸 면만 남긴다구현이 바뀌면 쓰는 쪽까지 깨진다
캡슐화상태를 감추고 공개 메서드로만 다룬다남의 코드가 체력을 음수로 만든다
상속부모 멤버를 물려받아 특수화한다같은 코드가 클래스마다 복사된다
다형성같은 호출이 실제 타입에 따라 갈린다타입이 늘 때마다 분기가 늘어난다

넷은 서로 헷갈리기 쉬운데 한 줄씩 붙여 두면 갈린다. 캡슐화는 내부 상태를 숨기고 공개 메서드로만 다루게 하는 것, 그러니까 필드를 private으로 감추고 프로퍼티나 메서드로만 드나들게 해서 지켜야 할 조건을 클래스 안에서 스스로 지키게 하는 것이다.

물려받아 재사용하는 것은 상속, 세부를 걷어내 단순화하는 것은 추상화, 같은 이름이 타입에 따라 다르게 도는 것은 다형성이다.

Unity에서는 [SerializeField] private 필드를 써서 인스펙터 노출과 캡슐화를 같이 챙기는 것이 관례다. 인스펙터에서는 값을 조정하면서 다른 스크립트는 내부 상태를 못 건드린다.

SOLID는 바뀔 자리를 미리 열어 두는 다섯 지침

다섯 지침은 지금 잘 도는 코드를 위한 것이 아니다.

다음에 바뀔 코드를 위한 것이다.

원칙뜻게임에서
SRP 단일 책임바뀌어야 할 이유가 하나뿐체력 계산과 체력바 연출을 분리
OCP 개방-폐쇄확장에는 열고 수정에는 닫는다새 무기는 분기 수정 없이 클래스 추가
LSP 리스코프 치환자식이 부모 자리에 들어가도 동작부모의 약속을 예외로 막지 않기
ISP 인터페이스 분리안 쓰는 메서드를 떠안기지 않는다공격 안 하는 것에 공격 계약을 안 붙임
DIP 의존 역전상위와 하위가 모두 추상화에 의존전투 로직은 IWeapon만 안다

표에 줄여 놓은 것을 풀면 이렇다. 단일 책임은 한 클래스가 바뀌어야 할 이유가 하나뿐이어야 한다는 뜻이다. 체력 규칙이 바뀔 때와 체력바 연출이 바뀔 때는 서로 다른 이유이므로 다른 클래스로 나누는 쪽이 맞고, 필드나 메서드 개수를 세는 규칙이 아니다.

개방-폐쇄는 새 기능을 추가할 때 기존 코드를 고치지 않고 새 코드를 더할 수 있는 구조를 말한다. 무기 종류마다 switch 문을 고치는 대신 공통 인터페이스를 두고 구현 클래스를 추가하면, 기존 코드를 건드리지 않아 회귀 위험이 줄어든다.

리스코프 치환은 자식 타입이 부모 타입 자리에 들어가도 프로그램이 올바르게 동작해야 한다는 원칙이다. Penguin : Bird의 Fly()가 예외를 던지면, 부모가 약속한 동작을 자식이 막은 셈이라 Bird를 받는 코드가 깨진다.

이럴 때는 나는 능력을 별도 인터페이스로 분리하는 식으로 설계를 바꾼다. 약속을 지키면서 동작을 강화하거나 다르게 구현하는 것은 위반이 아니다.

인터페이스 하나로 OCP와 DIP를 같이 지킨다

무기가 늘 때마다 switch를 고치는 코드는 무기를 하나 더할 때마다 전투 로직 전체를 다시 검증하게 만든다. 인터페이스를 두고 구현만 더하면 기존 코드는 손대지 않는다.

의존 역전은 호출 방향을 뒤집으라는 말이 아니다. 상위 모듈이 하위 구현을 직접 알지 말고 둘 다 추상화에 의존하게 하라는 뜻이다. 인터페이스를 쓰는 쪽인 상위가 정의하고 하위가 그것을 구현하게 하는 것이 핵심이고, 의존성 주입은 이 원칙을 실제로 굴리려고 구현체를 밖에서 넣어 주는 기법이다.

덤으로 결합도가 내려간다. 결합도가 높으면 한 클래스를 고칠 때 붙어 있는 클래스까지 줄줄이 고쳐야 하고 테스트도 따로 못 한다. 구체 타입 말고 계약에만 의존하면 구현을 갈아 끼우거나 가짜 구현으로 바꿔 끼워 테스트할 수 있다.

반대로 결합을 키우는 것들은 정해져 있다. 공개 필드와 정적 변수를 늘리는 것, 그리고 상속 계층을 깊게 쌓는 것이다.

전투 로직이 구체 무기 대신 계약만 아는 코드다:

public interface IWeapon { void Fire(Vector3 origin); }

public class Attacker : MonoBehaviour
{
    private IWeapon weapon;                     // 구체 타입이 아니라 계약에 의존

    public void Equip(IWeapon w) => weapon = w; // 구현은 밖에서 넣어 준다

    private void Update()                       // 어떤 무기인지 몰라도 발사된다
    {
        if (Input.GetButtonDown("Fire1")) weapon?.Fire(transform.position);
    }
}

상속은 얕을 때만, 나머지는 컴포지션

다형성은 두 갈래다. 메서드 오버로딩이나 제네릭처럼 컴파일 시점에 어느 함수를 부를지 정해지는 것이 정적 다형성이고, virtual과 override로 실행 중 실제 타입을 보고 정해지는 것이 동적 다형성이다.

오버로딩과 오버라이딩을 뒤집어 놓은 설명이 가장 흔한 함정이다. 동적은 가상 함수 테이블을 한 번 더 거치므로, 매 프레임 수천 번 도는 루프에서는 비용을 따져 본다.

그럼 언제 상속인가? “~이다” 관계가 뚜렷하고 공통 동작이 분명하며 계층이 얕을 때다. 날기·헤엄치기·공격 같은 능력을 상속으로 조합하려 들면 FlyingSwimmingEnemy 같은 클래스가 늘고 계층이 굳어 바꾸기 어려워진다.

컴포지션은 이동·체력·공격 같은 기능을 독립 컴포넌트로 따로 두고 필요한 것만 붙인다. 조합이 자유롭고 재사용이 쉬워, 깊은 상속 계층이 부르는 중복과 경직성을 피한다. Unity의 GameObject와 컴포넌트가 이 방식을 엔진 차원에서 구현한 것이다.

면접에서 이렇게 답한다

  • 객체지향이란 — 데이터와 규칙을 객체로 묶어 책임을 나누는 방식이다. 네 특징으로 설명하고, 얻는 것은 변경이 한곳에 갇히는 것이라고 덧붙인다.
  • SOLID를 적용한 예 — 무기가 늘 때마다 분기를 고치던 코드를 IWeapon으로 바꿨다고 말한다. 원칙 이름을 외우는 것보다 고친 코드 하나가 강하다.
  • LSP를 어기는 코드 — Bird를 상속한 Penguin이 Fly()에서 예외를 던지는 경우다. Bird를 믿고 쓰는 코드가 깨지니 “난다”를 별도 인터페이스로 뺀다.
  • 상속과 컴포지션 — 기본은 컴포지션이다. 모든 팝업이 공유하는 열기·닫기 흐름처럼 공통 동작이 뚜렷하면 얕은 상속이 더 읽기 쉽다고 단서를 단다.
  • 결합도 낮추기 — 구체 타입 대신 인터페이스에 의존하고, 참조는 밖에서 받는다. 먼 시스템끼리는 이벤트로 알린다.

이런 오해를 한다

  • “DIP는 호출 방향을 뒤집는 것” — 뒤집는 것은 의존 대상이다. 인터페이스를 상위 쪽 필요에 맞춰 정의하고 하위가 구현한다.
  • “SRP는 클래스를 작게 쪼개라는 뜻” — 개수를 세는 규칙이 아니다. 기준은 바뀌어야 할 이유이고, 한 매니저에 다 모으는 것이 가장 크게 어긴 꼴이다.
  • “오버라이딩이 정적 다형성” — 반대다. 오버로딩이 컴파일 시점, 오버라이딩이 실행 시점이다.
  • “자식이 부모와 다르게 동작하면 LSP 위반” — 약속을 지키면서 구현을 바꾸는 것은 다형성의 목적이다. 위반은 약속 자체를 깨뜨릴 때다.

3줄 정리

  • 데이터와 규칙을 한 클래스에 묶어 고칠 곳을 모은다.
  • SOLID의 핵심은 갈아 끼울 자리를 인터페이스로 여는 것.
  • 상속은 얕은 계층에만, 나머지는 컴포지션으로 조합한다.
