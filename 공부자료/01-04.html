컬렉션·문자열·LINQ

내부 자료구조를 알아야 무엇이 O(1)이고 어디서 할당이 생기는지 보인다

인벤토리에서 아이템 하나를 찾는 코드가 리스트 순회라면 개수에 비례해 느려진다. Dictionary로 바꾸면 개수와 상관없이 일정하다. 이 차이는 문법이 아니라 내부 자료구조에서 온다.

List는 배열을 품고 두 배로 자란다

배열은 길이가 고정된 연속 메모리다. 그래서 인덱스 접근이 가장 빠르다. List<T>는 그 배열을 안에 품고, 모자라면 보통 두 배짜리 새 배열로 옮겨 담는다.

그래서 Add는 평균 O(1)이다. 다만 늘어나는 순간에는 복사 비용과 버려진 배열만큼의 가비지가 생긴다. 개수를 대충이라도 알면 생성자에 용량을 넘겨 재할당을 줄인다.

Remove를 해도 Capacity는 줄지 않는다. 중간 삽입과 삭제는 뒤 원소를 전부 밀어야 해서 비싸다.

Dictionary가 평균 O(1)인 이유

Dictionary<TKey, TValue>는 키의 GetHashCode()로 버킷을 정한다. 그 버킷 안에서만 Equals로 비교한다. 전체를 훑지 않으니 평균 O(1)이다.

뒤집으면 해시가 한쪽으로 몰릴 때가 최악이다. 한 버킷을 길게 훑게 되어 O(n)이 된다. 그래서 키 타입의 GetHashCode 품질이 성능을 좌우한다.

커스텀 타입을 키로 쓰면 GetHashCode와 Equals를 함께 재정의한다. 그 기준 필드는 넣은 뒤에 바뀌면 안 된다. 열거 순서도 보장되지 않는다.

정렬된 순회가 필요하면 SortedDictionary나 SortedSet을 쓴다. 균형 이진 탐색 트리라 조회가 O(log n)이 되는 것을 감수한다.

string은 불변이라 고치면 새것이 생긴다

Replace나 ToUpper는 원본을 고치지 않는다. 바뀐 새 문자열을 돌려줄 뿐이다. 반환값을 다시 담지 않으면 아무 일도 일어나지 않는다.

불변이라 생기는 실수와 그 대안을 나란히 둔 코드다: 

string s = "hello";
s.ToUpper();        // 반환값을 버렸으므로 s는 그대로 "hello"
s = s.ToUpper();    // 새 문자열을 다시 담아야 바뀐다

var sb = new StringBuilder();
foreach (var n in names)
    sb.Append(n).Append(", ");   // 이어 붙일 때마다 새 문자열을 만들지 않는다
string line = sb.ToString();

같은 이유로 반복문에서 +=로 이어 붙이면 매번 새 문자열이 생긴다. 이전 것은 그대로 가비지가 된다. 조각이 많으면 StringBuilder로 버퍼에 이어 쓴다.

Split처럼 배열과 문자열을 한꺼번에 만드는 메서드도 있다. 매 프레임 도는 코드에서는 피한다.

LINQ는 결과를 요구할 때 비로소 계산한다

Where나 Select는 호출하는 순간 계산하지 않는다. foreach로 돌리거나 ToList(), Count()로 결과를 요구할 때 계산한다. 이것을 지연 실행이라 한다.

원본은 바뀌지 않고 새 시퀀스가 나온다. 원본을 바꾼 뒤에 열거하면 결과가 달라지는 것도 지연 실행 때문이다.

읽기 좋은 대신 이터레이터 객체와 람다가 힙에 생긴다. 초기화나 에디터 도구, 로딩 코드에는 마음껏 쓴다. 매 프레임 도는 경로에서는 for 문으로 풀어 쓰는 편이 안전하다.

면접에서 이렇게 답한다

  • 배열과 List의 차이 — List는 내부에 배열을 두고 자동으로 늘리는 동적 배열이다. 크기가 고정이고 성능이 예민한 자리는 배열을 쓴다. 개수가 변하는 자리는 List를 쓰되 예상 개수를 용량으로 미리 준다.
  • Dictionary는 어떻게 O(1)인가 — 키의 해시로 버킷을 바로 찾고 그 안에서만 비교하기 때문이다. 해시가 몰리면 한 버킷을 훑게 돼 최악 O(n)이다. 그래서 키 타입의 GetHashCode 품질이 성능을 좌우한다.
  • 문자열 연결이 왜 문제인가 — string이 불변이라 이어 붙일 때마다 새 객체가 생긴다. 이전 것은 가비지가 된다. 매 프레임 UI 텍스트를 이렇게 만들면 GC 끊김의 원인이라 StringBuilder나 보간을 쓴다.
  • LINQ를 실무에서 쓰나 — 읽기 쉬워서 초기화와 에디터 도구, 로딩 코드에는 적극적으로 쓴다. 매 프레임 도는 경로에서는 할당 때문에 걷어낸다. 판단 근거는 프로파일러의 GC Alloc 수치라고 덧붙인다.

이런 오해를 한다

  • s.ToUpper();를 호출하면 s가 바뀐다 — string은 불변이라 새 문자열이 반환될 뿐이다. s = s.ToUpper();처럼 다시 담아야 한다.
  • List는 연결 리스트다 — List<T>는 내부가 배열인 동적 배열이다. 중간 삽입과 삭제가 잦으면 뒤 원소를 밀어야 해서 오히려 비싸다.
  • Dictionary는 넣은 순서대로 열거된다 — 순서는 보장되지 않는다. 순서가 필요하면 SortedDictionary나 별도의 리스트를 함께 둔다.
  • LINQ는 호출하는 순간 결과가 만들어진다 — 대부분 지연 실행이라 열거할 때 계산된다. 원본을 바꾼 뒤에 결과가 달라지는 것도 이 때문이다.

3줄 정리

  • List는 배열을 품고 두 배로 자라는 동적 배열이다
  • Dictionary는 해시로 버킷을 골라 평균 O(1)이 된다
  • string은 불변, LINQ는 지연 실행. 둘 다 할당을 만든다
