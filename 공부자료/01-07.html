예외 처리

스택 추적은 throw 자리에서 채워지고 catch는 하나만 골라 실행된다

라이브 빌드 로그에 스택 추적이 찍혔다. 그런데 맨 윗줄이 우리 catch 줄이다. 진짜 터진 자리는 어디에도 없다.

throw ex; 한 줄이 한 일이다.

스택 추적은 throw가 실행되는 자리에서 채워진다

예외는 '여기서는 더 못 한다'를 호출 스택 위로 올려 보내는 장치다. 던져지면 런타임이 현재 메서드에서 맞는 catch를 찾고, 없으면 자신을 부른 메서드로 한 칸 올라가 다시 찾는다.

여기서 중요한 사실 하나가 나온다. StackTrace는 예외 객체를 만들 때가 아니라 throw 문이 실행되는 지점에서 채워진다.

throw;는 잡은 예외를 원래 스택 추적째로 다시 올린다. throw ex;는 그 줄이 새 출발점이 되어 진짜 원인의 위치를 지운다. 로그 한 줄이 전부인 라이브 빌드에서는 이 차이가 크다.

스택 추적이 자꾸 남의 catch 줄을 가리킨다면 여기부터 의심한다.

원인을 감싸 올리고 싶으면 새 예외를 만든다. throw new XxxException(message, ex)로 InnerException에 원본을 담는다.

catch는 위에서부터 하나만 고른다

catch 절은 위에서부터 차례로 검사한다. 타입이 맞는 첫 하나만 실행되고 나머지는 건너뛴다.

파생 예외를 위에, Exception 같은 기반 예외를 아래에 적는 규칙이 여기서 나온다. 순서를 뒤집으면 아래 절에 영원히 도달할 수 없어 컴파일 오류가 난다.

재던지기와 감싸 올리기를 한 메서드에 모은 코드다:

static void Load(string path)
{
    var file = File.OpenRead(path);
    try { Parse(file); }                  // 여기서 FormatException이 났다고 하자
    catch (FormatException) { throw; }    // O: 원래 발생 위치가 그대로 남는다
    // catch (FormatException ex) { throw ex; }   X: 추적이 이 줄부터 다시 쌓인다
    catch (Exception ex)                  // 기반 예외는 아래에 적는다
    {
        throw new InvalidOperationException($"{path} 로드 실패", ex);
    }
    finally { file.Dispose(); }           // 예외가 나든 return을 하든 실행된다
}

같은 예외 타입을 조건으로 나누려면 예외 필터를 쓴다. catch (IOException e) when (조건) 형태다. 필터 식은 스택을 되감기 전에 평가되므로, 통과하는 시점의 호출 스택과 지역 변수가 그대로 남아 있다.

finally가 실행되지 않는 경우도 있나

거의 없다. finally는 제어가 블록을 떠날 때 실행된다. 예외가 났든 안 났든, catch에서 다시 던졌든, try 안에서 return했든 마찬가지다.

return도 예외가 아니다. 반환값을 먼저 계산하고, finally를 실행한 다음, 돌아간다.

자원 해제를 여기에 두는 이유가 그것이다. using은 컴파일러가 try-finally로 바꿔 주는 문법이다. 빠져나가는 경우는 Environment.FailFast처럼 프로세스가 그 자리에서 끝날 때뿐이다.

예외를 흐름 제어로 쓰지 않는 이유

예외는 던지는 순간 스택 정보를 모은다. 그 일이 매 프레임 도는 코드에서 반복되면 그대로 스파이크가 된다.

try 블록에 들어가는 비용은 사실상 없다. 비싼 쪽은 던지는 순간이다.

자주 일어나는 실패를 예외로 처리하지 않는 이유가 여기 있다. int.TryParse와 Dictionary.TryGetValue가 성공 여부를 반환값으로 알려 주는 모양인 것도 같은 까닭이다.

면접에서 이렇게 답한다

  • throw와 throw ex의 차이 — throw;는 잡은 예외를 그대로 다시 올려 원래 발생 위치의 스택 추적을 유지한다. throw ex;는 추적이 그 catch 위치에서 다시 시작돼 진짜 원인을 잃는다. 문맥을 덧붙이려면 새 예외로 감싸 InnerException에 원본을 남긴다고 답한다.
  • try-catch-finally의 실행 순서 — 예외가 나면 위에서부터 타입이 맞는 catch 하나만 실행되고, 그다음 finally가 실행된다. 여러 catch가 함께 실행되는 일은 없다.
  • catch 순서를 왜 신경 쓰나 — 기반 예외를 위에 두면 아래 절이 절대 실행될 수 없고, 컴파일러가 그것을 오류로 막는다. 구체적인 예외부터 위에 쓴다.
  • finally가 실행되지 않는 경우가 있나 — 거의 없다고 답한다. Environment.FailFast처럼 프로세스가 그 자리에서 끝나는 경우뿐이다. 그래서 자원 해제는 finally나 using에 맡겨도 된다.

이런 오해를 한다

  • “타입이 맞는 catch가 여러 개면 전부 실행된다” — 위에서부터 검사해 처음 맞는 하나만 실행한다. 나머지는 건너뛴다.
  • “throw ex;가 무엇을 던지는지 명시해서 더 낫다” — 명시적으로 보일 뿐 스택 추적을 날린다. 같은 예외를 다시 올릴 거라면 throw;가 맞다.
  • “try나 catch 안에서 return하면 finally를 건너뛴다” — 반환값을 계산한 뒤 finally를 실행하고 나서 돌아간다.
  • “Exception 하나로 다 잡아 두면 안전하다” — 복구할 수 없는 예외까지 삼키면 잘못된 상태로 계속 돌다 엉뚱한 곳에서 터진다.
  • “try 블록은 그 자체로 느리다” — 예외가 나지 않으면 진입 비용은 사실상 없다. 비싼 것은 실제로 던지는 순간이다.

3줄 정리

  • 스택 추적은 throw 문이 실행되는 자리에서 채워진다
  • 재던질 때는 throw ex가 아니라 throw를 쓴다
  • catch는 위에서부터 하나만, finally는 거의 언제나 실행된다
