가비지 컬렉션

루트에서 닿는가로 수거하는 원리와 Unity GC가 .NET과 다른 점

전투 중에 한 프레임이 툭 튄다. 프로파일러를 보면 가비지 컬렉션(GC)이 돌고 있다. 무엇이 수거 대상인지 알아야 그 할당을 없앨 수 있다.

수거 기준은 참조 개수가 아니라 루트에서 닿는가

GC는 참조가 몇 개인지 세지 않는다. 스택의 지역 변수, 정적 필드, 레지스터 같은 루트에서 출발한다. 참조를 따라가며 도달한 객체에 표시하고(mark), 표시되지 않은 것을 회수한다(sweep).

그래서 서로만 참조하는 객체 무리도 루트에서 끊기면 통째로 수거된다. 순환 참조가 문제가 되지 않는 이유다.

뒤집으면 누수는 안 쓰는데도 루트에서 닿는 것이다. 정적 컬렉션에 계속 담아 두거나 이벤트 구독을 해제하지 않은 경우가 전부 여기에 해당한다.

.NET은 세대로 나눠 0세대만 자주 훑는다

대부분의 객체는 금방 죽는다. .NET의 GC는 이 관찰에 기대어 힙을 0·1·2세대로 나눈다. 0세대만 자주 싸게 훑는다.

0세대 수집에서 살아남으면 1세대로, 또 살아남으면 2세대로 승격된다. 2세대 수집은 힙 전체를 훑기 때문에 드물게 일어나고 비싸다.

약 85,000바이트 이상인 큰 객체는 따로 큰 개체 힙(LOH)에 할당된다. 복사 비용이 커서 기본적으로 압축하지 않아 단편화가 생기기 쉽다. 2세대와 함께 수집돼 비싸므로 큰 배열은 새로 만들기보다 풀에 넣고 재사용한다.

Unity의 GC는 세대가 없다

중요한 점은 Unity가 이 세대별 GC를 쓰지 않는다는 것이다. Mono든 IL2CPP든 Boehm GC를 쓴다. 세대 구분이 없고 객체를 옮기지 않아 힙이 단편화될 수 있다.

증분 GC는 수집 작업을 여러 프레임에 나눈다. 한 번에 멈추는 시간은 줄지만 할당 자체는 줄지 않는다. Unity 2022 LTS 기준으로 증분 GC는 기본으로 켜져 있다.

결국 게임에서 할 일은 GC를 튜닝하는 것이 아니다. 매 프레임 생기는 할당을 풀링과 캐싱으로 없애는 쪽이다.

GC가 모르는 자원은 직접 풀어야 한다

파일 핸들, 소켓, 네이티브 플러그인이 잡은 메모리는 GC가 모른다. IDisposable로 직접 풀어야 한다. using은 try-finally로 컴파일되므로 예외가 나도 Dispose가 불린다.

누수가 나는 구독과 예외에도 안전한 해제를 한자리에 둔 코드다: 

class HudPanel
{
    public void Show() => GameEvents.Died += OnDied;
    public void Hide() => GameEvents.Died -= OnDied;
    // Hide를 빼먹으면 정적 이벤트가 이 패널을 계속 참조해 수거되지 않는다
    void OnDied() { }
}

// using은 try-finally로 컴파일된다. 예외가 나도 Dispose가 불린다
using (var stream = File.OpenRead("save.dat")) { }

소멸자(Finalize)는 안전망으로만 둔다. 불리는 시점이 정해져 있지 않다. 파이널라이저 큐를 한 번 거치느라 객체 수거가 오히려 한 번 더 미뤄진다.

면접에서 이렇게 답한다

  • C#의 GC는 어떻게 동작하나 — 루트에서 도달 가능한 객체를 표시하고 나머지를 회수하는 마크 앤 스윕이다. 참조 카운팅이 아니므로 순환 참조도 수거된다. 대신 정적 필드나 이벤트로 루트에 매달린 객체는 영원히 남는다.
  • 세대를 나누는 근거 — 대부분의 객체가 금방 죽는다는 경험칙이다. 갓 만든 객체만 모아 자주 싸게 수집하면 전체 힙을 훑는 비싼 수집을 덜 하게 된다.
  • Unity의 GC는 무엇이 다른가 — Boehm GC라 세대가 없고 객체를 옮기지 않아 단편화가 생긴다. 증분 GC는 멈춤 시간을 여러 프레임에 나눌 뿐이다. 대책은 풀링과 캐싱으로 할당을 줄이는 쪽이다.
  • Dispose와 Finalize의 차이 — Dispose는 내가 시점을 정해 부르는 해제다. Finalize는 GC가 언젠가 부르는 안전망이다. unmanaged 자원은 using으로 Dispose를 보장하는 것이 원칙이다.

이런 오해를 한다

  • 2세대 수집이 0세대보다 자주 일어나고 싸다 — 반대다. 0세대가 자주 싸게 돌고, 2세대는 힙 전체를 훑어 드물게 일어나며 비싸다.
  • 순환 참조는 수거되지 않는다 — 참조 카운팅을 쓰던 COM 시절의 이야기다. 도달 가능성으로 판단하므로 루트에서 끊기면 함께 수거된다.
  • Unity도 세대별 GC를 쓴다 — Boehm GC라 세대 구분이 없다. LOH 같은 .NET의 구분도 그대로 적용되지 않는다.
  • 증분 GC를 켜면 할당을 신경 쓰지 않아도 된다 — 한 번에 멈추는 시간을 나눌 뿐 총량은 그대로다. 할당이 많으면 수집도 그만큼 자주 돈다.
  • 소멸자를 만들어 두면 자원이 제때 풀린다 — 호출 시점이 정해져 있지 않고 수거만 늦춘다. 명시적으로 Dispose를 부르는 것이 원칙이다.

3줄 정리

  • 루트에서 닿으면 살고, 닿지 않으면 수거된다
  • 누수는 안 쓰는데도 루트에 매달려 있는 객체다
  • Unity는 세대 없는 Boehm GC. 답은 할당 줄이기다
