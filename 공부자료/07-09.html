자료구조·알고리즘

풀이 기법

재귀·DP·그리디·비트 연산은 언제 성립하는지가 핵심이다. 조건과 반례로 외운다

면접에서 DP로 풀면 된다고 답하면 다음 질문이 바로 온다. 왜 DP가 되느냐다.

기법은 이름이 아니라 성립 조건을 알아야 쓸 수 있다.

재귀는 깊이가 곧 메모리다

재귀는 호출할 때마다 매개변수·지역 변수·복귀 주소가 스택 프레임으로 쌓이므로 깊이가 그대로 메모리다. 깊어지면 스택 오버플로가 난다.

재귀 호출이 함수의 마지막 동작이면 꼬리 호출이라 부른다. 돌아와서 할 일이 없으므로 프레임을 새로 쌓지 않고 재사용해 반복문처럼 돈다. return n * Fact(n - 1);처럼 호출 결과에 무언가를 더해서 돌려주면 꼬리 호출이 아니다.

그럼 C#은 이 최적화를 해 주나. 보장하지 않는다. .NET JIT이 적용할 수도 있는데 보장하지 않으므로, 깊은 재귀는 직접 반복문이나 명시적 스택으로 바꾸는 편이 안전하다.

DP는 조건 두 개, 그리디는 반례 하나

동적 계획법은 두 조건이 모두 맞을 때만 쓴다. 같은 부분 문제가 여러 번 나오고(겹치는 부분 문제), 부분 문제의 최적해로 전체 최적해를 만들 수 있어야(최적 부분 구조) 동적 계획법이 통한다. 부분 문제가 겹치고 최적 부분 구조를 가질 때다.

메모이제이션은 계산한 답을 표에 저장해 시간을 줄이는 대신 공간을 더 쓰는 맞바꿈이다. 하향식 메모이제이션은 재귀 깊이가 문제가 될 수 있고, 상향식 타뷸레이션은 반복문이라 그 걱정이 없다.

부분 문제가 겹치지 않으면 저장할 이유가 없고, 그때는 그냥 분할 정복이다. 분할 정복은 문제를 작은 문제로 나누고(divide), 각각 풀고(conquer), 결과를 합치는(combine) 세 단계로 돈다.

문제를 작게 쪼개 각각 푼 뒤 합쳐 전체 답을 낸다는 뜻이고, 병합 정렬과 퀵 정렬, 이진 탐색이 대표 예다. 부분 문제가 서로 겹치지 않는다는 점이 겹치는 부분 문제를 저장해 재활용하는 동적 계획법과의 결정적 차이다.

그리디는 지금의 최선이 전체 최선으로 이어질 때만 옳고, 그렇지 않으면 동적 계획법으로 모든 금액의 최적값을 채워 올려야 한다. 동전이 1원·3원·4원뿐일 때 6원을 만들어 보라.

그리디로 4원을 먼저 집으면 남은 2원을 1원 두 개로 채워 3개가 되지만, 3원 두 개를 쓰면 2개로 끝난다. 그리디는 3개, 최적은 2개라서 최적해가 아니다.

반례 하나면 그리디는 무너진다. 한국 화폐처럼 큰 단위가 작은 단위의 배수로 떨어지면 그리디가 최적해와 일치한다.

비트 연산 네 가지로 마스크를 다룬다

켜기·끄기·뒤집기·확인이 한 묶음이다. 끄기는 해당 비트만 0인 마스크를 만들어 AND 하므로 x & ~(1 << n)이고, 켜기는 x | (1 << n), 뒤집기는 x ^ (1 << n), 확인은 (x >> n) & 1이다. Unity의 LayerMask가 이 규칙을 그대로 쓴다: 

int mask = 0;
mask |= 1 << enemy;                      // 켜기
mask |= 1 << water;
mask &= ~(1 << water);                   // 끄기
mask ^= 1 << water;                      // 뒤집기
bool hasEnemy = ((mask >> enemy) & 1) == 1;   // 확인

시프트로 2의 거듭제곱 곱셈도 대신할 수 있다. 8을 곱하려면 x << 3을 쓰며, 다만 음수나 자료형 비트 수 이상으로 밀 때는 결과가 달라지니 주의한다. int의 시프트 횟수는 하위 5비트만 쓰여 x << 32는 제자리이고, 음수의 >>는 부호 비트를 채운다.

LRU 캐시는 두 구조를 겹쳐야 O(1)이다

LRU 캐시는 조회와 갱신이 모두 O(1)이어야 쓸모가 있다. 한쪽만 쓰면 순서 찾기나 노드 찾기 중 하나가 O(N)으로 남는다.

그래서 해시 맵과 이중 연결 리스트를 함께 쓴다. 둘을 겹친다.

해시 맵으로 키에서 노드를 O(1)에 찾고, 이중 연결 리스트로 최근 사용 순서를 유지하면 노드를 맨 앞으로 옮기거나 꼬리를 버리는 일도 링크만 갈아 끼우면 되므로 O(1)이다.

C#에서는 Dictionary<TKey, LinkedListNode<TKey>>와 LinkedList<TKey> 조합이 그대로 답이며, 텍스처나 에셋 캐시에 흔히 쓴다.

면접에서 이렇게 답한다

  • 재귀는 콜 스택에서 어떻게 도나 — 호출마다 매개변수·지역 변수·복귀 주소가 프레임으로 쌓이고 반환하며 걷힌다. 깊이가 곧 메모리라 한계를 넘으면 스택 오버플로다. 꼬리 호출은 프레임 재사용이 가능하지만 C#은 보장하지 않는다고 못을 박는다.
  • 그리디와 DP를 어떻게 가르나 — 반례를 찾아본다고 답한다. 1·3·4원으로 6원을 만들 때 그리디는 세 개, 최적은 두 개라 깨진다. 반례가 없다고 볼 근거가 서면 그리디, 아니면 DP다.
  • LRU 캐시 구현 — 해시 맵과 이중 연결 리스트를 함께 쓴다. 맵으로 키에서 노드를 O(1)에 찾고, 리스트로 최근 사용 순서를 유지해 링크 교체만으로 앞으로 옮기거나 꼬리를 버린다.

이런 오해를 한다

  • “C#도 꼬리 재귀를 최적화해 준다” — IL에 꼬리 호출 명령은 있다. JIT이 적용한다는 보장이 없을 뿐이다.
  • “호출 결과를 곱해 반환해도 꼬리 호출” — 돌아와서 할 일이 남아 프레임을 재사용할 수 없다.
  • “메모이제이션은 공짜다” — 시간을 줄이는 대신 표만큼 공간을 쓴다. 상태가 많으면 메모리가 먼저 터진다.
  • “Dictionary만으로 LRU를 O(1)에 만든다” — 버릴 항목을 찾는 순서 정보가 없어 O(N)이 남는다.

3줄 정리

  • 재귀는 깊이가 메모리다. C#은 꼬리 호출을 안 보장한다
  • DP는 조건 두 개, 그리디는 반례로 검증한다
  • LRU는 맵과 이중 연결 리스트를 겹쳐야 O(1)이다
