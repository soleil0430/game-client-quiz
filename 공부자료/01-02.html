C# 언어

객체지향 문법

부르는 쪽이 구체 타입을 모르게 하는 장치와 가상 메서드 표의 원리

슬라임, 궁수, 보스를 한 루프에서 돌린다. 타입마다 if를 달아 공격을 부르는 코드라면, 몬스터를 하나 추가할 때마다 이 루프를 다시 열어야 한다.

상속과 인터페이스, 가상 메서드는 그 수정을 없애자고 있는 장치다.

타입이 늘 때마다 루프를 고치지 않으려면

목표는 하나다. 부르는 쪽이 구체 타입을 모른 채 일을 시키게 만드는 것. Attack()을 시키는 코드는 상대가 슬라임인지 보스인지 몰라도 된다.

둘 중 무엇을 쓸지는 물려줄 것이 있느냐로 갈린다. 추상 클래스는 필드와 생성자, 구현이 있는 메서드를 함께 가질 수 있어 공통 상태와 기본 동작을 물려주는 자리에 맞다. 인터페이스는 인스턴스 필드를 가질 수 없고, 서로 관계없는 클래스들이 같은 기능을 약속할 때 쓴다.

C#은 클래스 다중 상속을 막고 인터페이스 다중 구현은 허용한다. 같은 멤버를 양쪽에서 물려받으면 어느 구현을 쓸지 정할 수 없는 죽음의 다이아몬드 문제를 이렇게 피한다. 정리하면 클래스는 하나만 상속하고 인터페이스는 여러 개 구현한다.

시그니처가 겹치는 인터페이스를 함께 구현할 때는 어떻게 하나. 명시적 인터페이스 구현(void IA.Attack())으로 각각 따로 정의하면 된다. 인터페이스끼리 상속하는 것도 가능하다.

부모 타입으로 불렀는데 왜 자식 구현이 도나

표 한 장 덕분이다. 타입마다 만들어진 가상 함수 테이블(vtable)에 실제 구현 주소가 들어가고, 호출은 객체가 가리키는 그 테이블을 한 번 더 거쳐 이뤄진다. 부모 타입 변수로 다뤄도 자식 구현이 불리는 것을 동적 바인딩이라 한다.

override는 이 표의 칸을 덮어쓴다. 그래서 부모 타입 변수로 불러도 재정의한 구현이 실행돼 자식 쪽 로그가 찍힌다. new는 덮어쓴 게 아니라 이름만 가린 것뿐이고, 부모 타입 변수로 부르면 변수 타입 기준으로 부모 구현이 실행된다.

다형성이 끊기므로, 의도한 재정의라면 override를 써야 한다. 간접 호출 때문에 일반 메서드보다 아주 약간 느리기는 하다. 더 재정의할 일이 없으면 sealed를 붙여 최적화 여지가 생기게 한다.

둘을 같은 자리에 놓고 출력을 비교한 코드다:

class Enemy { public virtual void Attack() => Debug.Log("적"); }
class Boss  : Enemy { public override void Attack() => Debug.Log("보스"); }
class Slime : Enemy { public new      void Attack() => Debug.Log("슬라임"); }

Enemy a = new Boss();
Enemy b = new Slime();
a.Attack();   // 보스 - override라 실제 객체 타입 기준
b.Attack();   // 적   - new라 변수 타입 기준

재정의를 그 클래스에서 끝내고 싶으면 sealed override다. 더 아래 자식이 다시 override 하지 못하게 막는다. sealed class는 상속 자체를 막으므로 다른 이야기고, private으로 바꾸면 자식에서 보이지 않아 다형성이 깨지고, new는 이름만 가리는 것이다.

오버로딩은 컴파일러가, 오버라이딩은 런타임이 고른다

오버로딩은 같은 이름에 매개변수 구성만 다르게 둔 것이다. 어느 것을 부를지는 컴파일 시점에 정해진다. 반환 타입은 판별에 쓰이지 않는다.

오버라이딩은 실행 중에 실제 타입을 보고 정한다. 같은 한 줄이 객체마다 다르게 동작하는 것도 그래서다.

static 생성자는 시점이 전부인 물건이다. 그 타입을 처음 사용하는 시점, 그러니까 첫 인스턴스 생성이나 정적 멤버 접근에 런타임이 딱 한 번만 호출한다. 매개변수도 접근 제한자도 붙일 수 없고 직접 호출할 수도 없다.

순서는 static 생성자 → 인스턴스 필드 초기화 → 인스턴스 생성자다. 호출 시점을 프로그래머가 못 정하므로 무거운 초기화는 넣지 않는 게 좋다.

합집합인 protected internal, 교집합인 private protected

접근 한정자는 이름만 봐서는 어느 쪽이 더 넓은지 보이지 않는다.

한정자 접근할 수 있는 곳
protected 어셈블리와 무관하게 파생 클래스
protected internal 같은 어셈블리 전체 + 다른 어셈블리의 파생 클래스 (합집합)
private protected 같은 어셈블리 안의 파생 클래스만 (교집합)

접근 범위는 private < protected/internal < protected internal < public 순으로 넓어진다. 합집합이라 같은 어셈블리면 상속 관계가 아니어도 되고, 다른 어셈블리면 파생 클래스에서 접근할 수 있다. 교집합인 private protected는 C# 7.2에 들어왔다.

제약은 타입 인자가 갖출 조건이다

제약도 범위를 좁히는 장치지만 잃는 쪽이 아니라 얻는 쪽이다. 제약이 없으면 T는 object 수준의 멤버만 쓸 수 있다. where T : IDamageable처럼 제약을 걸면 컴파일 타임에 타입을 검증하고, 그 인터페이스 멤버를 캐스팅 없이 호출할 수 있다.

class, struct, new(), 특정 기반 타입 등을 조합해 쓸 수 있다. struct 제약은 박싱 없이 값 형식을 다루게 해 준다.

Dog 리스트를 Animal 리스트로 받을 수 있나

Dog가 Animal을 상속해도 두 제네릭 타입은 남남이다. List<T>는 읽기와 쓰기를 모두 하므로 무공변이고, 상위 타입으로 받게 해 주면 Animal 통에 Cat을 넣어 버릴 수 있기 때문이다.

꺼내기만 하는 자리는 안전하다. 공변성은 이런 자리를 out으로 표시하며, IEnumerable<T>의 T는 공변이라 상위 타입으로 대입된다. IEnumerable<Dog>를 IEnumerable<Animal>로 받는 코드가 그대로 컴파일된다.

반공변성은 반대로 받기만 하는 자리이고 in으로 표시하며, Action<Animal>을 Action<Dog> 자리에 넣을 수 있게 한다. 변성은 인터페이스와 델리게이트에만 선언할 수 있으며, 값 형식 타입 인자에는 적용되지 않는다.

남의 클래스에 메서드를 붙이는 법

Transform에 헬퍼 하나를 붙이고 싶은데 그 코드는 고칠 수 없다. 확장 메서드가 이 자리에 쓰인다.

정적 클래스의 정적 메서드로 만들고, 첫 인자에 this를 붙여 확장 대상을 지정한다. 문법은 그게 전부다. 호출은 인스턴스 메서드처럼 보이지만 실제로는 정적 호출이라, 대상의 private 멤버에는 접근하지 못한다.

LINQ가 IEnumerable<T>를 이 방식으로 확장한 대표 사례이고, Unity에서는 Transform이나 Vector3에 헬퍼를 붙일 때 자주 쓴다.

반대로 partial은 한 타입의 정의를 여러 파일에 나눠 적게 해 준다. 같은 어셈블리 안에서만 되고, 나눠 쓴 조각은 컴파일 시점에 하나로 합쳐진다. 코드 생성기가 만든 파일과 사람이 쓴 파일을 분리할 때 주로 쓰고, 이미 컴파일된 남의 클래스에 기능을 더하고 싶으면 partial이 아니라 확장 메서드를 써야 한다.

어트리뷰트는 붙여 두는 쪽지다

어트리뷰트는 타입이나 멤버에 메타데이터를 붙여 두는 문법이다. 클래스·필드·메서드에 붙는 부가 정보이고, 컴파일된 어셈블리의 메타데이터로 남아 리플렉션으로 읽는다.

붙였다고 코드가 실행되는 게 아니다. 그 정보를 읽는 쪽, 그러니까 직렬화기나 에디터, 테스트 러너가 동작을 바꾼다. Unity의 [SerializeField], [RequireComponent], [ContextMenu]가 대표적인 예다.

면접에서 이렇게 답한다

  • 인터페이스와 추상 클래스 중 무엇을 쓰나 — 물려줄 공통 상태와 기본 동작이 있으면 추상 클래스다. 상속 계층이 다른 타입들이 같은 기능을 약속하게 하려면 인터페이스다. C#은 클래스 상속이 하나뿐이니 확장 지점은 인터페이스로 열어 두는 편이 안전하다고 덧붙인다.
  • 가상 메서드는 어떻게 동작하나 — 타입마다 가상 메서드 표가 있고 호출이 그 표를 거쳐 실제 구현으로 간다고 먼저 말한다. 간접 호출이라 아주 약간 느리다. 더 재정의할 일이 없으면 sealed를 붙여 최적화 여지를 준다는 데까지 가면 좋다.
  • 오버로딩과 오버라이딩의 차이 — 이름이 같고 매개변수가 다른 메서드를 여러 개 두는 것이 오버로딩이고 컴파일 시점에 결정된다. 오버라이딩은 상속 관계에서 가상 메서드를 다시 구현하는 것이고 실행 중에 결정된다. 결정 시점을 짚어 주는 것이 핵심이다.
  • 상속은 허용하되 재정의만 막으려면 — 그 메서드를 sealed override로 선언한다. sealed class라고 답하면 상속 자체를 막아 버려 조건을 넘어선다.

이런 오해를 한다

  • “new로 재정의해도 override와 결과가 같다” — new는 가리기일 뿐이다. 부모 타입 변수로 부르면 부모 구현이 실행된다.
  • “protected internal은 같은 어셈블리의 파생 클래스만” — 그것은 private protected다. protected internal은 합집합이라 같은 어셈블리면 상속 관계가 아니어도 접근된다.
  • “반환 타입만 달라도 오버로딩이다” — 오버로딩 판별에 반환 타입은 쓰이지 않는다. 그대로 컴파일 오류가 난다.
  • “인터페이스는 구현을 전혀 가질 수 없다” — C# 8부터 기본 구현을 넣을 수 있고, Unity는 2021.2 이후 C# 9 기준이다. 다만 인스턴스 필드는 못 가지니 상태를 물려주려면 여전히 추상 클래스다.
  • “어트리뷰트를 붙이면 코드가 실행된다” — 어트리뷰트는 메타데이터일 뿐이다. 그것을 리플렉션으로 읽는 쪽이 동작을 바꾼다.

3줄 정리

  • 부르는 쪽이 구체 타입을 모르게 하는 것이 목적이다
  • override는 가상 메서드 표를 덮어쓰고 new는 이름만 가린다
  • 오버로딩은 컴파일 시점, 오버라이딩은 실행 중에 정해진다
