C++ 기초

메모리와 포인터

GC가 없으니 소유권을 코드에 적는다. RAII와 unique_ptr이 그 문법이다

C#에서는 이 객체를 누가 책임지는지 코드에 적을 일이 거의 없다. 가비지 컬렉션(GC)이 알아서 걷어 간다.

C++에는 그 담당자가 없다. 그래서 소유권과 수명을 코드로 적는다.

C#의 using 자리를 C++은 스코프가 맡는다

자원을 생성자에서 얻고 소멸자에서 해제해 수명을 묶는 기법이 RAII다. 메모리뿐 아니라 파일, 락 같은 자원에 그대로 쓴다. 스택 객체는 스코프를 벗어날 때 반드시 소멸자가 호출되므로, 예외가 튀어도 중간에서 일찍 반환이 일어나도 해제가 빠지지 않는다.

std::unique_ptr과 std::lock_guard가 대표적인 예이고, C#에서는 IDisposable과 using 문이 비슷한 역할을 한다. 다만 using은 부르는 쪽이 매번 적어야 한다.

중간에 빠져나가도 텍스처가 닫히는 형태다:

void Load() {
    auto tex = std::make_unique<Texture>("hero.png");  // 생성자에서 연다
    if (!tex->IsValid())
        return;          // 여기서 나가도
    Use(*tex);
}                        // 스코프를 벗어나면 소멸자가 닫는다

소유자가 몇 명인가로 스마트 포인터를 고른다

스마트 포인터는 RAII를 포인터에 씌운 것이다. 셋 중 무엇을 쓸지는 질문 하나로 정해진다. 이 자원의 주인이 몇 명인가.

종류소유쓰는 자리
unique_ptr혼자기본 선택. 복사가 막혀 있고 move로 넘긴다
shared_ptr여럿(참조 카운트)수명을 정말 나눠 가질 때만
weak_ptr없음(관찰만)카운트를 올리지 않는 참조, lock으로 확인

unique_ptr은 단독 소유라 복사가 막혀 있고 std::move로 소유권을 넘긴다. shared_ptr은 참조 카운트가 0이 될 때 객체를 해제한다. weak_ptr은 카운트를 올리지 않고 관찰만 하며, 쓸 때는 lock()으로 shared_ptr을 얻어 객체가 살아 있는지 확인한다. 카운트 증감은 스레드 안전하지만 가리키는 객체에 대한 접근은 동기화되지 않는다.

new와 malloc의 차이도 여기서 나온다. new는 타입에서 필요한 크기를 계산해 할당하고 생성자를 호출하며, 실패하면 기본적으로 std::bad_alloc 예외를 던진다. malloc은 바이트 수를 받아 할당만 하고 실패하면 NULL을 돌려준다.

그러니 new와 free, malloc과 delete를 섞으면 소멸자 호출과 해제 방식이 어긋난다. 결과는 정의되지 않은 동작이다. new[]를 delete로 해제하는 것도 같은 죄다.

참조 카운트는 순환을 풀지 못한다

shared_ptr 둘이 서로를 가리키면 카운트가 1 아래로 내려가지 않는다. 둘 다 영영 해제되지 않는다. C#에서는 겪지 않는 누수다.

GC는 루트에서 닿을 수 있는지를 보므로 서로만 붙잡고 있는 섬도 수거해 간다. 참조 카운트에는 그런 시야가 없고 눈앞의 숫자만 본다.

한쪽을 weak_ptr로 바꾸면 그 참조는 수를 올리지 않게 되어 고리가 끊기고, 쓸 때는 lock()으로 살아 있는지 확인해 shared_ptr를 얻는다. 부모-자식 구조라면 부모가 자식을 shared_ptr로, 자식이 부모를 weak_ptr로 갖는 것이 보통이다.

예외도 없이 조용히 망가지는 것들

참조는 선언과 동시에 대상을 정해야 하고 한번 정하면 다른 대상을 가리키도록 바꿀 수 없어, 늘 유효한 객체를 가리킨다고 보고 쓴다. 포인터는 nullptr일 수 있고 다른 주소로 바꿀 수 있으며 +1 같은 산술 연산도 된다. 그래서 값이 없을 수 있으면 포인터, 반드시 있으면 참조로 받는 것이 읽는 사람에게 의도를 알려 준다.

기본 복사 생성자는 멤버를 그대로 복사하는 얕은 복사라, 포인터 멤버가 있으면 포인터 값만 복사돼 두 객체가 같은 메모리를 가리켜 이중 해제가 일어날 수 있다. 둘 다 소멸하면 같은 메모리를 두 번 해제하고, 한쪽에서 고친 값이 다른 쪽에도 보인다. 새 메모리를 잡아 내용을 옮기는 깊은 복사를 직접 쓰거나, 아예 소유권이 분명한 unique_ptr·shared_ptr로 바꾸는 편이 안전하다.

배열과 vector의 []는 범위를 검사하지 않아 정의되지 않은 동작이 된다. 바로 죽으면 차라리 낫고, 남의 변수를 조용히 덮어써서 한참 뒤 엉뚱한 곳에서 터지는 것이 더 흔하다. 검사가 필요하면 vector::at()이 예외를 던지고, 디버깅에는 AddressSanitizer 같은 도구를 쓴다.

배열 이름도 포인터와 같지 않다. int a[10]에서 sizeof(a)는 전체 크기인 40이지만, 함수에 넘기면 포인터로 바뀌어(decay) sizeof는 포인터 크기인 8이 된다. 그래서 C 스타일 배열을 넘길 때는 길이를 따로 인자로 받아야 하고, 이 실수를 막으려고 std::array나 std::vector를 쓴다. 배열 이름은 주소 상수라 다른 곳을 가리키도록 대입할 수도 없다.

구조체 크기도 멤버 합과 다르다. struct A { char c; int i; char d; };에서 int는 4바이트 경계에 정렬되므로 char c 뒤에 3바이트 패딩이 들어가고, char d 뒤에도 구조체 크기가 가장 큰 정렬 단위(4)의 배수가 되도록 3바이트가 더 붙어 12바이트가 된다. 멤버를 int i; char c; char d; 순서로 두면 8바이트로 줄어드니, 선언 순서가 크기를 바꾼다.

면접에서 이렇게 답한다

  • RAII란 — 자원의 수명을 객체의 수명에 묶는 기법이라고 한 줄로 말한다. 생성자에서 얻고 소멸자에서 놓으면 예외나 조기 반환에도 새지 않으며, C#의 using 문과 목적이 같다고 이어 붙인다.
  • 스마트 포인터는 어떻게 고르나 — 소유자가 하나면 unique_ptr을 기본으로 쓴다. 수명을 정말 나눠 가질 때만 shared_ptr을 쓰고, 역방향 참조는 weak_ptr로 둔다.
  • malloc과 new의 차이는 — new는 크기 계산과 생성자 호출까지 하고 실패하면 예외를 던진다. malloc은 할당만 하고 NULL을 주며, 섞어 쓰면 정의되지 않은 동작이 된다.
  • 얕은 복사와 깊은 복사는 — 얕은 복사는 포인터 값만 복사해 이중 해제가 생긴다. 깊은 복사는 새 메모리를 잡아 내용을 옮기며, 요즘은 소유권이 분명한 타입으로 문제 자체를 없앤다.

이런 오해를 한다

  • “shared_ptr을 쓰면 누수가 없다” — 서로 가리키는 순환이 생기면 그대로 샌다. GC와 달리 참조 카운트는 순환을 못 푼다.
  • “배열 범위를 넘으면 예외가 난다” — C#의 예외를 떠올린 오해다. 검사가 필요하면 vector의 at을 쓰고, 디버깅에는 AddressSanitizer를 쓴다.
  • “참조도 nullptr일 수 있다” — 참조는 초기화 없이 만들 수 없다. 없을 수 있는 값은 포인터로 표현한다.
  • “delete와 free는 이름만 다르다” — delete는 소멸자를 부르고 free는 부르지 않는다. 짝을 맞추지 않으면 정의되지 않은 동작이다.

3줄 정리

  • RAII는 자원 수명을 스코프에 묶는다
  • 소유자 수로 unique·shared·weak를 고른다
  • 참조 카운트는 순환 참조를 풀지 못한다
