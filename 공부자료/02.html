기본 구조

GameObject는 그릇이고 컴포넌트가 기능이다. 프리팹·씬·레이어·특수 폴더가 그 위에 얹힌다

핵심 개념

Unity는 상속이 아니라 합성으로 오브젝트를 만든다. GameObject 자체에는 기능이 없고, Renderer나 Rigidbody, 직접 만든 스크립트 같은 컴포넌트를 붙여야 보이고 움직인다. 상속으로 기능을 쌓으면 "날면서 부서지는 적" 같은 조합마다 새 클래스가 필요하지만, 합성은 컴포넌트를 하나 더 붙이면 끝나 조합이 늘어도 클래스가 늘지 않는다. MonoBehaviour는 Awake나 Update 같은 엔진 콜백을 받는 컴포넌트의 기반 클래스다.

예외가 Transform이다. 모든 GameObject가 반드시 갖고 지울 수 없으며, 부모-자식 관계 자체를 Transform이 들고 있어 하이어라키의 계층이 곧 Transform의 계층이다. 자식의 localPosition은 부모 기준, position은 월드 기준이라 부모를 옮기면 자식의 월드 좌표가 따라 움직이고, 부모를 끄거나 파괴하면 자식도 함께 꺼지고 파괴된다. 무기를 손 본에 붙일 때 쓰는 성질이 이것이다.

프리팹은 GameObject 구성을 통째로 저장한 에셋 원본이다. 원본을 고치면 씬의 인스턴스 전부에 전파되고, 인스턴스마다 값을 덮어써(Override) 차이를 둘 수 있다. 2018.3부터 중첩 프리팹과 배리언트도 쓴다. 씬에 직접 배치하지 말라는 이유는 둘이다. 씬 파일은 오브젝트가 전부 든 큰 텍스트 한 덩어리라 여럿이 고치면 충돌이 나는데 프리팹은 파일이 갈라져 충돌이 줄고, Instantiate나 풀링에 그대로 쓸 수 있다.

씬 로드는 기본이 LoadSceneMode.Single이라 기존 씬을 닫고 연다. Additive를 주면 겹쳐 열려서 지형, 몬스터 배치, UI를 나눠 작업하고 실행할 때 합칠 수 있다. 내릴 때는 UnloadSceneAsync, 새 오브젝트가 들어갈 씬은 SetActiveScene으로 정한다.

Layer는 32개뿐인 비트 값이다. 제한된 대신 집합 검사가 비트 연산 한 번이라 카메라 Culling Mask, Layer Collision Matrix, Raycast의 LayerMask처럼 "이 무리만" 걸러내는 곳에 쓴다. 1 << layer나 LayerMask.GetMask("Enemy")로 만든다. Tag는 제한이 없는 문자열 표식이고, CompareTag로 비교하면 문자열 할당을 피한다. 폴더 이름에도 엔진이 특별히 취급하는 것이 있다.

폴더동작
Resources참조 여부와 상관없이 폴더 안 전부가 빌드에 들어가고, 경로 문자열로 로드한다
StreamingAssets변환·압축 없이 원본 그대로 패키징된다. 읽기 전용이고 안드로이드에서는 APK 안이라 UnityWebRequest로 읽는다
Editor에디터 확장용 스크립트를 둔다. 빌드에서 제외된다
Plugins네이티브 라이브러리와 서드파티 플러그인을 둔다

경로도 갈린다. Application.dataPath는 설치된 앱의 데이터 폴더라 플랫폼에 따라 읽기 전용이거나 막힌다. 세이브와 설정은 어디서나 쓰기가 되는 persistentDataPath에 둔다. 다만 사용자가 열어 볼 수 있고 앱을 지우면 사라지므로, 조작되면 안 되는 값은 서버에 둔다.

면접에서 이렇게 답한다

  • GameObject와 Component의 관계는 — GameObject는 컴포넌트를 담는 그릇이고 기능은 컴포넌트가 맡는다. 상속이 아니라 합성이라 조합이 늘어도 클래스가 늘지 않는다. Transform만 제거할 수 없다.
  • 프리팹을 쓰는 이유는 — 원본 하나를 고치면 모든 인스턴스에 전파되니 수정 지점이 한곳이다. 씬에 직접 배치하면 씬 파일이 커져 머지 충돌이 나고, 런타임 생성이나 풀링에 쓸 수 없다.
  • Tag와 Layer를 어떻게 나눠 쓰나 — 렌더링이나 충돌 대상처럼 집합으로 거를 일은 Layer로 한다. 32개 제한이 있는 대신 비트마스크라 빠르다. 개수가 필요한 표식은 Tag로 하되 CompareTag로 비교한다.
  • 세이브 파일은 어디에 두나 — persistentDataPath다. dataPath는 플랫폼에 따라 쓰기가 막힌다. 다만 사용자가 열어 고칠 수 있는 자리라 재화 같은 값은 서버에 두고 클라이언트는 표시만 한다.

흔한 오해

  • GameObject를 상속해 적 클래스를 만든다 — GameObject는 sealed라 상속이 안 된다. 기능은 MonoBehaviour를 상속한 컴포넌트로 만들어 붙인다.
  • Transform도 필요 없으면 뗀다 — 제거할 수 없는 유일한 컴포넌트다. UI에서는 RectTransform이 그 자리를 대신한다.
  • Resources에 넣으면 빌드가 가벼워진다 — 반대다. 참조하지 않는 에셋까지 전부 들어가고 시작할 때 목록을 만드느라 로딩도 느려진다.
  • StreamingAssets는 어디서나 File API로 읽힌다 — 안드로이드에서는 압축된 APK 안의 경로라 일반 파일 API로 열리지 않는다.

생명주기와 스크립팅

엔진이 언제 내 함수를 부르는지 알면 초기화·물리·파괴에서 나는 버그가 대부분 사라진다

핵심 개념

Unity 스크립트에는 main이 없다. 게임 루프는 엔진이 들고 있고 내가 쓴 함수는 엔진이 부르는 콜백이라 "언제 몇 번 불리는가"가 곧 설계 제약이 된다. 한 프레임은 아래 FixedUpdate부터 LateUpdate까지 돈 뒤 렌더링으로 끝난다.

함수호출 시점여기에 두는 일
Awake로드될 때 한 번. 꺼져 있어도 불린다자기 초기화, 컴포넌트 캐싱
OnEnable활성화될 때마다이벤트 구독
Start켜진 뒤 첫 Update 직전 한 번남을 찾는 초기화
FixedUpdate고정 간격마다. 한 프레임에 0번일 수도 여러 번일 수도물리
Update프레임마다 한 번입력, 일반 로직
LateUpdate모든 Update가 끝난 뒤카메라 추적, 본 보정
OnDisable비활성화될 때와 파괴 직전이벤트 해제
OnDestroy파괴될 때 한 번마지막 정리

Awake와 Start가 갈리는 이유는 함께 로드된 오브젝트 전부의 Awake가 끝난 뒤에야 Start가 시작되기 때문이다. Awake 때는 남이 준비되지 않았을 수 있다. 종료는 OnApplicationQuit → OnDisable → OnDestroy 순이지만 모바일에서 강제 종료되면 셋 다 안 불려서, 저장은 OnApplicationPause(true)에 두는 편이 안전하다.

FixedUpdate가 따로 있는 이유는 물리가 일정한 간격으로 적분해야 같은 결과가 나오기 때문이다. Fixed Timestep은 기본 0.02초, Time.fixedDeltaTime으로 읽는다. 반면 Update는 호출 횟수가 기기 성능을 타므로 시간에 비례하는 값에는 Time.deltaTime을 곱해야 기기마다 같은 속도가 된다. timeScale이 0이면 Update는 불리되 deltaTime이 0이 되고 FixedUpdate는 멈춰서, 일시정지 연출에는 unscaledDeltaTime을 쓴다.

코루틴은 스레드가 아니다. yield가 든 메서드를 컴파일러가 IEnumerator 상태 머신으로 바꾸고, Unity가 매 프레임 MoveNext를 불러 다음 yield까지만 진행시킨다. 메인 스레드에서 돌아 Unity API를 쓸 수 있지만 무거운 계산을 넣으면 프레임이 끊긴다. 오브젝트가 꺼지면 코루틴도 멈추나 async/await는 CancellationToken으로 끊어야 한다.

파괴에도 함정이 둘 있다. Destroy는 지연 파괴라 그 프레임의 Update가 끝난 뒤 렌더링 전에 지워진다. 그리고 UnityEngine.Object는 네이티브 객체를 감싼 C# 객체라 파괴돼도 껍데기가 남는다. Unity는 ==를 오버로드해 이를 null처럼 보이게 하지만(fake null), is null·?.·ReferenceEquals는 오버로드를 타지 않아 접근하다 예외를 낸다.

면접에서 이렇게 답한다

  • 생명주기를 설명하라 — Awake, OnEnable, Start로 초기화하고 한 프레임은 FixedUpdate(필요한 횟수만큼) → Update → LateUpdate → 렌더링 순이다. 끝날 때 OnDisable, OnDestroy다.
  • Awake와 Start를 어떻게 나누나 — Awake가 전부 끝난 뒤 Start가 불리므로 자기 초기화는 Awake, 남을 참조하는 초기화는 Start에 둔다.
  • 물리는 어느 함수에 두나 — FixedUpdate다. 고정 간격이라 프레임레이트가 달라도 결과가 같다. 입력만 Update에서 받아 플래그로 넘긴다.
  • Update 1000개와 매니저 하나 중 무엇이 빠른가 — 매니저다. 네이티브에서 매니지드로 넘어오는 비용이 호출마다 붙어 한 번 넘어가 반복문을 도는 편이 싸다. 빈 Update도 지운다.

흔한 오해

  • timeScale이 0이면 Update도 멈춘다 — Update는 계속 불린다. 멈추는 건 deltaTime이 0이 되는 시간 기반 로직과 FixedUpdate다.
  • 코루틴은 별도 스레드에서 돈다 — 메인 스레드다. 진짜 병렬은 스레드나 Job System이 필요하다.
  • 파괴된 오브젝트에 ?.를 쓰면 안전하다 — 오히려 위험하다. 재정의된 ==를 타지 않아 파괴된 객체에 그대로 접근한다.
  • transform.position.y = 0f;는 Unity가 막은 것이다 — C# 문법이다. Vector3가 구조체라 프로퍼티가 복사본을 돌려준다.

직렬화와 데이터

인스펙터에 값이 보이는 이유부터 세이브 파일을 어디에 어떻게 두는지까지가 한 줄기다

핵심 개념

직렬화는 메모리 위의 객체를 저장하고 다시 복원할 수 있는 형태로 펴는 일이다. Unity에서 중요한 것은 씬, 프리팹, ScriptableObject 에셋, 인스펙터 표시가 전부 같은 직렬화 시스템 하나 위에 있다는 점이다. 인스펙터에 필드가 보이는 것은 그 필드가 직렬화 대상이기 때문이고, 그래서 인스펙터에 안 보이는 값은 씬에도 저장되지 않는다.

규칙은 단순하다. public 필드이거나 [SerializeField]가 붙은 private 필드여야 하고 타입도 직렬화 가능해야 한다. 프로퍼티, static 필드, Dictionary는 대상이 아니다. 클래스나 구조체를 통째로 저장하려면 [System.Serializable]을 붙인다. public으로 열어 캡슐화를 깨는 대신 private 필드에 [SerializeField]를 붙이는 방식을 실무에서 흔히 쓴다.

[CreateAssetMenu(menuName = "Game/Weapon Data")]
public class WeaponData : ScriptableObject
{
    [SerializeField] private int damage = 10;   // private이지만 인스펙터에 나온다
    public int Damage => damage;                // 프로퍼티는 직렬화되지 않는다
}

Dictionary가 안 되는 이유는 Unity 직렬화기가 필드를 순서대로 늘어놓는 단순한 형식이라 키-값 구조를 표현하지 못해서다. 필요하면 ISerializationCallbackReceiver를 구현해 저장 직전에 키 리스트와 값 리스트로 폈다가 로드 직후에 다시 조립한다.

ScriptableObject는 씬에 붙지 않는 데이터 컨테이너다. 에셋 파일로 저장해 두면 여러 프리팹이 복사본이 아니라 같은 참조를 공유하므로 무기 스탯 하나를 고치면 그걸 쓰는 모두가 바뀌고 메모리에도 한 벌만 올라간다. 대신 MonoBehaviour와 달리 Update 같은 이벤트를 받지 않는다. 주의할 점은 에디터와 빌드의 차이다. 에디터에서는 프로젝트의 에셋 파일을 그대로 가리켜 플레이 중 바꾼 값이 에셋에 남고 다음 실행에까지 영향을 준다. 빌드에서는 읽기 전용으로 패키징되어 실행하는 동안만 유지되고 앱을 다시 켜면 원래 값으로 돌아온다. 그래서 변하지 않는 설정과 원본 데이터에만 쓰고, 변하는 상태는 따로 저장한다.

저장 수단은 셋으로 갈린다. PlayerPrefs는 int·float·string만 다루는 키-값 저장소로, 윈도우는 레지스트리, macOS와 iOS는 plist, 안드로이드는 SharedPreferences에 암호화 없이 평문으로 남아 누구나 열어 고칠 수 있다. 구조가 있는 데이터는 JSON으로 만들어 persistentDataPath에 파일로 저장한다. JsonUtility는 Unity 직렬화를 그대로 쓰므로 위 규칙을 똑같이 따르고 Dictionary·다형성·null·최상위 배열을 다루지 못하는 대신 가볍고 빠르다. Newtonsoft.Json은 그 제약이 없지만 리플렉션을 써서 느리고 IL2CPP에서 코드 스트리핑에 걸릴 수 있다.

세이브 시스템은 버전과 손상을 전제로 만든다. 데이터에 version 필드를 두고 읽을 때 옛 버전이면 마이그레이션을 태운다. 쓰는 도중 앱이 죽으면 파일이 반만 남으므로, 임시 파일에 먼저 쓰고 성공하면 원본 이름으로 바꿔 원자적으로 교체하며 직전 파일을 백업으로 남긴다.

면접에서 이렇게 답한다

  • public 필드와 [SerializeField]의 차이는 — 둘 다 직렬화되어 인스펙터에 나온다. 다른 점은 접근 제한자뿐이라, 값은 인스펙터에서 조정하되 코드에서는 외부가 못 건드리게 하려고 private 필드에 [SerializeField]를 붙인다.
  • ScriptableObject는 어디에 쓰나 — 여러 오브젝트가 공유하는 설정 데이터의 원본으로 쓴다. 프리팹마다 복사하지 않아 수정 지점이 하나고 메모리도 한 벌만 쓴다. 빌드에서는 읽기 전용이라 변하는 상태는 따로 저장한다.
  • 점수나 설정을 어떻게 저장하나 — 옵션 같은 가벼운 값은 PlayerPrefs, 구조가 있는 데이터는 JSON으로 persistentDataPath에 파일로 쓴다. 둘 다 평문이라 재화나 진행도는 서버에 두고 검증한다.
  • 세이브 구조가 바뀌면 — 파일에 버전 번호를 같이 저장하고 읽을 때 버전별 마이그레이션을 태운다. 쓰기는 임시 파일에 한 뒤 이름을 바꿔 교체해서 도중에 죽어도 이전 파일이 남게 한다.

흔한 오해

  • 프로퍼티도 인스펙터에 나온다 — 직렬화 대상이 아니다. 백킹 필드를 private으로 두고 [SerializeField]를 붙여야 저장되고 보인다.
  • ScriptableObject에 값을 써 두면 세이브가 된다 — 에디터에서만 에셋에 남는다. 빌드에서는 앱을 끄면 사라지므로 세이브 수단이 아니다.
  • ScriptableObject도 Update를 받는다 — 씬의 오브젝트가 아니라 엔진 콜백을 받지 않는다. 갱신이 필요하면 MonoBehaviour가 불러 준다.
  • PlayerPrefs는 앱 안에 숨겨져 있어 안전하다 — 평문으로 남아 사용자가 열어 고칠 수 있다.

스크립팅 백엔드

내가 쓴 C#이 기기에서 실제로 실행되기까지 — Mono의 JIT과 IL2CPP의 AOT가 갈리는 지점

핵심 개념

C# 소스는 그대로 실행되지 않는다. 먼저 IL(중간 언어)로 컴파일되고, 그 IL을 기기에서 어떻게 네이티브 명령으로 바꿔 돌릴지를 정하는 것이 스크립팅 백엔드다. Unity는 Mono와 IL2CPP 둘을 제공한다.

Mono는 JIT이다. IL을 앱에 담아 두고 실행 중에 필요한 메서드를 그때그때 네이티브로 번역해서 빌드가 빠르고 개발 반복에 좋다. IL2CPP는 AOT다. IL을 전부 C++ 소스로 변환한 뒤 플랫폼 네이티브 컴파일러로 미리 컴파일한다. 실행 시점에 번역할 것이 없어 빠르고, 실행 중 코드 생성을 금지하는 iOS에서는 선택이 아니라 필수다. 대신 C++ 변환과 컴파일이 통째로 들어가 빌드가 오래 걸린다.

항목Mono (JIT)IL2CPP (AOT)
변환 시점실행 중에 IL을 네이티브로빌드 때 IL을 C++로, 다시 네이티브로
빌드 시간짧다길다
실행 성능보통대체로 더 빠르다
런타임 코드 생성가능불가능
쓰이는 곳에디터·개발 빌드iOS는 필수, 안드로이드 출시에도 사실상 표준

AOT라는 성질에서 제약이 따라온다. 첫째, System.Reflection.Emit처럼 실행 중에 코드를 만드는 기능을 쓸 수 없다. 리플렉션으로 읽는 것은 되지만 새로 만드는 것이 안 된다. 둘째, 아무도 참조하지 않는 것처럼 보이는 타입을 잘라내는 코드 스트리핑이 돈다. 문자열 이름으로만 접근하는 코드는 잘려 나가므로 link.xml에 보존 대상을 적거나 [Preserve]를 붙인다. 셋째, 값 타입 제네릭은 빌드 때 쓰인 조합만 생성되어 런타임에 새 조합을 만들면 예외가 난다.

C# 문법 버전도 여기에 묶인다. Unity 2022 LTS는 C# 9와 .NET Standard 2.1 수준이라 그보다 최신 문법은 컴파일러가 거부하고, 통과하더라도 대응하는 런타임 API가 없으면 실행 시점에 깨진다. Unity 6부터 지원 범위가 올라가므로 팀이 쓰는 버전부터 확인한다.

개발 편의 쪽에는 도메인 리로드가 있다. 에디터에서 플레이를 누르면 Unity가 매니지드 도메인을 다시 올려 static 필드를 초기값으로 되돌리고 이벤트 구독을 끊는다. 매번 새로 켠 상태가 되지만 프로젝트가 커지면 그만큼 기다린다. Reload Domain을 끄면 진입이 빨라지는 대신 static 값과 이벤트 구독이 이전 플레이 상태 그대로 남는다. 에디터 전용 설정이라 빌드에는 영향이 없다.

public static class ScoreBoard
{
    private static int total;

    // 도메인 리로드를 꺼도 플레이를 시작할 때마다 static을 되돌린다
    [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
    private static void ResetStatics() => total = 0;
}

면접에서 이렇게 답한다

  • Mono와 IL2CPP의 차이는 — Mono는 IL을 실행 중에 번역하는 JIT이고 IL2CPP는 IL을 C++로 바꿔 미리 컴파일하는 AOT다. IL2CPP가 실행은 빠르지만 빌드가 길고, iOS처럼 JIT이 금지된 플랫폼에서는 필수다.
  • IL2CPP로 바꾸면 무엇을 조심하나 — 런타임 코드 생성이 막히고 코드 스트리핑이 돈다. 문자열로만 접근하는 타입은 잘릴 수 있어 link.xml이나 [Preserve]로 보존한다. 제네릭도 빌드 때 쓰인 조합만 생성된다.
  • 최신 C# 문법을 쓰면 — 에디터 버전이 지원하는 C# 버전까지만 쓸 수 있고 2022 LTS는 C# 9다. 문법이 통과해도 런타임 API가 없으면 실행 시점에 깨지므로 지원 범위를 먼저 확인한다.
  • 도메인 리로드는 왜 신경 쓰나 — 진입 시간을 줄이려고 끄면 static 값과 이벤트 구독이 남아 두 번째 플레이부터 동작이 달라진다. RuntimeInitializeOnLoadMethod로 static을 직접 초기화해 두면 안전하다.

흔한 오해

  • IL2CPP는 C++로 바꿔 주니 그 C++을 읽고 고치면 된다 — 사람이 읽으라고 만든 코드가 아니다. 최적화와 디버깅은 C# 쪽에서 한다.
  • IL2CPP에서는 리플렉션을 아예 못 쓴다 — 읽는 리플렉션은 된다. 막히는 것은 Reflection.Emit 같은 실행 중 코드 생성이고, 나머지는 스트리핑에 잘리지 않게 보존하면 쓸 수 있다.
  • IL2CPP로 바꾸면 항상 빨라진다 — 스크립트 실행은 대체로 빨라지지만 GPU나 로드가 병목이면 체감 차이가 없다. 빌드 시간은 확실히 늘어난다.
  • 에디터에서 잘 돌면 IL2CPP 빌드도 똑같이 돈다 — 에디터는 Mono라 스트리핑도 AOT 제약도 없다. 리플렉션이나 제네릭이 많은 코드는 IL2CPP 빌드로 따로 확인해야 한다.

에셋과 리소스 관리

무엇을 언제 메모리에 올리고 언제 내리는가 — Resources·AssetBundle·Addressables의 선택 기준

핵심 개념

모바일 게임의 에셋은 기기 메모리보다 크다. 그래서 질문은 늘 하나다. 지금 필요한 것만 올리고 나머지는 어떻게 미뤄 두는가. 방식은 셋이다.

ResourcesAssetBundleAddressables
빌드 포함폴더 전부번들로 묶은 것만그룹으로 묶은 것만
로드경로 문자열번들을 열고 이름으로주소로 비동기
원격 배포불가직접 구현기본 지원
의존성·해제직접직접참조 카운트

Resources를 지양하라는 이유는 둘이다. 폴더 안 에셋은 참조하지 않아도 전부 빌드에 들어가 용량을 먹고, 시작할 때 전체 목록을 인덱싱하느라 구동이 늦어진다. 문서는 1만 개면 저사양 모바일에서 수 초가 걸린다고 적고 있다.

AssetBundle은 에셋을 묶은 아카이브 파일이고, Addressables는 그 위에 주소 체계와 참조 카운트 관리를 얹은 상위 시스템이다. 번들을 직접 다루면 만나는 문제가 중복이다. 어느 번들에도 지정하지 않은 의존 에셋은 그것을 참조하는 모든 번들에 복사본으로 들어간다. 공유 텍스처가 번들 열 개에 들어가면 용량도 메모리도 열 배다. 해법은 공통 텍스처·머티리얼·셰이더를 별도 번들로 떼어 지정하는 것이고, Addressables는 Analyze 창의 중복 의존성 검사로 찾아 준다. 같은 이유로 로컬 프리팹이 원격 번들의 머티리얼을 참조하면 원격을 받기 전에는 로드가 실패한다.

해제도 직관과 다르다. 텍스처나 메시의 실제 데이터는 C# 힙이 아니라 네이티브 메모리에 있어서 C# 참조가 사라지고 GC가 돌아도 풀리지 않는다. Resources.UnloadUnusedAssets가 돌아야 아무도 참조하지 않는 에셋이 내려가고, Single 모드 씬 로드 때 이 호출이 일어난다. 전체를 훑는 비싼 작업이라 로딩 화면에서 부른다. Addressables는 Release만큼 참조 카운트가 줄고, 번들 안 에셋이 모두 해제돼야 번들이 내려간다.

로딩 화면에서 알아 둘 숫자는 0.9다. LoadSceneAsync의 progress는 데이터 로드가 끝나면 0.9까지만 오르고 나머지는 씬 활성화 몫이라, allowSceneActivation을 false로 두면 0.9에서 대기하다 true로 바꾸는 순간 활성화된다.

AsyncOperation op = SceneManager.LoadSceneAsync(name);
op.allowSceneActivation = false;        // 0.9에서 멈춰 기다린다

while (op.progress < 0.9f)
{
    bar.value = op.progress / 0.9f;     // 0~1로 정규화해 표시
    yield return null;
}

op.allowSceneActivation = true;         // 연출이 끝나면 활성화

면접에서 이렇게 답한다

  • 셋의 차이는 — Resources는 폴더 전부가 빌드에 박히고 인덱싱 비용이 든다. AssetBundle은 묶은 것만 넣고 원격 배포도 되지만 의존성과 해제를 직접 관리해야 한다. Addressables는 그 위에서 주소와 참조 카운트를 대신 관리한다.
  • 에셋이 번들에 중복되는 것을 어떻게 막나 — 번들에 지정되지 않은 의존 에셋은 참조하는 번들마다 복사되므로 공유 에셋을 공통 번들로 떼어 지정한다. Analyze로 찾아낼 수 있다.
  • 참조를 끊으면 메모리가 바로 돌아오나 — 아니다. 네이티브 메모리라 GC로 풀리지 않고 Resources.UnloadUnusedAssets가 돌아야 내려간다. Addressables는 Release로 참조 카운트를 줄인다.
  • CDN 비용을 줄이려면 — 클라이언트가 줄일 수 있는 건 전송량이다. 번들을 갱신 단위로 쪼개 바뀐 것만 받게 하고, 텍스처 압축과 해상도를 정리하고, 로컬 캐시와 해시 검사로 같은 파일을 두 번 받지 않게 한다.
  • 로비 진입이 15초라면 — 먼저 구간을 나눠 잰다. 다운로드, 에셋 로드, 초기화 중 어디가 긴지에 따라 손댈 곳이 다르다. 첫 화면에 필요 없는 로드를 미루고, 순차로 하던 것을 겹치고, 초기화는 프레임에 나눈다.

흔한 오해

  • Resources는 동기라 느리고 Addressables는 비동기라 빠르다 — Resources에도 LoadAsync가 있다. 차이는 빌드 포함 방식과 의존성·해제 관리다.
  • Addressables면 메모리 관리가 알아서 된다 — 참조 카운트를 대신 셀 뿐이다. Release를 부르지 않으면 번들이 그대로 남는다.
  • 번들 하나로 크게 묶는 게 항상 낫다 — 요청 수는 줄지만 일부만 바뀌어도 전체를 다시 받고 필요 없는 에셋까지 메모리에 올라온다. 갱신 빈도와 함께 쓰이는 단위로 묶는다.
  • Destroy하면 그 텍스처도 함께 내려간다 — 씬의 인스턴스만 사라지고 에셋은 언로드 전까지 남는다.

UI

Canvas가 언제 다시 그려지는지를 알면 해상도 대응도 최적화도 같은 이야기가 된다

핵심 개념

uGUI는 셋이 역할을 나눠 맡는다. Canvas는 자식 UI들의 사각형과 색을 모아 하나의 메시로 만들어 그리는 루트다. RectTransform은 Transform을 확장해 앵커(부모의 어디에 붙을지), 피벗(무엇을 기준으로 회전·크기 변경할지), 크기를 다루는 UI 전용 트랜스폼이다. EventSystem은 입력이 들어오면 Graphic Raycaster로 어떤 UI가 맞았는지 찾아 전달한다. 버튼이 안 눌리는 문제의 첫 번째 원인은 씬에 EventSystem이 없는 것이다.

성능 이야기는 전부 Canvas가 메시를 다시 만드는 시점에서 나온다. Canvas는 자식 그래픽 하나만 바뀌어도 그 Canvas 전체의 메시를 다시 만든다. 정적인 배경 100장과 매 프레임 바뀌는 타이머가 같은 Canvas에 있으면 숫자 하나 때문에 배경 100장이 매 프레임 재구성된다. 그래서 갱신 빈도가 다른 UI는 Canvas를 나눈다. 다만 배칭은 Canvas 경계를 넘지 못하니 무작정 쪼개면 드로우 콜이 늘어난다. 기준은 계층 구조가 아니라 얼마나 자주 바뀌는가다.

해상도 대응은 두 축으로 나뉜다. 크기는 CanvasScaler를 Scale With Screen Size로 두고 기준 해상도와 Match(너비와 높이 중 어느 쪽을 따를지)를 정해 비례시킨다. 화면비 차이는 스케일로 못 푼다. 이건 앵커의 몫이라 한쪽 구석에 붙는 요소는 그 방향에 앵커를 두고, 늘어나야 하는 요소는 앵커를 벌려 스트레치로 만든다. 노치가 있는 기기는 Screen.safeArea를 읽어 루트 RectTransform을 안쪽으로 민다.

3D를 따라다니는 체력 바는 World Space Canvas로 캐릭터에 붙이거나(거리에 따라 작아진다) Overlay Canvas에 두고 화면 좌표로 옮기는(항상 같은 크기) 두 방식이 있다. 뒤쪽은 카메라가 움직인 뒤에 잡아야 하므로 Update가 아니라 LateUpdate에서 갱신한다.

void LateUpdate()   // 카메라가 움직인 뒤에 잡아야 한 프레임 밀리지 않는다
{
    Vector3 world = target.position + offset;
    Vector3 view = Camera.main.WorldToViewportPoint(world);
    bool visible = view.z > 0f;   // z가 음수면 카메라 뒤라 좌표가 뒤집힌다

    if (bar.gameObject.activeSelf != visible) bar.gameObject.SetActive(visible);
    if (visible) bar.position = Camera.main.WorldToScreenPoint(world);
}

UI Toolkit은 구조가 다르다. UI가 게임오브젝트가 아니라 VisualElement 트리이고 레이아웃을 UXML과 USS(CSS 비슷한 스타일 시트)로 쓴다. 수천 개를 만들어도 씬 계층이 무거워지지 않는다. 대신 2022 LTS 시점에는 월드 스페이스 UI를 지원하지 않아 런타임 게임 UI는 uGUI가 기본이었고, 월드 스페이스는 Unity 6에서 들어왔다.

면접에서 이렇게 답한다

  • Canvas, RectTransform, EventSystem의 역할은 — Canvas는 자식 UI를 메시로 합쳐 그리는 루트, RectTransform은 앵커와 피벗으로 위치와 크기를 정하는 UI 전용 트랜스폼, EventSystem은 레이캐스트로 입력 대상을 찾아 전달하는 쪽이다. EventSystem이 없으면 화면은 나오는데 클릭만 안 먹는다.
  • 여러 해상도와 화면비를 어떻게 맞추나 — 크기는 CanvasScaler를 Scale With Screen Size로 두고 기준 해상도와 Match로 맞추고, 화면비는 앵커로 흡수한다. 노치 기기는 Safe Area를 읽어 루트를 안쪽으로 민다.
  • UI 요소가 아주 많을 때 — 갱신 빈도로 Canvas를 나눠 리빌드 범위를 줄이고, 누를 일 없는 이미지는 Raycast Target을 끈다. 목록은 화면에 보이는 만큼만 만들어 재활용하고, 숨길 때는 알파를 낮추지 말고 Canvas 컴포넌트를 끈다.
  • NGUI와 uGUI의 차이는 — NGUI는 에셋 스토어 서드파티 UI였고 uGUI는 그 개발자를 영입해 엔진에 내장한 공식 UI다. 아틀라스를 손으로 관리하던 방식이 스프라이트 패커와 Canvas 배칭으로 들어왔다.

흔한 오해

  • 알파를 0으로 만들면 안 그려진다 — 투명해질 뿐 메시는 그대로 만들어지고 배치에도 들어간다. 실제로 빼려면 Canvas 컴포넌트를 끄거나 게임오브젝트를 비활성화한다.
  • Canvas는 하나로 두는 게 좋다 — 반대다. 하나에 몰면 작은 변경 하나가 전체 리빌드를 부른다. 다만 잘게 쪼개면 배칭이 끊기므로 갱신 빈도 기준으로 나눈다.
  • CanvasScaler만 설정하면 화면비도 해결된다 — 스케일만 다룬다. 16:9와 20:9의 남는 폭은 앵커로 처리해야 하고, 안 그러면 요소가 쏠리거나 잘린다.
  • Raycast Target은 켜 둬도 공짜다 — 입력이 들어올 때마다 그래픽을 하나하나 검사한다. 배경이나 텍스트처럼 누를 일이 없는 것은 꺼 둔다.

물리

Rigidbody가 있느냐 없느냐로 충돌 이벤트와 비용이 갈린다는 것이 물리의 출발점이다

핵심 개념

물리 엔진은 모든 콜라이더를 매 틱 서로 비교하지 않는다. Rigidbody가 없는 콜라이더는 영영 움직이지 않는다고 보고 정적 구조에 미리 구워 둔다. 그래서 Rigidbody 없는 콜라이더끼리는 겹쳐도 아무 이벤트가 오지 않는다. Collider는 모양이고 Rigidbody는 그 모양이 시뮬레이션에 참여한다는 표시다.

조합OnCollisionEnterOnTriggerEnter
Collider ↔ Collider (Rigidbody 없음)없음없음
Rigidbody ↔ Collider발생발생
Kinematic Rigidbody ↔ Collider없음발생
Rigidbody ↔ Rigidbody발생발생
Kinematic ↔ Kinematic없음발생

Trigger와 Collision의 갈림길은 밀어내느냐다. Is Trigger를 켜면 서로 통과하며 들어옴·나감만 알려주므로 획득 범위나 인식 범위에 쓴다. 꺼져 있으면 엔진이 겹침을 풀며 반발력을 계산해 접촉점·상대 속도·충격량을 Collision 객체로 넘긴다. 트리거는 밀어낼 게 없으니 이 정보도 없다. 정적 콜라이더를 옮기면 정적이라 믿고 만든 구조를 다시 만들어야 해 비싸므로, 움직일 물체에는 Is Kinematic Rigidbody를 붙여 엔진이 이동을 인지하게 한다.

콜라이더 모양은 판정 공식이 단순한 순서대로 싸다. Sphere·Capsule·Box 다음이 Convex Mesh이고, 볼록하지 않은 MeshCollider는 서로 충돌시킬 수 없어 지형 전용이다.

이동은 셋으로 갈린다. transform.Translate는 물리를 건너뛰고 좌표만 바꿔 벽을 통과한다. AddForce는 힘을 줘 F=ma로 가속을 만들므로 질량이 클수록 덜 움직인다. MovePosition은 "다음 틱에 여기로 간다"고 알려주는 이동이라 충돌 검사와 보간이 유지돼, 조작감을 직접 잡는 캐릭터에 쓴다.

// 입력은 Update에서 읽는다. FixedUpdate에서 읽으면 짧게 누른 키를 통째로 놓친다
void Update() => input = new Vector3(Input.GetAxisRaw("Horizontal"), 0f, Input.GetAxisRaw("Vertical"));

void FixedUpdate()   // 이동은 물리 틱에 맞춘다 (rb는 Is Kinematic)
{
    rb.MovePosition(rb.position + input.normalized * (speed * Time.fixedDeltaTime));
}

탐지는 Raycast와 SphereCast다. Raycast는 굵기가 없는 선이라 얇은 물체나 틈을 통과해 버리고, SphereCast는 반지름을 가진 구를 쓸어 보내 그 굵기 안의 충돌을 잡는 대신 비싸다. 비용을 줄이는 가장 값싼 수단은 Layer Collision Matrix라, 레이어 쌍 체크를 끄면 그 조합은 검사에서 통째로 빠진다. Physic Material은 성능이 아니라 마찰과 반발, 즉 촉감을 정하는 에셋이고 질량은 Rigidbody의 Mass에서 정한다.

면접에서 이렇게 답한다

  • 두 오브젝트가 충돌하려면 — 양쪽에 Collider가 있고 적어도 한쪽에 Rigidbody가 있어야 한다. Rigidbody 없는 콜라이더끼리는 정적으로 취급돼 이벤트가 오지 않는다.
  • Trigger와 Collision의 차이는 — 트리거는 통과시키며 들어옴과 나감만 알려주고, 충돌은 밀어낸 뒤 접촉점과 충격량까지 넘긴다.
  • Kinematic Rigidbody와 Static Collider는 — 둘 다 힘에 반응하지 않지만, 정적 콜라이더를 옮기면 정적이라 가정하고 만든 구조를 재구축해야 해서 비싸다.
  • Translate와 AddForce의 차이는 — Translate는 물리를 건너뛴 순간 이동이라 벽을 통과하고, AddForce는 질량에 따라 가속이 정해지는 물리 이동이다.
  • 물리 기반 캐릭터 이동을 만든다면 — Kinematic Rigidbody에 캡슐 콜라이더를 두고 입력은 Update에서 모아 FixedUpdate에서 MovePosition으로 옮긴다. 접지와 벽 판정은 SphereCast로 한다.

흔한 오해

  • 트리거끼리는 Rigidbody 없이도 이벤트가 온다 — 오지 않는다. 트리거 SphereCollider만 붙은 두 오브젝트를 겹쳐도 조용하다. 한쪽에 Kinematic Rigidbody라도 붙여야 한다.
  • MeshCollider가 정확하니 그냥 쓰면 된다 — Convex를 켜야 다른 Rigidbody와 충돌하고(볼록 껍질로 근사, 기본 최대 255면), 그래도 기본 도형보다 훨씬 비싸다. 움직이는 물체는 도형 몇 개를 조합한다.
  • FixedUpdate가 Update보다 자주 불린다 — 기본 0.02초, 초당 50번이다. 60fps면 Update가 더 자주 돈다.

애니메이션·카메라·입력

상태 머신이 클립을 고르고, 카메라는 늦게 따라가고, 입력은 기기가 아니라 의미로 묶는다

핵심 개념

Animation 컴포넌트는 클립을 이름으로 재생하는 레거시다. 지금 쓰는 Animator(Mecanim)는 Animator Controller라는 상태 머신을 들고 다닌다. 상태, 전이, 파라미터, 레이어(상·하체를 따로 재생)를 다루므로 스크립트는 animator.SetFloat("Speed", v)처럼 상황만 알려주고 무슨 클립이 나갈지는 컨트롤러가 정한다. 휴머노이드 아바타로 구우면 뼈 구조가 다른 캐릭터에도 같은 애니메이션을 리타기팅해 쓸 수 있다.

전이와 블렌드 트리는 층이 다르다. 전이는 상태와 상태 사이를 시간을 두고 넘어가는 것이고, 블렌드 트리는 한 상태 안에서 파라미터 값에 따라 여러 클립의 가중치를 섞는 것이다. 걷기와 달리기를 Speed로 잇는 건 블렌드 트리(1D)이고, 서 있다가 공격으로 넘어가는 건 전이다.

IK(역운동학)는 방향이 반대인 계산이다. FK가 관절 각도를 넣어 손끝 위치를 얻는다면 IK는 손끝 목표를 주고 거기에 닿는 관절 각도를 역으로 푼다. 경사면에 발 높이를 맞추거나 손을 무기 손잡이에 붙일 때 쓴다. Animator 레이어의 IK Pass를 켜야 OnAnimatorIK가 불리고, 그 안에서 SetIKPosition과 SetIKPositionWeight로 목표와 가중치를 준다.

연출은 Timeline과 Cinemachine이 나눠 맡는다. Timeline은 애니메이션·오디오·활성화 트랙을 시간축에 배치하는 편집기이고, Cinemachine은 Virtual Camera들이 추적·조준·흔들림 규칙을 갖고 Brain이 붙은 실제 Camera 하나를 조종하는 구조다. 3인칭 카메라를 직접 만들면 추적, 감쇠, 벽 충돌 회피, 시야각 보정을 각각 붙여야 한다. 이때 반드시 LateUpdate에서 카메라를 옮긴다. Update에서 옮기면 아직 안 움직인 캐릭터 위치를 따라가 한 프레임씩 떨린다.

입력은 새 Input System이 구조를 바꿨다. 예전 Input Manager는 Input.GetKeyDown(KeyCode.Space)처럼 기기의 키를 직접 물었다. 새 시스템은 "점프"라는 액션을 정의하고 키보드 스페이스·패드 버튼·터치를 그 액션의 바인딩으로 연결해, 리바인딩과 플랫폼별 조작이 데이터로 해결된다.

void OnEnable()
{
    move = actions.FindAction("Move");   // 키보드 WASD와 패드 스틱이 한 액션에 묶여 있다
    jump = actions.FindAction("Jump");
    jump.performed += OnJump;            // 눌린 순간만 필요하면 콜백
    actions.Enable();
}

void OnDisable() { jump.performed -= OnJump; actions.Disable(); }   // 구독은 반드시 푼다

void Update() { Vector2 dir = move.ReadValue<Vector2>(); }   // 매 프레임 값은 폴링

면접에서 이렇게 답한다

  • Animation과 Animator의 차이는 — Animation은 클립을 이름으로 재생하는 레거시고, Animator는 상태·전이·파라미터·레이어를 가진 상태 머신으로 클립을 고른다.
  • IK는 무엇이고 언제 쓰나 — 목표 지점을 주고 관절 각도를 역으로 푸는 계산이다. 경사면 발 위치 보정이나 손을 무기에 고정할 때 쓴다.
  • 3인칭 카메라는 어떻게 구현하나 — 추적, 감쇠, 벽 충돌 회피를 나눠 만들고 반드시 LateUpdate에서 옮긴다. 실무에서는 Cinemachine의 Virtual Camera로 조합하고 상황별로 전환한다.
  • 트윈 라이브러리는 왜 쓰나 — 이징 곡선, 중간 취소, 연속 재생을 매번 코루틴으로 다시 만들지 않기 위해서다. 대신 대상이 파괴될 때 트윈도 같이 죽여야 한다.
  • 새 Input System은 무엇이 다른가 — 키를 직접 묻는 대신 액션을 정의하고 기기별 바인딩을 따로 연결한다. 그래서 리바인딩과 멀티 플랫폼 대응이 설정 데이터로 끝난다.

흔한 오해

  • Animator는 Animation의 이름만 바뀐 것 — 재생 방식 자체가 다르다. Animation에는 상태 머신도 파라미터도 리타기팅도 없다.
  • 블렌드 트리와 전이는 같은 것 — 블렌드 트리는 한 상태 안에서 클립을 동시에 섞고, 전이는 상태 사이를 넘어간다. 전이만으로 속도별 이동을 만들면 계단처럼 끊긴다.
  • Virtual Camera가 실제 카메라다 — Virtual Camera에는 Camera 컴포넌트가 없다. 규칙만 들고 있고 실제로 그리는 건 Brain이 붙은 카메라 하나다. Timeline도 컷신 전용이 아니라 런타임 연출에 그대로 쓴다.
  • 새 Input System을 넣으면 Input.GetKey를 못 쓴다 — Active Input Handling을 Both로 두면 둘 다 동작한다. New만 고르면 옛 API가 예외를 던진다.

AI와 길찾기

NavMesh는 지형을 미리 단순화해 둔 그래프이고, FSM과 행동 트리는 판단을 조직하는 방식이다

핵심 개념

길찾기를 매번 지형 삼각형 전체에서 풀면 비싸다. 그래서 NavMesh는 걸을 수 있는 바닥만 골라 볼록 다각형으로 미리 구워 둔 데이터다. 에이전트 반지름·키·오를 수 있는 높이·경사 한계를 기준으로 굽기 때문에, 같은 지형이라도 덩치가 다른 몬스터는 다른 NavMesh가 필요하다. 탐색은 이 다각형 그래프 위에서 A*로 폴리곤 순서를 찾고, 그 통로를 직선으로 펴서 꺾이는 지점 목록을 만든 뒤 에이전트가 차례로 향한다.

실제 이동은 NavMeshAgent가 맡는다. SetDestination으로 목적지만 주면 경로 계산, 속도·가속·회전, 다른 에이전트와의 회피까지 직접 처리한다. 즉 이건 물리 이동이 아니다. Rigidbody로도 밀면 둘이 서로 위치를 고쳐 떨리므로, 붙일 때는 Is Kinematic으로 둔다.

지형이 런타임에 바뀌면 세 가지로 나눠 대응한다. 건물이 세워지듯 바닥 자체가 바뀌면 AI Navigation 패키지의 NavMeshSurface로 그 영역을 다시 굽는다. 문이나 상자처럼 잠깐 막는 물체는 NavMeshObstacle을 붙이는데, carving을 켜면 NavMesh에 구멍을 뚫어 경로가 돌아가고 끄면 경로는 그대로 두고 회피만 한다. 움직이는 동안은 carving을 끄고 멈추면 켜는 것이 보통이다. 사다리나 점프처럼 끊긴 구간은 NavMeshLink로 잇는다. Unity 2022부터 이 기능들은 엔진 내장 Navigation 창이 아니라 com.unity.ai.navigation 패키지에 있다.

판단 쪽은 FSM이 출발점이다. 상태 하나가 한 가지 행동을 맡고 조건이 맞으면 다른 상태로 넘긴다. 들어올 때 준비와 나갈 때 정리를 상태가 직접 갖는 것이 핵심이라, "추격을 그만두면 속도를 되돌린다" 같은 규칙이 흩어지지 않는다.

public void Change(IState next)
{
    if (current == next) return;   // 같은 상태로 다시 들어가 Enter를 반복하지 않는다
    current?.Exit();               // 나가는 정리는 상태가 직접 갖는다
    current = next;
    current.Enter();
}

FSM의 한계는 규모다. 상태마다 어디로 갈 수 있는지를 일일이 적으므로 상태가 n개면 전이가 최대 n의 제곱에 가까워진다. "어떤 상태에 있든 체력이 20% 아래면 도망" 같은 전역 규칙을 넣으려면 모든 상태를 고쳐야 한다. 행동 트리는 전이를 없애고 매 틱 루트부터 트리를 평가한다. Selector는 자식을 왼쪽부터 시도해 처음 성공한 것을 쓰고(우선순위), Sequence는 전부 성공해야 성공한다(절차). 도망 가지를 맨 왼쪽에 붙이면 그 규칙이 모든 상황에 자동으로 우선한다. 대신 매 틱 트리를 훑는 비용과 구조를 읽는 난이도가 생긴다. FSM도 계층형(HFSM)으로 묶으면 꽤 버티므로, 상태가 대여섯 개이고 규칙이 뚜렷하면 FSM이 더 단순하다.

면접에서 이렇게 답한다

  • NavMesh란 무엇이고 AI 이동에 어떻게 쓰나 — 걸을 수 있는 바닥을 볼록 다각형으로 미리 구워 둔 그래프다. NavMeshAgent에 SetDestination으로 목적지를 주면 그 그래프 위에서 A*로 경로를 찾아 따라간다. 에이전트 반지름과 경사 한계로 굽기 때문에 덩치가 다른 유닛은 별도 설정이 필요하다.
  • 런타임에 NavMesh를 갱신하려면 — 바닥 자체가 바뀌면 NavMeshSurface로 다시 굽고, 잠깐 막는 물체는 NavMeshObstacle의 carving으로 구멍을 낸다. 움직이는 동안은 carving을 끄고 멈추면 켜는 식으로 재굽기 비용을 아낀다.
  • FSM은 어떻게 구현하나 — 상태를 인터페이스로 두고 Enter, Tick, Exit을 갖게 한 뒤 상태 머신은 전환만 책임진다. 전환 시 이전 상태의 Exit을 반드시 부르게 해서 정리 로직이 한곳에 모이게 한다.
  • FSM 말고 다른 방식은 — 행동 트리는 전이 대신 매 틱 트리를 위에서 평가해 Selector로 우선순위를, Sequence로 절차를 표현한다. 전역 규칙을 가지 하나로 넣을 수 있어 상태가 많아질수록 유리하고, 규모가 작으면 FSM이 더 읽기 쉽다.

흔한 오해

  • NavMesh는 한 번 구우면 못 바꾼다 — NavMeshSurface로 다시 굽거나 NavMeshObstacle로 구멍을 낼 수 있다. 다만 다시 굽는 건 비싸므로 영역을 쪼개거나 장애물 방식으로 대신한다.
  • NavMeshAgent는 Rigidbody로 움직인다 — 에이전트가 직접 위치를 정한다. 물리와 같이 쓰면 서로 위치를 고쳐 떨리므로 Rigidbody는 Kinematic으로 둔다.
  • SetDestination은 매 프레임 불러도 싸다 — 목적지가 바뀌면 경로를 다시 계산한다. 유닛이 수백이면 이게 병목이 되므로 일정 거리 이상 움직였을 때만 갱신한다.
  • 행동 트리가 FSM보다 항상 낫다 — 상태가 적고 전이 규칙이 뚜렷하면 FSM이 더 짧고 읽기 쉽다. 행동 트리는 매 틱 평가 비용과 학습 비용이 있다.
  • NavMesh만 깔면 서로 안 부딪힌다 — 에이전트끼리의 회피는 별도의 Obstacle Avoidance 품질 설정이고, 품질을 높이면 그만큼 비싸진다.

빌드와 플랫폼

빌드 용량은 대부분 텍스처와 오디오이고, 설치 실패는 대부분 아키텍처 설정 문제다

핵심 개념

빌드 크기를 줄이는 이유는 저장 공간이 아니라 설치 전에 이탈하는 사람이다. 용량이 커질수록 설치 전환율이 떨어지고, 구글 플레이는 App Bundle 크기에 상한이 있어(초과분은 Play Asset Delivery로 분리) 넘기면 아예 올리지 못한다. 무엇부터 줄일지는 감이 아니라 빌드 리포트로 정한다. 빌드 직후 Editor.log에 에셋 종류별 용량이 남는다.

항목방법보통 효과
텍스처ASTC 등 플랫폼 압축, Max Size 하향, 불필요한 밉맵·알파 제거가장 크다
오디오BGM은 Vorbis + Streaming, 짧은 효과음은 ADPCM, 샘플레이트 하향크다
코드Managed Stripping Level 상향, 안 쓰는 패키지 제거중간
배포 구조Addressables로 빼서 나중에 내려받기초기 용량만 준다

텍스처가 1등인 이유는 압축 포맷 하나로 몇 배가 갈리기 때문이다. 같은 2048 크기라도 RGBA32 무압축은 16MB, ASTC 6x6은 1MB 수준이다. 코드 쪽 Managed Stripping은 진입점에서 도달 가능한 코드만 남기는데, 리플렉션으로만 부르는 타입은 도달 불가로 보여 같이 지워진다. 이걸 막는 것이 link.xml이다.

Resources 폴더는 이 맥락에서 함정이다. 참조가 하나도 없어도 폴더 안의 모든 에셋이 빌드에 들어가고, 앱 시작 시 인덱스를 만드느라 기동도 느려진다. 필요한 것만 그때 불러오려면 Addressables를 쓴다. 반대로 주석이나 변수 이름을 줄이는 것은 컴파일 결과에 남지 않아 용량과 무관하다.

안드로이드 아키텍처는 ARMv7이 32비트, ARM64가 64비트 명령어 집합이다. 구글 플레이는 2019년 8월부터 64비트 지원을 요구해 ARMv7만 올리면 등록이 거부된다. ARM64는 IL2CPP 백엔드에서만 빌드된다는 점이 중요한데, Mono로 두면 Player Settings에서 ARM64 체크박스 자체가 비활성이다. "최신 기기에 APK가 설치되지 않는다"는 문제는 대개 ARM64 미포함이거나 Target API Level이 스토어 요구치보다 낮은 경우다. 둘 다 체크하면 APK 하나에 두 벌이 들어가 커지므로, 스토어 배포는 App Bundle로 올려 기기에 맞는 것만 내려가게 한다.

기기에서 도는 빌드의 로그는 adb logcat으로 본다. Android Logcat 패키지를 깔면 에디터 창에서 패키지 이름과 로그 레벨로 걸러 볼 수 있다. Development Build를 켜면 스택 트레이스가 온전히 남고 프로파일러도 붙지만 오버헤드가 있어 성능 수치는 상대 비교로만 쓴다. 서드파티 SDK는 대개 Gradle 의존성 충돌과 매니페스트 병합에서 사고가 나고, 결제는 영수증 검증을 반드시 서버에서 해야 한다.

면접에서 이렇게 답한다

  • 빌드 크기를 왜, 어떻게 줄이나 — 설치 전환율과 스토어 상한 때문이다. 먼저 빌드 리포트로 무엇이 큰지 확인하고, 대개 텍스처 압축 포맷과 Max Size에서 가장 큰 폭이 나온다. 그다음이 오디오 설정, 코드 스트리핑, Addressables 분리 순이다.
  • ARMv7과 ARM64의 차이는 — 32비트와 64비트 명령어 집합이고, 구글 플레이가 64비트를 필수로 요구한다. ARM64는 IL2CPP에서만 빌드되므로 백엔드를 IL2CPP로 바꾸고 두 아키텍처를 모두 체크한 뒤 App Bundle로 배포한다.
  • 최신 기기에 설치가 안 된다면 — 먼저 ARM64가 빠졌는지, Target API Level이 스토어 요구치보다 낮은지를 본다. 그다음 minSdkVersion과 서명, 설치 로그를 adb logcat으로 확인한다.
  • 기기 로그는 어떻게 보나 — adb logcat이나 Unity의 Android Logcat 창으로 본다. 개발 중에는 Development Build로 스택 트레이스를 살리고, 출시 빌드는 크래시 리포팅으로 모아서 본다.
  • 서드파티 SDK와 결제는 — Gradle 의존성 충돌과 매니페스트 병합이 주된 사고 지점이라 버전을 맞추고 병합 결과를 확인한다. 결제는 영수증을 서버에서 검증해 클라이언트 변조로 아이템이 나가지 않게 한다.

흔한 오해

  • 주석과 변수 이름을 줄이면 빌드가 작아진다 — 컴파일 결과에 남지 않는다. 용량은 에셋과 컴파일된 코드가 차지한다.
  • Resources 폴더에 넣으면 관리가 편하다 — 참조가 없어도 전부 빌드에 들어가고 시작 속도까지 느려진다. 동적 로딩이 필요하면 Addressables를 쓴다.
  • IL2CPP로 바꾸면 빌드가 작아진다 — 네이티브 코드로 변환하므로 오히려 커질 수 있다. 얻는 것은 실행 속도와 ARM64 지원이다.
  • 빌드 크기를 줄이면 프레임도 오른다 — 용량은 다운로드와 로딩 시간에 영향을 줄 뿐 한 프레임의 계산량과는 다른 축이다.
  • ARMv7만 올려도 요즘 기기는 다 돌아간다 — 기기가 실행은 해도 구글 플레이가 등록을 거부한다.

DOTS와 최신 기능

ECS는 데이터를 한 줄로 늘어놓아 캐시를 살리는 구조이고, Job과 Burst가 함께 가야 값을 한다

핵심 개념

GameObject 방식이 느려지는 지점은 계산량이 아니라 메모리를 읽는 순서다. MonoBehaviour는 각각 힙에 따로 할당돼 주소가 흩어져 있고, Transform 값을 만질 때마다 C# 쪽에서 엔진 네이티브 쪽으로 넘어간다. 유닛 1만 개를 순회하면 CPU는 매번 캐시에 없는 주소를 기다리게 되고, 이 기다림이 실제 연산보다 몇 배 길다.

ECS는 이 배치를 뒤집는다. 엔티티는 번호일 뿐이고 데이터는 컴포넌트 타입 조합(아키타입)이 같은 것끼리 모아 청크라는 연속 메모리 블록에 저장한다. System은 "LocalTransform과 Velocity를 둘 다 가진 것"을 쿼리해 그 청크들을 앞에서부터 쭉 훑는다. 주소가 순서대로 이어지니 캐시 라인 하나에 여러 개가 같이 딸려오고 프리페처도 다음에 읽을 곳을 맞힌다. 여기에 Job System으로 워커 스레드에 나눠 돌리고, Burst 컴파일러가 그 코드를 LLVM으로 SIMD가 들어간 네이티브로 바꾼다. 셋이 같이 있을 때 값을 한다.

[BurstCompile]
public partial struct MoveSystem : ISystem
{
    [BurstCompile]
    public void OnUpdate(ref SystemState state)
    {
        float dt = SystemAPI.Time.DeltaTime;

        // 두 컴포넌트를 다 가진 엔티티만 골라 청크 단위로 순서대로 훑는다
        foreach (var (tr, v) in SystemAPI.Query<RefRW<LocalTransform>, RefRO<Velocity>>())
            tr.ValueRW.Position += v.ValueRO.Value * dt;
    }
}

대가도 분명하다. 컴포넌트가 struct라 참조 타입을 못 담고, 문자열이나 매니지드 객체를 쓰려면 별도 처리가 필요하다. 엔티티에 컴포넌트를 붙이거나 떼면 아키타입이 바뀌어 데이터를 다른 청크로 옮기는 구조 변경이 일어나므로, 매 프레임 붙였다 떼는 설계는 오히려 느리다. 에디터 워크플로와 디버깅, 기존 플러그인 연동도 전부 다르다. 그래서 현실적인 선택은 전면 전환이 아니라 대량 유닛, 탄막, 군중처럼 개수가 압도적인 부분만 ECS로 돌리는 하이브리드다. Entities 1.0 정식 버전은 Unity 2022 LTS 시기에 나왔고 Unity 6에서 안정화가 더 진행됐지만, 게임의 기본 골격은 여전히 GameObject다.

Unity 6에서 하나만 고른다면 GPU Resident Drawer가 설명하기 좋다. 렌더링이 느린 이유가 GPU 계산이 아니라 CPU가 오브젝트마다 드로우 콜을 준비하는 비용인 경우가 많은데, 이 기능은 BatchRendererGroup API로 메시 데이터를 GPU 쪽에 상주시켜 CPU의 준비 작업을 크게 줄인다. 같이 들어온 GPU Occlusion Culling은 가려진 인스턴스를 GPU에서 걸러낸다. 그 외에 Render Graph 정리, 플랫폼별 빌드 설정을 에셋으로 관리하는 Build Profiles, 멀티플레이 설정을 모은 Multiplayer Center가 있다.

면접에서 이렇게 답한다

  • ECS란 무엇인가 — 엔티티는 식별자, 컴포넌트는 순수 데이터, 시스템은 그 데이터를 처리하는 로직으로 나눈 구조다. 상속으로 기능을 물려주는 대신 어떤 컴포넌트를 가졌느냐로 동작이 정해진다.
  • GameObject 방식보다 왜 빠른가 — 같은 컴포넌트 조합을 가진 엔티티의 데이터를 연속된 메모리에 모아 두고 순서대로 훑기 때문에 캐시 미스가 크게 준다. 여기에 Job System으로 코어를 나눠 쓰고 Burst로 SIMD까지 얹으면 몇 배 차이가 난다.
  • 언제 도입하나 — 유닛 수천에서 수만처럼 같은 처리를 대량으로 반복하는 구간에 먼저 쓴다. 워크플로와 디버깅 방식이 달라 전면 전환은 비용이 크므로 하이브리드로 시작해 효과를 측정한 뒤 넓힌다.
  • Unity 6의 특징 하나를 소개하라 — GPU Resident Drawer를 말한다. 오브젝트마다 CPU가 드로우 콜을 준비하던 비용을 GPU 상주 데이터와 BatchRendererGroup으로 옮겨, 오브젝트가 많은 씬에서 CPU 렌더 스레드 부하를 줄여 주는 기능이라고 설명한다.

흔한 오해

  • ECS를 쓰면 무조건 빨라진다 — 대상 개수가 적으면 구조 변경과 쿼리 오버헤드만 남는다. 수천 개 이상을 같은 방식으로 처리할 때 이득이 나온다.
  • ECS가 곧 멀티스레딩이다 — 별개다. 병렬화는 Job System이 하고, ECS는 그 Job이 읽기 좋은 형태로 데이터를 배치할 뿐이다.
  • Burst를 켜면 모든 C#이 빨라진다 — Burst가 컴파일할 수 있는 것은 값 타입과 NativeContainer만 쓰는 제한된 코드다. 매니지드 객체를 건드리면 빠진다.
  • DOTS가 MonoBehaviour를 대체했다 — Unity 6에서도 기본은 GameObject다. DOTS는 필요한 부분에 골라 쓰는 선택지다.
  • GPU Resident Drawer를 켜면 드로우 콜이 사라진다 — 없어지는 게 아니라 CPU가 준비하던 일이 GPU 쪽으로 옮겨진다. GPU가 이미 한계면 도움이 되지 않는다.
