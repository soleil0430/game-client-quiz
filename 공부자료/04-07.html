그래픽스·렌더링

Unity 렌더 파이프라인과 셰이더

URP는 C#으로 짠 렌더 파이프라인이다. 확장은 Renderer Feature, 비용은 배리언트다

Built-in용으로 짠 조명 셰이더를 URP 프로젝트에 넣으면 분홍색이 된다. 프레임을 그리는 순서와 셰이더 규약이 통째로 바뀌었기 때문이다. 무엇이 어디로 옮겨졌는지부터 잡아야 전환 비용이 보인다.

SRP는 그리는 순서를 C#으로 연 틀이다

Built-in 렌더 파이프라인은 프레임을 그리는 순서가 엔진 내부(C++)에 고정돼 있었다. 개발자는 이미지 이펙트나 커맨드 버퍼처럼 정해진 구멍으로만 끼어들 수 있었다.

SRP(Scriptable Render Pipeline)는 그 순서를 C#으로 짜게 연 틀이다. URP와 HDRP는 유니티가 SRP 위에 만들어 둔 구현이다. URP는 모바일부터 PC까지, HDRP는 고사양 PC와 콘솔용이다.

주제 Built-in URP
셰이더 인클루드 UnityCG.cginc Core.hlsl
패스 태그 ForwardBase UniversalForward
확장 지점 이미지 이펙트, GrabPass Renderer Feature
포스트 프로세싱 별도 패키지 Volume 내장

표준 셰이더를 쓰던 머티리얼은 URP의 자동 변환 도구가 바꿔 준다. 직접 쓴 셰이더는 사람이 다시 쓴다. Shader Graph로 만든 것은 URP와 HDRP 양쪽에서 쓸 수 있다.

Renderer Feature로 패스를 하나 더 끼운다

Renderer Feature는 URP 렌더러의 정해진 시점에 패스를 추가하는 확장점이다. 불투명을 그린 뒤 같은 위치를 고를 수 있다.

외곽선 그리기, 화면을 복사해 왜곡에 쓰기, 특정 레이어 재렌더가 대표적이다. 순서 자체를 갈아엎어야 할 때만 커스텀 SRP를 고려한다. 유지 비용이 크기 때문이다.

셰이더 분기는 워프 안에서 갈릴 때 비싸다

GPU는 수십 개 스레드를 한 묶음(워프·웨이브)으로 묶어 같은 명령을 실행한다. 묶음 안에서 조건이 갈리면 양쪽을 모두 실행하고 결과만 골라 쓴다. 머티리얼 상수처럼 묶음 전체가 같은 값으로 갈리는 분기는 싸다.

키워드로 배리언트를 나누면 분기 자체가 사라진다. 대신 조합 수가 문제로 넘어온다:

#pragma multi_compile _ _MAIN_LIGHT_SHADOWS  // 항상 컴파일, 런타임 토글
#pragma shader_feature_local _EMISSION       // 안 쓰면 빌드에서 빠짐

half4 frag(Varyings i) : SV_Target
{
    half4 c = SAMPLE_TEXTURE2D(_BaseMap, sampler_BaseMap, i.uv);
    #ifdef _EMISSION
        c.rgb += _EmissionColor.rgb;   // 이 줄은 배리언트에만 들어간다
    #endif
    return c;
}

배리언트는 빌드와 첫 사용에서 값을 치른다

키워드 조합마다 셰이더가 따로 컴파일된다. 키워드가 늘면 조합이 곱으로 폭발한다. 빌드 시간과 용량이 커지고, 처음 쓰는 배리언트를 GPU에 올리는 순간 프레임이 튄다.

대응은 세 가지다. 안 쓰는 조합이 빠지도록 shader_feature를 쓰고, 빌드 스트리핑으로 잘라 낸다. 남는 것은 Shader Variant Collection으로 로딩 중에 미리 워밍업한다.

컴퓨트 셰이더는 렌더링 파이프라인 밖에서 GPU 병렬 연산을 쓰는 프로그램이다. 서로 독립적인 데이터 수만 건에 같은 계산을 하는 입자 시뮬레이션·컬링·이미지 처리에 맞는다. 결과를 CPU로 되읽으면 동기화 대기가 생긴다.

파티클 시스템과 VFX Graph를 나눠 쓰는 것도 같은 이유다. 파티클 시스템은 CPU가 갱신해 스크립트·물리와 엮기 쉽다. VFX Graph는 컴퓨트 셰이더로 GPU가 갱신해 수가 많을 때 유리하다.

면접에서 이렇게 답한다

  • Built-in, URP, HDRP 중 무엇을 고르나 — 모바일이 타깃이면 URP다. 다만 Built-in용 커스텀 셰이더는 다시 써야 하는 경우가 많다. 전환 비용을 일정에 잡는다.
  • Renderer Feature는 언제 쓰나 — 불투명을 그린 뒤 외곽선을 얹는 식으로 정해진 시점에 패스를 더 넣을 때 쓴다. 커스텀 SRP는 유지 비용이 커서 구조 자체를 갈아야 할 때만 고려한다.
  • 셰이더 분기가 느린 이유 — GPU는 워프 단위로 같은 명령을 실행한다. 워프 안에서 조건이 갈리면 양쪽을 다 돌고 결과만 고른다.
  • 배리언트가 많아지면 — 빌드 시간과 용량이 늘고 처음 쓰는 배리언트를 올릴 때 히칭이 생긴다. shader_feature와 스트리핑으로 줄이고 남는 건 미리 워밍업한다.
  • 컴퓨트 셰이더는 언제 쓰나 — 수만 건의 독립적인 데이터에 같은 계산을 반복할 때 쓴다. 결과를 GPU 안에서 소비해야 이득이 남는다.

이런 오해를 한다

  • URP로 바꾸면 셰이더는 그대로 돈다 — 인클루드 파일과 패스 태그가 다르다. Built-in용 조명 셰이더는 대개 재작성이 필요하다.
  • 셰이더 분기도 CPU의 if처럼 한쪽만 실행된다 — 워프 안에서 갈리면 양쪽을 다 돈다.
  • 배리언트는 GPU만 느려지게 한다 — 실제 문제는 빌드 시간, 용량, 첫 사용 시점의 히칭이다.
  • VFX Graph가 파티클 시스템의 상위 호환이다 — CPU 쪽 상호작용이 제한적이고 컴퓨트 셰이더 지원 기기가 필요하다. 게임플레이에 얽힌 효과는 파티클 시스템이 낫다.
  • 포스트 프로세싱은 공짜에 가깝다 — 화면 픽셀 수에 비례하는 패스다. 모바일에서는 타일 메모리를 비웠다 채우는 비용까지 붙는다.

3줄 정리

  • SRP는 그리는 순서를 C#으로 짜게 연 틀이다
  • 확장은 Renderer Feature, 순서 교체는 커스텀 SRP
  • 배리언트 값은 빌드 용량과 첫 사용 히칭으로 온다
