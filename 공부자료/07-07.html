자료구조·알고리즘

정렬과 탐색

정렬은 최악·추가 공간·안정성으로 고른다. 정렬해 두면 탐색이 O(log N)이다

랭킹 100만 명에서 특정 점수 구간만 뽑아야 한다. 정렬 없이 하면 질의가 올 때마다 100만 개를 훑는다.

한 번 정렬해 두면 그다음부터는 스무 번이면 끝난다.

정렬은 속도가 아니라 최악·공간·안정성으로 고른다

비교로만 정렬하면 아무리 잘해도 O(N log N)보다 빠를 수 없다. 평균 속도가 선택 기준이 되지 못하는 이유다.

실제로 갈리는 것은 셋이다. 최악일 때 어떻게 되는지, 추가 메모리를 얼마나 쓰는지, 같은 값의 순서를 지키는지.

정렬 평균 최악 추가 공간 안정
퀵 O(N log N) O(N²) O(log N) 아니다
병합 O(N log N) O(N log N) O(N) 그렇다
힙 O(N log N) O(N log N) O(1) 아니다
삽입 O(N²) O(N²) O(1) 그렇다
계수 O(N + K) O(N + K) O(K) 그렇다

퀵이 O(N²)가 되는 경우와 인트로 정렬

퀵 정렬은 피벗으로 작은 쪽과 큰 쪽을 나눈 뒤 각각을 재귀적으로 다시 정렬한다. 분할이 반씩 되면 재귀 깊이가 log N이다. 매번 한쪽으로 쏠리면 깊이가 N이 되어 O(N²)로 떨어진다.

이미 정렬된 배열에서 첫 원소를 피벗으로 삼는 소박한 구현이 정확히 그 경우다. 무작위 피벗이나 세 값의 중간값을 피벗으로 써서 이를 피한다.

실무 정렬 함수는 퀵·힙·삽입 정렬을 섞어(인트로 정렬) 최악을 막는다. 퀵으로 시작해 재귀가 깊어지면 힙으로, 구간이 작아지면 삽입으로 갈아탄다. 퀵은 제자리 정렬이라 병합 정렬보다 추가 메모리가 적고 캐시 효율이 좋지만 안정 정렬은 아니다.

마지막이 삽입인 이유는 따로 있다. 이미 자리에 가까운 원소는 비교 한 번에 끝나므로 원소가 거의 안 밀려 O(N)에 가깝다. 거의 정렬된 입력에서 삽입 정렬이 O(N)에 수렴한다는 성질이라, 그래서 실무 라이브러리도 구간이 작아지면 삽입 정렬로 갈아탄다.

선택 정렬과 힙 정렬은 입력 상태와 무관하게 각각 O(N²), O(N log N)으로 고정이다. 입력이 이미 정렬돼 있어도 덕을 못 본다는 뜻이다.

병합 정렬은 입력과 무관하게 최악에도 O(N log N)이고 안정 정렬이지만, 병합용 배열 O(N)이 더 든다. 퀵 정렬은 평균 O(N log N)에 제자리로 돌아 메모리와 캐시 면에서 유리한 대신, 피벗을 잘못 고르면 최악 O(N²)이고 불안정하다.

그래서 외부 정렬이나 연결 리스트 정렬에는 병합 정렬을, 메모리에 통째로 올라가는 배열 정렬에는 퀵 정렬 계열을 쓴다.

비교를 안 하면 O(N log N)보다 빠를 수 있다

표 맨 아래 계수 정렬만 O(N + K)다. 비교 정렬의 하한인 O(N log N)을 넘어선다. 값을 서로 비교하지 않기 때문이다.

계수 정렬은 값마다 개수를 세어 자리를 잡으므로, 원소 수 N과 값의 범위 K에 대해 O(N + K)에 끝나고 만다. 값의 범위가 좁은 정수 키를 대량으로 정렬할 때가 제자리다.

대신 크기 K짜리 카운트 배열이 필요해 값의 범위가 넓으면 메모리가 폭발하고, 실수나 임의 비교 기준에는 쓸 수 없다. 기수 정렬은 자릿수별로 계수 정렬을 반복해 K가 큰 정수에도 쓸 수 있게 만든 변형이다.

안정 정렬은 언제 필요한가

안정 정렬은 비교 기준이 같은 원소들의 원래 순서를 유지한다. 여러 기준으로 차례로 정렬하거나 동점자 순서를 보존해야 할 때 필요하다.

랭킹 화면을 떠올려 보라. 이름순 목록을 점수순으로 다시 정렬하며 동점자의 이름순을 지킬 때가 그렇다. 병합 정렬과 삽입 정렬은 안정적이고, 퀵 정렬과 힙 정렬은 보통 불안정하다.

C#의 Array.Sort와 List<T>.Sort는 두 메서드 모두 인트로소트를 쓰며 제자리·불안정 정렬이고, 그래서 같은 키의 원래 순서는 안 지켜진다.

같은 키의 원래 순서를 지켜야 하면 안정 정렬인 LINQ의 OrderBy를 쓰되, 새 시퀀스를 만들어 할당이 생긴다는 점은 감안한다. 매 프레임 도는 코드라면 그 할당이 그대로 GC 부담이다. 정렬 기준은 IComparer<T>나 Comparison<T> 대리자로 넘긴다.

이진 탐색은 값보다 경계를 묻는다

정렬돼 있으면 이진 탐색으로 O(log N)에 찾는다. 비교할 때마다 남은 범위를 절반으로 줄이므로 로그가 나온다. 2의 20제곱이 약 104만이라 100만 개는 약 20번 안에 찾는다.

공짜는 아니다. 데이터가 정렬돼 있어야 하고, 삽입이 잦으면 정렬을 유지하는 비용이 커서 해시 테이블이나 균형 트리가 나을 수 있다.

면접에서 묻는 것은 값 하나보다 경계다. lower bound는 찾는 값보다 크거나 같은 첫 원소의 위치, upper bound는 그 값을 초과하는 첫 위치이므로, 둘의 차이가 그 값의 개수다.

값이 없으면 끼워 넣을 자리를 돌려주므로 -1 같은 실패 표시가 아니다. 이 점이 자주 헷갈린다. 중간 인덱스는 (lo + hi) / 2 대신 lo + (hi - lo) / 2로 계산해 오버플로를 피한다: 

// value 이상인 첫 위치. 없으면 끼워 넣을 자리를 돌려준다
public static int LowerBound(int[] sorted, int value)
{
    int lo = 0, hi = sorted.Length;          // [lo, hi) 반열린 구간
    while (lo < hi)
    {
        int mid = lo + (hi - lo) / 2;        // (lo + hi) / 2는 오버플로 위험
        if (sorted[mid] < value) lo = mid + 1;
        else hi = mid;                       // <= 로 바꾸면 upper bound
    }
    return lo;
}

면접에서 이렇게 답한다

  • 퀵 정렬과 최악 — 피벗으로 나눠 재귀로 정렬하고 평균 O(N log N)이다. 분할이 한쪽으로 쏠리면 재귀 깊이가 N이 되어 O(N²)다. 무작위 피벗으로 피하고, 실무 구현은 인트로 정렬로 최악을 O(N log N)에 묶는다고 이어 답한다.
  • 퀵과 병합 중 무엇을 쓰나 — 메모리에 올라가는 배열이면 제자리로 돌고 캐시 효율이 좋은 퀵 계열을 쓴다. 최악을 보장해야 하거나 안정 정렬이 필요하면 O(N) 추가 공간을 쓰더라도 병합을 쓴다.
  • lower bound와 upper bound — 각각 값 이상인 첫 위치와 값을 초과하는 첫 위치다. 두 위치를 빼면 그 값이 몇 개 들었는지 바로 나온다. 둘 다 이진 탐색이라 O(log N)이다.

이런 오해를 한다

  • “퀵 정렬은 항상 O(N log N)” — 피벗이 쏠리면 O(N²)다. 평균과 최악을 나눠 말해야 한다.
  • “List.Sort는 안정 정렬이다” — 불안정이다. 같은 키의 순서가 필요하면 OrderBy를 쓰거나 비교자에 두 번째 기준을 넣는다.
  • “거의 정렬된 데이터에도 퀵이 낫다” — 삽입 정렬이 O(N)에 수렴하고, 소박한 퀵은 오히려 최악이 된다.
  • “lower bound는 값이 없으면 -1을 준다” — 끼워 넣을 자리를 준다. 실제로 있는지는 그 위치의 값을 봐야 안다.

3줄 정리

  • 비교 정렬은 O(N log N)이 한계다. 최악과 안정성으로 고른다
  • 퀵은 쏠리면 O(N²). 실무 구현은 인트로 정렬이다
  • 이진 탐색은 값이 아니라 경계를 구하는 도구다
