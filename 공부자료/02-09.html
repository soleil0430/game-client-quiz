Unity 엔진

AI와 길찾기

NavMesh는 지형을 미리 단순화해 둔 그래프이고, 판단은 FSM에서 시작해 행동 트리로 넘어간다

몬스터가 벽을 돌아 플레이어에게 와야 한다. 매 프레임 지형 삼각형 전체에서 길을 풀면 유닛 몇 마리에 프레임이 무너진다. NavMesh는 그 계산을 미리 해 둔 데이터다.

NavMesh는 걸을 수 있는 바닥만 구워 둔 그래프다

NavMesh는 걸을 수 있는 바닥만 골라 볼록 다각형으로 미리 구워 둔 데이터다. 탐색은 이 다각형 그래프 위에서 A* 로 폴리곤 순서를 찾는다. 그 통로를 직선으로 펴면 꺾이는 지점 목록, 즉 경로가 나온다.

굽는 기준은 에이전트 반지름과 키, 오를 수 있는 높이, 경사 한계다. 그래서 같은 지형이라도 덩치가 다른 몬스터는 다른 NavMesh가 필요하다.

NavMeshAgent는 물리로 움직이지 않는다

SetDestination으로 목적지만 주면 NavMeshAgent가 나머지를 한다. 경로 계산, 속도와 가속, 회전, 다른 에이전트와의 회피까지 직접 처리한다.

이건 물리 이동이 아니다. Rigidbody로도 밀면 둘이 서로 위치를 고쳐 떨린다. 에이전트에 Rigidbody를 붙일 때는 Is Kinematic으로 둔다.

SetDestination은 목적지가 바뀔 때마다 경로를 다시 계산한다. 유닛이 수백이면 이게 병목이라, 목표가 일정 거리 이상 움직였을 때만 갱신한다.

지형이 바뀌면 다시 굽거나 구멍을 뚫는다

런타임 변화는 세 가지로 나눠 대응한다. 건물이 세워지듯 바닥 자체가 바뀌면 NavMeshSurface로 그 영역만 다시 굽는다.

문이나 상자처럼 잠깐 막는 물체는 NavMeshObstacle을 붙인다. carving을 켜면 NavMesh에 구멍을 뚫어 경로가 돌아가고, 끄면 경로는 그대로 두고 회피만 한다. 움직이는 동안은 끄고 멈추면 켜는 것이 보통이다.

사다리나 점프처럼 끊긴 구간은 NavMeshLink로 잇는다. Unity 2022부터 이 기능들은 엔진 내장 Navigation 창이 아니라 com.unity.ai.navigation 패키지에 있다.

상태가 늘면 전이가 제곱으로 늘어난다

판단 쪽은 FSM이 출발점이다. 상태 하나가 한 가지 행동을 맡고, 조건이 맞으면 다른 상태로 넘긴다. 들어올 때 준비와 나갈 때 정리를 상태가 직접 갖는 것이 핵심이다:

public void Change(IState next)
{
    if (current == next) return;   // 같은 상태로 다시 들어가 Enter를 반복하지 않는다
    current?.Exit();               // 나갈 때 정리는 상태가 직접 갖는다
    current = next;
    current.Enter();               // 들어올 때 준비도 마찬가지다
}

한계는 규모다. 상태마다 어디로 갈 수 있는지를 적으므로 상태가 n개면 전이가 n의 제곱에 가까워진다. 어떤 상태에서든 체력이 20% 아래면 도망가게 하려면 모든 상태를 고쳐야 한다.

행동 트리는 전이를 없애고 매 틱 루트부터 트리를 평가한다. Selector는 자식을 왼쪽부터 시도해 처음 성공한 것을 쓴다. Sequence는 전부 성공해야 성공한다.

대신 매 틱 트리를 훑는 비용과 구조를 읽는 난이도가 생긴다. 상태가 대여섯 개이고 규칙이 뚜렷하면 FSM이 더 단순하다.

면접에서 이렇게 답한다

  • NavMesh란 무엇이고 AI 이동에 어떻게 쓰나 — 걸을 수 있는 바닥을 볼록 다각형으로 미리 구워 둔 그래프입니다. SetDestination으로 목적지를 주면 그 위에서 A* 로 경로를 찾아 따라갑니다. 반지름과 경사 한계로 굽기 때문에 덩치가 다른 유닛은 별도 설정이 필요합니다.
  • 런타임에 NavMesh를 갱신하려면 — 바닥이 바뀌면 NavMeshSurface로 다시 굽고, 잠깐 막는 물체는 NavMeshObstacle의 carving으로 구멍을 냅니다. 움직이는 동안은 carving을 꺼 재굽기 비용을 아낍니다.
  • FSM은 어떻게 구현하나 — 상태를 인터페이스로 두고 Enter, Tick, Exit을 갖게 한 뒤 상태 머신은 전환만 책임집니다. 전환할 때 이전 상태의 Exit을 반드시 불러 정리 로직을 한곳에 모읍니다.
  • FSM 말고 다른 방식은 — 행동 트리는 매 틱 트리를 위에서 평가해 Selector로 우선순위를, Sequence로 절차를 표현합니다. 전역 규칙을 가지 하나로 넣을 수 있어 상태가 많을수록 유리합니다.

이런 오해를 한다

  • NavMesh는 한 번 구우면 못 바꾼다 — NavMeshSurface로 다시 굽거나 NavMeshObstacle로 구멍을 낼 수 있다. 다시 굽는 것이 비싸 영역을 쪼개 쓴다.
  • NavMeshAgent는 Rigidbody로 움직인다 — 에이전트가 직접 위치를 정한다. 물리와 같이 쓰면 서로 위치를 고쳐 떨리므로 Rigidbody는 Kinematic으로 둔다.
  • SetDestination은 매 프레임 불러도 싸다 — 목적지가 바뀌면 경로를 다시 계산한다. 유닛이 수백이면 이게 병목이 된다.
  • 행동 트리가 FSM보다 항상 낫다 — 상태가 적고 전이 규칙이 뚜렷하면 FSM이 더 짧고 읽기 쉽다. 행동 트리는 매 틱 평가 비용이 있다.
  • NavMesh만 깔면 서로 안 부딪힌다 — 에이전트끼리의 회피는 별도의 품질 설정이고, 높이면 그만큼 비싸진다.

3줄 정리

  • NavMesh는 걸을 수 있는 바닥을 미리 구워 둔 그래프다
  • 에이전트 이동은 물리가 아니라 에이전트가 직접 한다
  • 상태가 적으면 FSM, 전역 규칙이 많아지면 행동 트리
