Unity 엔진

에셋과 리소스 관리

에셋은 기기 메모리보다 크다. 무엇을 언제 올리고 내리는지가 세 방식으로 갈린다

모바일 게임의 에셋을 다 합치면 기기 메모리보다 크다. 전부 올리면 죽고, 필요할 때마다 올리면 로딩이 길어진다.

지금 필요한 것만 올리고 나머지를 어떻게 미루느냐가 문제다.

Resources 폴더가 빌드와 구동을 무겁게 하는 이유

Resources 폴더는 참조 여부를 따지지 않는다. 폴더 안에 있다는 이유만으로 전부 빌드에 들어간다. 시작할 때 전체 목록을 인덱싱하느라 구동도 늦어진다.

문서는 에셋이 1만 개면 저사양 모바일에서 수 초가 걸린다고 적고 있다. 게임 화면이 뜨기도 전에 버리는 시간이다.

로드 방식은 아래 셋 중에서 고른다.

기준ResourcesAssetBundleAddressables
빌드 포함폴더 전부번들로 묶은 것만그룹으로 묶은 것만
로드경로 문자열번들을 열고 이름으로주소로 비동기
원격 배포불가직접 구현기본 지원
의존성·해제직접직접참조 카운트

AssetBundle은 에셋을 묶은 아카이브 파일이다. Addressables는 그 위에 주소 체계와 참조 카운트 관리를 얹은 상위 시스템이다.

공유 텍스처가 번들 열 개에 복사되는 문제

번들을 직접 다루면 중복을 만난다. 어느 번들에도 지정하지 않은 의존 에셋은, 그것을 참조하는 번들마다 복사본으로 들어간다. 공유 텍스처가 번들 열 개에 들어가면 용량도 메모리도 열 배다.

해법은 공통 텍스처와 머티리얼, 셰이더를 별도 번들로 떼어 지정하는 것이다. Addressables는 Analyze 창의 중복 의존성 검사로 이런 곳을 찾아 준다.

반대 방향의 함정도 있다. 로컬 프리팹이 원격 번들의 머티리얼을 참조하면, 원격을 받기 전에는 로드가 실패한다.

참조를 끊어도 메모리가 돌아오지 않는다

텍스처나 메시의 실제 데이터는 C# 힙이 아니라 네이티브 메모리에 있다. C# 참조를 끊고 GC가 돌아도 그쪽은 그대로다. Resources.UnloadUnusedAssets가 돌아야 아무도 참조하지 않는 에셋이 내려간다.

이 호출은 Single 모드로 씬을 로드할 때 함께 일어난다. 전체를 훑는 비싼 작업이라 보통 로딩 화면 뒤에 숨긴다. Addressables는 Release를 부른 만큼 참조 카운트가 줄고, 번들 안 에셋이 모두 해제돼야 번들이 내려간다.

Destroy가 지우는 것은 씬에 놓인 인스턴스뿐이다. 에셋 자체는 언로드 전까지 메모리에 남는다.

로딩 바는 왜 0.9에서 멈추나

LoadSceneAsync의 progress가 0.9까지만 오르기 때문이다. 데이터 로드가 끝난 지점이 0.9이고, 남은 0.1은 씬 활성화 몫이다. allowSceneActivation을 false로 두면 딱 0.9에서 기다린다.

연출을 마친 뒤 씬을 띄우는 로딩 화면 코드다:

AsyncOperation op = SceneManager.LoadSceneAsync(name);
op.allowSceneActivation = false;      // 0.9에서 멈춰 기다린다

while (op.progress < 0.9f)
{
    bar.value = op.progress / 0.9f;   // 0~1로 정규화해 보여 준다
    yield return null;
}

op.allowSceneActivation = true;       // 연출이 끝나면 활성화한다

진행도를 0.9로 나눠야 바가 100%까지 찬다. 그대로 쓰면 다 끝난 로딩을 90%짜리로 보여 주게 된다.

면접에서 이렇게 답한다

  • 셋의 차이 — Resources는 폴더 전부가 빌드에 박히고 인덱싱 비용이 든다고 답한다. AssetBundle은 묶은 것만 넣고 원격 배포도 되지만 의존성과 해제를 직접 관리한다. Addressables는 그 위에서 주소와 참조 카운트를 대신 관리한다.
  • 참조를 끊으면 메모리가 바로 돌아오나 — 아니라고 먼저 자른다. 네이티브 메모리라 GC로 풀리지 않고 Resources.UnloadUnusedAssets가 돌아야 내려간다. Addressables는 Release로 참조 카운트를 줄인다.
  • 로비 진입이 15초라면 — 먼저 구간을 나눠 잰다고 말한다. 다운로드와 에셋 로드와 초기화 중 어디가 긴지에 따라 손댈 곳이 다르다. 첫 화면에 필요 없는 로드는 미루고, 순차로 하던 것을 겹친다.

이런 오해를 한다

  • “Resources는 동기라 느리고 Addressables는 비동기라 빠르다” — Resources에도 LoadAsync가 있다. 차이는 빌드 포함 방식과 의존성·해제 관리다.
  • “Addressables면 메모리 관리가 알아서 된다” — 참조 카운트를 대신 셀 뿐이다. Release를 부르지 않으면 번들이 그대로 남는다.
  • “번들 하나로 크게 묶는 게 낫다” — 일부만 바뀌어도 전체를 다시 받고, 필요 없는 에셋까지 올라온다. 갱신 빈도와 함께 쓰이는 단위로 묶는다.
  • “Destroy하면 그 텍스처도 함께 내려간다” — 씬의 인스턴스만 사라진다. 에셋은 언로드 전까지 남는다.

3줄 정리

  • Resources는 폴더 전부가 빌드에 박혀 구동을 늦춘다
  • 번들에 지정 안 된 공유 에셋은 번들마다 복사된다
  • 메모리는 UnloadUnusedAssets나 Release로만 내려간다
