에셋과 리소스 관리

무엇을 언제 메모리에 올리고 언제 내리는가 — Resources·AssetBundle·Addressables의 선택 기준

핵심 개념

모바일 게임의 에셋은 기기 메모리보다 크다. 그래서 질문은 늘 하나다. 지금 필요한 것만 올리고 나머지는 어떻게 미뤄 두는가. 방식은 셋이다.

ResourcesAssetBundleAddressables
빌드 포함폴더 전부번들로 묶은 것만그룹으로 묶은 것만
로드경로 문자열번들을 열고 이름으로주소로 비동기
원격 배포불가직접 구현기본 지원
의존성·해제직접직접참조 카운트

Resources를 지양하라는 이유는 둘이다. 폴더 안 에셋은 참조하지 않아도 전부 빌드에 들어가 용량을 먹고, 시작할 때 전체 목록을 인덱싱하느라 구동이 늦어진다. 문서는 1만 개면 저사양 모바일에서 수 초가 걸린다고 적고 있다.

AssetBundle은 에셋을 묶은 아카이브 파일이고, Addressables는 그 위에 주소 체계와 참조 카운트 관리를 얹은 상위 시스템이다. 번들을 직접 다루면 만나는 문제가 중복이다. 어느 번들에도 지정하지 않은 의존 에셋은 그것을 참조하는 모든 번들에 복사본으로 들어간다. 공유 텍스처가 번들 열 개에 들어가면 용량도 메모리도 열 배다. 해법은 공통 텍스처·머티리얼·셰이더를 별도 번들로 떼어 지정하는 것이고, Addressables는 Analyze 창의 중복 의존성 검사로 찾아 준다. 같은 이유로 로컬 프리팹이 원격 번들의 머티리얼을 참조하면 원격을 받기 전에는 로드가 실패한다.

해제도 직관과 다르다. 텍스처나 메시의 실제 데이터는 C# 힙이 아니라 네이티브 메모리에 있어서 C# 참조가 사라지고 GC가 돌아도 풀리지 않는다. Resources.UnloadUnusedAssets가 돌아야 아무도 참조하지 않는 에셋이 내려가고, Single 모드 씬 로드 때 이 호출이 일어난다. 전체를 훑는 비싼 작업이라 로딩 화면에서 부른다. Addressables는 Release만큼 참조 카운트가 줄고, 번들 안 에셋이 모두 해제돼야 번들이 내려간다.

로딩 화면에서 알아 둘 숫자는 0.9다. LoadSceneAsync의 progress는 데이터 로드가 끝나면 0.9까지만 오르고 나머지는 씬 활성화 몫이라, allowSceneActivation을 false로 두면 0.9에서 대기하다 true로 바꾸는 순간 활성화된다.

AsyncOperation op = SceneManager.LoadSceneAsync(name);
op.allowSceneActivation = false;        // 0.9에서 멈춰 기다린다

while (op.progress < 0.9f)
{
    bar.value = op.progress / 0.9f;     // 0~1로 정규화해 표시
    yield return null;
}

op.allowSceneActivation = true;         // 연출이 끝나면 활성화

면접에서 이렇게 답한다

  • 셋의 차이는 — Resources는 폴더 전부가 빌드에 박히고 인덱싱 비용이 든다. AssetBundle은 묶은 것만 넣고 원격 배포도 되지만 의존성과 해제를 직접 관리해야 한다. Addressables는 그 위에서 주소와 참조 카운트를 대신 관리한다.
  • 에셋이 번들에 중복되는 것을 어떻게 막나 — 번들에 지정되지 않은 의존 에셋은 참조하는 번들마다 복사되므로 공유 에셋을 공통 번들로 떼어 지정한다. Analyze로 찾아낼 수 있다.
  • 참조를 끊으면 메모리가 바로 돌아오나 — 아니다. 네이티브 메모리라 GC로 풀리지 않고 Resources.UnloadUnusedAssets가 돌아야 내려간다. Addressables는 Release로 참조 카운트를 줄인다.
  • CDN 비용을 줄이려면 — 클라이언트가 줄일 수 있는 건 전송량이다. 번들을 갱신 단위로 쪼개 바뀐 것만 받게 하고, 텍스처 압축과 해상도를 정리하고, 로컬 캐시와 해시 검사로 같은 파일을 두 번 받지 않게 한다.
  • 로비 진입이 15초라면 — 먼저 구간을 나눠 잰다. 다운로드, 에셋 로드, 초기화 중 어디가 긴지에 따라 손댈 곳이 다르다. 첫 화면에 필요 없는 로드를 미루고, 순차로 하던 것을 겹치고, 초기화는 프레임에 나눈다.

흔한 오해

  • Resources는 동기라 느리고 Addressables는 비동기라 빠르다 — Resources에도 LoadAsync가 있다. 차이는 빌드 포함 방식과 의존성·해제 관리다.
  • Addressables면 메모리 관리가 알아서 된다 — 참조 카운트를 대신 셀 뿐이다. Release를 부르지 않으면 번들이 그대로 남는다.
  • 번들 하나로 크게 묶는 게 항상 낫다 — 요청 수는 줄지만 일부만 바뀌어도 전체를 다시 받고 필요 없는 에셋까지 메모리에 올라온다. 갱신 빈도와 함께 쓰이는 단위로 묶는다.
  • Destroy하면 그 텍스처도 함께 내려간다 — 씬의 인스턴스만 사라지고 에셋은 언로드 전까지 남는다.
