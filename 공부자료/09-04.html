네트워크

멀티플레이 구조

판정 권한을 어디 두느냐가 구조다. 비용·공정성·지연이 거기 딸려 온다

같은 순간을 두 사람이 보는데 한쪽은 맞혔다고, 한쪽은 피했다고 알고 있다. 이러면 게임이 성립하지 않는다.

무엇이 진짜인지 정하는 자리를 하나 만들어 두는 이유다. 그 자리를 어디에 두느냐가 곧 멀티플레이 구조다.

판정하는 쪽이 어디냐로 구조가 갈린다

권한은 판정하는 주체를 가리킨다. 맞았는지, 아이템을 먹었는지, 지금 어디 서 있는지를 정하는 쪽이다. 이 자리를 옮기면 서버 비용과 공정성, 지연이 한꺼번에 따라 움직인다.

방식판정 주체서버 비용치트 내성약점
데디케이티드 서버전용 서버상시 발생강함운영과 지역별 배치 비용
리슨 서버(호스트)플레이어 한 명의 기기없음약함호스트가 유리하고 이전이 필요
P2P각 클라이언트없음약함인원이 늘면 연결 수가 급증
릴레이여전히 호스트·클라이언트중계 비용만그대로중계를 거쳐 지연이 는다

릴레이는 길만 뚫고 판정은 하지 않는다

플레이어 대부분은 공유기 뒤 사설 IP를 쓴다. 밖에서 바로 연결할 수 없으니 홀 펀칭으로 구멍을 뚫거나 중계 서버가 패킷을 옮겨 준다. Unity의 Relay와 Lobby 서비스가 그 역할이다.

여기서 릴레이는 전달만 하고 판정은 하지 않는다. 릴레이를 붙여도 호스트 방식의 치트 취약점은 그대로 남는다는 뜻이다. 검증은 권한을 가진 쪽에서만 일어난다.

전부 보내면 대역폭이 먼저 터진다

서버 권한 구조에서 클라이언트는 입력을 보내고 서버는 상태를 돌려준다. 모든 오브젝트의 모든 값을 매 틱 보내면 트래픽은 인원 수와 오브젝트 수의 곱으로 는다. 스무 명이 각자 오브젝트 스무 개를 본다면 한 틱에 사백 번이다.

그럼 무엇을 덜어 내나. 눈에 안 보이는 것부터다.

먼 오브젝트는 주기를 늘리거나 아예 빼는 것이 관심 영역이다. 여기에 바뀐 값만 보내는 델타 전송을 겹쳐 쓴다. 빈 구간은 받는 쪽에서 보간과 예측으로 메운다.

거리에 따라 전송 주기를 벌리는 관심 영역의 최소 형태다:

public static float SendInterval(float distanceToViewer)
{
    // 눈앞에 있는 것만 촘촘히 보낸다
    if (distanceToViewer < 20f) return 1f / 20f;   // 초당 20회
    if (distanceToViewer < 60f) return 1f / 5f;    // 초당 5회
    return NoSend;                                 // 그 밖은 보내지 않는다
}

서버도 C#이면 규칙 코드를 그대로 나눠 쓴다

패킷 정의와 수치 계산식, 데이터 모델을 클라이언트와 같은 코드로 쓸 수 있다. 규칙이 어긋날 일이 줄고 시뮬레이션 결과도 맞추기 쉽다. 서버 로직은 보통 Unity 엔진 없이 .NET 콘솔 프로그램으로 돌린다.

공짜는 아니다. C#에도 가비지 컬렉션(GC)이 있어 서버에서도 할당을 줄여야 한다. 언어가 무엇이든 전제 하나는 바뀌지 않는다. 클라이언트가 보낸 값은 서버가 반드시 검증한다.

면접에서 이렇게 답한다

  • 데디케이티드·호스트·P2P·릴레이의 차이 — 판정을 전용 서버가 하면 데디케이티드, 플레이어 기기가 겸하면 리슨 서버다. 릴레이는 판정 구조가 아니라 NAT를 우회하는 전달 경로라고 못을 박는다.
  • 호스트 방식의 장단점 — 서버 운영비가 없고 호스트는 지연이 거의 없다. 대신 모두가 호스트의 회선에 묶이고, 판정 권한이 플레이어 기기에 있어 조작에 약하다.
  • 권한과 리플리케이션 빈도 — 판정 대상 상태는 서버가 쥐고 클라이언트는 입력만 보낸다. 거리와 중요도로 주기를 나누고 바뀐 값만 델타로 보낸다고 이어 말한다.
  • 서버를 C#으로 두면 무엇이 좋은가 — 패킷과 규칙 코드를 클라이언트와 공유해 불일치를 줄인다. 검증 책임이 서버에 있다는 전제는 언어와 무관하다.

이런 오해를 한다

  • “릴레이를 쓰면 치트가 막힌다” — 릴레이가 하는 일은 패킷을 옮기는 것까지다. 판정은 여전히 호스트 기기가 한다.
  • “P2P는 서버를 안 거치니 항상 빠르다” — NAT 때문에 연결 자체가 안 되는 경우가 많다. 인원이 늘면 상향 대역폭이 먼저 터진다.
  • “호스트 방식은 서버가 없는 구조다” — 플레이어 기기가 서버를 겸할 뿐이다. 권한이 믿을 수 없는 기기에 있다는 점이 다르다.
  • “전송 빈도를 올리면 정확해진다” — 대역폭과 서버 부하가 먼저 한계에 닿는다. 정확도는 권한 구조와 보정에서 나온다.

3줄 정리

  • 구조 선택은 판정 권한을 어디 두느냐다
  • 릴레이는 NAT를 우회하는 통로일 뿐이다
  • 전송은 거리로 줄이고 빈틈은 보간으로 메운다
