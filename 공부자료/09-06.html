네트워크

클라이언트-서버 신뢰성

응답이 없다고 처리가 안 된 건 아니다. 멱등 키로 중복 지급을 막는다

구매 버튼을 눌렀는데 응답이 오지 않는다. 로딩 아이콘만 돌다 멈췄다.

여기서 그냥 다시 보내면 결제가 두 번 될 수 있다. 신뢰성 설계는 이 한 장면에서 시작한다.

타임아웃은 처리되지 않았다는 뜻이 아니다

요청이 서버에 닿기 전에 끊겼을 수도 있다. 처리는 멀쩡히 끝났는데 응답만 돌아오는 길에 사라졌을 수도 있다.

둘 중 어느 쪽인가. 클라이언트에서 보면 두 장면은 똑같이 생겼다.

"타임아웃이니 다시 보낸다"는 곧 "구매가 두 번 처리될 수 있다"와 같은 말이다. 막아야 할 것은 재시도가 아니라 중복 반영이다. 재시도 자체는 오히려 있어야 한다.

같은 키로 다시 보내면 한 번만 반영된다

멱등성은 같은 요청을 몇 번 보내도 결과가 한 번 보낸 것과 같아지는 성질이다. 요청마다 고유 키를 붙이고, 서버가 그 키로 처리 기록을 남겨 만든다. 같은 키가 또 오면 저장해 둔 결과를 그대로 돌려준다.

조건이 둘이다. 우선 재시도할 때 키가 같아야 한다. 보낼 때마다 새로 만들면 서버 눈에는 그냥 다른 구매다.

나머지 하나는 트랜잭션이다. 재화 반영과 키 기록을 한 묶음으로 처리해야 한다. 따로 두면 재화는 들어갔는데 키는 아직 없는 순간이 생기고, 하필 그 틈에 재시도가 닿으면 두 번 지급된다.

인앱 결제라면 스토어 영수증이 그대로 키가 된다.

응답을 기다리다 앱이 꺼지는 경우도 같은 장치로 푼다. 키를 보내기 전에 저장해 두고, 다시 켰을 때 미완료 키가 남아 있으면 같은 키로 다시 보낸다. 로그인 직후 재화와 인벤토리를 서버에서 통째로 받아 맞추면 더 확실하다.

키를 저장하고 같은 키로 재시도하는 최소 형태다:

// 키는 보내기 전에 저장한다. 재시작한 뒤에도 같은 키여야 같은 요청이다
string id = PlayerPrefs.GetString("pendingBuy", "");

for (int n = 0; n < 5; n++)
{
    var req = UnityWebRequest.Post(url, body, "application/json");
    req.SetRequestHeader("Idempotency-Key", id);   // 서버가 중복을 가르는 기준
    yield return req.SendWebRequest();
    if (req.result == UnityWebRequest.Result.Success) break;
    if (req.responseCode >= 400 && req.responseCode < 500) break;  // 4xx는 그만
    yield return new WaitForSeconds(Mathf.Pow(2f, n) + Random.value);  // 백오프
}

즉시 재시도는 복구 중인 서버를 다시 쓰러뜨린다

모든 기기가 같은 간격으로 즉시 다시 보내면 요청이 한 지점에 몰린다. 겨우 일어서던 서버가 그 파도에 다시 넘어간다. 서버 쪽에서 보면 공격 트래픽과 모양이 같아 아예 차단될 수도 있다.

실패할 때마다 간격을 배로 늘리고, 기기마다 다른 무작위 지연을 얹는다. 지수 백오프와 지터다. 타임아웃과 5xx만 다시 보내고, 4xx는 몇 번을 보내도 답이 같으니 멈춘다.

서버가 먼저 거는 말은 큐로 받는다

서버가 먼저 말하려면 연결이 살아 있어야 한다. 소켓이나 WebSocket을 열어 두고 수신 루프에서 읽는다. HTTP만 쓴다면 주기적으로 물어보는 폴링으로 흉내 낸다.

수신은 별도 스레드에서 돈다. 받은 데이터는 큐에 넣고 메인 스레드 Update에서 꺼낸다. 다른 스레드에서 Unity API를 부르면 그 자리에서 예외가 난다.

면접에서 이렇게 답한다

  • 응답 전에 끊긴 요청을 한 번만 처리하려면 — 요청마다 멱등 키를 붙이고 서버가 키와 결과를 함께 기록한다고 답한다. 같은 키가 오면 처리 없이 이전 결과를 돌려주고, 반영과 기록은 한 트랜잭션으로 묶는다는 조건까지 말한다.
  • 응답을 기다리다 앱이 죽었다면 — 재실행 때 남은 미완료 키로 같은 요청을 다시 보내거나 결과를 조회한다. 로그인 직후 서버 상태를 받아 화면을 맞춘다.
  • 즉시 재시도가 왜 위험한가 — 복구 시점에 요청이 몰려 서버를 다시 쓰러뜨린다. 공격으로 오인돼 차단될 수도 있으니 지수 백오프와 지터, 최대 횟수를 함께 둔다.
  • 재화 계산을 클라이언트에 두면 — 왕복이 없어 즉시 반응하지만 메모리와 패킷 조작에 뚫린다. 연출만 먼저 보여 주고 값은 서버 응답으로 덮어쓴다고 정리한다.

이런 오해를 한다

  • “타임아웃이 났으니 서버는 처리하지 않았다” — 처리는 끝나고 응답만 사라진 경우와 구분되지 않는다. 막을 대상은 중복 반영이다.
  • “클라이언트에서 중복 전송만 막으면 된다” — 앱 재설치와 기기 변경, 다중 접속에서 무너진다. 중복을 막을 책임은 기록을 가진 서버에 있다.
  • “TCP를 쓰니 중복은 없다” — TCP가 책임지는 범위는 한 연결 안의 순서와 유실까지다. 끊긴 뒤 다시 보낸 요청은 서버에 새 요청으로 보인다.

3줄 정리

  • 응답 없음은 처리 여부를 알려 주지 않는다
  • 같은 멱등 키 + 한 트랜잭션이 중복을 막는다
  • 재시도는 지수 백오프와 지터로 늦춘다
