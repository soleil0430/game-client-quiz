동기화

count++는 세 단계라 중간에 끊긴다. lock·Interlocked·CAS 중 상황에 맞는 것을 고른다

두 스레드가 카운터를 100만 번씩 올렸는데 200만이 안 나온다. 재현도 들쭉날쭉해서 로그로 잡기 어렵다. 소스 한 줄이 기계 명령 하나가 아니라는 데서 시작하는 문제다.

count++는 한 줄이지만 세 단계다

count++는 읽고, 1을 더하고, 다시 쓰는 세 단계다. 두 스레드가 같은 값을 읽어 각자 더해 쓰면 증가 한 번이 사라진다. 실행 순서에 따라 결과가 달라지는 이 버그가 경쟁 상태다.

그래서 이 세 단계를 쪼개지지 않는 하나로 묶어야 한다. 임계 구역을 락으로 감싸거나 하드웨어의 원자적 명령 하나로 처리한다. 임계 구역 해법이 갖춰야 할 조건은 셋이다.

  • 상호 배제 — 한 번에 하나만 들어간다
  • 진행 — 비어 있으면 대기자 중에서 진입자가 정해진다
  • 한정 대기 — 무한정 밀리지 않는다. FIFO로 고정하라는 뜻은 아니다

lock·Interlocked·세마포어 중 무엇을 고르나

도구보장쓰는 자리
lock(Monitor)하나만 진입, 소유권 있음여러 줄짜리 갱신
Interlocked(CAS)한 변수의 읽기·갱신이 원자적카운터·플래그
세마포어동시 진입 수를 카운트로 제한동시 다운로드 5개 제한

같은 카운터를 두 가지 방식으로 올리는 모습:

private int _count;                   // 여러 스레드가 같이 늘리는 카운터
private readonly object _lock = new object();   // 이 락 전용 객체를 따로 둔다

public void AddByLock()
{
    lock (_lock) { _count++; }        // 세 단계를 한 덩어리로 묶는다
}

public void AddByInterlocked()
{
    Interlocked.Increment(ref _count);  // 경합이 없으면 커널까지 안 간다
}

CAS는 "이 값이 아직 내가 읽은 값이면 새 값으로 바꾸라"를 하드웨어가 한 번에 처리한다. 실패하면 커널로 가지 않고 다시 읽어 재시도한다. 경합이 심하면 재시도가 늘어 손해이고, 값이 A에서 B로 갔다 다시 A가 되면 못 알아채는 ABA 문제도 있다.

데드락은 네 조건이 다 모여야 생긴다

락이 여러 개면 데드락이 따라온다. 상호 배제, 점유 대기, 비선점, 순환 대기 네 조건이 모두 성립할 때만 생긴다. 그래서 하나만 깨면 막힌다.

실무에서 깨는 것은 대개 순환 대기다. 락을 늘 같은 순서로 잡으면 고리가 생기지 않는다. Monitor.TryEnter로 제한 시간을 두는 방법도 있다.

코어를 늘렸는데 안 빨라지면 거짓 공유를 본다

CPU는 메모리를 64바이트 캐시 라인 단위로 다룬다. 서로 다른 카운터라도 한 배열에 붙어 있으면, 한쪽이 쓸 때 다른 쪽 캐시 라인이 무효화된다.

논리적으로는 안 겹치는데 하드웨어에서 겹치는 이 현상이 거짓 공유다. 스레드별 지역 변수에 모았다가 마지막에 합치면 사라진다.

면접에서 이렇게 답한다

  • 경쟁 상태란 — 실행 순서에 따라 결과가 달라지는 버그다. count++가 세 단계라 중간에 선점되면 증가가 사라진다. 락으로 감싸거나 Interlocked.Increment로 바꿔 해결한다.
  • 뮤텍스와 세마포어의 차이 — 뮤텍스는 소유권이 있어 잠근 스레드가 풀고 하나만 들어간다. 세마포어는 카운트만큼 동시에 들어가고 소유 개념이 없다.
  • 데드락 조건과 예방 — 네 조건이 모두 성립해야 생기므로 하나만 깨면 된다. 실무에서는 락 순서를 정해 순환 대기를 없앤다. 회피는 은행원 알고리즘처럼 할당 전에 따지는 쪽이다.
  • 락 없이 스레드 안전을 만들려면 — CAS로 읽고 계산한 뒤 값이 그대로일 때만 바꾸고 실패하면 재시도한다. 경합이 심하면 락보다 비쌀 수 있다.
  • Lock-Free와 Wait-Free — Lock-Free는 최소 한 스레드는 진행한다는 보장이라 특정 스레드가 굶을 수 있다. Wait-Free는 모든 스레드가 유한 단계에 끝난다는 보장이다.

이런 오해를 한다

  • int 증가는 원자적이다 — 읽기·더하기·쓰기 세 단계라 중간에 끊긴다. 값의 크기나 오버플로 문제가 아니다.
  • 기아도 데드락 조건이다 — 기아는 계속 밀려 실행되지 못하는 다른 문제다. 데드락 조건 넷에 들어가지 않는다.
  • 이진 세마포어는 뮤텍스와 같다 — 동시 진입 수만 같고 소유권 규칙이 다르다.
  • 스핀락이 항상 빠르다 — 임계 구역이 아주 짧고 코어가 여럿일 때만 이득이다. 코어가 하나거나 대기가 길면 CPU만 태운다.
  • lock(this)면 충분하다 — 외부가 같은 객체를 잠글 수 있다. 전용 private readonly object를 따로 둔다.

3줄 정리

  • 한 줄짜리 증가도 세 단계라 중간에 끊겨 값이 사라진다
  • 여러 줄 갱신은 lock, 한 변수는 Interlocked가 맞다
  • 데드락은 네 조건이 다 모일 때만 생기니 락 순서를 고정한다
