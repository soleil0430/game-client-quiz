동기화

공유 자원이 왜 깨지는지 알고 lock·Interlocked·CAS 중 상황에 맞는 것을 고른다

핵심 개념

동기화는 여러 스레드가 같은 데이터를 건드릴 때 중간 상태를 보지 못하게 막는 일이다. 문제의 뿌리는 소스 한 줄이 기계 명령 한 개가 아니라는 점이다. count++는 읽고, 1을 더하고, 다시 쓰는 세 단계다. 두 스레드가 같은 값을 읽어 각자 더해 쓰면 증가 한 번이 사라진다. 100만 번씩 돌렸는데 200만보다 작게 나오는 경쟁 상태가 이것이다.

그래서 이 세 단계를 쪼개지지 않는 하나로 묶어야 한다. 임계 구역을 락으로 감싸거나 하드웨어의 원자적 명령 하나로 처리한다. 임계 구역 해법의 조건은 상호 배제, 진행(비어 있으면 대기자 중에서 진입자가 정해진다), 한정 대기(무한정 밀리지 않는다) 셋이며, 한정 대기는 FIFO 고정이 아니라 굶주림이 없어야 한다는 뜻이다.

도구보장쓰는 자리
lock(Monitor)하나만 진입, 소유권 있음여러 줄짜리 갱신
Interlocked(CAS)한 변수의 읽기·갱신이 원자적카운터·플래그
세마포어동시 진입 수를 카운트로 제한동시 다운로드 5개 제한
private int _count;
private readonly object _lock = new object();

public void AddByLock()
{
    lock (_lock) { _count++; }   // Monitor.Enter/Exit + try-finally로 펼쳐진다
}

public void AddByInterlocked()
{
    Interlocked.Increment(ref _count);  // 경합이 없으면 커널로 가지 않는다
}

public void DoubleIt()   // 계산이 낀 갱신을 락 없이 처리하는 CAS 재시도
{
    int old, want;
    do
    {
        old = Volatile.Read(ref _count);
        want = old * 2;
    }
    while (Interlocked.CompareExchange(ref _count, want, old) != old);
}

CAS는 이 값이 아직 내가 읽은 값이면 새 값으로 바꾸라는 동작을 하드웨어가 한 번에 처리한다. 실패하면 커널로 가지 않고 다시 읽어 재시도하지만, 경합이 심하면 재시도가 늘어 손해다. 값이 A에서 B로 갔다 다시 A가 되면 못 알아채는 ABA 문제도 있다.

락이 여러 개면 데드락이 따라온다. 상호 배제, 점유 대기, 비선점, 순환 대기 네 조건이 모두 성립할 때만 생기므로 하나만 깨면 막힌다. 실무에서는 락을 늘 같은 순서로 잡아 순환 대기를 없애거나 Monitor.TryEnter로 제한 시간을 둔다.

코어를 늘려도 기대만큼 빨라지지 않으면 거짓 공유를 의심한다. CPU는 메모리를 64바이트 캐시 라인 단위로 다뤄서, 다른 카운터라도 한 배열에 붙어 있으면 한쪽이 쓸 때 다른 쪽 캐시 라인이 무효화된다. 스레드별 지역 변수에 모았다 합치면 사라진다.

면접에서 이렇게 답한다

  • 경쟁 상태란 — 실행 순서에 따라 결과가 달라지는 버그다. count++가 세 단계라 중간에 선점되면 증가가 사라진다. 락으로 감싸거나 Interlocked.Increment로 바꿔 해결한다.
  • 뮤텍스와 세마포어의 차이 — 뮤텍스는 소유권이 있어 잠근 스레드가 풀고 하나만 들어간다. 세마포어는 카운트만큼 동시에 들어가고 소유 개념이 없다.
  • 데드락 조건과 예방 — 네 조건이 모두 성립해야 생기므로 하나만 깨면 된다. 실무에서는 락 순서를 정해 순환 대기를 없앤다. 회피는 은행원 알고리즘처럼 할당 전에 따지는 쪽이다.
  • 락 없이 스레드 안전을 만들려면 — CAS로 읽고 계산한 뒤 값이 그대로일 때만 바꾸고 실패하면 재시도한다. 경합이 심하면 락보다 비쌀 수 있다.
  • 스레드 수 기준 — CPU를 계속 쓰는 작업은 코어 수 안팎, 입출력 작업은 더 많이 둔다. 스레드 풀은 미리 만든 스레드를 재사용해 생성 비용을 아낀다.
  • Lock-Free와 Wait-Free — Lock-Free는 최소 한 스레드는 진행한다는 보장이라 특정 스레드가 굶을 수 있고, Wait-Free는 모든 스레드가 유한 단계에 끝난다는 보장이다.

흔한 오해

  • int 증가는 원자적이다 — 읽기·더하기·쓰기 세 단계라 중간에 끊긴다. 값의 크기나 오버플로 문제가 아니다.
  • 기아도 데드락 조건이다 — 기아는 계속 밀려 실행되지 못하는 다른 문제다.
  • 이진 세마포어는 뮤텍스와 같다 — 동시 진입 수만 같고 소유권 규칙이 다르다.
  • 스핀락이 항상 빠르다 — 임계 구역이 아주 짧고 코어가 여럿일 때만 이득이고, 코어가 하나거나 대기가 길면 CPU만 태운다.
  • lock(this)면 충분하다 — 외부가 같은 객체를 잠글 수 있어 전용 private readonly object를 둔다.
