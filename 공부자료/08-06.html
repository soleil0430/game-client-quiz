운영체제·동시성

동기화

count++는 세 단계라 중간에 끊긴다. lock·Interlocked·CAS 중 상황에 맞는 것을 고른다

두 스레드가 카운터를 100만 번씩 올렸는데 200만이 안 나온다. 재현도 들쭉날쭉해서 로그로 잡기 어렵다.

소스 한 줄이 기계 명령 하나가 아니라는 데서 시작하는 문제다.

count++는 한 줄이지만 세 단계다

count++는 메모리에서 값을 읽고, 1을 더하고, 다시 쓰는 비원자적 연산이다. 읽기·더하기·쓰기가 원자적이지 않아, 두 스레드가 같은 값을 읽고 각자 더해 쓰면 경쟁 상태로 증가분이 사라져서 증가 한 번이 조용히 사라진다. 실행 순서에 따라 결과가 달라지는 이 버그가 경쟁 상태다.

lock으로 임계 구역을 보호하거나 Interlocked.Increment 같은 원자적 연산을 쓰면 해결된다. 200만은 int 범위 안이라 오버플로와는 관계없다.

세 단계를 쪼개지지 않는 하나로 묶는 것이 해법이다. 임계 구역을 락으로 감싸거나 하드웨어의 원자적 명령 하나로 처리한다.

임계 구역 해법이 갖춰야 할 조건은 셋이다. 상호 배제는 한 번에 한 스레드만 임계 구역에 들어가는 것, 진행은 아무도 들어가 있지 않으면 들어가려는 스레드 중에서 진입자가 정해지는 것, 한정 대기는 기다리는 스레드가 무한정 밀리지 않는 것이다.

진행 조건은 비어 있으면 대기자가 들어가게 한다는 뜻이다. 한정 대기는 순서를 FIFO로 고정하라는 뜻이 아니라 굶주림이 없어야 한다는 뜻이고, 상호 배제만으로는 기아도 데드락도 막지 못한다.

lock·Interlocked·세마포어 중 무엇을 고르나

도구 보장 쓰는 자리
lock(Monitor) 하나만 진입, 소유권 있음 여러 줄짜리 갱신
Interlocked(CAS) 한 변수의 읽기·갱신이 원자적 카운터·플래그
세마포어 동시 진입 수를 카운트로 제한 동시 다운로드 5개 제한

뮤텍스는 소유 개념이 있는 잠금이라 잠근 스레드가 해제하며, 한 번에 한 스레드만 들어간다. 세마포어는 정수 카운트로 동시에 들어갈 수 있는 수를 제한하며(연결 5개까지 같은 식이다), 소유 개념이 없어 다른 스레드가 해제할 수도 있다.

카운트가 1인 이진 세마포어는 뮤텍스와 비슷하지만 소유권 규칙이 다르다. 둘 다 잘못 쓰면 데드락이 생길 수 있다.

같은 카운터를 두 가지 방식으로 올려 보자: 

private int _count;                   // 여러 스레드가 같이 늘리는 카운터
private readonly object _lock = new object();   // 이 락 전용 객체를 따로 둔다

public void AddByLock()
{
    lock (_lock) { _count++; }        // 세 단계를 한 덩어리로 묶는다
}

public void AddByInterlocked()
{
    Interlocked.Increment(ref _count);  // 경합이 없으면 커널까지 안 간다
}

lock(obj)는 Monitor.Enter와 try/finally 안의 Monitor.Exit로 펼쳐지는 문법이다. 그렇게 펼쳐지며 예외가 나도 락이 풀린다.

잠금 대상은 참조 형식이어야 해서 값 형식은 컴파일 오류이고, lock 블록 안에서는 await를 쓸 수 없다. lock(this)는 외부에서 같은 객체를 잠글 수 있어 전용 private readonly object를 두는 것이 관례이며, 프로세스 간 배타는 Mutex가 맡는다.

CAS는 값이 예상과 같을 때만 바꾸는 원자적 연산이다. 이 값이 아직 내가 읽은 값이면 새 값으로 바꾸라는 동작을 하드웨어가 한 번에 처리하는 명령이며, C#에서는 Interlocked.CompareExchange가 이에 해당한다.

실패하면 커널로 가지 않고 값을 다시 읽어 재시도하므로, 경합이 심하면 재시도가 늘어 손해다. 값이 A에서 B로 갔다 다시 A가 되면 못 알아채는 ABA 문제도 있다.

스핀락은 짧은 임계 구역에서만 이득이다

스핀락은 재우지 않고 계속 돌면서 락을 노리므로, 잠깐만 기다리면 되는 짧은 임계 구역에서는 문맥 전환 비용을 아껴 이득이다. 임계 구역이 아주 짧고 코어가 여러 개일 때가 그 자리다.

반대로 대기가 길거나 코어가 하나면 락을 쥔 쪽이 실행되지 못한 채 CPU만 태운다. 실무에서는 잠깐 스핀하다 안 되면 잠드는 하이브리드 락을 많이 쓴다.

락을 아예 안 쓰는 길도 있다. Lock-Free는 전체로 보면 적어도 한 스레드는 진행한다는 보장이라, 특정 스레드가 재시도에 계속 실패해 굶을 수 있다.

Wait-Free는 스레드마다 정해진 단계 안에 반드시 끝남을 보장한다. 더 강한 보장이며 그만큼 구현이 어렵다. 둘 다 락을 쓰지 않으니 락을 쥔 스레드가 멈춰 생기는 데드락은 없다.

데드락은 네 조건이 다 모여야 생긴다

락이 여러 개면 데드락이 따라온다. 상호 배제, 점유와 대기, 비선점, 순환 대기 네 조건이 모두 성립할 때 생기므로, 하나만 깨도 막을 수 있다.

대응은 네 갈래다. 예방은 이 네 조건 중 하나만 깨도 되며, 실무에서는 락을 항상 같은 순서로 잡아 순환 대기를 없애는 방법을 많이 쓴다. 그것이 대표적이다.

회피는 실행 중 요청을 받아 줘도 안전한지 따져 허락하는 방식으로, 은행원 알고리즘이 여기 속한다. 은행원 알고리즘은 할당 전에 안전 상태인지 따진다.

탐지는 데드락이 생긴 뒤에 찾아내는 것이고, 회복은 프로세스를 죽이거나 자원을 빼앗아 푸는 것이다. Monitor.TryEnter로 제한 시간을 두는 방법도 있다.

기아(starvation)는 다른 문제다. 우선순위가 낮은 작업이 계속 밀려 실행되지 못한다. 서로 물고 늘어져 멈추는 것이 아니라 순서에서 계속 뒤로 밀리는 별개의 문제다.

스레드는 몇 개가 적당한가

CPU를 계속 쓰는 작업은 코어 수를 넘겨 봐야 문맥 전환만 늘어나므로, CPU 위주 작업은 코어 수 근처로 잡는 것이 적당하다. 코어 수 안팎이 적당하고, 입출력처럼 대기가 긴 작업은 그보다 많이 둬야 CPU가 놀지 않는다.

스레드 풀은 미리 만들어 둔 스레드를 재사용해 생성·소멸 비용과 스레드 폭증을 막는다. 풀 스레드에서 오래 블로킹하면 다른 작업이 밀리므로, 긴 작업은 따로 떼어 둔다.

코어를 늘렸는데 안 빨라지면 거짓 공유를 본다

CPU 캐시는 흔히 64바이트 단위(캐시 라인)로 데이터를 다룬다. 논리적으로 다른 변수라도 같은 캐시 라인에 있으면, 한 코어가 값을 바꿀 때 다른 코어의 해당 캐시 라인이 무효화돼 계속 다시 읽어야 한다.

같은 캐시 라인을 함께 써서 서로 캐시를 무효화하는 이 현상이 거짓 공유다. 스레드별 데이터 사이에 패딩을 넣어 떨어뜨리거나, 스레드마다 지역 변수로 계산한 뒤 마지막에 합치면 줄어든다.

면접에서 이렇게 답한다

  • 경쟁 상태란 — 실행 순서에 따라 결과가 달라지는 버그다. count++가 세 단계라 중간에 선점되면 증가가 사라진다고 예를 든다. 락으로 감싸거나 Interlocked.Increment로 바꿔 해결한다.
  • 뮤텍스와 세마포어의 차이 — 뮤텍스는 소유권이 있어 잠근 스레드가 풀고 하나만 들어간다. 세마포어는 카운트만큼 동시에 들어가고 소유 개념이 없다.
  • 데드락 조건과 예방 — 네 조건이 모두 성립해야 생기므로 하나만 깨면 된다. 실무에서는 락 순서를 정해 순환 대기를 없앤다. 회피는 은행원 알고리즘처럼 할당 전에 따지는 쪽이라고 구분해 말한다.
  • 락 없이 스레드 안전을 만들려면 — CAS로 읽고 계산한 뒤 값이 그대로일 때만 바꾸고 실패하면 재시도한다. 경합이 심하면 락보다 비쌀 수 있다는 단서를 붙인다.
  • Lock-Free와 Wait-Free — Lock-Free는 최소 한 스레드는 진행한다는 보장이라 특정 스레드가 굶을 수 있다. Wait-Free는 모든 스레드가 유한 단계에 끝난다는 보장이다.

이런 오해를 한다

  • “int 증가는 원자적이다” — 읽기·더하기·쓰기 세 단계라 중간에 끊긴다. 값의 크기나 오버플로 문제가 아니다.
  • “기아도 데드락 조건이다” — 기아는 계속 밀려 실행되지 못하는 다른 문제다. 데드락 조건 넷에 들어가지 않는다.
  • “이진 세마포어는 뮤텍스와 같다” — 동시 진입 수만 같고 소유권 규칙이 다르다.
  • “스핀락이 항상 빠르다” — 임계 구역이 아주 짧고 코어가 여럿일 때만 이득이다. 코어가 하나거나 대기가 길면 CPU만 태운다.
  • “lock(this)면 충분하다” — 외부가 같은 객체를 잠글 수 있다. 전용 private readonly object를 따로 둔다.

3줄 정리

  • 한 줄짜리 증가도 세 단계라 중간에 끊겨 값이 사라진다
  • 여러 줄 갱신은 lock, 한 변수는 Interlocked가 맞다
  • 데드락은 네 조건이 다 모일 때만 생기니 락 순서를 고정한다
