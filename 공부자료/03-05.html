최적화·메모리

캐시 친화와 데이터 지향

CPU는 캐시 라인 64바이트를 통째로 읽는다. 훑는 순서대로 붙여 둔다

원소 10만 개를 앞에서부터 끝까지 더하는 루프를 배열과 연결 리스트로 각각 짜 보자. 복잡도는 둘 다 O(n)인데 실행 시간은 몇 배로 벌어진다. 왜 갈릴까?

코드가 아니라 메모리 배치에서 갈린다.

CPU는 64바이트를 통째로 가져온다

CPU는 메인 메모리에서 값을 하나씩 집어 오지 않는다. 필요한 주소 주변을 캐시 라인 단위로 통째로 끌고 온다. 보통 64바이트다.

L1에서 읽으면 몇 사이클, 메인 메모리까지 나가면 수백 사이클이다. 캐시 미스 한 번이 연산 수백 번 값인 셈이다. 끌고 온 라인을 끝까지 쓰느냐가 실제 속도를 정한다.

둘 다 순회는 O(n)이지만, 배열은 원소가 연속된 메모리에 있어 캐시에 올라온 블록에서 다음 원소를 바로 읽는다. 하드웨어 프리페처가 그다음 블록까지 미리 당겨 오기도 한다. 연결 리스트는 노드가 흩어져 있어 다음 노드로 넘어갈 때마다 캐시 미스가 나기 쉽다.

맨 앞의 몇 배 차이는 여기서 나온다. 복잡도가 아니라 캐시 적중률이 높기 때문에 빠른 것이다. 같은 이유로 데이터 지향 설계는 자주 함께 쓰는 데이터를 연속된 배열로 모은다.

C#의 다차원 배열 arr[i, j]도 같은 이야기다. 행 우선으로 연속 배치되므로 j를 안쪽에서 증가시키면 연속된 주소를 훑어 메모리를 앞에서부터 차례로 읽고, 한 번 올라온 캐시 라인을 끝까지 쓰게 되어 미스가 줄어든다.

반대로 i를 안쪽에 두면 한 행 길이만큼 건너뛰며 접근해, 캐시 라인을 한 칸만 쓰고 버리게 된다. 루프 두 줄의 순서를 바꾼 것뿐인데 시간이 갈린다.

구조체는 큰 필드부터 선언한다

CPU가 효율적으로 읽을 수 있게 필드는 자기 크기의 배수 위치에 놓인다. 어긋나는 틈은 패딩이 메운다. byte(1) 뒤에 long(8)이 오면 7바이트 패딩이 생기고, 끝에도 전체 크기가 8의 배수가 되게 패딩이 붙어 필드 크기 합보다 큰 24바이트가 된다.

선언 순서실제 배치크기
byte a; long b; byte c;a(1) + 패딩(7) + b(8) + c(1) + 패딩(7)24바이트
long b; byte a; byte c;b(8) + a(1) + c(1) + 패딩(6)16바이트

큰 필드부터 두면 16바이트로 줄어든다. 줄 하나 옮겨 8바이트를 번 셈이다. 원소가 아주 많은 배열에서는 이 8바이트가 캐시 라인 하나에 들어가는 원소 수를 바꿔 메모리와 캐시 효율에 영향을 준다.

AoS와 SoA 중 무엇을 고르나

AoS(구조체의 배열)는 한 원소 안에 모든 필드를 붙여 둔다. SoA(배열들의 구조체)는 필드마다 배열을 따로 둔다. 답은 접근 패턴이 정한다.

파티클 데이터를 두 방식으로 잡은 코드다:

public struct ParticleAos     // AoS: 한 원소 안에 네 필드가 붙어 있다
{
    public Vector3 Position;
    public Vector3 Velocity;
    public Color32 Color;
    public float Lifetime;
}

public class ParticleSoa      // SoA: 필드마다 배열을 따로 둔다
{
    public Vector3[] Positions;
    public Vector3[] Velocities;
    // 위치만 도는 루프는 Positions 배열만 읽는다
}

SoA는 같은 필드끼리 모아 두므로, 위치만 갱신하는 식으로 일부 필드만 훑는 루프에서 캐시 라인을 낭비 없이 채우고 SIMD도 태우기 쉽다. 반대로 한 객체의 모든 필드를 함께 쓰는 처리에는 AoS가 낫다. 무엇이 유리한지는 접근 패턴이 정한다.

데이터 지향 설계(DOD)는 이 판단을 앞쪽에 두는 사고방식이다. 캐시가 좋아하는 형태로 데이터 배치를 먼저 정하고 로직을 거기에 맞춘다. 객체부터 나누는 습관과 반대편에 있다.

DOTS의 ECS는 같은 컴포넌트 조합을 가진 엔티티를 청크 단위 연속된 메모리에 모아 이를 구현하고, Job System이 여러 워커 스레드로 나눠 돌리며, Burst가 그 코드를 SIMD를 활용한 네이티브 코드로 컴파일한다. ECS 청크가 SoA에 가까운 배치이고, 나머지 둘은 그 위에서 도는 실행 장치다.

할당자는 해제 순서로 고른다

풀 할당자는 같은 크기 블록을 재사용한다. 아무 순서로 풀어도 되면서 단편화도 막는다.

스택(선형) 할당자는 포인터를 앞으로 밀며 할당하고, 해제는 저장해 둔 표시까지 포인터를 되돌려 한꺼번에 한다. 그래서 할당과 해제가 매우 싸지만 LIFO 순서로만 풀 수 있다. 프레임 단위 임시 메모리처럼 수명이 같은 데이터에 쓴다.

임의 순서로 해제해야 하면 같은 크기 블록을 재사용하는 풀 할당자가 맞다. 슬랩 할당자는 같은 타입용 영역을 미리 잡아 두고 초기화된 조각을 꺼내 준다.

면접에서 이렇게 답한다

  • 캐시를 잘 쓰려면 — 함께 쓰는 데이터를 연속으로 두고 접근 순서와 메모리 순서를 맞춘다고 말한다. 배열 순회를 기본으로 하고, 루프가 읽지 않는 필드는 다른 배열로 뺀다.
  • 연결 리스트가 배열보다 느린 이유 — 노드가 흩어져 있어 다음 노드로 갈 때마다 캐시 미스가 난다. 복잡도는 같아도 메모리 접근 상수가 다르다고 정리한다.
  • AoS와 SoA를 어떻게 고르나 — 한 객체의 필드를 다 쓰면 AoS, 일부 필드만 대량으로 훑으면 SoA가 유리하다. 접근 패턴이 정한다고 답한다.
  • DOD와 DOTS의 관계 — DOD는 데이터 배치를 먼저 정하는 사고방식이다. DOTS의 ECS·Job·Burst는 그것을 엔진 차원에서 구현한 도구라고 구분해 말한다.

이런 오해를 한다

  • “복잡도가 같으면 성능도 같다” — O 표기는 상수를 버린다. 맨 앞의 배열과 연결 리스트가 그 상수 차이다.
  • “struct 크기는 필드 크기의 합이다” — 정렬 때문에 패딩이 들어간다. 큰 필드부터 선언하면 줄어든다.
  • “SoA가 항상 빠르다” — 한 원소의 모든 필드를 함께 읽는 처리에서는 여러 배열을 오가며 미스가 늘어난다.
  • “DOTS를 써야 DOD를 하는 것이다” — 일반 MonoBehaviour에서도 배열 순회와 필드 분리로 같은 효과를 낸다.
  • “스택 할당자는 아무 순서로나 해제한다” — 되감기 방식이라 LIFO만 가능하다. 임의 순서가 필요하면 풀 할당자를 쓴다.

3줄 정리

  • CPU는 캐시 라인 64바이트를 통째로 읽어 온다
  • 훑는 순서대로 붙여 두면 같은 코드가 빨라진다
  • 일부 필드만 도는 루프면 SoA, 다 쓰면 AoS
