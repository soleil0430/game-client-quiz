캐시 친화와 데이터 지향

CPU는 캐시 라인 64바이트를 통째로 읽는다. 훑는 순서대로 붙여 둔다

같은 O(n) 순회인데 배열이 연결 리스트보다 몇 배 빠르다. 차이는 코드가 아니라 메모리 배치에서 온다. CPU가 값을 어떻게 읽어 오는지 알면 이유가 보인다.

CPU는 64바이트를 통째로 가져온다

CPU는 메인 메모리에서 값을 하나씩 읽지 않는다. 주소 주변을 캐시 라인 단위로 통째로 가져온다. 보통 64바이트다.

L1 접근은 몇 사이클이고 메인 메모리는 수백 사이클이다. 그래서 올라온 라인을 끝까지 쓰느냐가 실제 속도를 가른다. 캐시 미스 한 번이 연산 수백 번 값이다.

배열은 원소가 연속으로 놓인다. 한 라인 안에서 다음 원소를 바로 읽고, 하드웨어 프리페처가 다음 블록도 미리 당겨 온다. 연결 리스트는 노드가 흩어져 있어 다음 노드마다 미스가 난다.

C#의 다차원 배열 arr[i, j]도 같은 이야기다. 마지막 인덱스가 연속이므로 j를 안쪽 루프에 둔다. 그래야 메모리를 앞에서부터 차례로 읽는다.

구조체는 큰 필드부터 선언한다

필드는 자기 크기의 배수 위치에 놓이고 그 사이를 패딩이 채운다. 선언 순서만 바꿔도 크기가 달라진다.

선언 순서실제 배치크기
byte a; long b; byte c;a(1) + 패딩(7) + b(8) + c(1) + 패딩(7)24바이트
long b; byte a; byte c;b(8) + a(1) + c(1) + 패딩(6)16바이트

원소가 수만 개면 이 8바이트가 캐시에 들어가는 원소 수를 바꾼다. 같은 루프가 불러오는 라인 수가 줄어든다.

일부 필드만 훑으면 SoA가 유리하다

AoS(구조체의 배열)는 한 원소 안에 모든 필드를 붙여 둔다. SoA(배열들의 구조체)는 필드마다 배열을 나눈다. 어느 쪽이 나은지는 접근 패턴이 정한다.

파티클 데이터를 두 방식으로 잡은 코드다: 

public struct ParticleAos     // AoS: 한 원소 안에 네 필드가 붙어 있다{public Vector3 Position;public Vector3 Velocity;public Color32 Color;public float Lifetime;}public class ParticleSoa      // SoA: 필드마다 배열을 따로 둔다{public Vector3[] Positions;public Vector3[] Velocities;// 위치만 도는 루프는 Positions 배열만 읽는다}

한 원소의 모든 필드를 함께 쓰는 처리에는 AoS가 낫다. 위치만 대량으로 훑는 루프에는 SoA가 낫다. SoA는 SIMD를 태우기도 쉽다.

데이터 지향 설계(DOD)는 이 판단을 앞에 두는 사고방식이다. 객체부터 나누는 대신 어떤 데이터를 어떤 순서로 훑을지 먼저 정한다. DOTS의 ECS·Job·Burst는 그것을 엔진 차원에서 구현한 도구다.

할당자는 해제 순서로 고른다

풀 할당자는 같은 크기 블록을 재사용한다. 임의 순서 해제를 허용하면서 단편화를 막는다.

스택(선형) 할당자는 포인터를 앞으로 밀며 잡고, 표시해 둔 지점까지 되감아 한꺼번에 푼다. 매우 싸지만 LIFO 순서만 가능하다. 슬랩 할당자는 같은 타입용 영역을 미리 잡아 초기화된 조각을 꺼내 준다.

면접에서 이렇게 답한다

  • 캐시를 잘 쓰려면 — 함께 쓰는 데이터를 연속으로 두고 접근 순서와 메모리 순서를 맞춘다. 배열 순회를 기본으로 하고, 루프가 읽지 않는 필드는 다른 배열로 뺀다.
  • 연결 리스트가 배열보다 느린 이유 — 노드가 흩어져 있어 다음 노드로 갈 때마다 캐시 미스가 난다. 복잡도는 같아도 메모리 접근 상수가 다르다.
  • AoS와 SoA를 어떻게 고르나 — 한 객체의 필드를 다 쓰면 AoS, 일부 필드만 대량으로 훑으면 SoA가 유리하다. 접근 패턴이 정한다.
  • DOD와 DOTS의 관계 — DOD는 데이터 배치를 먼저 정하는 사고방식이다. DOTS의 ECS·Job·Burst는 그것을 엔진 차원에서 구현한 도구다.

이런 오해를 한다

  • 복잡도가 같으면 성능도 같다 — O 표기는 상수를 버린다. 캐시 미스 한 번이 연산 수백 번 값이다.
  • struct 크기는 필드 크기의 합이다 — 정렬 때문에 패딩이 들어간다. 큰 필드부터 선언하면 줄어든다.
  • SoA가 항상 빠르다 — 한 원소의 모든 필드를 함께 읽는 처리에서는 여러 배열을 오가며 미스가 늘어난다.
  • DOTS를 써야 DOD를 하는 것이다 — 일반 MonoBehaviour에서도 배열 순회와 필드 분리로 같은 효과를 낸다.
  • 스택 할당자는 아무 순서로나 해제한다 — 되감기 방식이라 LIFO만 가능하다. 임의 순서가 필요하면 풀 할당자를 쓴다.

3줄 정리

  • CPU는 캐시 라인 64바이트를 통째로 읽어 온다
  • 훑는 순서대로 붙여 두면 같은 코드가 빨라진다
  • 일부 필드만 도는 루프면 SoA, 다 쓰면 AoS
