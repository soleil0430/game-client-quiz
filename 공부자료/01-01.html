타입과 메모리

타입은 값을 다루는 약속이고, 메모리는 그 값이 놓이는 자리다

타입과 메모리는 면접에서 늘 붙어 나온다. 타입이 저장 방식과 복사 방식을 정하고, 그 결과가 메모리에 그대로 드러나기 때문이다.

먼저 두 단어의 뜻을 맞추고 시작한다. 그다음 같은 코드가 타입에 따라 왜 다르게 움직이는지 본다.

타입은 약속이고, 메모리는 자리다

타입은 값을 어떻게 저장하고 다룰지 정해 둔 약속이다. 크기가 몇 바이트인지, 대입할 때 무엇이 복사되는지가 타입에 적혀 있다.

메모리는 그 값이 실제로 놓이는 자리다. C#에서 자리는 크게 둘로 나뉜다.

  • 스택: 메서드가 도는 동안만 쓰는 임시 자리다. 메서드가 끝나면 통째로 사라진다.
  • 힙: 메서드가 끝나도 남아야 하는 객체가 놓이는 자리다. 아무도 쓰지 않게 되면 가비지 컬렉터(GC)가 치운다.

이 둘을 나눠 두는 이유는 수명이 다르기 때문이다. 스택은 정리가 공짜에 가깝고, 힙은 GC가 돌아야 정리된다.

변수는 값을 담거나 주소를 담는다

C#의 타입은 두 갈래다. 갈림길은 변수 안에 무엇이 들어 있느냐다.

  • 값 형식(int, float, bool, enum, struct): 변수 안에 값 자체가 들어 있다.
  • 참조 형식(class, 배열, string, 델리게이트): 힙에 있는 객체의 주소가 들어 있다.

그래서 대입의 뜻이 달라진다. 값 형식을 대입하면 값 전체가 새로 복사돼 둘이 남남이 되고, 참조 형식을 대입하면 주소만 복사돼 둘이 같은 객체를 가리킨다.

적의 좌표를 담은 struct를 다른 변수에 넣고 고치면 원본은 그대로다. 같은 코드를 class로 바꾸면 원본까지 바뀐다. 이 차이를 모르면 버그의 원인을 엉뚱한 곳에서 찾는다.

값 형식이 스택에만 사는 것은 아니다

값 형식은 선언된 자리에 얹혀서 산다. 지역 변수면 그 메서드의 스택 프레임에, 클래스 필드면 그 객체와 함께 힙에, 배열 요소면 배열 안에 있다.

반대 방향도 마찬가지다. struct 안에 string 필드가 있으면 struct에는 주소만 들어 있다. 문자열 객체 자체는 힙에 따로 있다.

큰 struct는 넘길 때마다 복사가 쌓인다

복사는 공짜가 아니다. struct는 대입하거나 인자로 넘길 때마다 필드 전체가 복사된다. 필드가 많은 struct를 매 프레임 넘기면 그 비용이 쌓인다.

복사 없이 넘기는 세 가지 한정자를 나란히 둔 코드다:

struct Bounds { public Vector3 Min, Max, Size; }

// in - 읽기 전용 참조. 복사가 없고 호출된 쪽이 고치지 못한다
static bool Contains(in Bounds b, Vector3 p) => p.x >= b.Min.x;

// ref - 복사가 없고 호출된 쪽이 원본을 고칠 수 있다
static void Expand(ref Bounds b, float pad) => b.Size += Vector3.one * pad;

// out - 초기화 없이 넘기고, 메서드가 끝나기 전에 반드시 채워야 한다
static void GetTile(Vector3 p, out int gx, out int gy)
    => (gx, gy) = ((int)p.x, (int)p.z);

타입 자체를 readonly struct로 선언하면 한 걸음 더 간다. 컴파일러가 안전을 위해 넣던 방어적 복사까지 사라진다.

박싱은 값 형식을 힙의 상자에 옮겨 담는 일이다

박싱은 값 형식을 object나 인터페이스로 올릴 때 일어난다. 힙에 상자를 만들고 값을 복사해 넣는다. 할당이 생기니 그대로 GC 부담이 된다.

제네릭 컬렉션은 이 상자를 만들지 않는다. List<int>는 int를 int인 채로 담는다. 반대로 object를 받는 옛 API에 값 형식을 넘기면 그 자리에서 박싱이 난다.

어느 자리에서 박싱이 나는지는 런타임 버전에 따라 달라졌다. enum을 키로 쓴 Dictionary가 대표적이다. 외우기보다 프로파일러로 할당을 확인하는 편이 낫다.

면접에서 이렇게 답한다

  • 값 형식과 참조 형식의 차이 — 변수가 값을 담느냐 주소를 담느냐의 차이다. 그래서 대입할 때 값 전체가 복사되는지, 같은 객체를 공유하는지가 갈린다. 저장 위치는 타입이 아니라 선언된 자리가 정한다고 덧붙인다.
  • class 대신 struct를 쓰는 기준 — 좌표나 색처럼 작고 의미가 값 하나에 가까운 데이터에 쓴다. 상속이나 null 표현이 필요하면 class다. 필드가 많아지면 복사 비용 때문에 오히려 손해다.
  • 박싱이 왜 문제인가 — 힙 할당과 값 복사가 함께 일어난다. 매 프레임 도는 코드에서는 GC를 자주 부른다. 제네릭과 in, readonly struct로 값 형식을 값 형식인 채 다루는 것이 해법이다.
  • ref, out, in의 차이 — 셋 다 참조로 넘긴다. ref는 미리 초기화해야 하고 메서드가 고칠 수 있다. out은 초기화 없이 넘기되 끝나기 전에 반드시 채워야 하고, in은 읽기 전용이다.

이런 오해를 한다

  • 값 형식은 항상 스택에 있다 — 클래스 필드나 배열 요소인 값 형식은 그 객체와 함께 힙에 있다. 위치는 타입이 아니라 선언된 자리가 정한다.
  • new를 쓰면 반드시 힙 할당이 일어난다 — new Vector3(0, 0, 0)은 그 자리에서 생성자만 돈다. 힙을 건드리지 않는다.
  • string을 object로 캐스팅하면 박싱이다 — string은 이미 참조 형식이라 주소만 옮겨 담는다. 박싱은 값 형식에서만 일어난다.
  • readonly로 선언한 List는 내용도 못 바꾼다 — 고정되는 것은 어느 리스트를 가리키는지뿐이다. Add나 원소 수정은 그대로 된다. 값이 쓰는 쪽 코드에 박혀 들어가는 const와는 다른 이야기다.
  • 얕은 복사만으로 원본과 분리된다 — MemberwiseClone은 참조 멤버를 원본과 공유한다. 세이브 데이터나 되돌리기에는 깊은 복사가 필요하다.

3줄 정리

  • 값 형식은 값을, 참조 형식은 주소를 변수에 담는다
  • 저장 위치는 타입이 아니라 선언된 자리가 정한다
  • 박싱은 값 형식이 object로 올라갈 때 나는 할당이다
