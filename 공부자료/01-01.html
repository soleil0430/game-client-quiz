타입과 메모리

타입은 변수가 값을 담을지 주소를 담을지 정하고, 거기서 복사와 저장 자리가 갈린다

적의 좌표를 담은 struct를 다른 변수에 넣고 값을 고쳤다. 원본은 멀쩡하다. 같은 코드에서 struct를 class로만 바꾸면 이번엔 원본까지 따라 바뀐다.

로직은 한 글자도 안 고쳤는데 결과가 갈린다. 타입이 무엇을 정하는 물건인지 알면 이 갈림길이 보인다.

타입은 약속이고, 메모리는 자리다

타입은 값을 어떻게 저장하고 다룰지 미리 정해 둔 약속이다. 크기가 몇 바이트인지, 대입할 때 무엇이 복사되는지가 여기 적혀 있다. 메모리는 그 값이 실제로 놓이는 자리고, C#에서 자리는 크게 둘로 나뉜다.

스택은 메서드가 도는 동안만 쓰는 임시 자리라 메서드가 끝나면 통째로 사라진다. 힙은 반대다. 메서드가 끝나도 남아야 하는 객체가 여기 놓이고, 아무도 쓰지 않게 되면 가비지 컬렉터(GC)가 치운다.

둘을 나눈 이유는 수명이 다르기 때문이다. 스택은 정리가 공짜에 가깝고, 힙은 GC가 한 바퀴 돌아야 정리된다.

변수는 값을 담거나 주소를 담는다

C#의 타입은 두 갈래다. 갈림길은 변수 안에 무엇이 들어 있느냐 하나뿐이다. 값 형식(int, float, bool, enum, struct)은 변수 안에 값 자체를 담는다. 참조 형식(class, 배열, string, 델리게이트)이 담는 것은 힙에 있는 객체의 주소다.

대입의 뜻이 여기서 갈린다. 값 형식을 대입하면 값 전체가 새로 복사돼 둘이 남남이 된다. 참조 형식을 대입하면 주소만 복사되니 둘이 같은 객체를 붙잡는다.

맨 앞에서 본 struct와 class 이야기가 이것이었다. var b = a; 뒤에 b를 바꿔도 a는 그대로지만, Point가 class였다면 a와 b가 같은 객체를 가리켜 바뀐 값이 출력된다.

그래서 struct는 좌표나 색처럼 작고 자주 복사되는 데이터에 맞다. 상속과 다형성, 인스턴스 공유, null 표현이 필요하면 class를 써야 한다.

그럼 값 형식은 항상 스택에 있나

아니다. 값 형식은 선언된 곳에 저장된다. 지역 변수면 그 메서드의 스택 프레임에, 클래스 필드나 배열 요소면 그 객체와 함께 힙에 놓인다.

반대 방향도 마찬가지다. struct 안에 string 필드가 있으면 struct가 들고 있는 것은 주소뿐이다. 문자열 객체 자체는 힙에 따로 떨어져 있다.

큰 struct는 넘길 때마다 복사가 쌓인다

복사는 공짜가 아니다. struct는 대입하거나 인자로 넘길 때마다 필드 전체가 따라간다.

아래 코드의 Bounds를 보자. Vector3 셋이니 36바이트다. 한 프레임에 천 번 넘기면 3만 6천 바이트가 복사된다.

필드가 많은 큰 struct일수록 복사 비용이 커서 오히려 손해다. 복사 없이 넘기는 한정자가 셋 있다:

struct Bounds { public Vector3 Min, Max, Size; }

// in - 읽기 전용 참조
static bool Contains(in Bounds b, Vector3 p) => p.x >= b.Min.x;

// ref - 호출된 쪽이 원본을 고칠 수 있다
static void Expand(ref Bounds b, float pad) => b.Size += Vector3.one * pad;

// out - 초기화 없이 넘긴다
static void GetTile(Vector3 p, out int gx, out int gy)
    => (gx, gy) = ((int)p.x, (int)p.z);

셋의 차이는 초기화 책임이다. ref는 넘기기 전에 값이 들어 있어야 하고, out은 초기화하지 않고 넘기는 대신 메서드가 끝나기 전에 반드시 대입해야 한다. Dictionary.TryGetValue처럼 결과를 여러 개 돌려줄 때 쓰는 것이 out이다.

셋 다 인자를 참조로 넘겨 호출한 쪽의 변수를 직접 바꾼다. in만 읽기 전용이라, 매개변수에 in을 붙여 넘기면 복사를 피하면서도 호출한 쪽의 값이 바뀌지 않는다. 같은 자리에서 object로 캐스팅해 넘기면 박싱이 일어나 힙 할당이 추가된다.

타입을 readonly struct로 선언해 두면 한 걸음 더 간다. 컴파일러가 안전을 위해 몰래 넣던 방어적 복사까지 막을 수 있다.

복사본을 고쳤는데 원본까지 바뀐다

참조 형식을 베낄 때는 한 겹이 더 있다. 얕은 복사는 필드 값만 그대로 옮기므로, 참조 멤버는 원본과 같은 객체를 가리킨다. 복사본의 인벤토리에 아이템을 넣으면 원본 인벤토리에도 들어가 있다.

깊은 복사는 참조가 가리키는 대상까지 새로 만들어 원본과 완전히 분리한다. MemberwiseClone은 얕은 복사라, 깊은 복사가 필요하면 직접 구현하거나 직렬화·역직렬화를 이용한다.

세이브 데이터나 되돌리기 기능처럼 원본이 바뀌면 안 되는 곳에서 이 구분이 문제가 된다.

박싱은 값 형식을 힙의 상자에 옮겨 담는 일이다

박싱은 값 형식을 object나 인터페이스 같은 참조 형식으로 바꿀 때 일어난다. 힙에 상자를 만들어 값을 복사하는 일이라, int a = 5; object o = a; 한 줄이면 박싱된다. 상자를 열어 값을 도로 꺼내는 것이 언박싱이다.

이 상자는 원본을 베껴 담는다. 넣은 뒤에 원본을 고쳐도 상자 안은 옛날 값 그대로다. 상자 하나를 만든 대가로 힙 할당이 하나 생기고, 그대로 GC 부담이 된다.

제네릭 컬렉션은 이 상자를 만들지 않는다. List<int>는 제네릭이라 int를 박싱 없이 저장한다. 반대로 object를 받는 옛 API에 값 형식을 넘기면 그 자리에서 박싱이 난다.

박싱이 아닌 것도 많다. int를 long으로 넓히는 변환은 값 형식끼리의 변환이고, string은 이미 참조 형식이며, int[]는 힙에 배열을 할당하지만 상자를 만들지는 않는다.

어느 자리에서 박싱이 나는지는 런타임 버전마다 달랐다. 외우려 들면 끝이 없으니 프로파일러로 할당을 보는 편이 빠르다.

const는 박히고 readonly는 정해진다

const는 컴파일 타임 상수라 값이 사용하는 쪽 코드에 그대로 박혀 들어간다. 라이브러리의 const 값을 바꾸면 쓰는 쪽도 다시 빌드해야 한다.

readonly는 런타임 상수로, 필드는 생성자까지는 대입할 수 있다. 인스턴스마다 다른 값을 정할 수 있다는 뜻이다.

다만 readonly List는 참조만 고정될 뿐이라 Add도 원소 수정은 그대로 된다.

없음까지 담아야 하면 int?

값 형식에는 null이 없다. 아직 정해지지 않은 레벨처럼 없음을 표현해야 하면 int?를 쓴다. Nullable<int>의 축약형으로, 값과 HasValue 플래그를 함께 담은 구조체이고 그래서 int? 자체도 값 형식이다.

구조체라 그 자체로는 힙 할당이 없다. 다만 HasValue가 false일 때 Value를 읽으면 InvalidOperationException이 난다. ??는 왼쪽이 null일 때만 오른쪽을 돌려주고, GetValueOrDefault()로 기본값을 받을 수도 있다.

캐스팅이 실패할 수 있는 자리

부딪힌 콜라이더가 Enemy인지 확신할 수 없는 자리가 있다. is는 맞는지 아닌지를 bool로 돌려주는 검사이고, as는 변환에 실패하면 예외 대신 null을 돌려준다.

as는 참조 형식(과 nullable)에만 쓸 수 있고, 값 형식에는 o as int? 형태로만 가능하다.

C# 7부터는 패턴 매칭 if (o is Enemy e) 한 줄로 검사와 변환을 한 번에 끝낸다. 캐스팅을 두 번 하지 않아도 되니 이쪽이 기본값이다.

런타임이 봐 주는 메모리, 그렇지 않은 메모리

여기까지가 managed 코드 안의 이야기다. C# 코드는 IL로 컴파일돼 런타임(Unity에서는 Mono나 IL2CPP) 위에서 실행되고, 메모리 회수와 타입 안전성을 그 런타임이 책임지고 관리한다.

반대쪽이 unmanaged 자원이다. 네이티브 플러그인이 잡은 메모리나 파일 핸들은 GC가 알지 못하므로 Dispose로 직접 해제해야 한다. C#에서도 unsafe 블록 안에서는 포인터를 쓸 수 있다.

면접에서 이렇게 답한다

  • 값 형식과 참조 형식의 차이 — 변수가 값을 담느냐 주소를 담느냐의 차이다. 그래서 대입할 때 값 전체가 복사되는지, 같은 객체를 공유하는지가 갈린다. 여기서 한 걸음 더 나가 어디에 저장되는지는 타입이 아니라 선언된 자리가 정한다고 덧붙인다.
  • class 대신 struct를 쓰는 기준 — 좌표나 색처럼 작고 의미가 값 하나에 가까운 데이터에 쓴다. 상속이 필요하거나 null로 없음을 표현해야 하면 class다. 필드가 많아지면 복사 비용 때문에 오히려 손해라는 이유까지 말한다.
  • 박싱이 왜 문제인가 — 힙 할당과 값 복사가 한꺼번에 일어난다. 매 프레임 도는 코드라면 그만큼 GC를 자주 부른다. 제네릭과 in, readonly struct로 값 형식을 값 형식인 채 다루는 것이 해법이다.
  • ref, out, in의 차이 — 셋 다 참조로 넘긴다. ref는 미리 초기화해야 하고 호출된 쪽이 고칠 수 있다. out은 초기화 없이 넘기되 끝나기 전에 반드시 채워야 한다. in은 읽기만 한다.

이런 오해를 한다

  • “값 형식은 스택” — 이 한 줄만 외우고 가면 꼬리 질문에서 막힌다. 클래스 필드나 배열 요소인 값 형식은 그 객체와 함께 힙에 있다.
  • “new를 쓰면 힙 할당” — new Vector3(0, 0, 0)은 그 자리에서 생성자만 돈다. 힙은 건드리지 않는다.
  • “string을 object로 캐스팅하면 박싱” — string은 이미 참조 형식이라 주소만 옮겨 담는다. 박싱은 값 형식에서만 일어난다.
  • “readonly List는 내용도 못 바꾼다” — 고정되는 것은 어느 리스트를 가리키는지뿐이다. Add도 되고 원소 수정도 된다. 값이 쓰는 쪽 코드에 박혀 들어가는 const와는 다른 이야기다.
  • “얕은 복사면 원본과 분리된다” — MemberwiseClone은 참조 멤버를 원본과 그대로 공유한다. 세이브 데이터나 되돌리기에는 깊은 복사가 필요하다.

3줄 정리

  • 값 형식은 값을, 참조 형식은 주소를 변수에 담는다
  • 저장 위치는 타입이 아니라 선언된 자리가 정한다
  • 박싱은 값 형식이 object로 올라갈 때 나는 할당이다
