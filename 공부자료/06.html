객체지향

데이터와 책임을 객체로 묶는 이유를 알고, SOLID로 바뀔 자리를 미리 열어 둔다

핵심 개념

객체지향은 데이터와 그것을 다루는 코드를 묶어 무엇이 무엇을 책임지는지를 구조에 드러내는 방식이다. 절차지향은 데이터와 함수가 따로 놀아서 규칙이 바뀌면 그 데이터를 만지는 함수를 전부 찾아 고쳐야 한다. 대가는 클래스와 간접 호출이 늘어 읽기 힘들어지는 것이다.

특징무엇이고 무엇을 얻나
추상화세부를 걷어내고 필요한 면만 남긴다. 구현이 바뀌어도 쓰는 쪽은 그대로다
캡슐화상태를 감추고 공개 메서드로만 다루게 한다. 지킬 조건을 클래스가 스스로 지킨다
상속부모의 멤버를 물려받아 특수화한다. 공통 동작이 한곳에 모인다
다형성같은 호출이 실제 타입에 따라 다르게 돈다. 타입마다 분기하는 코드가 사라진다

Unity에서는 [SerializeField] private 필드로 인스펙터 노출과 캡슐화를 같이 챙기는 것이 관례다. SOLID는 바뀔 자리를 미리 열어 두기 위한 다섯 지침이다.

원칙뜻게임에서
SRP 단일 책임바뀌어야 할 이유가 하나뿐체력 계산과 체력바 연출을 분리
OCP 개방-폐쇄확장에는 열리고 수정에는 닫힌다새 무기는 분기 수정 없이 클래스 추가
LSP 리스코프 치환자식이 부모 자리에 들어가도 동작부모의 약속을 예외로 막지 않기
ISP 인터페이스 분리안 쓰는 메서드를 떠안기지 않는다공격 안 하는 것엔 공격 계약을 안 붙임
DIP 의존 역전상위와 하위가 모두 추상화에 의존전투 로직은 IWeapon만 안다

OCP와 DIP는 같은 장치로 지켜진다. 분기를 고치는 대신 인터페이스를 두고 구현을 더하면 기존 코드는 손대지 않는다.

public interface IWeapon { void Fire(Vector3 origin); }

public class Attacker : MonoBehaviour
{
    private IWeapon weapon;  // 구체 타입이 아니라 계약에 의존

    public void Equip(IWeapon w) => weapon = w;  // 구현은 밖에서 넣는다

    private void Update() { if (Input.GetButtonDown("Fire1")) weapon?.Fire(transform.position); }
}

다형성은 두 갈래다. 오버로딩이나 제네릭처럼 컴파일 시점에 대상이 정해지면 정적, virtual과 override로 실행 중 실제 타입을 보고 정해지면 동적이다. 동적 쪽은 가상 함수 테이블을 거친다.

상속은 "~이다" 관계가 뚜렷하고 계층이 얕을 때만 쓸 만하다. 날기·헤엄치기를 상속으로 조합하면 FlyingSwimmingEnemy 같은 클래스가 불어난다. Unity의 GameObject와 컴포넌트가 컴포지션을 엔진 차원에서 구현한 것이다.

면접에서 이렇게 답한다

  • 객체지향이란 — 데이터와 규칙을 객체로 묶어 책임을 나누는 방식이다. 네 특징으로 설명하고, 얻는 것은 변경이 한곳에 갇히는 것이라고 덧붙인다.
  • SOLID를 적용한 예 — 무기가 늘 때마다 분기를 고치던 코드를 IWeapon으로 바꿔 새 무기가 클래스 추가만으로 끝나게 했다고 말한다. 원칙 이름보다 고친 코드 하나가 강하다.
  • LSP를 어기는 코드 — Bird를 상속한 Penguin이 Fly()에서 예외를 던지면 Bird를 믿고 쓰는 코드가 깨진다. "난다"를 별도 인터페이스로 뺀다고 답한다.
  • 상속과 컴포지션 — 기본은 컴포지션이고, 모든 팝업이 공유하는 열기·닫기 흐름처럼 공통 동작이 뚜렷하고 계층이 얕을 때는 상속이 더 읽기 쉽다.
  • 결합도 낮추기 — 구체 타입 대신 인터페이스에 의존하고, 참조는 밖에서 받고, 먼 시스템끼리는 이벤트로 알린다. 줄줄이 따라 고칠 곳을 없애는 것이 목적이다.

흔한 오해

  • DIP는 호출 방향을 뒤집는 것 — 방향이 아니라 의존 대상을 바꾸는 것이다. 인터페이스를 상위 쪽 필요에 맞춰 정의하고 하위가 구현한다.
  • SRP는 클래스를 작게 쪼개라는 뜻 — 개수를 세는 규칙이 아니다. 기준은 바뀌어야 할 이유이고, 모든 기능을 한 매니저에 모으는 것이 가장 크게 어긴 꼴이다.
  • 오버라이딩이 정적 다형성 — 반대다. 오버로딩이 컴파일 시점, 오버라이딩이 실행 시점이다.
  • 자식이 부모와 다르게 동작하면 LSP 위반 — 약속을 지키면서 구현을 바꾸는 것은 다형성의 목적이다. 위반은 약속을 깨뜨릴 때다.

디자인 패턴

패턴을 생성·구조·행위로 나눠 대고, 게임에서 실제로 쓴 것을 코드로 말한다

핵심 개념

디자인 패턴은 자주 나오는 설계 문제의 이름 붙은 해결책이다. 이름을 대면 팀이 같은 그림을 떠올리지만, 문제가 없는데 꺼내면 클래스만 는다. GoF 분류는 만드는 생성, 엮는 구조, 주고받는 행위다.

갈래패턴정리
생성싱글톤인스턴스를 하나로 제한, 전역 접근점
생성팩토리 메서드어떤 구체 타입을 만들지 감춤
생성빌더생성을 단계로 쪼갬

구조어댑터안 맞는 인터페이스를 맞춤
구조퍼사드하위 시스템을 한 창구로
구조프록시원본 대신 서서 접근 가로챔
구조데코레이터인터페이스 그대로 기능 덧씌움

기타컴포넌트부품으로 조합. Unity 구조

추상 팩토리·플라이웨이트는 생성·구조, 템플릿 메서드는 행위다. 싱글톤은 DontDestroyOnLoad로 남긴 것이 씬을 다시 로드할 때 그 씬의 같은 매니저와 겹쳐 둘이 되므로 Awake 중복 처리가 핵심이다.

public class SoundManager : MonoBehaviour
{
    public static SoundManager Instance { get; private set; }

    private void Awake()
    {
        if (Instance != null && Instance != this) { Destroy(gameObject); return; }
        Instance = this;
        DontDestroyOnLoad(gameObject);
    }
}

상태 패턴은 Update의 if-else 더미를 상태 객체로 나눈다. 진입·갱신·퇴장이 상태마다 모여, bool로 관리할 때 생기는 불가능한 조합을 막는다.

public interface IState { void Enter(); void Tick(); void Exit(); }

public class StateMachine
{
    private IState current;

    public void Change(IState next) { current?.Exit(); current = next; current.Enter(); }
    public void Tick() => current?.Tick();
}

옵저버는 C#에서 event가 곧 구현이다. 알리는 쪽이 누가 듣는지 모르니 반응을 추가해도 주체는 안 바뀐다. OnEnable에서 +=, OnDisable에서 -=로 짝을 맞춘다. 빠뜨리면 구독자를 붙들어 누수와 예외가 난다.

면접에서 이렇게 답한다

  • 아는 패턴을 말해 보라 — 세 갈래를 나누고 갈래마다 써 본 것을 든다. "보스 페이즈를 상태 패턴으로 나눴다"처럼 쓴 자리를 댄다.
  • 싱글톤의 문제와 대안 — 전역 접근이라 결합이 커지고, 가짜 구현을 못 끼워 테스트가 막히며, 초기화 순서와 씬 수명이 걸린다. 대안은 주입이다.
  • 멀티스레드에서 하나임을 보장 — 널 검사와 생성 사이에 다른 스레드가 끼어들 수 있으니 lock이나 Lazy에 맡긴다.
  • 전략과 의존성 주입의 차이 — 전략은 알고리즘을 인터페이스 뒤로 빼는 설계, 주입은 구현을 누가 넣느냐는 기법이다. 층위가 달라 같이 쓴다.

흔한 오해

  • 싱글톤은 접근할 때마다 객체가 생긴다 — 하나를 재사용하니 할당이 없다. 비용은 결합도와 테스트다.
  • volatile이면 인스턴스가 하나가 된다 — 값이 보이게 할 뿐 생성이 한 번임은 보장하지 않는다.
  • 옵저버는 등록 순서대로 돈다 — 기대면 안 된다. 순서가 중요하면 직접 호출로 푼다.
  • C# event와 UnityEvent는 같다 — UnityEvent는 인스펙터 연결 대신 무겁다.

아키텍처

시스템끼리 어떻게 찾고 부르는지를 정해, 다음 기능을 넣는 비용을 낮추는 일이다

핵심 개념

아키텍처의 목적은 멋진 그림이 아니라 다음 기능을 넣는 비용을 낮추는 것이다. 그 비용을 정하는 것은 대개 "시스템끼리 서로를 어떻게 찾고 부르는가" 하나다. 방식은 셋뿐이고 결합도와 흐름 추적을 맞바꾼다.

방식결합도흐름 추적어디에 쓰나
구체 클래스 직접 참조높다가장 쉽다늘 붙어 다니는 관계
인터페이스 + 주입중간코드에 보인다교체·테스트가 필요한 협력
이벤트·메시지 버스낮다어렵다먼 시스템에 던지는 알림

의존성 주입은 쓸 협력 객체를 스스로 만들지 않고 밖에서 받는 것이다. 컨테이너가 있어야 주입인 것이 아니라 생성자나 메서드 인자로 넘기기만 해도 주입이고, 인스펙터 연결도 넓게 보면 밖에서 넣어 주는 것이다. 인터페이스는 "무엇을 해 줄 수 있는가"라는 계약만 남기고 구현을 감춘다.

public interface ISaveStore { void Save(string json); }

public class ScoreService
{
    private readonly ISaveStore store;

    public ScoreService(ISaveStore store) => this.store = store;  // 생성자 주입

    public void Record(int score) => store.Save(score.ToString());
}

// MonoBehaviour는 생성자를 쓸 수 없어 초기화 메서드로 주입한다
public class ScoreView : MonoBehaviour
{
    private ScoreService service;

    public void Init(ScoreService service) => this.service = service;
}

이벤트 버스는 발행자가 누가 받는지 모른 채 던지므로 결합이 가장 느슨하다. 대신 이벤트가 이벤트를 부르는 연쇄, 구독 순서 의존, 해제 누락이 겹치면 원인을 찾기 어렵다. 전부 버스로 통신하면 호출 흐름이 코드에 남지 않으니, 가까운 관계는 주입으로 먼 시스템 알림은 버스로 나눈다.

UI에는 MVC 계열을 쓴다. 모델은 데이터와 규칙, 뷰는 표시와 입력 전달, 컨트롤러는 입력을 받아 모델을 고친다. 핵심은 모델이 뷰를 모르게 해서 화면을 갈아엎어도 규칙 코드를 안 건드리는 것이다. MVP는 뷰를 더 얇게 두고 프레젠터가 중개하며, MVVM은 바인딩으로 그 연결을 자동화한다. 대신 클래스가 늘어 작은 팝업에는 과하다.

ECS는 방향 자체가 다르다. 엔티티에 순수 데이터인 컴포넌트를 붙이고 로직은 시스템에 두며, 같은 컴포넌트를 가진 엔티티를 메모리에 촘촘히 모아 한 번에 훑는다. 캐시 적중률이 높고 일감을 나누기 쉬워 수만 개를 반복할 때 유리하다. 상속 기반 구조는 데이터와 로직이 객체마다 흩어져 있고 가상 호출을 탄다.

정의를 정확히 해 둘 것 셋. 프레임워크와 라이브러리는 누가 누구를 부르나로 갈린다. Update가 엔진에 의해 불리면 프레임워크, 내가 부르는 수학 유틸리티는 라이브러리다. 순수 함수는 같은 입력에 늘 같은 결과를 내고 부수 효과가 없어 테스트와 멀티스레드에 유리하다. Lua로 콘텐츠 규칙을 빼면 재심사 없이 고칠 수 있지만, 인터프리터 비용 때문에 매 프레임 도는 계산은 C#에 남긴다.

면접에서 이렇게 답한다

  • 전 회사 아키텍처를 설명하라 — 레이어를 나열하지 말고 "무엇이 자주 바뀌었고 그래서 어디를 갈아 끼울 수 있게 뒀는지"로 말한다. 콘텐츠 데이터, UI, 서버 통신 중 무엇이 가장 자주 바뀌었는지부터 꺼낸다.
  • 의존성 주입이 왜 필요한가 — 구체 클래스를 직접 new하면 교체할 수 없고 테스트에서 가짜를 넣을 수 없다. 인터페이스로 계약만 남기면 서버 연동을 로컬 스텁으로 바꿔 끼우는 일이 호출부 수정 없이 된다.
  • 이벤트가 많아지면 — 연쇄 호출과 구독 순서 의존으로 추적이 어려워지고 해제 누락이 누수로 이어진다. 이벤트의 범위를 정하고 중요한 흐름은 직접 호출로 남긴다고 답한다.
  • 레거시 리팩터링 — 한 번에 갈아엎지 않는다. 바꿀 곳 주변에 재현 절차를 먼저 만들고, 인터페이스로 경계를 그은 뒤 그 안에서 조금씩 교체한다.

흔한 오해

  • 의존성 주입은 성능 최적화 — 목적은 결합도를 낮추는 설계다. 오히려 간접 호출이 한 겹 는다.
  • 이벤트 버스를 쓰면 결합이 사라진다 — 직접 참조가 없어질 뿐 메시지 형식이라는 계약이 남고, 디버깅 비용은 올라간다.
  • 뷰가 데이터를 직접 읽고 써도 MVC다 — 그 순간 분리가 무너진다. 모델이 뷰를 모르게 하는 것이 목적이다.
  • ECS로 바꾸면 무조건 빨라진다 — 같은 처리를 대량 반복할 때 유리하다. 종류가 제각각인 소수 오브젝트는 이득이 적고 전환 비용이 크다.
  • 순수 함수는 static 함수다 — 상관없다. 기준은 같은 입력에 같은 결과인지와 부수 효과가 없는지다.

게임 시스템 설계

요구와 제약을 먼저 묻고, 나중에 바꿔도 깨지지 않는 데이터 구조로 설계한다

핵심 개념

시스템 설계 질문은 정답을 맞히는 문제가 아니라 무엇을 먼저 물어보는지를 보는 문제다. "인벤토리를 설계하라"를 들으면 클래스부터 그리지 말고 제약을 확인한다. 칸 수가 정해져 있나, 같은 아이템이 겹쳐 쌓이나, 정렬·필터가 필요한가, 수량은 수십 개인가 수만 개인가, 서버가 최종 권한을 갖나. 이 답이 자료구조를 정한다. 칸이 고정이면 배열, 아이디로 찾는 일이 잦으면 딕셔너리를 함께 둔다.

스탯은 기본값과 보정 목록을 따로 두고 필요할 때 합산하는 것이 정석이다. 붙을 때 최종 수치에 더하고 풀릴 때 빼면 곱연산이나 상한이 섞이는 순간 원래 값으로 안 돌아온다. 목록으로 들고 있으면 순서가 달라도 결과가 같고 출처도 추적된다. 합산이 부담되면 캐시하고 목록이 바뀔 때만 다시 계산한다.

public struct StatModifier { public float Add; public float Mul; }  // Mul 0.2f면 +20%

public class Stats
{
    public float BaseAttack = 10f;

    private readonly List<StatModifier> mods = new List<StatModifier>();
    private float cached;
    private bool dirty = true;

    public void Add(StatModifier m)    { mods.Add(m);    dirty = true; }
    public void Remove(StatModifier m) { mods.Remove(m); dirty = true; }

    public float Attack
    {
        get
        {
            if (!dirty) return cached;
            float add = 0f, mul = 1f;
            foreach (var m in mods) { add += m.Add; mul += m.Mul; }
            cached = (BaseAttack + add) * mul;
            dirty = false;
            return cached;
        }
    }
}

세이브는 저장 항목이 반드시 바뀐다는 전제로 설계한다. 파일에 스키마 버전을 넣고 읽을 때 버전에 맞춰 변환해 올리면, 기존 진행을 지키면서 구조를 바꿀 수 있다. 빠진 항목은 실패시키지 말고 기본값으로 채운다.

저장 위치맞는 용도주의
PlayerPrefs설정값처럼 작고 잃어도 되는 것평문이라 변조가 쉽다
파일(JSON 등)진행도 전체버전 필드, 저장 중 종료 대비(임시 파일 후 교체)
서버재화처럼 검증이 필요한 것결과가 아니라 행동을 보내고 서버가 계산한다

절차적 생성은 같은 시드와 규칙이면 항상 같은 결과가 나오게 만드는 것이 기본이다. 그러면 맵 전체 대신 시드 하나만 저장해도 복원된다. 청크마다 좌표에서 시드를 파생시키면 멀리 있는 지형을 버렸다 다시 만들어도 같은 모습이다.

면접에서 이렇게 답한다

  • 인벤토리를 설계하라 — 칸 제한과 스택 여부, 최대 아이템 수, 서버 검증 여부를 먼저 묻고 자료구조를 고른다. 그다음 데이터와 표시를 나눠 아이템이 바뀌면 UI가 바뀐 칸만 갱신하게 했다고 말한다.
  • 버프와 장비로 스탯이 계속 바뀐다면 — 기본값은 그대로 두고 보정 목록을 합산해 최종값을 낸다. 순서에 무관하고 출처 추적이 되며, 캐시와 더티 플래그로 성능도 해결된다고 답한다.
  • 세이브·로드 설계 — 포맷에 버전을 넣고 변환 단계를 둔다. 빠진 항목은 기본값, 저장 중 종료에 대비해 임시 파일에 쓴 뒤 교체, 중요한 값은 서버 검증이다.
  • 나중에 서버를 붙인다면 — 규칙 계산을 UI와 분리해 순수 함수에 가깝게 두고 저장·조회를 인터페이스 하나로 감싼다. 구현만 서버 호출로 바꾸면 되고, 시간도 기기 시계 대신 서버 시간을 받게 통로를 모은다.
  • 업적·퀘스트 시스템 — 조건을 코드가 아니라 데이터로 두고, 게임 쪽은 "적 처치" 같은 사건만 던진다. 진행 시스템이 그 사건으로 조건을 갱신하면 새 업적이 데이터 추가만으로 는다.

흔한 오해

  • 버프는 붙을 때 더하고 풀릴 때 빼면 된다 — 곱연산이나 상한이 섞이면 원래 값으로 안 돌아와 수치가 새는 대표적 함정이다.
  • 세이브는 메모리 덤프가 빠르고 간단하다 — 필드가 하나만 늘거나 순서가 바뀌어도 기존 파일이 전부 깨진다. 버전을 가진 명시적 포맷을 쓴다.
  • 절차적 맵은 시스템 시간을 시드로 쓰면 된다 — 같은 맵을 두 번 만들 수 없어 복원과 버그 재현이 불가능해진다.
  • 로컬 저장을 서버로 그대로 옮기면 된다 — 결과만 저장하던 구조는 서버가 검증할 근거가 없다. 계획이 있으면 처음부터 행동을 기록하고 규칙 계산을 한곳에 모은다.
