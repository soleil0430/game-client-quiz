복잡도

입력이 커질 때 비용이 어떤 속도로 자라는지를 재는 자다. 상수 배는 실측으로 따진다

핵심 개념

복잡도는 입력 크기 N이 커질 때 비용이 어떤 속도로 자라는가를 나타낸다. 연산 횟수가 자라는 속도가 시간 복잡도, 추가로 쓰는 메모리가 자라는 속도가 공간 복잡도다. 빅오 표기법은 여기서 가장 빨리 자라는 항만 남기고 상수 배와 하위 항을 버린다. N이 충분히 커지면 3N² + 100N + 5에서 N² 항이 나머지를 완전히 압도하므로 O(N²)라고 쓴다.

복잡도N이 100만일 때 대략대표 예
O(1)1배열 인덱스 접근, Dictionary 조회
O(log N)20이진 탐색, 균형 트리 조회, 힙 삽입
O(N)1,000,000전체 순회, 선형 탐색
O(N log N)2천만비교 기반 정렬(List<T>.Sort)
O(N²)1조모든 쌍을 도는 이중 루프
O(2ⁿ)사실상 불가부분집합 전수 탐색

O(log N)이 작은 이유는 한 번 볼 때마다 후보가 절반으로 줄기 때문이다. 100만을 반씩 나누면 스무 번이면 하나가 남는다. 반대로 O(N²)이 위험한 이유는 N이 두 배가 되면 비용이 네 배가 되기 때문이다. 게임에서 유닛끼리 쌍으로 충돌을 검사하는 코드가 전형적이다.

// N마리를 모두 짝지으면 N(N-1)/2번 — O(N²)
for (int i = 0; i < units.Count; i++)
    for (int j = i + 1; j < units.Count; j++)
        CheckCollision(units[i], units[j]);

유닛이 100마리면 4,950쌍이라 60fps에서도 버티지만 1,000마리면 약 50만 쌍이 되어 한 프레임 예산 16.7ms를 넘긴다. 이럴 때 격자나 쿼드트리로 공간을 나눠 가까운 것끼리만 비교하도록 바꾸는 것이 복잡도를 낮추는 최적화다.

다만 빅오는 증가 추세만 말한다. 상수 배와 하위 항을 버렸으므로 N이 작을 때는 복잡도가 나쁜 쪽이 더 빠를 수 있다. 원소 네다섯 개짜리 목록이라면 해시 계산과 버킷 조회를 거치는 Dictionary보다 배열을 그냥 훑는 쪽이 빠른 경우가 흔하다. 같은 O(N log N) 정렬끼리도 캐시 지역성과 분기 예측 때문에 실측이 몇 배씩 갈린다. 그래서 복잡도는 설계를 고를 때 쓰는 자이고, 실제 성능은 프로파일러로 재야 한다.

또 하나 알아 둘 것이 분할 상환(amortized) 복잡도다. List<T>.Add는 내부 배열이 꽉 찬 순간에만 O(N) 복사가 일어나고 그 일이 드물게 생기므로, 여러 번에 걸쳐 평균을 내면 한 번에 O(1)이다. 최악이 O(N)이라고 해서 평균까지 O(N)인 것은 아니다.

면접에서 이렇게 답한다

  • 시간 복잡도와 공간 복잡도란 — 입력 크기가 커질 때 연산 횟수와 추가 메모리가 각각 얼마나 빨리 늘어나는지를 나타낸 값이다. 빅오는 가장 빨리 자라는 항만 남기므로 알고리즘끼리 규모가 커졌을 때의 우열을 비교하는 데 쓴다.
  • 흔한 복잡도의 크기 순서 — O(1) < O(log N) < O(N) < O(N log N) < O(N²) < O(2ⁿ) 순이다. log N은 절반씩 줄이는 구조에서, N log N은 정렬처럼 전체를 훑으면서 절반씩 쪼개는 구조에서 나온다.
  • O(1)이 항상 O(N²)보다 빠른가 — 아니다. 빅오는 상수 배를 버린 값이라 입력이 작으면 역전될 수 있다. 실제로 원소 몇 개짜리 컬렉션에서는 해시 조회보다 선형 탐색이 빨랐던 경험이 있고, 그래서 최종 판단은 실기기 프로파일링으로 한다.
  • 시간과 공간 중 무엇을 택하나 — 모바일에서는 메모리 한도가 먼저 걸리는 경우가 많아, 미리 계산해 캐시하는 방식을 쓰기 전에 그 표가 차지할 용량과 절약되는 프레임 시간을 같이 본다.

흔한 오해

  • 빅오가 실행 시간을 알려 준다 — 증가 추세만 말한다. O(N)짜리 두 코드의 실측이 10배 차이 나는 일은 흔하다.
  • 복잡도가 같으면 성능이 같다 — 메모리 접근 패턴이 다르면 같은 O(N)도 캐시 적중률 때문에 몇 배씩 벌어진다.
  • 상수 배는 무시해도 된다 — 이론에서 버리는 것이지 코드에서 버리는 것이 아니다. 매 프레임 도는 루프의 상수 배 2배는 그대로 2배 비용이다.
  • 최악이 O(N)이면 평균도 O(N)이다 — 동적 배열 확장처럼 드물게 일어나는 비용은 분할 상환하면 O(1)이 된다.

배열과 리스트

연속 메모리냐 흩어진 노드냐에 따라 접근 비용과 캐시 적중률이 함께 갈린다

핵심 개념

배열과 연결 리스트의 차이는 원소를 메모리에 어떻게 놓느냐에서 전부 파생된다. 배열은 같은 크기의 원소를 빈틈없이 이어 붙이므로 i번째 주소를 시작 주소 + i × 원소 크기로 바로 계산한다. 그래서 임의 접근이 O(1)이지만, 중간에 끼워 넣으려면 뒤쪽을 전부 한 칸씩 밀어야 해서 O(n)이다. 연결 리스트는 노드마다 다음 참조를 들고 흩어져 있어 i번째를 찾으려면 처음부터 따라가야 해 O(n)이지만, 넣을 자리의 노드를 들고 있다면 참조 두 개만 고쳐 O(1)에 끝난다.

연산배열 · List<T>연결 리스트 · LinkedList<T>
인덱스로 접근O(1)O(n)
맨 뒤에 추가O(1) 분할 상환O(1)
맨 앞·중간 삽입/삭제O(n) (뒤 원소 이동)노드를 알면 O(1), 찾아야 하면 O(n)
순회O(n), 캐시에 유리O(n), 캐시 미스 잦음
원소당 메모리값만값 + 참조 2개 + 헤더

복잡도가 같은 순회에서 실측이 갈리는 이유는 CPU가 메모리를 캐시 라인(보통 64바이트) 단위로 읽기 때문이다. 배열은 한 번 읽으면 뒤따라 쓸 원소까지 캐시에 딸려 오고 프리페처가 다음 라인을 미리 당겨 온다. 연결 리스트는 노드가 힙에 흩어져 있어 참조를 따라갈 때마다 새 라인을 읽어야 하고, 주소를 읽어야 다음 주소를 알 수 있어 미리 당겨 오지도 못한다.

C#의 List<T>는 내부에 T[]를 들고 있는 동적 배열이다. Add로 채우다 용량이 차면 대개 두 배 크기의 새 배열을 할당해 전부 복사하고 옛 배열은 GC 대상이 된다. 그 순간만 O(n)이고 확장이 드물게 일어나므로 Add 한 번의 분할 상환 비용은 O(1)이다. 넣을 개수를 미리 알면 new List<T>(capacity)로 잡아 두어 복사와 GC 할당을 없애는 것이 게임 코드의 기본 요령이다. 반대로 LinkedList<T>는 원소마다 노드 객체를 할당하므로 GC 압박이 크다. 실무에서는 중간 삽입·삭제가 매우 잦고 노드 참조를 이미 들고 있는 경우(LRU 캐시 같은)가 아니면 거의 언제나 List<T>가 낫다.

연결 리스트 뒤집기는 단골 문제다. 참조 세 개로 링크 방향만 돌리면 시간 O(n), 공간 O(1)이다.

public static Node Reverse(Node head)
{
    Node prev = null, curr = head;
    while (curr != null)
    {
        Node next = curr.Next;  // 먼저 보관하지 않으면 뒤쪽을 통째로 잃는다
        curr.Next = prev;
        prev = curr;
        curr = next;
    }
    return prev;  // 원래 꼬리가 새 머리다
}

면접에서 이렇게 답한다

  • 배열과 연결 리스트의 차이 — 배열은 연속 메모리라 인덱스 접근이 O(1)이고 중간 삽입이 O(n)이다. 연결 리스트는 노드를 참조로 잇기 때문에 정반대로, 접근이 O(n)이고 위치를 알면 삽입·삭제가 O(1)이다. 실전에서는 캐시 지역성 때문에 배열이 더 유리하다.
  • List와 LinkedList 중 무엇을 썼나 — 거의 List<T>를 썼다. 순회가 압도적으로 많고 노드 할당이 없어 GC에도 유리하기 때문이다. LinkedList<T>는 노드 참조를 들고 잦은 재배치를 하는 캐시 만료 목록에만 썼다.
  • 동적 배열이 꽉 차면 — 두 배 용량의 새 배열을 잡아 전체를 복사한다. 한 번은 O(n)이지만 분할 상환하면 Add당 O(1)이고, 개수를 알면 생성자에 용량을 넘겨 확장을 피한다.
  • 연결 리스트 뒤집기 — 이전·현재·다음 세 참조를 두고 링크를 하나씩 반대로 돌린다. 다음 노드를 먼저 보관해야 뒤쪽을 잃지 않는다. 시간 O(n), 공간 O(1)이다.

흔한 오해

  • 삽입·삭제는 연결 리스트가 항상 빠르다 — 자리를 찾는 비용 O(n)이 빠진 말이다. 인덱스만 아는 상태라면 배열 쪽이 더 빠른 경우가 많다.
  • 복잡도가 같으니 순회 속도도 같다 — 캐시 미스 때문에 같은 O(n) 순회가 몇 배씩 차이 난다. 이것이 배열을 기본으로 삼는 실질적인 이유다.
  • List<T>.Remove는 싸다 — 찾는 데 O(n), 뒤 원소를 당기는 데 또 O(n)이다. 순서가 중요하지 않다면 마지막 원소와 맞바꾼 뒤 끝을 지우면 O(1)이다.
  • Clear()하면 메모리가 줄어든다 — Count만 0이 되고 내부 배열 용량은 그대로 남는다. 풀링에서는 이 성질이 오히려 이득이다.

스택·큐·우선순위 큐

꺼내는 순서 규칙 하나가 자료구조를 가른다. 후입선출·선입선출·우선순위 순

핵심 개념

스택과 큐는 저장 방식이 아니라 꺼내는 순서 규칙으로 정의된 자료구조다. 스택은 마지막에 넣은 것을 먼저 꺼내고(LIFO), 큐는 먼저 넣은 것을 먼저 꺼낸다(FIFO). 둘 다 가운데 원소를 보는 기능을 일부러 제공하지 않는다. 할 수 있는 일을 줄인 대신 모든 연산이 O(1)이고, 읽는 사람에게 "여기서는 이 순서로만 쓴다"는 의도가 드러난다.

구조꺼내는 순서게임에서 쓰는 곳
스택가장 최근 것UI 팝업 쌓기와 뒤로 가기, 실행 취소, DFS, 호출 스택
큐가장 오래된 것스폰 대기열, 입력·패킷 버퍼, 순차 로딩 작업, BFS 대기열
우선순위 큐우선순위가 가장 높은 것A* 열린 목록, 쿨다운·버프 만료 타이머, 이벤트 스케줄러

C#의 Stack<T>와 Queue<T>는 내부가 배열이다. 특히 Queue<T>는 원형 버퍼라 머리와 꼬리 인덱스를 배열 끝에서 0으로 감아 쓴다. 덕분에 Dequeue가 뒤 원소를 당기는 O(n) 작업이 아니라 머리 인덱스를 한 칸 옮기는 O(1) 작업이 된다. 연결 리스트로 구현해도 O(1)이지만 원소마다 노드를 할당해 GC를 건드리므로 배열 구현이 낫다.

스택 두 개로 큐를 만드는 문제는 "뒤집기를 두 번 하면 원래 순서"라는 성질을 쓴다. 넣기용과 꺼내기용 스택을 두고, 꺼내기용이 비었을 때만 넣기용을 통째로 옮긴다. 원소당 이동이 한 번뿐이라 분할 상환 O(1)이다. 호출할 때마다 옮기면 매번 O(N)이라 이득이 사라진다.

public class QueueByStacks<T>
{
    readonly Stack<T> _in = new Stack<T>();
    readonly Stack<T> _out = new Stack<T>();

    public void Enqueue(T item) => _in.Push(item);

    public T Dequeue()
    {
        if (_out.Count == 0)          // 비었을 때만 통째로 옮긴다
            while (_in.Count > 0)
                _out.Push(_in.Pop());
        return _out.Pop();
    }
}

우선순위 큐는 넣은 순서와 무관하게 우선순위가 가장 높은 것부터 꺼내는 큐다. 정렬된 리스트로 만들면 꺼내기는 O(1)이지만 삽입이 O(N)이라, 보통 이진 힙으로 구현해 최솟값 조회 O(1), 삽입과 최솟값 삭제를 각각 O(log N)으로 맞춘다. .NET 6부터는 PriorityQueue<TElement, TPriority>가 표준으로 들어왔고 내부는 배열 기반 4진 최소 힙이며, 우선순위가 같은 원소끼리는 선입선출을 보장하지 않는다. 다만 Unity 2022 LTS의 API 호환성 수준은 .NET Standard 2.1 또는 .NET Framework라 이 타입이 없으므로, Unity에서는 이진 힙을 직접 쓰거나 패키지를 가져다 쓴다.

면접에서 이렇게 답한다

  • 스택과 큐의 차이와 활용 — 스택은 후입선출, 큐는 선입선출이다. UI 팝업을 쌓았다가 뒤에서부터 닫는 흐름은 스택, 스폰 대기열이나 순차 로딩 작업은 큐로 잡았다. 둘 다 가운데 접근을 막는 대신 모든 연산이 O(1)이다.
  • 스택 두 개로 큐 만들기 — 넣기용과 꺼내기용 스택을 둔다. 꺼내기용이 비었을 때만 넣기용을 전부 옮기면 두 번 뒤집혀 순서가 바로잡히고, 원소당 이동이 한 번이라 분할 상환 O(1)이다.
  • 배열 구현과 연결 리스트 구현의 차이 — 배열은 캐시에 유리하고 노드 할당이 없지만 용량이 차면 재할당이 필요하다. 연결 리스트는 재할당이 없는 대신 원소마다 힙 할당이 생겨 GC를 건드린다. Queue<T>는 원형 버퍼라 배열이면서도 양끝 연산이 O(1)이다.
  • 우선순위 큐란 — 우선순위가 높은 원소부터 꺼내는 큐이고 보통 이진 힙으로 구현해 삽입·삭제가 O(log N)이다. A*의 열린 목록이 대표적이고, .NET 6의 PriorityQueue는 Unity 기본 런타임에 없어 직접 구현했다.

흔한 오해

  • 우선순위 큐를 순회하면 우선순위 순으로 나온다 — 힙은 부모가 자식보다 앞선다는 부분 순서만 지킨다. UnorderedItems라는 이름이 그대로 말해 준다.
  • 우선순위 큐는 정렬된 리스트다 — 그렇게 만들면 삽입이 O(N)이다. 힙은 전체 정렬을 포기하는 대신 삽입을 O(log N)으로 낮춘 구조다.
  • 배열로 만든 큐는 Dequeue가 O(N)이다 — 원형 버퍼로 머리 인덱스만 옮기면 O(1)이다.
  • 스택 두 개 큐는 꺼낼 때마다 옮긴다 — 매번 옮기면 호출마다 O(N)이라 의미가 없다. 꺼내기용이 빌 때만 옮겨야 한다.

해시

키를 숫자로 바꿔 자리를 정한다. 충돌 처리와 로드 팩터가 평균 O(1)을 떠받친다

핵심 개념

해시 테이블은 키에서 저장 위치를 계산으로 바로 얻는 자료구조다. 키를 해시 함수에 넣어 정수를 얻고, 그 값을 버킷 수로 나눈 나머지를 자리로 삼아 저장한다. 찾을 때도 같은 계산을 하므로 비교를 반복하지 않고 한 번에 자리를 찍을 수 있다. 이것이 평균 O(1)의 정체다.

문제는 서로 다른 키가 같은 자리로 가는 충돌이다. 키의 가짓수가 버킷 수보다 많으므로 아무리 좋은 해시 함수를 써도 원리상 없앨 수 없다. 해결은 두 갈래다.

방식동작주의점
체이닝같은 버킷에 목록으로 매단다한 버킷에 몰리면 목록을 훑어 O(n)
개방 주소법빈 칸을 탐사해 들어간다삭제한 자리를 그냥 비우면 뒤로 밀려 들어간 원소를 못 찾는다. 삭제 표시(tombstone)가 필요하다

해시 값이 같아도 키가 같다는 보장은 없으므로 자리를 찾은 뒤 Equals로 최종 확인을 한다. .NET의 Dictionary는 체이닝 계열이지만 버킷마다 노드를 할당하지 않고 엔트리 배열에 다음 인덱스를 들고 잇는 방식이라, 할당과 캐시 면에서 유리하다.

로드 팩터는 원소 수를 버킷 수로 나눈 값이다. 커질수록 한 버킷에 여럿이 몰려 조회가 느려지므로, 기준을 넘으면 버킷을 키우고 원소를 다시 배치한다(리사이즈). 버킷 수가 바뀌면 나머지 값이 달라지므로 원소 위치는 유지되지 않는다. 리사이즈 한 번은 O(N)이지만 드물어 평균 조회는 여전히 O(1)이다. 담을 개수를 알면 new Dictionary<K, V>(capacity)로 잡아 재배치를 없앤다.

좋은 해시 함수의 조건은 셋이다. 고르게 흩뿌릴 것, 계산이 쌀 것, 같은 키에 항상 같은 값을 줄 것. C#에서는 Equals를 재정의하면 GetHashCode도 함께 재정의해야 한다. 규약이 "같은 객체면 같은 해시"이기 때문이다. 구조체를 키로 쓸 때 IEquatable<T>가 없으면 비교마다 박싱이 일어나 매 프레임 할당이 생긴다. 게임 코드에서는 아래가 기본이다.

public readonly struct GridCell : IEquatable<GridCell>
{
    public readonly int X, Y;
    public GridCell(int x, int y) { X = x; Y = y; }
    public bool Equals(GridCell other) => X == other.X && Y == other.Y;
    public override bool Equals(object obj) => obj is GridCell c && Equals(c);
    public override int GetHashCode() => HashCode.Combine(X, Y);
}

주의할 것은 가변 필드를 키에 쓰는 경우다. Dictionary에 넣어 둔 뒤 그 필드를 바꾸면 해시가 달라져 원래 버킷에서 다시 찾지 못한다. 키 타입은 불변이 안전하다.

면접에서 이렇게 답한다

  • 해시 테이블은 어떻게 동작하나 — 키를 해시 함수로 정수로 바꾸고 버킷 수로 나눈 나머지를 자리로 써서 바로 접근한다. 해시가 같아도 키는 다를 수 있어 마지막에 Equals로 확인한다. 평균 O(1), 충돌이 몰리면 최악 O(n)이다.
  • 충돌은 어떻게 해결하나 — 버킷에 목록으로 잇는 체이닝과, 빈 칸을 찾아 들어가는 개방 주소법이 있다. 개방 주소법은 캐시에 유리하지만 삭제할 때 tombstone을 남기지 않으면 탐사가 끊겨 원소를 잃는다.
  • 로드 팩터와 리사이즈 — 원소 수 / 버킷 수이며 기준을 넘으면 버킷을 늘려 재배치한다. 버킷 수가 바뀌어 자리가 달라지므로 O(N)이 들지만 드물어 평균은 O(1)이다.
  • Dictionary와 SortedDictionary — Dictionary는 해시 테이블이라 평균 O(1)이나 순회 순서를 보장하지 않고, SortedDictionary는 트리라 O(log N)이지만 키 순서로 순회할 수 있다.

흔한 오해

  • 해시가 같으면 같은 키다 — 아니다. 반대만 성립한다. 그래서 Equals 비교가 따라붙는다.
  • 좋은 해시 함수를 쓰면 충돌이 없다 — 키 공간이 버킷보다 넓어 원리상 불가능하다. 좋은 함수는 충돌을 없애지 않고 고르게 퍼뜨린다.
  • Dictionary 조회는 언제나 O(1)이다 — 해시가 한쪽에 몰리면 O(n)까지 떨어진다. GetHashCode를 대충 만들면 그렇게 된다.
  • 리사이즈해도 원소 위치는 그대로다 — 버킷 수가 바뀌면 나머지 값이 달라져 전부 다시 배치된다.
  • Dictionary를 순회하면 넣은 순서로 나온다 — 보장되지 않는다. 이 순서에 기댄 저장이나 리플레이는 언젠가 깨진다.

트리와 힙

전체 순서를 지키는 트리와 최솟값만 지키는 힙. 무엇을 포기했는지가 다르다

핵심 개념

이진 탐색 트리(BST)는 왼쪽 < 부모 < 오른쪽 규칙을 모든 노드에서 지키는 트리다. 덕분에 값을 찾을 때 비교마다 한쪽 가지를 통째로 버릴 수 있어, 탐색·삽입·삭제 비용이 트리 높이에 비례한다. 균형이 잡히면 높이가 log N이라 O(log N)이다.

문제는 균형이 저절로 잡히지 않는다는 것이다. 1, 2, 3, 4, 5를 순서대로 넣으면 오른쪽 자식으로만 붙어 높이가 n인 편향 트리가 되고, 사실상 연결 리스트라 모든 연산이 O(n)이다. 정렬된 데이터를 넣는 일은 흔해서 실제 라이브러리는 균형 트리를 쓴다. 레드-블랙 트리는 색 변경과 회전으로 높이를 log N에 묶고, AVL 트리는 좌우 높이 차를 1 이하로 유지해 조회는 빠르지만 회전이 잦다. 그래서 변경이 잦은 범용 컨테이너는 레드-블랙 트리를 쓴다. C#의 SortedDictionary와 SortedSet, C++ std::map이 그 예다. 중위 순회하면 항상 오름차순이 나온다.

힙은 목적이 다르다. 부모가 자식보다 작거나 같다(최소 힙)는 조건만 지키고 형제끼리 순서는 보지 않는다. 전체 정렬을 포기한 대가로 유지가 싸다. 루트가 최솟값이라 조회는 O(1)이고, 삽입은 끝에 붙인 뒤 위로 올리고, 삭제는 루트 자리에 마지막 원소를 올려 내리므로 둘 다 O(log N)이다. 대신 임의 값 찾기는 전체를 훑어 O(N)이다.

힙은 완전 이진 트리(마지막 레벨을 뺀 모든 레벨이 꽉 차고 마지막 레벨은 왼쪽부터 채워진 트리)라 중간에 빈칸이 없다. 덕분에 포인터 없이 배열로 표현한다. 0번부터 채우면 인덱스 i의 자식이 2i+1과 2i+2, 부모가 (i-1)/2다. 참조가 없어 메모리도 적고 연속 배치라 캐시에 잘 맞는다.

// 최소 힙 삽입: 끝에 넣고 부모보다 작으면 위로 올린다
static void Push(List<int> heap, int value)
{
    heap.Add(value);
    int i = heap.Count - 1;
    while (i > 0)
    {
        int parent = (i - 1) / 2;
        if (heap[parent] <= heap[i]) break;
        (heap[i], heap[parent]) = (heap[parent], heap[i]);
        i = parent;
    }
}

Dictionary (해시)평균 O(1)평균 O(1)불가
SortedDictionary (균형 트리)O(log N)O(log N)가능
SortedList (정렬 배열)O(log N)O(N)가능, 인덱스도
이진 힙최솟값만 O(1)O(log N)불가

트라이(Trie)는 문자열을 문자 하나씩 간선으로 쪼개 저장해 접두사를 공유하는 단어를 한 경로에 모은다. 길이 L인 탐색이 단어 수와 무관하게 O(L)이라 자동 완성, 사전 검색, 금칙어 필터에 쓰고 노드마다 자식 목록을 들어 메모리를 많이 먹는다.

면접에서 이렇게 답한다

  • 이진 탐색 트리와 복잡도 — 왼쪽 < 부모 < 오른쪽 규칙 덕에 비교마다 한쪽을 버려 높이에 비례하는 비용이 든다. 균형이면 O(log N), 정렬된 순서로 넣으면 치우쳐 O(n)까지 간다.
  • 균형 트리는 편향을 어떻게 해결하나 — 삽입·삭제 뒤 회전으로 높이를 log N에 묶는다. 레드-블랙은 조건이 느슨해 회전이 적어 변경이 잦은 곳에, AVL은 조회 위주인 곳에 유리하다.
  • 힙의 구조와 삽입·삭제 — 부모가 자식보다 작은 완전 이진 트리다. 삽입은 끝에 넣고 위로 올리고, 삭제는 루트를 빼고 마지막 원소를 올려 내려 둘 다 O(log N)이다. 빈칸이 없어 배열로 저장하고 자식이 2i+1, 2i+2다.
  • 힙과 이진 탐색 트리의 차이 — 힙은 최솟값만 빠르게 주는 부분 순서 구조고, BST는 전체 순서를 유지해 정렬 순회와 범위 질의가 된다.

흔한 오해

  • 힙은 정렬된 구조다 — 부모-자식 관계만 지킨다. 배열을 그대로 출력해도 정렬 순서가 아니다.
  • 이진 탐색 트리는 항상 O(log N)이다 — 균형을 맞추는 트리만 그렇다. 균형 로직이 없으면 정렬 입력에 O(n)이 된다.
  • 힙에서 특정 값 찾기도 O(log N)이다 — 최솟값 경로만 보장되어 임의 탐색은 O(N)이다.
  • 완전 이진 트리는 모든 레벨이 꽉 찬 트리다 — 그건 포화 이진 트리다. 완전 이진 트리는 마지막 레벨만 왼쪽부터 채워지면 된다.
  • 정렬이 필요하면 무조건 SortedDictionary — 삽입이 드물고 순회가 많으면 배열 기반 SortedList가 메모리와 캐시에 낫다.

그래프와 경로 탐색

길찾기는 그래프 탐색이다. BFS·다익스트라·A*의 차이와 유닛이 많을 때 비용 줄이는 법

핵심 개념

게임의 길찾기는 결국 그래프 탐색이다. 격자 맵의 칸, 웨이포인트, NavMesh 폴리곤이 정점이고 "붙어 있어 건너갈 수 있다"가 간선이다. 담는 방법은 둘인데, 인접 행렬은 V×V 칸을 잡아 공간이 O(V²)인 대신 간선 유무를 O(1)에 보고, 인접 리스트는 공간이 O(V + E)에 한 정점의 이웃을 이웃 수만큼만 훑는다. 격자 맵은 칸마다 이웃이 4~8개뿐인 희소 그래프라 리스트 쪽이 맞고, 이웃은 좌표로 즉석에서 계산해 저장조차 하지 않는다.

방법자료구조언제 쓰나
BFS큐가중치가 모두 같을 때의 최단 경로
DFS스택·재귀경로 존재 확인, 사이클 탐지, 위상 정렬
다익스트라우선순위 큐가중치가 다르고 음수가 없을 때. 힙으로 O((V + E) log V)
벨만-포드간선 목록음수 간선이 있을 때. O(VE), 음수 사이클도 판정한다
A*우선순위 큐 + 휴리스틱목표가 정해진 길찾기

A*는 다익스트라에 "목표까지 얼마나 남았나"라는 추정치 h를 더한 것이다. f = g(여기까지 든 실제 비용) + h가 작은 노드부터 펼치므로 목표 반대편을 덜 뒤진다. h가 실제 남은 비용을 넘지 않으면 최단 경로가 보장되고, 실제 값에 가까울수록 펼치는 노드가 준다. h를 0으로 두면 그대로 다익스트라다.

using UnityEngine;

public static class Heuristics
{
    // 4방향만 움직이는 격자: 맨해튼 거리
    public static float Manhattan(Vector2Int a, Vector2Int b)
        => Mathf.Abs(a.x - b.x) + Mathf.Abs(a.y - b.y);

    // 대각선도 허용하는 격자: 옥타일 거리
    // 여기서 맨해튼을 쓰면 실제보다 크게 잡는 과대평가라 최단 보장이 깨진다
    public static float Octile(Vector2Int a, Vector2Int b)
    {
        int dx = Mathf.Abs(a.x - b.x), dy = Mathf.Abs(a.y - b.y);
        return (dx + dy) + (Mathf.Sqrt(2f) - 2f) * Mathf.Min(dx, dy);
    }
}

연결 관계만 보는 문제도 있다. 최소 신장 트리는 모든 정점을 잇는 간선 V-1개의 가중치 합이 가장 작은 트리이고, 크루스칼은 간선을 싼 순서로 보며 사이클이 생기지 않는 것만 고른다. 이때 두 끝 정점이 이미 같은 덩어리인지 판정하는 것이 Union-Find이고, 경로 압축과 union by rank를 함께 쓰면 연산당 거의 상수 시간이다.

Unity에서는 탐색을 직접 짜는 대신 NavMesh를 쓴다. 씬 지오메트리에서 구운 걸어 다닐 수 있는 폴리곤 위에서 A*를 도는 구조다. NavMesh.CalculatePath는 그 자리에서 계산해 돌려주므로 한 프레임에 여러 번 부르면 바로 스파이크가 되고, NavMeshAgent.SetDestination은 요청만 걸고 다음 프레임 이후에 pathPending이 내려간다. 유닛이 수백이면 비용이 유닛 수와 노드 수의 곱으로 늘므로, 요청을 큐에 모아 프레임당 개수를 정하고, 구역 경로를 먼저 푸는 계층적 길찾기(HPA*)를 쓰고, 같은 목적지로 몰리는 무리에는 플로우 필드나 캐시한 경로를 공유한다.

면접에서 이렇게 답한다

  • DFS와 BFS의 차이 — BFS는 큐로 가까운 곳부터 층층이 넓혀 가중치가 모두 같으면 최단을 보장한다. DFS는 스택이나 재귀로 한 갈래를 끝까지 파고들어 최단은 보장하지 않지만 사이클 탐지와 위상 정렬에 쓴다.
  • 다익스트라와 A*를 언제 나눠 쓰나 — 목표가 하나면 A*, 한 지점에서 모든 곳까지의 거리가 필요하면 다익스트라다. A*는 남은 거리 추정치를 더해 탐색을 목표 쪽으로 몰아 준 것이고, 추정치를 0으로 두면 다익스트라와 같아진다.
  • 음수 간선이 있으면 — 다익스트라는 확정한 거리가 다시 줄지 않는다는 전제라 답이 틀어진다. 벨만-포드로 모든 간선을 V-1번 완화해 O(VE)에 풀고, V번째에도 완화되면 음수 사이클로 판정한다.
  • 유닛이 많을 때 비용을 줄이는 법 — 경로 요청을 큐에 모아 프레임마다 나눠 처리하고, 계층적 길찾기와 플로우 필드로 한 번에 푸는 노드 수를 줄인다. 격자 해상도를 낮추는 것이 가장 효과가 크다.

흔한 오해

  • 다익스트라는 어떤 그래프에서도 최단을 준다 — 음수 간선이 있으면 틀린다. 확정한 정점을 다시 보지 않기 때문이다.
  • 가중치에 상수를 더해 음수를 없애면 된다 — 간선 수가 많은 경로가 더 불리해져 최단 경로 자체가 바뀐다.
  • 휴리스틱은 크게 잡을수록 빨라서 좋다 — 빨리 끝나지만 최단 보장이 깨진다.
  • 인접 행렬이 항상 빠르다 — 간선 유무만 O(1)이고, 이웃 순회는 그 행 V칸을 훑어 O(V)다.

정렬과 탐색

정렬마다 최악과 안정성이 다르다. 그 차이와 이진 탐색의 경계 찾기를 정리한다

핵심 개념

비교로만 정렬하면 아무리 잘해도 O(N log N)보다 빠를 수 없다. 그래서 정렬 선택은 속도가 아니라 최악일 때 어떻게 되는지, 추가 메모리를 얼마나 쓰는지, 같은 값의 순서를 지키는지로 갈린다.

정렬평균최악추가 공간안정
퀵O(N log N)O(N²)O(log N)아니다
병합O(N log N)O(N log N)O(N)그렇다
힙O(N log N)O(N log N)O(1)아니다
삽입O(N²)O(N²)O(1)그렇다
계수O(N + K)O(N + K)O(K)그렇다

퀵 정렬은 피벗으로 작은 쪽과 큰 쪽을 나눈 뒤 각각을 다시 정렬한다. 분할이 반씩 되면 재귀 깊이가 log N이지만 매번 한쪽으로 쏠리면 깊이가 N이 되어 O(N²)이다. 이미 정렬된 배열에서 첫 원소를 피벗으로 삼는 소박한 구현이 정확히 그 경우다. 그래서 무작위 피벗이나 세 값의 중간값을 쓰고, 실무 라이브러리는 인트로 정렬(퀵으로 시작해 재귀가 깊어지면 힙, 구간이 작아지면 삽입)로 최악을 막는다. 마지막 단계가 삽입 정렬인 이유는 거의 정렬된 입력에서 삽입 정렬이 O(N)에 수렴하기 때문이다.

안정 정렬은 비교 기준이 같은 원소들의 원래 순서를 지킨다. 랭킹 화면처럼 이름순 목록을 점수순으로 다시 정렬하면서 동점자의 이름순을 지켜야 할 때 필요하다. C#에서 Array.Sort와 List<T>.Sort는 인트로 정렬이라 제자리·불안정이고, LINQ의 OrderBy는 안정이지만 새 시퀀스를 만들어 할당이 생긴다. 매 프레임 도는 코드면 이 할당이 GC 부담이다.

정렬돼 있으면 이진 탐색으로 O(log N)에 찾는다. 2의 20제곱이 약 104만이라 100만 개도 스무 번이면 된다. 면접에서는 값 하나보다 경계를 묻는다. lower bound는 찾는 값 이상인 첫 위치, upper bound는 그 값을 초과하는 첫 위치이고 둘의 차이가 그 값의 개수다. 값이 없어도 끼워 넣을 자리를 돌려주므로 실패 표시가 아니다.

public static class Bounds
{
    // value 이상인 첫 위치. 없으면 끼워 넣을 자리(배열 길이)를 돌려준다
    public static int LowerBound(int[] sorted, int value)
    {
        int lo = 0, hi = sorted.Length;          // [lo, hi) 반열린 구간
        while (lo < hi)
        {
            int mid = lo + (hi - lo) / 2;        // (lo + hi) / 2는 오버플로 위험
            if (sorted[mid] < value) lo = mid + 1;
            else hi = mid;
        }
        return lo;                               // <= 로 바꾸면 upper bound
    }
}

면접에서 이렇게 답한다

  • 퀵 정렬과 최악 — 피벗으로 나눠 재귀로 정렬하고 평균 O(N log N)이다. 분할이 한쪽으로 쏠리면 재귀 깊이가 N이 되어 O(N²)이고, 무작위 피벗이나 세 값의 중간값으로 피한다. 실무 구현은 인트로 정렬로 최악을 O(N log N)에 묶는다.
  • 퀵과 병합 중 무엇을 쓰나 — 메모리에 올라가는 배열이면 제자리로 돌고 캐시 효율이 좋은 퀵 계열을 쓴다. 최악을 보장해야 하거나 안정 정렬이 필요하거나 연결 리스트·외부 정렬이면 O(N) 추가 공간을 쓰더라도 병합을 쓴다.
  • 안정 정렬이 필요한 때 — 여러 기준으로 차례로 정렬할 때다. 점수순으로 다시 정렬해도 동점자의 이름순이 유지돼야 하면 안정 정렬이어야 한다. C#은 List.Sort가 불안정이라 OrderBy를 쓰거나 비교자에 두 번째 기준을 넣는다.
  • lower bound와 upper bound — 각각 값 이상인 첫 위치와 값을 초과하는 첫 위치이고 둘의 차이가 그 값의 개수다. 둘 다 이진 탐색이라 O(log N)이다.

흔한 오해

  • 퀵 정렬은 항상 O(N log N)이다 — 피벗이 쏠리면 O(N²)다. 평균과 최악을 나눠 말한다.
  • List.Sort는 안정 정렬이다 — 불안정이다. 같은 키의 순서가 필요하면 OrderBy를 쓴다.
  • 거의 정렬된 데이터에도 퀵이 낫다 — 삽입 정렬이 O(N)에 수렴하고, 소박한 퀵은 오히려 최악이 된다.
  • lower bound는 값이 없으면 -1을 준다 — 끼워 넣을 자리를 준다. 실제로 있는지는 그 위치의 값을 봐야 안다.

공간 분할

n² 비교를 없애는 구조다. 그리드·쿼드트리·BVH가 각각 언제 유리한지 가른다

핵심 개념

공간 분할은 "내 주변에 무엇이 있나"를 전수 검사 없이 답하기 위한 구조다. 유닛 n개가 서로를 찾으면 비교가 n²번이라 천 개만 돼도 백만 번이다. 공간을 미리 칸이나 상자로 나눠 두면 후보가 주변에 실제로 있는 개수로 줄어든다. 물리의 브로드페이즈와 렌더링의 컬링이 같은 발상이다.

구조유리한 상황약점
균일 그리드고르게 퍼지고 크기가 비슷할 때. 칸 번호가 나눗셈 한 번이라 갱신이 싸다한곳에 몰리면 한 칸에 다 들어가 다시 O(n)이 된다
쿼드트리·옥트리밀도가 들쭉날쭉할 때. 붐비는 칸만 넷(3D는 여덟)으로 더 쪼갠다움직이는 객체는 칸을 넘을 때마다 다시 넣어야 한다
BVH레이·프러스텀 질의. 공간이 아니라 객체를 상자로 묶는다트리를 짓는 비용이 크고, 많이 움직이면 다시 맞춰야 한다

BVH가 레이캐스트에 강한 이유는 건너뛰기다. 물체를 감싸는 경계 상자(AABB)를 계층으로 묶어 두면, 레이가 부모 상자와 만나지 않는 순간 그 안의 자식과 삼각형을 전부 버린다. 그래서 평균 비용이 O(log N) 수준으로 떨어진다.

직접 짜는 것은 대개 균일 그리드다. 셀 크기는 질의 반경과 비슷하게 잡는다.

using System.Collections.Generic;
using UnityEngine;

public class SpatialHash
{
    readonly float _cell;
    readonly Dictionary<Vector2Int, List<Transform>> _cells
        = new Dictionary<Vector2Int, List<Transform>>();

    public SpatialHash(float cellSize) { _cell = cellSize; }

    Vector2Int Key(Vector3 p)
        => new Vector2Int(Mathf.FloorToInt(p.x / _cell), Mathf.FloorToInt(p.z / _cell));

    public void Add(Transform t)
    {
        Vector2Int k = Key(t.position);
        if (!_cells.TryGetValue(k, out List<Transform> list)) _cells[k] = list = new List<Transform>();
        list.Add(t);
    }

    // 결과 리스트를 재사용해 매 프레임 호출해도 할당이 없다
    public void Query(Vector3 center, float radius, List<Transform> result)
    {
        result.Clear();
        Vector2Int c = Key(center);
        int r = Mathf.CeilToInt(radius / _cell);
        float sqr = radius * radius;

        for (int dx = -r; dx <= r; dx++)
            for (int dy = -r; dy <= r; dy++)
                if (_cells.TryGetValue(new Vector2Int(c.x + dx, c.y + dy), out List<Transform> list))
                    foreach (Transform t in list)  // 칸 안에서만 실제 거리 검사
                        if ((t.position - center).sqrMagnitude <= sqr) result.Add(t);
    }
}

Unity 물리도 프로젝트 설정의 브로드페이즈 방식(Sweep and Prune, Multibox Pruning 등)으로 후보를 추린다. 범위 질의는 Physics.OverlapSphereNonAlloc처럼 미리 잡은 배열에 담고 LayerMask로 후보를 좁힌다.

면접에서 이렇게 답한다

  • 주변 유닛을 빠르게 찾으려면 — 전수 비교는 질의마다 O(n), 서로 찾으면 O(n²)이라 공간을 칸으로 나눈다. 반경이 닿는 칸만 검사하면 후보가 주변 밀도에 비례하는 수준으로 준다.
  • 그리드와 쿼드트리 중 무엇을 쓰나 — 고르게 퍼지고 크기가 비슷하면 갱신이 싼 균일 그리드, 한곳에 몰리면 밀도에 맞춰 쪼개는 쿼드트리·옥트리다. 셀 크기를 질의 반경에 맞추는 것이 그리드 성능의 핵심이다.
  • BVH가 레이 판정을 빠르게 하는 원리 — 물체를 감싼 AABB를 계층으로 묶고, 레이가 부모 상자와 만나지 않으면 그 아래 전체를 건너뛴다.

흔한 오해

  • ID나 이름으로 정렬해 두면 주변 검색도 빨라진다 — 기준이 위치가 아니면 위치 질의에 쓸 수 없다.
  • BVH는 레이가 지나는 모든 삼각형을 검사한다 — 상자에 안 맞은 가지는 통째로 버린다.
  • 공간 분할을 하면 정밀 검사가 필요 없다 — 후보를 줄일 뿐이라 칸 안에서는 실제 거리로 다시 검사한다.

풀이 기법

재귀·DP·그리디·비트 연산은 각각 언제 성립하는지가 핵심이다. 조건과 반례로 외운다

핵심 개념

풀이 기법 질문은 "무엇인가"보다 언제 성립하는가를 본다.

재귀는 호출할 때마다 매개변수·지역 변수·복귀 주소가 스택 프레임으로 쌓인다. 깊이가 곧 메모리라 깊어지면 스택 오버플로가 난다. 재귀 호출이 함수의 마지막 동작이면(꼬리 호출) 돌아와서 할 일이 없으니 프레임을 재사용할 수 있는데, return n * Fact(n - 1);처럼 결과에 무언가를 더 하면 꼬리 호출이 아니다. C#과 .NET JIT은 이 최적화를 보장하지 않으므로 깊은 재귀는 반복문이나 Stack<T>로 바꾸는 편이 안전하다.

동적 계획법은 두 조건이 모두 맞을 때만 쓴다. 같은 부분 문제가 여러 번 나오고(겹치는 부분 문제), 부분 문제의 최적해로 전체 최적해를 만들 수 있어야(최적 부분 구조) 한다. 메모이제이션은 시간을 공간과 맞바꾸는 것이다. 부분 문제가 겹치지 않으면 저장할 이유가 없고 그냥 분할 정복(나누고, 풀고, 합친다)이다.

그리디는 지금의 최선이 전체 최선으로 이어질 때만 옳다. 동전이 1원·3원·4원뿐일 때 6원을 큰 것부터 집으면 4+1+1로 세 개지만 3+3이면 두 개다. 큰 단위가 작은 단위의 배수로 떨어지면 그리디가 최적해와 일치한다.

비트 연산은 켜기 x | (1 << n), 끄기 x & ~(1 << n), 뒤집기 x ^ (1 << n), 확인 (x >> n) & 1이 한 묶음이다. 시프트가 2의 거듭제곱 곱셈을 대신하므로 8을 곱하려면 x << 3이다. 단 int의 시프트 횟수는 하위 5비트만 쓰여 x << 32는 제자리이고, 음수의 >>는 부호 비트를 채운다.

using UnityEngine;

public static class MaskExample
{
    // 비트 켜기·끄기·확인. Unity의 LayerMask가 이 규칙을 그대로 쓴다
    public static int Build()
    {
        int enemy = LayerMask.NameToLayer("Enemy");
        int water = LayerMask.NameToLayer("Water");

        int mask = 0;
        mask |= 1 << enemy;                      // 켜기
        mask |= 1 << water;
        mask &= ~(1 << water);                   // 끄기
        mask ^= 1 << water;                      // 뒤집기

        bool hasEnemy = ((mask >> enemy) & 1) == 1;   // 확인
        Debug.Log(hasEnemy);
        return mask;
    }
}

LRU 캐시는 조회와 갱신을 모두 O(1)로 만드는 게 핵심이다. 해시 맵만 쓰면 버릴 항목을 찾는 데, 리스트만 쓰면 키로 노드를 찾는 데 O(N)이 남는다. 둘을 겹쳐야 양쪽이 O(1)이 된다. C#이면 Dictionary<TKey, LinkedListNode<TKey>>로 노드를 찾고, LinkedList<TKey>로 최근 사용 순서를 유지해 앞으로 옮기거나 꼬리를 버리는 일을 링크 교체로 끝낸다. 텍스처·에셋 캐시가 이 구조다.

면접에서 이렇게 답한다

  • 재귀는 콜 스택에서 어떻게 도나 — 호출마다 매개변수·지역 변수·복귀 주소가 프레임으로 쌓이고 반환하며 걷힌다. 깊이가 곧 메모리라 한계를 넘으면 스택 오버플로다. 꼬리 호출은 프레임 재사용이 가능하지만 C#은 보장하지 않는다.
  • 동적 계획법의 적용 조건 — 겹치는 부분 문제와 최적 부분 구조 두 가지다. 같은 계산이 반복되지 않으면 저장할 이유가 없고, 부분 최적해로 전체 최적해가 안 만들어지면 표를 채워도 답이 아니다.
  • 그리디와 DP를 어떻게 가르나 — 반례를 찾아본다. 1·3·4원으로 6원을 만들 때 그리디는 세 개, 최적은 두 개라 깨진다. 반례가 없다고 볼 근거가 서면 그리디, 아니면 DP다.
  • LRU 캐시 구현 — 해시 맵과 이중 연결 리스트를 함께 쓴다. 맵으로 키에서 노드를 O(1)에 찾고, 리스트로 최근 사용 순서를 유지해 링크 교체만으로 앞으로 옮기거나 꼬리를 버린다.

흔한 오해

  • C#도 꼬리 재귀를 최적화해 준다 — IL에 꼬리 호출 명령은 있지만 JIT이 적용한다는 보장은 없다.
  • 호출 결과를 곱해 반환해도 꼬리 호출이다 — 돌아와서 할 일이 남아 프레임을 재사용할 수 없다.
  • 메모이제이션은 공짜다 — 시간을 줄이는 대신 표만큼 공간을 쓴다. 상태가 많으면 메모리가 먼저 터진다.
  • Dictionary만으로 LRU를 O(1)에 만들 수 있다 — 버릴 항목을 찾는 순서 정보가 없어 O(N)이 남는다.

코딩 테스트와 실기 유형

라이브 코딩·코드 리뷰 과제에서 보는 것은 정답이 아니라 푸는 과정과 예외 처리다

핵심 개념

실기는 세 가지로 나온다. 화면을 공유하며 기본 개념을 변형한 문제를 푸는 라이브 코딩, 제출한 풀이를 두고 "왜 이렇게 풀었나, 더 줄일 곳은 없나"를 묻는 풀이 리뷰, 일부러 버그를 심은 코드에서 문제를 찾는 코드 리뷰 과제다. 셋 다 최종 답보다 과정을 본다.

그래서 순서를 고정해 두면 흔들리지 않는다. 입력 크기와 값의 범위를 먼저 되묻고(N이 10만인지 10억인지에 따라 답이 달라진다), 빈 배열·원소 하나·중복·음수·오버플로 같은 예외 케이스를 입으로 짚고, 무식한 풀이를 복잡도와 함께 말한 뒤 개선안을 제안하고, 합의된 다음에 짠다. 다 짠 뒤에는 작은 입력을 손으로 돌려 본다. 말없이 10분 코딩하는 것이 가장 나쁜 답이다.

단골 문제는 정해져 있고 대부분 한 번만 훑고 추가 공간을 쓰지 않는 풀이를 기대한다. 1부터 N 중 빠진 수는 N * (N + 1) / 2에서 배열의 합을 빼면 되지만 N이 크면 합이 오버플로하므로 XOR이 더 안전하다. 중복 찾기는 HashSet<T> 한 번 훑기, 문자열 뒤집기는 양 끝에서 좁혀 오는 맞바꾸기, 행렬 90도 회전은 전치 뒤 각 행 뒤집기다. 라이브러리 없이 문자열을 정수로 바꾸는 문제는 부호·공백·잘못된 문자·오버플로를 어디까지 처리하는지가 평가 대상이고, 실무라면 int.TryParse로 실패를 값으로 받는다고 덧붙이면 좋다.

public static class Puzzles
{
    // 1..n 중 하나가 빠진 배열에서 빠진 수. 합 공식과 달리 오버플로가 없다
    public static int Missing(int[] a, int n)
    {
        int x = 0;
        for (int i = 1; i <= n; i++) x ^= i;
        foreach (int v in a) x ^= v;           // 짝지어 상쇄되고 빠진 수만 남는다
        return x;
    }

    // N×N 행렬을 제자리에서 시계 방향 90도 회전. 시간 O(N²), 공간 O(1)
    public static void RotateClockwise(int[,] m)
    {
        int n = m.GetLength(0);
        for (int i = 0; i < n; i++)            // 전치: [i, j]와 [j, i]를 맞바꾼다
            for (int j = i + 1; j < n; j++)
                (m[i, j], m[j, i]) = (m[j, i], m[i, j]);

        for (int i = 0; i < n; i++)            // 각 행을 좌우로 뒤집는다
            for (int j = 0; j < n / 2; j++)
                (m[i, j], m[i, n - 1 - j]) = (m[i, n - 1 - j], m[i, j]);
    }
}

코드 리뷰 과제에 심는 버그도 목록이 짧다. 배열 한 칸 초과(i <= n), 대입과 비교 혼동, null 접근, 초기화하지 않은 변수, 해제하지 않는 자원이다. C#은 if (x = 5)가 컴파일 오류지만 bool 변수라면 if (isReady = true)가 그대로 통과한다. 클라이언트 면접이면 이벤트를 구독만 하고 해제하지 않아 객체가 살아남는 누수를 짚으면 가산점이 된다.

면접에서 이렇게 답한다

  • 문제를 받으면 무엇부터 하나 — 입력 크기와 값의 범위를 먼저 확인한다. N에 따라 O(N²)이 되는지가 갈리기 때문이다. 그다음 예외 케이스를 짚고, 무식한 풀이를 복잡도와 함께 말한 뒤 개선안을 제안하고 합의되면 짠다.
  • 빠진 수 하나 찾기 — 1부터 N까지의 합에서 배열의 합을 빼면 O(N) 시간, O(1) 공간에 끝난다. 합이 오버플로할 것 같으면 1부터 N까지와 배열 원소를 모두 XOR해 같은 값을 얻는다.
  • 행렬 90도 회전 — 전치한 뒤 각 행을 좌우로 뒤집으면 시계 방향, 전치 뒤 행 순서를 뒤집으면 반시계 방향이다. 맞바꾸기만 하므로 추가 배열 없이 O(N²)에 된다.
  • 이 코드의 문제는 — 경계부터 본다. 조건이 i <= n이면 마지막에 arr[n]을 읽는다. C#은 IndexOutOfRangeException으로 바로 티가 나지만 C/C++라면 조용히 엉뚱한 메모리를 읽어 더 찾기 어렵다.

흔한 오해

  • 답이 맞으면 통과다 — 복잡도와 예외 케이스를 스스로 말하지 않으면 감점이다. 과정이 평가 대상이다.
  • 유효한 인덱스는 0부터 n까지다 — n - 1까지다. 한 칸 초과가 가장 흔한 버그다.
  • 합 공식은 언제나 안전하다 — N이 크면 합이 int 범위를 넘는다. long으로 올리거나 XOR을 쓴다.
  • 전치만 하면 회전이 된다 — 전치는 대각선 대칭일 뿐이라 행을 뒤집어야 회전이 된다.
  • 막히면 조용히 생각하는 게 낫다 — 화면에 아무것도 없으면 판단할 근거가 없다. 막힌 지점을 말하면 힌트가 나온다.
