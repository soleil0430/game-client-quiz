게임 시스템 설계

클래스보다 제약을 먼저 묻고, 나중에 바뀌어도 안 깨질 구조를 고른다

"인벤토리를 설계해 보라"는 질문에 클래스부터 그리면 절반은 틀린 답이 된다. 칸이 고정인지, 같은 아이템이 겹쳐 쌓이는지에 따라 자료구조가 통째로 달라지기 때문이다.

시스템 설계 질문은 정답을 맞히는 문제가 아니다. 무엇을 먼저 물어보는지를 보는 문제다.

자료구조를 정하는 것은 다섯 가지 제약이다

인벤토리를 들으면 아래를 먼저 확인한다. 답이 나오면 구조는 거의 따라 나온다.

  • 칸 수가 정해져 있나 — 고정이면 배열, 무제한이면 리스트
  • 같은 아이템이 겹쳐 쌓이나 — 쌓이면 수량 필드가 필요하다
  • 아이디로 찾는 일이 잦나 — 잦으면 딕셔너리를 함께 둔다
  • 수십 개인가 수만 개인가 — 정렬·필터 비용이 여기서 갈린다
  • 서버가 최종 권한을 갖나 — 가지면 결과가 아니라 행동을 보낸다

데이터와 표시도 나눈다. 아이템 목록이 바뀌면 UI는 전체가 아니라 바뀐 칸만 갱신하게 둔다.

버프는 빼지 말고 목록으로 들고 합산한다

붙을 때 최종 수치에 더하고 풀릴 때 빼는 방식은, 곱연산이나 상한이 섞이는 순간 원래 값으로 안 돌아온다. 수치가 조금씩 새는 대표적인 함정이다.

보정을 목록으로 들고 있으면 푸는 순서가 달라도 결과가 같고, 어떤 버프가 붙었는지 출처도 남는다.

기본값과 보정 목록을 나눠 두고 읽을 때 합산하는 코드다:

public struct StatModifier { public float Add; public float Mul; }  // Mul 0.2f = +20%

public class Stats
{
    public float BaseAttack = 10f;    // 기본값은 절대 건드리지 않는다
    private readonly List<StatModifier> mods = new List<StatModifier>();

    public void Add(StatModifier m) => mods.Add(m);        // 붙을 때 목록에 넣고
    public void Remove(StatModifier m) => mods.Remove(m);  // 풀릴 때 목록에서 뺀다

    public float Attack()                    // 읽을 때 목록을 처음부터 합산한다
    {
        float add = 0f, mul = 1f;
        foreach (var m in mods) { add += m.Add; mul += m.Mul; }
        return (BaseAttack + add) * mul;     // 더하기 먼저, 곱하기 나중
    }
}

합산이 부담되면 결과를 캐시하고, 목록이 바뀔 때만 더티 플래그를 세워 다시 계산한다.

세이브는 저장 항목이 바뀐다는 전제로 짠다

파일에 스키마 버전을 넣고, 읽을 때 버전에 맞춰 변환해 올린다. 그러면 기존 진행을 지키면서 구조를 바꿀 수 있다. 빠진 항목은 실패시키지 말고 기본값으로 채운다.

저장 위치맞는 용도주의
PlayerPrefs설정값처럼 작고 잃어도 되는 것평문이라 변조가 쉽다
파일(JSON 등)진행도 전체버전 필드, 저장 중 종료 대비(임시 파일에 쓴 뒤 교체)
서버재화처럼 검증이 필요한 것결과가 아니라 행동을 보내고 서버가 계산한다

시드가 같으면 같은 맵이 나오게 만든다

절차적 생성의 기본은 같은 시드와 같은 규칙이면 항상 같은 결과다. 그러면 맵 전체 대신 시드 하나만 저장해도 복원된다.

청크마다 좌표에서 시드를 파생시키면, 멀리 있는 지형을 버렸다 다시 만들어도 같은 모습이 나온다.

면접에서 이렇게 답한다

  • 인벤토리를 설계하라 — 칸 제한과 스택 여부, 최대 아이템 수, 서버 검증 여부를 먼저 묻고 자료구조를 고른다. 그다음 데이터와 표시를 나눠 바뀐 칸만 갱신하게 했다고 말한다.
  • 버프와 장비로 스탯이 계속 바뀐다면 — 기본값은 그대로 두고 보정 목록을 합산해 최종값을 낸다. 순서에 무관하고 출처 추적이 되며, 캐시와 더티 플래그로 성능도 해결된다.
  • 세이브·로드 설계 — 포맷에 버전을 넣고 변환 단계를 둔다. 빠진 항목은 기본값, 저장 중 종료에 대비해 임시 파일에 쓴 뒤 교체, 중요한 값은 서버 검증이다.
  • 나중에 서버를 붙인다면 — 규칙 계산을 UI와 분리해 순수 함수에 가깝게 두고, 저장·조회를 인터페이스 하나로 감싼다. 시간도 기기 시계 대신 서버 시간을 받게 통로를 모은다.
  • 업적·퀘스트 시스템 — 조건을 코드가 아니라 데이터로 두고, 게임 쪽은 "적 처치" 같은 사건만 던진다. 진행 시스템이 그 사건으로 조건을 갱신하면 새 업적이 데이터 추가만으로 는다.

이런 오해를 한다

  • 버프는 붙을 때 더하고 풀릴 때 빼면 된다 — 곱연산이나 상한이 섞이면 원래 값으로 안 돌아온다. 수치가 새는 대표적 함정이다.
  • 세이브는 메모리 덤프가 빠르고 간단하다 — 필드가 하나만 늘거나 순서가 바뀌어도 기존 파일이 전부 깨진다. 버전을 가진 명시적 포맷을 쓴다.
  • 절차적 맵은 시스템 시간을 시드로 쓰면 된다 — 같은 맵을 두 번 만들 수 없다. 복원과 버그 재현이 불가능해진다.
  • 로컬 저장을 서버로 그대로 옮기면 된다 — 결과만 저장하던 구조는 서버가 검증할 근거가 없다. 계획이 있으면 처음부터 행동을 기록한다.

3줄 정리

  • 클래스보다 제약을 먼저 묻는다. 구조는 따라 나온다.
  • 스탯은 기본값과 보정 목록을 나눠 두고 합산한다.
  • 세이브는 버전, 절차적 생성은 시드로 재현한다.
