모바일 GPU와 그래픽스 API

타일 기반 GPU는 대역폭을 아끼는 대신 그린 화면을 되읽는 것을 싫어한다

데스크톱에서 멀쩡하던 후처리가 폰에서 프레임을 깎아 먹는 일이 있다. 모바일 GPU는 화면을 타일로 쪼개 칩 안에서 그리기 때문이다. 이 구조를 모르면 무엇이 왜 비싼지 설명이 안 된다.

모바일의 한계는 연산이 아니라 대역폭이다

모바일 기기에서 진짜 한계는 연산 능력이 아니다. 메모리 대역폭과 전력이다. 칩 바깥의 메인 메모리를 한 번 오가는 비용이 산술 연산 수십 번보다 비싸다.

그 비용은 그대로 발열과 배터리로 돌아온다. 발열이 오르면 기기가 클럭을 낮춰 프레임이 또 떨어진다. 모바일 GPU가 타일 기반 구조를 쓰는 이유가 여기 있다.

타일 기반은 모았다가 타일 하나씩 그린다

데스크톱의 즉시 모드 GPU는 드로우 콜이 들어오면 곧바로 메인 메모리의 프레임버퍼에 그린다. 타일 기반 GPU는 먼저 한 프레임의 지오메트리를 모두 받는다. 화면 타일마다 어떤 삼각형이 걸치는지 목록을 만든다.

그다음 타일 하나씩 칩 안의 빠른 메모리에서 색과 깊이를 처리한다. 끝난 타일의 결과만 메인 메모리에 쓴다. 깊이 버퍼와 MSAA 샘플은 타일 안에서 소비하고 버리므로 대역폭을 크게 아낀다.

주제 즉시 모드(데스크톱) 타일 기반(모바일)
그리는 시점 드로우 콜이 오면 바로 지오메트리를 모은 뒤 타일 단위로
MSAA 메모리 대역폭 부담이 크다 타일 안에서 해소해 상대적으로 싸다
렌더 타깃 전환 비교적 가볍다 타일을 내보냈다 들여오는 비용이 붙는다
불리한 것 오버드로, 대역폭 디퍼드 G-버퍼, 풀스크린 블릿, 그랩 패스

되읽기와 렌더 타깃 전환이 비싸진다

이 구조에서 실무 규칙 네 개가 나온다. 첫째, 렌더 타깃을 중간에 바꾸거나 그린 결과를 셰이더에서 되읽으면 손해다. 타일을 메인 메모리로 내보냈다가 다시 들여와야 한다.

포스트 프로세싱, 카메라 스택, URP의 Opaque Texture, Built-in의 GrabPass가 모두 여기 걸린다.

둘째, 디퍼드가 불리한 것도 같은 이유다. G-버퍼 여러 장을 쓰고 다시 읽는 왕복이 타일 메모리에 담기 힘들다.

셋째, 프레임 시작에 화면을 제대로 클리어하는 편이 낫다. 클리어하지 않으면 GPU가 이전 내용을 타일로 불러와야 해서 오히려 비싸진다. 넷째, 알파 테스트는 조기 깊이 판정을 무효화하므로 나뭇잎처럼 꼭 필요한 곳에만 쓴다.

저수준 API는 CPU 쪽만 빨라진다

그래픽스 API 쪽도 같은 오버헤드 이야기다. OpenGL ES와 DX11은 상태 검증·동기화·메모리 관리를 드라이버가 알아서 해 줬다. 그 대가로 드로우 콜마다 CPU 비용이 붙고 렌더 명령을 한 스레드에서만 만들 수 있었다.

Vulkan·DX12·Metal은 그 일을 앱이 직접 맡는 저수준 API다. 드라이버 오버헤드가 줄고 커맨드 버퍼를 여러 스레드에서 병렬로 기록할 수 있다. 드로우 콜이 많아 CPU가 병목인 씬에서 이득이 크다.

반대로 GPU가 병목이면 API를 바꿔도 프레임은 그대로다. Unity에서는 Player Settings의 Graphics APIs 목록에서 고른다. 안드로이드는 기기 편차가 커서 Vulkan을 앞에 두되 OpenGL ES 3을 폴백으로 남기는 구성이 흔하다.

면접에서 이렇게 답한다

  • 모바일 GPU와 데스크톱 GPU의 차이 — 모바일은 대역폭과 전력이 한계라 화면을 타일로 쪼개 칩 안 메모리에서 그리고 끝난 타일만 내보낸다. 그래서 MSAA는 상대적으로 싸다. 렌더 타깃을 바꾸거나 그린 결과를 되읽는 동작이 비싸다.
  • 그래서 무엇을 피하나 — 불필요한 풀스크린 패스, 카메라 스택 남발, 그랩 패스, 모바일 디퍼드를 줄인다. 프레임 시작 클리어는 생략하지 않고, 알파 테스트는 꼭 필요한 머티리얼에만 쓴다.
  • Vulkan과 OpenGL ES 3 중 무엇을 쓰나 — 드로우 콜이 많아 CPU가 병목이면 Vulkan이 유리하다. 다만 안드로이드는 드라이버 편차가 있어 대상 기기에서 실제로 재 보고 정한다. 목록에 ES 3을 폴백으로 남겨 둔다.
  • 저수준 API가 빠른 이유 — 드라이버가 하던 검증과 동기화를 앱이 맡아 드로우 콜당 CPU 비용이 준다. 커맨드 버퍼를 여러 스레드에서 미리 기록할 수도 있다. GPU 병목에는 도움이 되지 않는다는 점을 같이 말한다.

이런 오해를 한다

  • 타일 기반은 드로우 콜이 오면 바로 그린다 — 지오메트리를 먼저 모아 타일별 목록을 만든 뒤 타일 단위로 그린다. 바로 그리는 쪽이 즉시 모드다.
  • 모바일에서는 MSAA가 무조건 비싸다 — 타일 안에서 해소되므로 상대적으로 싸다. 오히려 비싼 것은 풀스크린 후처리 계열이다.
  • Vulkan으로 바꾸면 프레임이 오른다 — CPU 드라이버 오버헤드가 병목일 때만 오른다. 픽셀 채우기나 셰이더가 병목이면 변화가 없다.
  • 저수준 API는 GPU 연산이 더 빠르다 — GPU가 하는 계산은 같다. 달라지는 것은 명령을 준비하는 CPU 쪽이다.
  • 화면을 클리어하지 않으면 그만큼 아낀다 — 타일 기반에서는 이전 프레임 내용을 타일로 불러와야 해서 오히려 손해다.

3줄 정리

  • 모바일의 한계는 연산이 아니라 대역폭과 전력
  • 타일 기반은 모아서 비닝한 뒤 타일 단위로 그린다
  • 저수준 API가 줄이는 것은 CPU 쪽 준비 비용뿐
