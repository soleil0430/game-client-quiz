네트워크

TCP와 UDP

TCP가 튀는 이유는 회선이 아니라 빠진 조각을 기다리기 때문이다

캐릭터 위치를 TCP로 보내면 패킷 하나만 잃어도 화면이 잠깐 멈춘다. 이미 도착한 뒷값까지 빠진 조각을 기다리기 때문이다. 어느 데이터에 무엇을 쓸지는 이 기다림을 아는 데서 갈린다.

TCP가 느려지는 건 회선이 아니라 기다림 때문

TCP는 바이트마다 순서 번호를 붙이고 ACK로 도착을 확인한다. 확인이 없으면 재전송하고 순서까지 맞춰 올린다. 그래서 중간 한 조각이 빠지면 뒤 데이터가 응용까지 못 올라간다.

이 멈춤이 head-of-line blocking이다. UDP에는 그 장치가 전부 없어 지나간 값을 기다리지 않는다. 주소만 적어 던지고 도착 여부도 순서도 책임지지 않는다.

그래서 고르는 기준은 하나로 줄어든다. 늦게 도착한 그 값이 아직 쓸모가 있는가다. 다음 값이 곧 오는 데이터라면 기다리는 쪽이 손해다.

연결을 세 번 주고받아야 여는 이유

양쪽이 각자의 초기 순서 번호를 보내고 도착을 확인받아야 한다. 두 번이면 서버는 자기 번호가 닿았는지 모른다. 그래서 SYN, SYN+ACK, ACK로 세 번이 필요하다.

종료가 네 번인 것도 같은 이유다. 한쪽이 FIN을 보내도 반대 방향은 아직 열려 있다. 먼저 닫은 쪽은 늦게 오는 패킷에 대비해 TIME_WAIT으로 머문다.

비정상 종료에는 FIN이 오지 않는다. 그래서 몇 초 주기로 하트비트를 주고받아 끊김을 판단한다. TCP keep-alive는 기본 주기가 분 단위라 게임에는 느리다.

무엇을 UDP로, 무엇을 TCP로 보내나

게임 데이터고르는 쪽이유
캐릭터 위치·입력(초당 20~60회)UDP다음 값이 곧 오므로 기다림이 손해다
스킬 확정, 아이템 획득, 채팅UDP 신뢰 채널·TCP놓치면 다음 패킷이 대신하지 못한다
로그인·결제·랭킹 조회TCP(HTTPS)유실이 안 되고 빈도가 낮다

실시간 게임은 UDP를 깔고 필요한 만큼만 신뢰성을 얹는다. 중요한 메시지에만 시퀀스 번호와 ACK를 붙이고 제때 없으면 재전송한다. 모든 패킷에 이 규칙을 걸면 TCP를 다시 만든 꼴이다.

TCP를 쓴다면 네이글은 끈다

네이글은 앞 데이터의 ACK를 기다리며 작은 데이터를 모아 보낸다. 패킷 수는 줄지만 입력이 수십 ms 늦게 나간다. 그래서 실시간 연결에서는 이 모으기를 꺼 둔다.

게임용 TCP 연결에서 네이글만 끄는 코드다:

using System.Net.Sockets;

public static TcpClient ConnectForGame(string host, int port)
{
    var client = new TcpClient();
    client.Connect(host, port);
    client.NoDelay = true;   // 작은 입력 패킷을 모으지 않고 바로 내보낸다
    return client;           // 재전송과 순서 보장은 그대로 남는다
}

패킷 크기는 MTU에 맞춘다. MTU는 한 번에 보낼 수 있는 상한이고 이더넷은 보통 1500바이트다. 넘으면 조각으로 나뉘는데, UDP는 조각 하나만 잃어도 원래 패킷 전체를 못 쓴다.

면접에서 이렇게 답한다

  • TCP와 UDP의 선택 기준 — TCP는 순서와 재전송을 보장하느라 손실이 나면 뒤 데이터가 밀린다. 최신 값만 의미 있는 위치와 입력은 UDP로, 유실이 안 되는 거래는 TCP로 나눈다.
  • 3-way handshake가 두 번으로 안 되는 이유 — 양쪽이 각자의 초기 순서 번호를 알리고 그것이 닿았음을 확인해야 한다. 두 번이면 서버는 자기 번호의 도착을 확인할 수 없다.
  • 4-way handshake와 TIME_WAIT — FIN과 ACK를 양방향으로 주고받아 네 번 오간다. 먼저 닫은 쪽이 TIME_WAIT으로 머물므로, 서버에 쌓이면 서버가 먼저 끊는 구조인지 본다.
  • 흐름 제어와 혼잡 제어 — 흐름 제어는 수신자 버퍼에, 혼잡 제어는 중간 네트워크 상태에 맞춘다. 실제 전송량은 두 윈도 중 작은 쪽으로 정해진다.
  • 상대가 갑자기 꺼진 것을 아는 법 — 비정상 종료에는 FIN이 오지 않아 다음 송신 전까지 모른다. 응용에서 하트비트를 주고받고 연속 실패 횟수로 판단한다.

이런 오해를 한다

  • UDP는 언제나 TCP보다 빠르다 — 손실이 없으면 큰 차이가 없다. 이점은 잃은 패킷을 기다리지 않는 것이지 회선 속도가 아니다.
  • NoDelay를 켜면 신뢰성이 사라진다 — 꺼지는 것은 작은 패킷 모아 보내기뿐이다. 재전송과 순서 보장은 그대로 동작한다.
  • TIME_WAIT은 서버에 생긴다 — 먼저 close한 쪽에 생긴다. 서버에 쌓였다면 서버가 먼저 끊고 있다는 신호다.
  • Connected 속성으로 연결 상태를 안다 — 마지막 통신 시점의 값이라 현재를 보장하지 않는다. 지금 살아 있는지는 하트비트로만 안다.

3줄 정리

  • TCP의 지연은 빠진 조각을 기다려서 생긴다
  • 위치는 UDP, 거래와 인증은 TCP로 나눈다
  • 실시간 TCP 연결은 네이글을 꺼 둔다
