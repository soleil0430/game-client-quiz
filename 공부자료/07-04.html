자료구조·알고리즘

해시

키를 숫자로 바꿔 자리를 정한다. 충돌 처리와 로드 팩터가 평균 O(1)을 떠받친다

유닛 1만 개에서 ID로 하나를 찾는다고 하자. 목록을 처음부터 훑으면 평균 5천 번을 비교한다. 해시 테이블은 비교를 한 번도 하지 않고 자리를 계산해 찍는다.

비교하는 대신 자리를 계산한다

해시 테이블은 키를 해시 함수로 버킷 위치로 바꿔 평균 O(1)에 넣고 찾는 구조다. 키를 해시 함수에 넣어 정수를 얻고, 그 값을 버킷 수로 나눈 나머지가 자리다.

찾을 때도 같은 계산을 하니 같은 자리가 나온다. 평균 O(1)의 정체는 이 계산 한 번이다.

충돌은 없앨 수 없고 처리하는 것이다

서로 다른 키가 같은 위치로 가는 일을 충돌이라 한다. 키 공간이 버킷 수보다 넓으므로 아무리 좋은 해시 함수를 써도 원리상 피할 수 없어서, 없애는 대신 처리한다.

해시 값이 같아도 키가 같다는 보장은 없다. 자리를 찾은 뒤 Equals로 최종 비교를 한 번 더 하는 이유다. 해시는 후보를 좁힐 뿐이다.

몰린 키를 어디에 두느냐에서 방식이 두 갈래로 갈린다.

방식 동작 주의점
체이닝 같은 버킷에 목록으로 매단다 한 버킷에 몰리면 훑어서 O(n)
개방 주소법 빈 칸을 탐사해 들어간다 삭제 자리를 그냥 비우면 뒤에 밀려 들어간 원소를 잃는다

체이닝은 같은 버킷에 연결 리스트로 원소를 매단다. 버킷마다 리스트를 하나 매달아 충돌한 것끼리 잇고, 찾을 때는 그 리스트만 훑는다.

개방 주소법은 비어 있는 다른 칸을 찾아 들어간다. 다음 칸부터 차례로 보는 선형 탐사, 간격을 제곱으로 벌리는 이차 탐사, 두 번째 해시 함수로 간격을 정하는 이중 해싱이 있다.

개방 주소법에서 삭제한 자리를 그냥 비우면 뒤에 탐사로 밀려 들어간 원소를 못 찾으므로, 지웠다는 표시(tombstone)를 남겨야 한다. 충돌을 체이닝 등으로 처리하고 나면 평균은 O(1)이지만, 한 버킷에 죄다 몰린 최악은 O(n)이다.

.NET의 Dictionary는 체이닝 계열이다. 다만 버킷마다 노드를 할당하지 않고 엔트리 배열에 다음 인덱스를 적어 잇는다. 할당과 캐시 양쪽을 챙긴 절충이다.

로드 팩터가 넘으면 전부 다시 배치한다

로드 팩터는 원소 수를 버킷 수로 나눈 값이고, 원소 수 대비 버킷 수가 모자랄수록 커진다. 한 버킷에 여럿이 몰리면 조회가 느려지므로, 충돌이 늘어난 시점에 리사이즈한다. 기준은 대개 0.7~1.0이다.

기준을 넘으면 버킷 배열을 늘려 키운 뒤 모든 원소를 새 버킷으로 다시 넣는다. 버킷 수가 바뀌면 나머지 값이 달라져 인덱스가 바뀌므로 원소 위치가 유지되지 않는다.

리사이즈는 O(N)이지만 드물게 일어나 평균 조회는 여전히 O(1)이며, 담을 개수를 미리 알면 new Dictionary<K, V>(capacity)로 잡아 리사이즈를 피한다.

어떤 타입이 키로 적합한가

좋은 해시 함수는 값을 버킷에 고르게 흩뿌리고, 계산이 빠르고, 같은 키에는 언제나 같은 값을 준다. 키가 조금만 달라도 값이 고르게 흩어져야 하고, 비슷한 키가 비슷한 값으로 몰리면 특정 버킷에 충돌이 쌓여 조회가 O(N)으로 떨어진다.

C#에서는 Equals를 재정의하면 GetHashCode도 함께 재정의해야 한다. 둘이 어긋나면 같다고 판정되는 두 키가 서로 다른 버킷에 앉는다.

구조체를 키로 쓸 때 IEquatable<T>가 없으면 비교마다 박싱이 일어난다. 매 프레임 도는 코드라면 매 프레임 할당이 생긴다는 말이다. 격자 좌표를 키로 쓰는 기본형은 이렇다: 

public readonly struct GridCell : IEquatable<GridCell>
{
    public readonly int X, Y;
    public GridCell(int x, int y) { X = x; Y = y; }
    // IEquatable이 있어야 비교할 때 박싱이 없다
    public bool Equals(GridCell other) => X == other.X && Y == other.Y;
    public override bool Equals(object obj) => obj is GridCell c && Equals(c);
    public override int GetHashCode() => HashCode.Combine(X, Y);
}

값이 바뀌는 가변 필드를 해시에 넣으면 사고가 난다. Dictionary에 넣어 둔 뒤 그 필드를 바꾸면 해시가 달라져, 넣어 둔 원소를 다시 못 찾게 된다. 키 타입은 불변이 안전하다.

키 순서대로 돌아야 한다면 해시가 아니다

Dictionary는 해시 테이블이라 평균 O(1)이지만 순회 순서를 전혀 보장하지 않는다. 자리가 해시 값으로 정해지니 넣은 순서도 키 순서도 아니다.

SortedDictionary는 레드-블랙 트리 기반이라 키가 정렬된 채 유지되고 조회가 O(log N)이다. 삽입과 삭제가 모두 O(log N)이고, 키 순서대로 순회할 수 있고 범위로 잘라 읽는 것도 된다.

정렬이 필요하면서 삽입이 드물다면 SortedList가 더 나을 수 있다. 배열 기반이라 메모리가 적고 인덱스 접근이 되는 대신, 중간 삽입이 O(N)으로 튄다.

면접에서 이렇게 답한다

  • 해시 테이블은 어떻게 동작하나 — 키를 해시 함수로 정수로 바꾸고, 버킷 수로 나눈 나머지를 자리로 써서 바로 접근한다. 해시가 같아도 키는 다를 수 있어 마지막에 Equals로 확인한다. 평균 O(1), 충돌이 한쪽에 몰리면 최악 O(n)이라고 마무리한다.
  • 충돌은 어떻게 해결하나 — 버킷에 목록으로 잇는 체이닝과, 빈 칸을 찾아 들어가는 개방 주소법이 있다. 개방 주소법은 캐시에 유리하지만 삭제 표시를 남기지 않으면 탐사가 끊겨 원소를 잃는다는 주의점까지 말한다.
  • Dictionary와 SortedDictionary — Dictionary는 해시 테이블이라 평균 O(1)이지만 순회 순서를 보장하지 않는다. SortedDictionary는 트리라 O(log N)이 드는 대신 키 순서로 순회할 수 있다.

이런 오해를 한다

  • “해시가 같으면 같은 키다” — 아니다. 반대만 성립한다. 그래서 Equals 비교가 뒤에 따라붙는다.
  • “좋은 해시 함수를 쓰면 충돌이 없다” — 키 공간이 버킷보다 넓어 원리상 불가능하다. 좋은 함수는 충돌을 없애는 게 아니라 고르게 퍼뜨린다.
  • “Dictionary 조회는 언제나 O(1)” — 해시가 한쪽에 몰리면 O(n)까지 떨어진다.
  • “리사이즈해도 원소 위치는 그대로다” — 버킷 수가 바뀌면 나머지 값이 달라져 전부 다시 배치된다.
  • “순회하면 넣은 순서로 나온다” — 보장되지 않는다. 이 순서에 기댄 저장이나 리플레이는 언젠가 깨진다.

3줄 정리

  • 키를 계산해 자리를 찍으므로 평균 O(1)이다
  • 충돌은 못 없앤다. 체이닝이나 개방 주소법으로 푼다
  • 키 타입은 불변으로, GetHashCode는 Equals와 짝으로
