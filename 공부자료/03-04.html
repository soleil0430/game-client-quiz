최적화·메모리

메모리와 GC

Unity GC는 힙 전체를 훑고 객체를 옮기지 않는다. 그래서 할당부터 줄인다

보스 패턴이 시작되는 순간 한 프레임이 툭 끊긴다. 프로파일러를 열어 그 프레임을 집으면 가비지 컬렉션(GC)이 들어와 있다. 언제 돌지는 우리가 고르지 못한다.

GC를 다루는 일은 결국 할당을 줄이는 일이다.

관리 힙과 네이티브 메모리는 정리 방법이 다르다

Unity 메모리는 크게 둘로 나뉜다. C# 객체가 올라가는 관리 힙, 그리고 텍스처·메시 같은 에셋이 쓰는 네이티브 메모리다. GC가 손대는 쪽은 앞의 하나뿐이다.

관리 힙에는 class 인스턴스, 배열, 문자열, 박싱된 값이 들어간다. 네이티브 쪽은 참조를 놓아 준 뒤 Resources.UnloadUnusedAssets나 번들 언로드로 치운다.

네이티브 쪽에서 덩치가 제일 큰 것은 대개 텍스처다. 압축 포맷과 Max Size가 메모리와 대역폭을 동시에 줄이는 가장 큰 수단이고, 밉맵은 약 33%를 더 쓰는 대신 원거리 품질을 높이므로 UI에는 불필요하다.

Read/Write Enabled는 반대로 간다. 켜서 사본을 가지고 있는다는 말은 GPU 쪽 말고 CPU 쪽에도 같은 데이터를 둔다는 뜻이라, 메모리가 약 두 배가 된다. 스크립트로 픽셀을 읽어야 할 때만 켜고 평소에는 끈다.

왜 한 번 커진 힙은 안 줄어드나

Unity 기본 GC(Boehm)는 객체를 옮기지 않는 non-compacting 방식이고 세대 구분도 없다. 수집할 때마다 힙 전체를 훑는다. 수집 중에는 메인 스레드가 멈추는데, 힙이 클수록 그 시간도 길어진다.

살아남은 객체를 옮기지도 않는다. 회수한 자리에 빈틈이 그대로 남고, 큰 할당으로 한 번 늘어난 힙은 대개 OS로 잘 반환되지 않아 최대 사용량이 그대로 남는다.

그림의 마지막 줄이 단편화다. 크고 작은 블록을 번갈아 할당하고 해제하면 빈자리가 잘게 흩어져, 빈 공간 총합이 충분해도 연속된 큰 블록을 못 잡아 할당이 실패할 수 있다.

크기가 같은 블록만 쓰는 풀 할당자가 단편화를 막는 대표적인 방법이고, 기본 GC는 객체를 옮기지 않으니 빈틈을 메워 주지도 않는다. 그래서 큰 버퍼는 미리 잡아 두고 재사용한다.

그럼 Incremental GC를 켜면 끝인가? 2019 이후 버전에서 이 옵션을 켜면 표시 단계를 여러 프레임에 잘게 나눠 스파이크를 완화할 뿐이다. 할당 자체는 그대로 남는다.

할당을 만들지 않는 코드로 바꾼다

먼저 무엇이 할당인지 가른다. Vector3는 struct라 pos += velocity * Time.deltaTime처럼 매 프레임 계산해도 힙 할당이 없다. 반면 배열을 새로 돌려주는 RaycastAll과 FindObjectsOfType, 새 문자열을 만드는 ToString, IEnumerator 객체를 만드는 StartCoroutine은 호출할 때마다 할당이 생긴다.

출발점은 매 프레임 새 배열과 새 문자열을 만들지 않는 것이다. 매 프레임 필요하다면 미리 만든 배열을 쓰는 NonAlloc 계열 API로 바꾸고, 텍스트는 값이 바뀔 때만 갱신하고, 참조는 캐싱으로 줄인다.

레이캐스트와 점수 표시에서 매 프레임 할당을 걷어낸 코드다:

readonly RaycastHit[] _hits = new RaycastHit[8];   // 버퍼를 미리 잡아 재사용
int _shownScore = -1;

void Update()
{
    // RaycastAll은 호출마다 새 배열을 만든다. NonAlloc은 이 버퍼를 채운다
    Physics.RaycastNonAlloc(transform.position, transform.forward, _hits, 50f);
    if (_score != _shownScore)        // 값이 바뀔 때만 문자열을 만든다
    {
        _shownScore = _score;
        _label.text = _shownScore.ToString();
    }
}

코루틴 대신 async를 쓰는 팀도 많은데, 표준 Task는 대기 객체마다 할당이 붙는다. UniTask는 UniTask 자체를 struct로 만들어 반환 객체 할당을 없애고, 완료를 통지하는 IUniTaskSource 구현체를 풀에서 꺼내 재사용한다. 반환 타입은 struct로 두고 대기 소스를 풀링한다는 뜻이다.

실행도 스레드가 아니라 Unity PlayerLoop 위에서 돌아 컨텍스트 전환이 없다. 반대로 GC를 끄거나 값을 박싱하는 방식은 오히려 멈춤과 할당을 늘린다.

풀링과 누수는 둘 다 상태를 되돌리는 문제다

자주 생기고 사라지는 오브젝트에는 풀링을 쓴다. Instantiate는 오브젝트와 컴포넌트를 새로 만들고 초기화하는 비용이 크고, 생성과 파괴가 반복되면 관리 힙 할당과 GC가 늘어난다. 풀링은 미리 만들어 둔 오브젝트를 껐다 켜며 재사용해 이 비용을 없애고 끊김을 막으려고 쓴다.

공짜는 아니다. 풀은 안 쓰는 객체까지 계속 붙잡고 있어 메모리 점유가 늘어난다는 점도 감안해야 한다.

더 자주 사고를 내는 쪽은 상태다. 재사용하는 객체에는 지난번 값이 그대로 남아 있어, 꺼낼 때 위치·체력·속도·남은 코루틴·이벤트 구독을 반드시 초기화해야 한다. 재사용이라 Awake와 Start는 다시 불리지 않으므로 초기화 코드는 OnEnable이나 전용 함수에 둔다.

파티클은 한 단계 더 손이 간다. 멈출 때 남아 있던 파티클이 그대로면 다시 켤 때 이전 잔상이 한 프레임 보인다. 그래서 꺼낼 때는 Clear()로 남은 파티클을 지우고 Play()로 시작한다.

반납할 때는 Stop(true, ParticleSystemStopBehavior.StopEmitting)으로 방출만 멈춰 남은 파티클이 수명을 다하게 두고, Stop Action을 Callback으로 두면 OnParticleSystemStopped에서 풀로 돌려보낼 수 있다.

누수도 얼굴이 비슷하다. GC는 참조가 끊긴 객체만 회수하므로, -=로 해제하지 않은 이벤트 핸들러나 static 컬렉션에 남은 참조는 객체를 계속 살려 둔다.

구독은 OnEnable에서 걸고 OnDisable에서 푸는 짝을 지킨다. 파괴된 오브젝트의 핸들러가 남으면 누수뿐 아니라 MissingReferenceException으로도 이어진다.

의심되면 Memory Profiler 스냅샷으로 누가 붙잡고 있는지 역추적한다.

면접에서 이렇게 답한다

  • 왜 힙 할당을 줄이나 — 할당이 쌓이면 GC가 돌고 그때 메인 스레드가 멈춘다고 말한다. Incremental GC로 완화해도 근본은 매 프레임 할당을 0에 가깝게 만드는 것이다. NonAlloc API, 버퍼 재사용, 풀링을 근거로 든다.
  • GC.Collect를 직접 부르나 — 평소에는 부르지 않는다. 로딩 화면이나 씬 전환처럼 이미 멈춰 있는 구간에서 에셋 언로드와 함께 한 번 정리하는 정도가 타당하다.
  • 풀링의 단점은 — 안 쓰는 객체까지 메모리를 계속 점유한다. 재사용이라 이전 상태가 남아 꺼낼 때 초기화가 필요하다. Awake와 Start가 다시 불리지 않는 점을 실수 지점으로 짚는다.
  • UniTask는 어떻게 할당을 없애나 — 반환 타입을 struct로 만들어 객체 할당을 없앤다. 완료를 알리는 소스는 풀에서 꺼내 재사용한다. 실행도 PlayerLoop 위에서 돌아 스레드 전환이 없다.

이런 오해를 한다

  • “GC가 알아서 하니 할당은 신경 안 써도 된다” — 언제 도는지 못 고르는 것이 문제다. 보스 등장 프레임에 들어오면 그 순간이 끊긴다.
  • “GC가 돌면 메모리가 OS로 반환된다” — Boehm GC는 객체를 옮기지 않고 힙도 잘 반환하지 않는다. 최고 사용량이 그대로 남는다.
  • “주기적으로 GC.Collect를 부르면 안정된다” — 전체 수집을 강제해 그 자리에서 멈춤을 만든다. 플레이 중 호출은 끊김을 손수 만드는 일이다.
  • “Read/Write Enabled를 켜면 메모리가 준다” — 반대다. CPU 쪽 사본이 생겨 약 두 배가 된다. 픽셀을 읽어야 할 때만 켠다.
  • “빈 공간이 많으면 할당은 성공한다” — 단편화되면 총량이 넉넉해도 연속된 큰 블록을 못 잡는다.

3줄 정리

  • GC가 도는 순간 메인 스레드가 멈춘다. 할당부터 줄인다
  • Boehm GC는 힙 전체를 훑고 객체를 옮기지 않는다
  • NonAlloc·버퍼 재사용·풀링이 기본 도구. 풀은 상태를 되돌린다
