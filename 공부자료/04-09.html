디버깅과 설계

안 보이는 물체는 추측하지 않는다. 드로우 콜 유무로 후보를 반으로 자른다

물체가 안 보일 때 후보를 하나씩 찍어 보면 반나절이 간다. 카메라·레이어·셰이더·노멀까지 후보가 너무 많다. 원인이 CPU 쪽인지 GPU 쪽인지부터 가르면 절반이 날아간다.

드로우 콜이 있나 없나로 먼저 가른다

첫 질문은 하나다. 그 드로우 콜이 아예 없는가, 있는데 화면에 안 남는가. 이 분기를 보여 주는 도구가 Frame Debugger다.

갈림길마다 확인할 후보가 정해져 있다. 순서대로 짚으면 추측할 일이 없다.

Frame Debugger에서 의심할 곳 구체적인 후보
드로우 콜이 없다 CPU가 애초에 안 보냈다 비활성 오브젝트, 프러스텀·오클루전 컬링, 카메라 Culling Mask, 스케일 0, 머티리얼 없음
있는데 화면에 안 남는다 GPU가 버렸다 백페이스 컬링(감는 순서·노멀 반전·음수 스케일), 깊이 테스트에 밀림, 알파 0, near·far 밖, 셰이더 컴파일 실패
있는데 순서가 이상하다 정렬 문제 렌더 큐, 반투명 정렬, ZWrite 설정

예를 들어 메시가 통째로 사라졌는데 드로우 콜은 찍혀 있다고 하자. 백페이스 컬링을 먼저 본다. 머티리얼에서 Cull Off로 켜 봤을 때 보이면 그 방향이 맞다.

분홍색으로 나오면 원인이 아예 다르다. 셰이더가 없거나 컴파일에 실패한 것이다.

Frame Debugger는 구성만 보여 준다

Frame Debugger는 한 프레임을 멈춰 드로우 콜을 순서대로 되짚는다. 각 단계에서 그때까지 그려진 화면, 쓰인 셰이더와 머티리얼과 프로퍼티 값, 렌더 타깃을 보여 준다. 이 드로우가 앞엣것과 왜 배칭되지 않았는지도 알려 준다.

대신 시간은 보여 주지 않는다. CPU 시간은 Profiler, 메모리는 Memory Profiler가 맡는다. GPU 단계별 타이밍은 RenderDoc이나 Xcode GPU Frame Capture 같은 외부 도구를 쓴다.

조명 시스템은 정적과 동적으로 갈라 짠다

설계 질문도 같은 뼈대로 답한다. 먼저 씬을 정적과 동적으로 가른다. 움직이지 않는 지형과 건물은 라이트맵으로 굽고, 움직이는 캐릭터는 라이트 프로브로 간접광을 받는다.

실시간 그림자는 디렉셔널 라이트 하나에만 준다. 나머지는 베이크하거나 블롭 섀도 같은 가짜로 대체한다.

기기 등급별로 그림자 거리·캐스케이드·해상도를 품질 티어로 묶어 둔다. 저사양 대응이 설정 교체로 끝난다. 시간대 변화가 필요하면 라이트맵 세트를 여러 벌 만들어 섞는 식으로 범위를 제한한다.

넓은 월드는 스트리밍이 먼저다

거대한 도시를 렌더링한다면 핵심은 한 번에 다 들고 있지 않는 것이다. 도시를 셀로 쪼개고 카메라 주변 셀만 비동기로 로드하고 언로드한다. Unity에서는 멀티 씬이나 Addressables로 구현한다.

로드 순간 히칭이 생기지 않게 프레임을 나눠 처리한다. 가까운 것만 자세히 그리려고 LOD를 쓰고, 먼 블록은 통째로 저해상도 메시나 임포스터로 바꾼다.

실내나 골목처럼 가림이 많은 구간은 오클루전 컬링이 특히 잘 듣는다. 같은 건물과 가로등이 반복되면 GPU 인스턴싱으로 드로우 콜을 묶는다. 월드가 아주 넓으면 좌표가 커져 float 정밀도가 떨어지므로 원점을 카메라 근처로 옮기는 처리도 같이 본다.

면접에서 이렇게 답한다

  • 렌더링 문제를 어떻게 디버깅하나 — Frame Debugger로 그 드로우 콜이 있는지부터 본다. 없으면 활성화·컬링·레이어 같은 CPU 쪽을, 있으면 백페이스 컬링·깊이·블렌딩 같은 GPU 쪽을 본다. 시간이 문제면 Profiler로, 메모리면 Memory Profiler로 옮겨 간다.
  • Frame Debugger로 무엇을 보나 — 드로우 순서, 각 드로우의 셰이더와 머티리얼과 렌더 타깃, 배칭이 깨진 이유를 본다. UI가 안 보이거나 배칭이 안 묶일 때 가장 먼저 켜는 도구다.
  • 삼각형 하나가 안 나온다면 — 감는 순서나 노멀이 뒤집혀 백페이스 컬링된 경우가 흔하다. 그 밖에 프러스텀·레이어 마스크 밖, 스케일 0, 깊이 테스트에 밀림, 셰이더 컴파일 실패를 순서대로 확인한다.
  • 조명 시스템을 설계한다면 — 정적은 라이트맵, 동적은 라이트 프로브로 나누고 실시간 그림자는 디렉셔널 하나로 제한한다. 기기 등급별 품질 티어를 만들어 그림자 거리와 해상도를 설정으로 갈아 끼울 수 있게 한다.
  • 거대한 도시를 다룬다면 — 셀 단위 스트리밍으로 주변만 로드하고, LOD와 임포스터로 정점을 줄인다. 오클루전 컬링과 GPU 인스턴싱으로 드로우 콜을 줄인다. 넓은 월드에서는 float 정밀도 때문에 원점 이동도 고려한다.

이런 오해를 한다

  • Frame Debugger로 CPU 시간이나 메모리를 본다 — 드로우 콜 구성만 보여 준다. 시간은 Profiler, 메모리는 Memory Profiler다.
  • 안 보이면 카메라 문제다 — 카메라만큼 흔한 원인이 백페이스 컬링, 깊이 테스트, 레이어 마스크다. 먼저 드로우 콜 유무로 범위를 나눈다.
  • 오클루전 컬링을 켜면 항상 이득이다 — 굽는 데이터가 늘고 런타임 판정 비용도 있다. 가림이 많은 실내나 도시형 씬에서 이득이 크다.
  • LOD만 넣으면 넓은 월드가 돌아간다 — LOD는 정점 수를 줄일 뿐 메모리에 올라온 에셋은 그대로다. 넓은 월드는 스트리밍으로 로드 자체를 줄인다.

3줄 정리

  • 드로우 콜 유무로 CPU 문제와 GPU 문제를 가른다
  • Frame Debugger는 구성만, 시간은 Profiler가 본다
  • 넓은 월드는 LOD보다 스트리밍이 먼저다
