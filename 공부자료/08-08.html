Unity와 멀티스레딩

순수 계산은 워커나 Job으로 넘기고, 엔진을 만지는 호출은 메인 스레드에 남긴다

경로 탐색 한 번에 프레임이 30ms씩 튄다. 계산을 다른 스레드로 넘기면 될 것 같은데, 거기서 Transform을 만지면 예외가 난다. 무엇을 넘기고 무엇을 남기는지가 규칙의 전부다.

엔진을 만지는 호출은 메인 스레드에만 남긴다

Transform, GameObject, UI 같은 대부분의 Unity API는 메인 스레드 전용이다. 다른 스레드에서 부르면 예외가 나거나 동작을 보장하지 못한다. 엔진 내부 상태가 단일 스레드 접근을 전제로 하기 때문이다.

전부 락을 걸면 흔한 호출 하나가 그만큼 비싸진다. 그래서 난수 생성이나 경로 탐색, 데이터 파싱처럼 엔진을 안 건드리는 계산만 워커 스레드로 보낸다. 결과 값만 메인 스레드에서 반영한다.

넘길 때는 ConcurrentQueue에 담아 Update에서 꺼낸다. Unity 2023 이후면 Awaitable.MainThreadAsync도 쓴다. 텍스처도 같아서 픽셀 계산은 백그라운드로 빼도 SetPixels와 Apply는 메인 스레드다.

코루틴·직접 만든 스레드·Job System 중 무엇을 쓰나

코루틴은 MonoBehaviour가 매 프레임 한 칸씩 돌려 주는 반복자다. Unity API를 그대로 쓰지만 한 칸이 무거우면 그 프레임이 밀린다. 일을 나눠 주는 장치이지 병렬로 만드는 장치가 아니다.

직접 만든 스레드는 병렬이지만 Unity API를 못 쓰고 수명 관리가 손에 남는다. Job System이 그 사이를 메운다. 엔진이 관리하는 워커 풀에 일을 올리고, 다룰 데이터를 값 형식과 네이티브 컨테이너로 제한한다.

두 Job이 같은 컨테이너에 동시에 쓰려 하면 안전 시스템이 알려 준다. 그래서 락을 직접 걸 일이 없다.

위치 갱신을 워커에 나눠 돌리고 결과만 메인 스레드에서 반영하는 모습:

[BurstCompile]
struct MoveJob : IJobParallelFor      // 인덱스별로 쪼개 워커들이 나눠 돈다
{
    [ReadOnly] public NativeArray<float3> Velocity;   // 읽기만 하면 동시 접근 허용
    public NativeArray<float3> Position;              // 쓰기는 한 Job만
    public float Delta;
    public void Execute(int i) => Position[i] += Velocity[i] * Delta;
}
// Update 안
var job = new MoveJob { Velocity = _v, Position = _p, Delta = Time.deltaTime };
job.Schedule(_p.Length, 64).Complete();   // 64개씩 나눠 돌리고 끝날 때까지 대기
for (int i = 0; i < _p.Length; i++)
    _transforms[i].position = _p[i];      // Unity API는 메인 스레드에서

NativeArray는 GC가 치워 주지 않는다

NativeArray를 쓰는 이유는 관리 힙 밖이라서다. Job과 Burst는 관리 객체를 다룰 수 없고, 값이 이어 붙어 캐시 효율도 좋다. 대신 GC가 치워 주지 않아 Dispose가 필요하다.

수명에 맞춰 Allocator.Temp·TempJob·Persistent 중에 고른다. Burst는 이 제한된 C# 부분집합을 LLVM으로 컴파일해 SIMD까지 쓴다.

면접에서 이렇게 답한다

  • 왜 다른 스레드에서 Unity API를 못 쓰나 — 엔진 내부 상태가 단일 스레드 접근을 전제로 하기 때문이다. 전부 락을 걸면 흔한 호출 하나가 그만큼 비싸진다.
  • 백그라운드 결과를 화면에 반영하려면 — 계산만 워커 스레드에서 하고 결과 값만 넘긴다. ConcurrentQueue에 담아 Update에서 적용하거나 동기화 컨텍스트로 되돌린다.
  • 코루틴과 스레드의 차이 — 코루틴은 메인 스레드에서 매 프레임 이어 실행되는 반복자라 Unity API를 쓰지만 병렬이 아니다. 스레드는 병렬이지만 Unity API를 못 쓴다.
  • Job System은 어떻게 성능을 올리나 — 워커 풀에 작업을 나눠 노는 코어를 쓴다. 데이터를 네이티브 컨테이너로 제한해 안전 시스템이 레이스를 잡아 준다. Burst를 붙이면 SIMD까지 써서 한 번 더 빨라진다.
  • 멀티스레드 코드를 어떻게 디버깅했나 — 안전 검사를 켜 둔 채 개발하고 로그에 스레드와 프레임 번호를 남겨 재현했다. 공유 상태를 줄이는 것이 근본 해결이었다.

이런 오해를 한다

  • 코루틴은 별도 스레드에서 돈다 — 메인 스레드에서 나눠 실행될 뿐이다. 무거운 계산을 넣으면 프레임만 밀린다.
  • Job 안에서도 Unity API를 쓸 수 있다 — 관리 객체와 Unity 오브젝트는 못 쓴다. 결과는 네이티브 컨테이너로 받는다.
  • NativeArray도 GC가 정리해 준다 — 관리 힙 밖이라 Dispose를 빼먹으면 누수로 남는다.
  • Job이 도는 중에도 같은 배열을 읽으면 된다 — 안전 시스템이 막는다. Complete로 기다리거나 읽기 전용으로 선언한다.
  • Burst를 붙이면 아무 코드나 빨라진다 — 제한된 C# 부분집합만 다뤄서 관리 객체를 쓰는 코드에는 붙지 않는다.

3줄 정리

  • 순수 계산만 워커로 보내고 엔진 호출은 메인 스레드에 남긴다
  • 코루틴은 병렬이 아니고, 병렬이 필요하면 Job System이다
  • NativeArray는 관리 힙 밖이라 Dispose를 직접 해야 한다
