렌더링 파이프라인

씬의 큐브 하나가 화면 픽셀이 되기까지 CPU와 GPU가 나눠 맡는 단계를 순서대로 꿴다

핵심 개념

렌더링은 무엇을 그릴지 정하는 CPU와 실제로 칠하는 GPU의 분업이다. CPU는 컬링으로 목록을 추리고 정렬한 뒤 렌더 스테이트를 잡고 드로우 콜을 보낸다. 이후 GPU 쪽 순서는 버텍스 셰이더 → 클리핑·원근 나눗셈·뷰포트 변환 → 래스터화 → 프래그먼트 셰이더 → 깊이·스텐실 테스트와 블렌딩 → 프레임 버퍼다. 화면 좌표가 나와야 어떤 픽셀을 덮는지 알고, 조각이 나와야 색을 계산하고, 색이 나와야 기존 값과 섞으므로 이 순서는 뒤집히지 않는다.

변환하는 일
모델(로컬 → 월드)오브젝트를 씬 좌표에 놓는다
뷰(월드 → 뷰)카메라를 원점으로 옮긴다
투영(뷰 → 클립)절두체를 정육면체로 펴 원근을 준비한다
원근 나눗셈(→ NDC)w로 나눠 멀수록 작아지게 한다
뷰포트(→ 화면)-1~1을 픽셀 좌표로 바꾼다

셰이더는 우리가 코드를 쓰는 프로그래머블 단계이고, 래스터라이저와 깊이·스텐실 테스트, 블렌딩은 하드웨어가 하는 고정 기능 단계다. 고정 단계도 동작은 Cull, ZWrite, Blend 같은 렌더 스테이트로 고른다.

여기서 드로우 콜·패스·렌더 스테이트의 관계도 정리된다. 셰이더의 패스는 한 번 그리는 방법이고, 렌더 스테이트는 그때 고정 기능 단계를 어떻게 설정할지이며, 드로우 콜은 그 상태로 이 메시를 그리라는 CPU의 명령이다. 배칭은 같은 상태로 그릴 수 있는 것들을 묶어 이 명령 횟수를 줄이는 일이다.

정점의 UV·색이 삼각형 내부 픽셀에서 정해지는 것은 래스터라이저가 무게중심 좌표로, 그것도 원근 보정을 넣어 보간하기 때문이다. 실행 횟수는 프래그먼트가 정점보다 훨씬 많으므로 픽셀마다 같은 결과가 나오는 계산은 버텍스 셰이더로 올린다.

GPU가 빠른 것은 같은 명령을 수많은 데이터에 한꺼번에 적용하는 구조라서다. 단순한 코어를 대량으로 두고 정점·픽셀을 묶음(워프) 단위로 돌리며 메모리 대기는 다른 묶음으로 감춘다. 대가로 분기 예측과 큰 캐시를 포기해, 한 묶음 안에서 if가 갈리면 양쪽을 다 실행하고 필요 없는 결과를 버린다. 스킨드 메시는 정점에 담긴 본 인덱스와 가중치로 본 행렬을 섞어 정점을 옮긴다.

모바일(타일 기반 GPU)은 지오메트리를 먼저 다 처리해 타일별로 나눠 담은 뒤(비닝) 타일 하나씩 칠한다. 색·깊이를 칩 안 타일 메모리에서 다뤄 대역폭이 싼 대신, 정점 처리 결과를 메모리에 적어 두므로 정점 수와 정점 속성 크기가 데스크톱보다 더 아프다. 프레임 도중 렌더 타겟을 바꾸거나 그린 화면을 다시 읽으면 타일을 내렸다 올리는 비용이 붙는다.

면접에서 이렇게 답한다

  • 큐브 하나가 화면에 그려지기까지 — CPU가 컬링·정렬을 거쳐 렌더 스테이트를 잡고 드로우 콜을 보내면, GPU가 정점을 클립 공간으로 옮기고 삼각형을 조각으로 래스터화한 뒤 조각마다 색을 계산하고, 깊이 테스트와 블렌딩을 거쳐 프레임 버퍼에 쓴다.
  • 세 단계의 역할 — 버텍스 셰이더는 정점마다, 프래그먼트 셰이더는 조각마다 도는 우리 코드고, 그 사이의 래스터라이저는 삼각형이 덮는 조각을 만들고 정점 값을 보간하는 고정 기능이다.
  • 정점 사이 값은 어떻게 정해지나 — 래스터라이저가 세 정점 값을 무게중심 좌표로, 원근 보정까지 넣어 보간해 넘긴다.
  • GPU는 왜 빠른가 — 같은 연산을 대량의 데이터에 동시에 적용하도록 단순 코어를 많이 둔 구조다. 대신 분기와 순차 의존이 큰 작업에는 약하다.

흔한 오해

  • 래스터라이저도 셰이더로 짠다 — 래스터화·깊이 테스트·블렌딩은 고정 기능이고, 우리는 렌더 스테이트로 동작만 고른다.
  • 투영 변환을 하면 화면 좌표가 나온다 — 투영은 클립 공간까지다. 원근 나눗셈과 뷰포트 변환이 남아 있다.
  • 깊이 테스트는 항상 픽셀 셰이더 뒤다 — 셰이더가 깊이를 바꾸거나 discard하지 않으면 하드웨어가 먼저 테스트해 셰이딩을 건너뛴다(Early-Z).
  • 프래그먼트 셰이더는 보이는 픽셀만큼만 돈다 — 가려진 조각도 실행될 수 있고, 미분값 때문에 2x2 묶음으로 돌아 가장자리에서는 버려지는 실행이 생긴다.

컬링과 가시성

안 그리는 것이 가장 싸다. 시야 밖·가려짐·뒷면·이미 가까운 픽셀을 어디서 거르는지 나눈다

핵심 개념

가장 빠른 렌더링은 아예 그리지 않는 것이다. 파이프라인 곳곳에 안 보이는 것을 버리는 관문이 있고, 거르는 대상과 단위가 다르다.

기법어디서무엇을 거르나단위
프러스텀 컬링CPU카메라 시야 밖오브젝트의 경계 볼륨
오클루전 컬링CPU다른 물체에 가려진 것오브젝트
백페이스 컬링GPU(래스터화 전)뒤를 보는 삼각형삼각형
깊이 테스트GPU더 가까운 것이 있는 자리픽셀

프러스텀 컬링은 Unity가 자동으로 하며, 오브젝트의 경계 상자가 절두체 여섯 평면 밖이면 목록에서 뺀다. 판정 단위가 오브젝트라서 지형 전체가 메시 하나면 귀퉁이만 보여도 전부 그려진다. 이런 메시는 쪼개야 컬링이 먹는다.

using UnityEngine;

// Renderer가 붙은 오브젝트에 함께 둔다
public class VisibilityGate : MonoBehaviour
{
    readonly Plane[] _planes = new Plane[6];   // 매 프레임 새 배열을 만들지 않는다

    public bool IsInFrustum(Camera cam, Renderer target)
    {
        GeometryUtility.CalculateFrustumPlanes(cam, _planes);   // 절두체 6평면을 채운다
        return GeometryUtility.TestPlanesAABB(_planes, target.bounds);  // 경계 상자 단위 판정
    }

    void OnBecameInvisible() { enabled = false; }  // 보일 때만 필요한 로직을 끈다
    void OnBecameVisible()   { enabled = true; }
}

오클루전 컬링은 벽 뒤처럼 가려진 오브젝트를 뺀다. Unity 기본 방식은 씬을 미리 구워(bake) 가시성 데이터를 만들고 런타임에 조회하므로, 조회 비용과 구운 데이터를 내고 드로우 콜을 사는 것이다. 막힌 실내에서는 크게 남고 개활지에서는 비용만 남는다.

LOD는 화면에서 차지하는 비율에 따라 폴리곤이 적은 메시로 갈아 끼워 정점·셰이딩 비용을 줄인다(LODGroup). 대신 단계별 메시를 다 들고 있어야 해 메모리와 용량은 늘고, 전환 순간 형태가 튀는 팝핑이 보인다.

백페이스 컬링은 화면에 투영된 세 정점이 감기는 방향(와인딩 순서)으로 앞뒤를 가른다. Unity는 시계 방향이 앞면이고 기본이 Cull Back이다. 정점 순서가 뒤집힌 메시가 안쪽만 보이는 것이 이 때문이며, 나뭇잎처럼 양면이 필요하면 Cull Off로 끈다.

깊이 버퍼는 픽셀마다 현재 깊이를 적어 두고 더 가까운 조각만 통과시켜, 그리는 순서와 무관하게 앞뒤를 맞춘다. 값이 비선형으로 저장돼 정밀도가 근평면에 몰리므로 near를 너무 작게 잡거나 far를 과하게 키우면 Z-파이팅이 난다.

모바일(타일 기반 GPU)은 타일 메모리 안에 깊이를 두어 깊이 테스트가 싸고, 가려질 픽셀의 셰이딩을 건너뛰는 하드웨어 기능(PowerVR의 HSR, Adreno의 LRZ)까지 있다. 그래서 데스크톱에서 쓰는 깊이 프리패스가 여기서는 지오메트리를 두 번 처리하는 손해가 되기 쉽다. 단 이 기능은 discard가 있으면 꺼진다. 반대로 CPU 예산이 빠듯해 오브젝트 수를 줄이는 컬링과 LOD는 더 중요하다.

면접에서 이렇게 답한다

  • 프러스텀 컬링과 오클루전 컬링의 차이 — 둘 다 CPU에서 그릴 목록을 줄이지만 프러스텀은 시야 밖을, 오클루전은 시야 안이지만 가려진 것을 뺀다. 프러스텀은 자동이고 오클루전은 베이크와 조회 비용이 들어 씬 구조를 보고 켠다.
  • 백페이스 컬링의 판정 기준 — 화면에 투영된 정점이 감기는 방향으로 앞뒤를 가르고 뒷면을 버린다. 메시 노멀이나 정점 순서가 뒤집히면 판정도 뒤집혀 안쪽만 보인다.
  • LOD의 장단점 — 거리에 따라 단순한 메시로 바꿔 정점과 셰이딩을 아끼지만, 단계별 메시만큼 메모리와 용량이 늘고 전환 순간 팝핑이 생긴다.
  • 깊이 버퍼의 동작 — 픽셀마다 깊이를 저장해 더 가까운 조각만 남기므로 순서와 무관하게 앞뒤가 맞는다. 정밀도가 근평면에 몰려 near/far 비율이 나쁘면 Z-파이팅이 난다.

흔한 오해

  • 오클루전 컬링은 켜기만 하면 이득이다 — 베이크 데이터와 조회 비용이 있어 가릴 것이 없는 개활지에서는 비용만 남는다.
  • 백페이스 컬링이 뒤에 있는 오브젝트를 거른다 — 거르는 것은 삼각형의 뒷면이다. 가려진 오브젝트는 오클루전 컬링, 가려진 픽셀은 깊이 테스트가 맡는다.
  • 프러스텀 컬링은 삼각형 단위다 — 오브젝트의 경계 볼륨 단위라, 거대한 단일 메시는 컬링이 거의 듣지 않는다.
  • LOD는 메모리도 줄여 준다 — 단계마다 메시를 따로 들고 있으므로 메모리와 빌드 용량은 오히려 는다.

드로우 콜과 배칭

드로우 콜은 CPU 비용이다. 배칭·인스턴싱·SRP Batcher가 각각 무엇을 줄이는지 구분한다

핵심 개념

드로우 콜은 CPU가 그래픽스 API에 "이 메시를 이 상태로 그려라"라고 보내는 명령이다. 비싼 쪽은 GPU가 삼각형을 그리는 일이 아니라 호출마다 CPU가 렌더 스테이트를 세팅하고 드라이버를 거치는 준비 비용이다. 그래서 드로우 콜이 많으면 GPU가 놀아도 CPU에서 막힌다. 통계 창의 Batches는 GPU로 보낸 그리기 묶음의 수, SetPass calls는 그 사이에 셰이더 패스와 렌더 스테이트를 바꾼 횟수이고, 상태 전환이 더 비싸 보통 SetPass calls를 먼저 본다.

줄이는 방법은 층이 다르다. 머티리얼 종류를 줄이고(아틀라스), 호출을 합치고(정적 배칭·메시 결합·인스턴싱), 호출당 준비 비용을 낮춘다(SRP Batcher).

기법조건줄어드는 것대가
정적 배칭Static + 같은 머티리얼드로우 콜 수합친 메시만큼 메모리
동적 배칭아주 작은 메시 + 같은 머티리얼드로우 콜 수매 프레임 CPU 병합
GPU 인스턴싱같은 메시 + 같은 머티리얼드로우 콜 수개체별 값은 인스턴스 프로퍼티
SRP BatcherURP·HDRP + 같은 셰이더 배리언트상태 설정·상수 업로드호출 수는 그대로, 셰이더 호환

배칭을 깨는 가장 흔한 실수는 renderer.material에 접근하는 것이다. 처음 접근하는 순간 전용 복사본이 생겨 머티리얼이 달라지고, 복사본은 오브젝트를 파괴해도 남는다.

using UnityEngine;

public class TintOnHit : MonoBehaviour
{
    static readonly int s_ColorId = Shader.PropertyToID("_BaseColor");
    MaterialPropertyBlock _block;
    Renderer _renderer;

    void Awake()
    {
        _renderer = GetComponent<Renderer>();
        _block = new MaterialPropertyBlock();
    }

    public void SetTint(Color color)
    {
        // _renderer.material.color = color; 는 복사본을 만들어 배칭을 깬다
        _renderer.GetPropertyBlock(_block);
        _block.SetColor(s_ColorId, color);
        _renderer.SetPropertyBlock(_block);
    }
}

메시도 머티리얼도 제각각인 나무 100그루라면, 먼저 텍스처를 아틀라스 한 장으로 합쳐 머티리얼을 하나로 만들고(배칭·인스턴싱의 전제), 움직이지 않으면 정적 배칭이나 메시 결합을, 같은 메시가 반복되면 인스턴싱을 쓴다. 스프라이트 아틀라스도 배칭 단위이자 로드 단위라, 같은 화면에 뜨는 UI끼리 묶어야 드로우 콜이 줄고 안 쓰는 이미지가 메모리에 올라오지 않는다.

모바일(타일 기반 GPU)에서는 CPU가 약하고 드라이버 오버헤드가 커서 같은 호출 수라도 데스크톱보다 훨씬 아프다. 특히 UI는 캔버스 리빌드에 더해 마스크나 중간에 낀 머티리얼로 배치가 쉽게 끊기므로, 자주 바뀌는 UI와 정적인 UI를 캔버스부터 나눈다.

면접에서 이렇게 답한다

  • 드로우 콜을 왜 줄이나 — 호출마다 렌더 스테이트 설정과 드라이버 비용이 들어 많아지면 CPU에서 프레임이 막힌다. 그래서 머티리얼을 통일하고 배칭·인스턴싱으로 호출을 합친다.
  • 정적 배칭과 동적 배칭 — 정적 배칭은 움직이지 않는 메시를 미리 합치는 대신 메모리를 더 쓰고, 동적 배칭은 매 프레임 CPU에서 합쳐 메시가 크면 손해다.
  • SRP Batcher와 GPU 인스턴싱 — SRP Batcher는 셰이더 배리언트만 같으면 머티리얼이 달라도 상태 설정 비용을 줄이지만 호출 수는 그대로다. 인스턴싱은 같은 메시·머티리얼을 한 번에 그려 호출 수를 줄인다.
  • material과 sharedMaterial — material은 접근하는 순간 복사본을 만들어 배칭을 깨고 정리 책임까지 남긴다.

흔한 오해

  • 드로우 콜은 GPU 부하다 — 주된 비용은 CPU의 준비와 드라이버 호출이라 삼각형이 적어도 호출이 많으면 느리다.
  • SRP Batcher를 켜면 드로우 콜이 준다 — 줄어드는 것은 호출당 준비 비용이고 Batches는 그대로일 수 있다.
  • 배칭은 켜면 항상 이득이다 — 동적 배칭은 큰 메시에서 병합 비용이 더 들고, 정적 배칭은 메모리를 더 쓴다.
  • 머티리얼만 같으면 한 번에 그려진다 — 중간에 다른 머티리얼이 하나 끼는 것만으로 배치가 나뉜다.
  • MaterialPropertyBlock은 항상 공짜다 — 인스턴싱과는 맞지만 URP의 SRP Batcher 호환은 깨진다.

텍스처

압축 포맷·밉맵·해상도가 메모리와 대역폭을 어떻게 정하는지 숫자로 잡아 둔다

핵심 개념

텍스처 비용은 두 가지다. 메모리 점유와 샘플링할 때 읽어 오는 대역폭이고, 둘 다 픽셀 수에 비례한다. 그래서 가로세로를 두 배로 키우면 메모리는 네 배가 된다. 화면에서 작게 보이는 텍스처의 Max Size를 낮추는 것이 가장 싸고 확실한 절감인 이유다.

PNG·JPG는 파일을 작게 보관하는 저장용 압축이라, 로드하면 풀려서 RGBA32 같은 원래 크기로 메모리에 올라간다. 반면 ASTC·ETC2 같은 GPU 압축 포맷은 압축된 상태 그대로 샘플링할 수 있어 메모리와 대역폭을 함께 줄인다. 모바일에서 포맷 선택이 곧 메모리 예산인 이유가 여기 있다.

포맷픽셀당 비트1024x1024 크기쓰임
RGBA32(무압축)324MB기준값. 런타임 생성 텍스처 정도
ASTC 4x481MB품질이 중요한 캐릭터·주요 UI
ASTC 6x6약 3.6약 0.45MB일반 소품·배경의 기본값
ASTC 8x820.25MB큰 배경, 디테일이 적은 면
ETC2 RGBA81MBASTC를 못 쓰는 구형 안드로이드 대응

밉맵은 원본을 가로세로 절반씩 줄인 이미지를 미리 만들어 두는 것이다. GPU는 인접 픽셀 사이의 UV 변화율을 보고 화면에서 텍셀이 얼마나 촘촘히 찍히는지 판단해 알맞은 레벨을 고른다. 멀리 있는 표면에서 원본을 그대로 읽으면 텍셀을 건너뛰며 샘플링해 반짝임이 생기는데, 밉맵은 이를 막고 작은 이미지를 읽어 텍스처 캐시 적중률도 올린다. 대신 전체 메모리가 약 33% 는다. 항상 같은 크기로 보이는 UI에는 보통 끈다.

필터링은 한 레벨 안에서 어떻게 섞느냐의 문제다. 포인트는 가장 가까운 텍셀 하나, 바이리니어는 이웃 네 텍셀, 트라이리니어는 거기에 인접한 두 밉 레벨까지 섞어 밉 경계의 띠를 없앤다. 아니소트로픽은 비스듬히 보이는 면에서 방향에 맞춰 샘플을 더 뽑아 흐려짐을 막는다. 샘플이 늘수록 비싸므로 바닥처럼 필요한 곳에만 올린다. 픽셀 아트는 일부러 포인트로 둔다.

모바일(타일 기반 GPU)에서 가장 귀한 자원은 대역폭이다. 타일 GPU는 색·깊이 버퍼를 칩 안에서 다뤄 아끼지만 텍스처 읽기는 여전히 메인 메모리에서 오므로, 압축과 밉맵이 곧 프레임과 발열·배터리로 직결된다. 주의할 점이 하나 더 있다. Crunch 압축은 배포 파일 크기만 줄이고 런타임에는 ASTC·ETC2로 풀리므로 메모리 사용량은 그대로다. 또 텍스처 변이 2의 거듭제곱이 아니면 블록 정렬이 어긋나 압축 효율이 떨어질 수 있다.

면접에서 이렇게 답한다

  • 모바일 텍스처 압축 포맷은 무엇을 쓰나 — 기본은 ASTC고, 블록 크기로 품질과 용량을 맞춘다. 캐릭터나 주요 UI는 4x4, 일반 소품은 6x6, 큰 배경은 8x8 식으로 나누고, ASTC를 못 쓰는 구형 안드로이드 대응이 필요하면 ETC2를 함께 굽는다.
  • 밉맵 레벨은 어떻게 고르나 — GPU가 인접 픽셀 사이의 UV 변화율로 화면 대비 텍셀 밀도를 계산해 레벨을 고른다. 멀리 있는 표면의 반짝임을 막고 캐시에도 유리한 대신 메모리가 약 33% 는다.
  • 텍스처 크기가 주는 영향 — 메모리는 가로x세로에 비례하므로 변을 두 배로 키우면 네 배가 된다. 그래서 최적화는 화면에서 작게 보이는 것부터 Max Size를 내리는 것으로 시작한다.
  • 아틀라스로 묶는 기준 — 같은 화면에 함께 나오는 것끼리 묶는다. 아틀라스는 배칭 단위이면서 로드 단위라, 여러 화면 것을 섞으면 쓰지 않는 이미지까지 메모리에 올라온다.

흔한 오해

  • PNG로 넣으면 압축된 채로 메모리에 올라간다 — PNG·JPG는 저장용 압축이라 로드하면 풀린다. GPU 메모리를 줄이려면 ASTC·ETC2 같은 GPU 압축 포맷으로 임포트해야 한다.
  • 밉맵은 메모리를 줄여 준다 — 레벨을 다 들고 있으므로 오히려 약 33% 늘어난다. 줄어드는 것은 샘플링 대역폭과 반짝임이다.
  • 밉맵을 끄면 더 선명해서 이득이다 — 멀어질수록 반짝이고 텍스처 캐시 적중률이 떨어져 느려진다. 끄는 것은 항상 원본 크기로 보이는 UI 정도다.
  • Crunch 압축이 런타임 메모리를 줄인다 — 줄어드는 것은 빌드·다운로드 용량이다.
  • 해상도를 절반으로 줄이면 메모리도 절반 — 가로세로가 함께 줄어 1/4이 된다.

투명도와 버퍼

알파 테스트와 블렌딩이 각각 무엇을 포기하는지, 오버드로와 스텐실은 어디서 비싼지 본다

핵심 개념

불투명이 싼 이유부터 잡아야 한다. 깊이를 쓰고 순서에 영향받지 않으므로, 앞에서 뒤로 그리면 뒤쪽 픽셀은 깊이 테스트에서 걸러져 프래그먼트 셰이더를 돌지도 않는다. 투명 처리는 이 이점 중 무엇을 포기하느냐의 문제다.

방식렌더 큐깊이 쓰기그리는 순서대가
불투명GeometryOn앞 → 뒤반투명 표현이 안 된다
알파 테스트(clip)AlphaTestOn앞 → 뒤discard가 사전 깊이 최적화를 막는다
알파 블렌딩TransparentOff뒤 → 앞오버드로와 정렬 의존
디더링GeometryOn앞 → 뒤가까이서 점 패턴이 보인다

알파 테스트는 프래그먼트 셰이더에서 clip()이나 discard로 픽셀을 버린다. 문제는 셰이더를 끝까지 돌려야 그 픽셀이 살아남는지 정해진다는 점이다. 가려질 픽셀의 셰이딩을 미리 건너뛰는 최적화(Early-Z, 타일 GPU의 HSR·LRZ)는 셰이더 실행 전에 깊이가 확정된다는 전제 위에 있어서, discard 하나로 그 전제가 깨진다. 컷아웃 나뭇잎이 화면을 크게 덮을 때 모바일에서 특히 비싼 이유다. 잎 모양에 맞춘 메시를 쓰거나 불투명 부분과 컷아웃 부분을 나누는 것이 대안이다.

알파 블렌딩은 이미 그려진 색 위에 섞는 연산이라 순서를 바꾸면 결과가 달라지고, 깊이 쓰기를 꺼 두므로 깊이 버퍼가 순서를 바로잡아 주지도 못한다. 그래서 Transparent 큐는 카메라에서 먼 것부터 정렬해 그린다. 다만 정렬 단위가 오브젝트라서 서로 뚫고 지나가거나 한 메시 안에서 면이 겹치면 해결되지 않는다. 이때는 깊이만 먼저 쓰는 패스를 두거나, 디더링으로 불투명 큐에 넣거나, 메시를 나눈다.

오버드로는 한 픽셀을 여러 번 칠하는 것이다. 삼각형 수가 아니라 화면을 덮은 면적과 겹친 횟수의 문제이므로, 반투명 파티클이 크고 겹칠수록 급증해 필레이트 병목이 된다. Scene 뷰의 Overdraw 드로 모드와 Frame Debugger로 확인하고, 파티클 크기·수를 줄이고, 알파가 0인 영역이 큰 사각형 대신 모양에 맞춘 메시를 쓰고, 보이지 않는 UI를 꺼서 줄인다.

스텐실 버퍼는 픽셀마다 작은 정수를 적어 두고, 이후 그리는 픽셀이 그 값과 비교해 통과할지 정하는 마스크용 버퍼다. Unity UI의 Mask가 이 방식으로 자식을 잘라 내고 거울·포탈·외곽선에도 쓴다. 마스크가 중첩되면 비교 값이 달라져 UI 배칭이 끊기므로, 사각형으로 충분하면 RectMask2D가 싸다.

모바일(타일 기반 GPU)에서는 블렌딩이 칩 안 타일 메모리에서 일어나 대역폭 부담은 덜하지만, 겹친 만큼 프래그먼트 셰이더가 다시 도는 필레이트 비용은 그대로다. 전면을 덮는 반투명 UI를 겹치거나 풀스크린 파티클을 쓰면 바로 프레임이 떨어진다. 알파 테스트가 HSR을 무력화하는 점까지 합치면, 모바일에서는 투명을 줄이는 것 자체가 최적화 항목이다.

면접에서 이렇게 답한다

  • 알파 테스트와 알파 블렌딩의 차이 — 알파 테스트는 픽셀을 버리거나 남기거나 둘 중 하나라 깊이를 쓰고 불투명처럼 다루고, 블렌딩은 뒤 색과 섞어야 해 깊이 쓰기를 끄고 뒤에서 앞으로 그린다. 전자는 사전 깊이 최적화를, 후자는 오버드로와 정렬을 대가로 낸다.
  • 모바일에서 알파 테스트가 느린 이유 — 타일 GPU는 가려질 픽셀의 셰이딩을 미리 건너뛰는데, discard가 있으면 셰이더를 끝까지 돌려야 깊이가 정해져 그 최적화가 꺼진다. 화면을 크게 덮는 컷아웃일수록 손해가 커진다.
  • 투명은 왜 정렬하나 — 블렌딩은 순서에 따라 결과가 달라지는 연산이고 깊이 쓰기를 껐기 때문에 깊이 버퍼가 잡아 주지 못한다. 그래서 먼 것부터 그리며, 오브젝트 단위 정렬이라 교차하는 경우는 메시를 나누거나 깊이 프리패스로 푼다.
  • 오버드로는 어떻게 확인하나 — Scene 뷰의 Overdraw 모드와 Frame Debugger로 어디가 몇 겹인지 본다. 파티클 크기와 수, 투명 영역이 큰 사각형 메시, 겹쳐 둔 전면 UI를 줄인다.

흔한 오해

  • 알파 테스트가 블렌딩보다 항상 싸다 — 데스크톱에서는 대체로 맞지만, 모바일에서는 discard가 사전 깊이 최적화를 막아 역전될 수 있다.
  • 반투명도 깊이 버퍼가 앞뒤를 맞춰 준다 — 반투명은 깊이 쓰기를 끈 채 그리므로 그리는 순서가 곧 결과다.
  • 오버드로는 폴리곤이 많아서 생긴다 — 겹쳐 칠한 픽셀 수의 문제라, 삼각형 두 장짜리 전면 쿼드 몇 개로도 심해진다.
  • Transparent 큐에 넣으면 정렬이 해결된다 — 정렬 단위가 오브젝트라 서로 교차하거나 한 메시 안에서 겹치는 면은 여전히 틀린다.
  • UI 마스크는 공짜다 — 스텐실 비교 값이 달라져 배칭이 끊긴다. 사각형이면 RectMask2D가 더 싸다.

광원이 많아질수록 비싸지는 이유를 알고 실시간·베이크·그림자 맵의 한계를 나눠 다룬다

핵심 개념

조명이 비싸지는 지점은 언제나 같은 계산을 몇 번 반복하느냐다. 포워드 렌더링은 오브젝트를 그릴 때 그 오브젝트에 영향을 주는 광원을 같이 계산하므로 비용이 대략 오브젝트 수 × 광원 수로 늘어난다. 디퍼드 렌더링은 위치·노멀·알베도 같은 표면 정보를 먼저 여러 렌더 타깃(G-버퍼)에 써 두고 조명은 화면 픽셀마다 한 번만 계산해, 광원이 늘어도 비용이 해상도 기준으로만 늘어난다. 대신 G-버퍼 왕복 대역폭이 들고 픽셀 하나에 재질 정보가 하나뿐이라 반투명은 포워드로 따로 그려야 하며 MSAA도 쓰기 어렵다.

경로조명 비용약점
포워드오브젝트 × 광원광원이 늘면 패스와 드로우 콜이 는다
Forward+타일에 닿는 광원만타일별 광원 목록 준비 비용
디퍼드화면 픽셀 수G-버퍼 대역폭, 반투명·MSAA 곤란

URP에서는 Universal Renderer 에셋의 Rendering Path에서 셋 중 하나를 고른다. Built-in의 포워드는 픽셀 광원 수에 상한(Quality Settings의 Pixel Light Count)이 있어 그 이상은 버텍스 라이트나 구면 조화로 떨어뜨렸지만, URP의 Forward+는 화면 타일에 닿는 광원만 계산해 그 상한을 사실상 없앴다(URP 14, Unity 2022 LTS부터).

움직이지 않는 빛은 미리 굽는다. 라이트맵은 정적 오브젝트의 표면 조명만 굽기 때문에 움직이는 캐릭터는 읽을 수 없고, 그래서 공간에 찍어 둔 라이트 프로브에서 주변 간접광을 보간해 받는다. 리플렉션 프로브는 그 지점에서 본 풍경을 큐브맵으로 구워 반사에 쓴다.

그림자는 광원에서 본 깊이를 텍스처(그림자 맵)에 구운 뒤, 화면 픽셀을 광원 공간으로 옮겨 저장된 깊이보다 멀면 가려진 것으로 판정한다. 해상도와 정밀도가 유한하므로 표면이 자기 자신을 가리는 것으로 오판해 줄무늬(섀도 애크니)가 생긴다. 깊이 비교에 바이어스를 주거나 그림자 맵을 그릴 때 앞면 대신 뒷면을 굽는 것이 표준 대응이고, 바이어스가 과하면 그림자가 발에서 떨어지는 피터 패닝이 나온다. Shadow Distance를 늘리면 같은 해상도를 더 넓게 나눠 쓰게 되어 계단이 오히려 심해진다.

조명 수식 자체는 단순하다. 램버트 디퓨즈는 saturate(dot(N, L)), 즉 노멀과 광원 방향의 내적이라 보는 방향과 무관하다. 스페큘러는 시선 벡터가 들어가 카메라가 움직이면 하이라이트도 따라 움직이고, 지수가 클수록 좁고 날카로워진다. 퐁은 반사 벡터를, 요즘 쓰는 블린-퐁은 하프 벡터를 쓴다. PBR은 이런 임의의 수식 대신 물리 제약을 지키는 BRDF를 쓴다. BRDF는 들어온 빛이 방향마다 얼마나 반사되는지 정의하는 함수이고, 에너지 보존은 그 반사량의 합이 입사 에너지를 넘지 않는다는 제약이다. 그래서 거칠어 하이라이트가 넓어지면 그만큼 밝기가 낮아진다.

면접에서 이렇게 답한다

  • 포워드와 디퍼드의 차이 — 포워드는 오브젝트를 그리면서 닿는 광원을 함께 계산해 비용이 오브젝트 수 × 광원 수로 큰다. 디퍼드는 표면 정보를 G-버퍼에 먼저 쓰고 조명은 화면 픽셀 단위로 한 번만 계산해 광원이 많을 때 유리하다. 대신 반투명과 MSAA가 곤란하다.
  • 모바일에서 디퍼드가 불리한 이유 — 타일 기반 모바일 GPU는 대역폭이 귀한데 디퍼드는 G-버퍼 왕복이 필수다. 광원이 많은 모바일 씬이면 디퍼드보다 URP의 Forward+를 먼저 쓴다.
  • 라이트 프로브와 리플렉션 프로브 — 라이트맵은 정적 오브젝트에만 구워지므로 움직이는 캐릭터는 라이트 프로브에서 간접광을 보간해 받는다. 리플렉션 프로브는 주변 환경을 큐브맵으로 구워 반사에 쓴다. 둘 다 런타임에는 읽기만 한다.
  • 그림자가 지저분하다 — 애크니인지 계단인지 먼저 가른다. 애크니면 바이어스와 뒷면 굽기로 줄이고, 계단이면 Shadow Distance를 줄이거나 캐스케이드와 해상도를 올린다.
  • MSAA·FXAA·TAA — MSAA는 커버리지와 깊이만 여러 샘플로 저장해 삼각형 에지만 부드럽게 하고 타일 GPU에서 싸다. FXAA는 최종 이미지 대비만 보고 흐리는 값싼 후처리, TAA는 샘플을 프레임마다 흔들어 누적해 품질은 좋지만 잔상이 생긴다.

흔한 오해

  • 디퍼드는 항상 빠르다 — 광원이 적으면 G-버퍼 고정 비용만 손해다.
  • 디렉셔널 라이트도 위치가 중요하다 — 방향만 쓰므로 위치를 옮겨도 결과가 같다.
  • 그림자 거리를 늘리면 그림자가 좋아진다 — 같은 해상도를 더 넓게 나눠 쓰는 것이라 오히려 계단이 심해진다.
  • 디퓨즈도 카메라 각도에 따라 밝기가 바뀐다 — 램버트 디퓨즈는 노멀과 광원 방향만 쓴다. 시선이 들어가는 쪽은 스페큘러다.
  • 에너지 보존은 광원 개수 제한이다 — 반사량의 합이 입사 에너지를 넘지 않는다는 재질 쪽 제약이고, 조명 개수와는 무관하다.
  • MSAA를 켜면 모든 지글거림이 사라진다 — 기하 에지만 다뤄서 알파 테스트 경계나 셰이더 내부 반짝임에는 듣지 않는다.

Unity 렌더 파이프라인과 셰이더

URP는 C#으로 짠 렌더 파이프라인이다. 확장은 Renderer Feature, 비용은 배리언트로 돌아온다

핵심 개념

Built-in 렌더 파이프라인은 프레임을 그리는 순서가 엔진 내부(C++)에 고정돼 있어, 개발자는 이미지 이펙트나 커맨드 버퍼처럼 정해진 구멍으로만 끼어들 수 있었다. SRP(Scriptable Render Pipeline)는 그 순서를 C#으로 짜게 연 틀이고, URP와 HDRP는 유니티가 SRP 위에 만들어 둔 구현이다. URP는 모바일부터 PC까지, HDRP는 고사양 PC·콘솔용이다.

그래서 Built-in용 조명 셰이더는 URP에서 그대로 돌지 않는 경우가 많다. 표준 셰이더를 쓰던 머티리얼은 URP의 자동 변환 도구가 바꿔 주지만, 직접 쓴 셰이더는 사람이 다시 쓴다. Shader Graph는 URP와 HDRP 양쪽에서 쓸 수 있다.

Renderer Feature는 URP 렌더러의 정해진 시점(예: 불투명을 그린 뒤)에 패스를 하나 더 끼워 넣는 확장점이다. 외곽선 그리기, 화면을 복사해 왜곡에 쓰기, 특정 레이어 재렌더가 대표적이다.

셰이더 성능에서 자주 걸리는 것이 분기다. GPU는 수십 개 스레드를 한 묶음(워프·웨이브)으로 묶어 같은 명령을 실행하므로, 묶음 안에서 조건이 갈리면 양쪽을 모두 실행하고 결과만 골라 쓴다. 머티리얼 상수처럼 묶음 전체가 같은 값으로 갈리는 분기는 싸다. 키워드로 배리언트를 나누면 분기가 사라지는 대신 배리언트 수가 문제가 된다.

#pragma multi_compile _ _MAIN_LIGHT_SHADOWS  // 항상 컴파일, 런타임 토글
#pragma shader_feature_local _EMISSION       // 안 쓰면 빌드에서 빠짐

half4 frag(Varyings i) : SV_Target
{
    half4 c = SAMPLE_TEXTURE2D(_BaseMap, sampler_BaseMap, i.uv);
    #ifdef _EMISSION
        c.rgb += _EmissionColor.rgb;
    #endif
    return c;
}

키워드 조합마다 셰이더가 따로 컴파일되므로 키워드가 늘면 조합이 곱으로 폭발한다. 빌드 시간과 용량이 커지고, 처음 쓰는 배리언트를 GPU에 올리는 순간 프레임이 튄다. 안 쓰는 조합이 빠지도록 shader_feature를 쓰고, 빌드 스트리핑으로 잘라 내고, 나머지는 Shader Variant Collection으로 로딩 중에 미리 워밍업한다.

컴퓨트 셰이더는 렌더링 파이프라인 밖에서 GPU 병렬 연산을 쓰는 프로그램이라, 서로 독립적인 데이터 수만 건에 같은 계산을 하는 입자 시뮬레이션·컬링·이미지 처리에 맞는다. 결과를 CPU로 되읽으면 동기화 대기가 생긴다. 파티클 시스템(CPU 갱신, 스크립트·물리 연동)과 VFX Graph(컴퓨트 셰이더로 GPU 갱신)를 나눠 쓰는 것도 같은 이유다.

면접에서 이렇게 답한다

  • Built-in, URP, HDRP 중 무엇을 고르나 — 모바일이 타깃이면 URP다. 다만 Built-in용 커스텀 셰이더는 다시 써야 하는 경우가 많아 전환 비용을 일정에 잡는다.
  • Renderer Feature는 언제 쓰나 — 불투명을 그린 뒤 외곽선을 얹는 식으로 정해진 시점에 패스를 더 넣을 때 쓴다. 커스텀 SRP는 유지 비용이 커서 구조 자체를 갈아야 할 때만 고려한다.
  • 셰이더 분기가 느린 이유 — GPU는 워프 단위로 같은 명령을 실행해서, 워프 안에서 조건이 갈리면 양쪽을 다 돌고 결과만 고른다.
  • 배리언트가 많아지면 — 빌드 시간과 용량이 늘고 처음 쓰는 배리언트를 올릴 때 히칭이 생긴다. shader_feature와 스트리핑으로 줄이고 남는 건 미리 워밍업한다.
  • 컴퓨트 셰이더는 언제 쓰나 — 수만 건의 독립적인 데이터에 같은 계산을 반복할 때 쓴다. 결과를 GPU 안에서 소비해야 이득이 남는다.

흔한 오해

  • URP로 바꾸면 셰이더는 그대로 돈다 — 인클루드 파일과 패스 태그가 달라 Built-in용 조명 셰이더는 대개 재작성이 필요하다.
  • 셰이더 분기도 CPU의 if처럼 한쪽만 실행된다 — 워프 안에서 갈리면 양쪽을 다 돈다.
  • 배리언트는 GPU만 느려지게 한다 — 실제 문제는 빌드 시간, 용량, 첫 사용 시점의 히칭이다.
  • VFX Graph가 파티클 시스템의 상위 호환이다 — CPU 쪽 상호작용이 제한적이고 컴퓨트 셰이더 지원 기기가 필요하다. 게임플레이에 얽힌 효과는 파티클 시스템이 낫다.
  • 포스트 프로세싱은 공짜에 가깝다 — 화면 픽셀 수에 비례하는 패스이고, 모바일에서는 타일 메모리를 비웠다 채우는 비용까지 붙는다.

모바일 GPU와 그래픽스 API

타일 기반 GPU는 대역폭을 아끼는 대신 그린 화면을 중간에 되읽는 것을 싫어한다

핵심 개념

모바일 기기에서 진짜 한계는 연산 능력보다 메모리 대역폭과 전력이다. 칩 바깥의 메인 메모리(DRAM)를 한 번 오가는 비용이 산술 연산 수십 번보다 비싸고, 그 비용이 그대로 발열과 배터리로 돌아온다. 모바일 GPU가 타일 기반 구조를 쓰는 이유가 여기 있다.

데스크톱의 즉시 모드 GPU(IMR)는 드로우 콜이 들어오면 곧바로 메인 메모리의 프레임버퍼에 그린다. 타일 기반 GPU는 먼저 한 프레임의 지오메트리를 모두 받아 화면 타일(예: 16×16, 32×32)마다 어떤 삼각형이 걸치는지 목록을 만들고(비닝), 그다음 타일 하나씩 칩 안의 빠른 메모리에서 색과 깊이를 처리한 뒤 끝난 타일의 결과만 메인 메모리에 쓴다. 깊이 버퍼와 MSAA 샘플은 타일 안에서 소비하고 버리므로 대역폭을 크게 아낀다.

불리한 것오버드로, 대역폭디퍼드 G-버퍼, 풀스크린 블릿, 그랩 패스

이 구조에서 나오는 실무 규칙이 몇 가지 있다. 첫째, 렌더 타깃을 중간에 바꾸거나 이미 그린 결과를 셰이더에서 되읽으면 타일 내용을 메인 메모리로 내보냈다가 다시 들여와야 한다. 포스트 프로세싱, 카메라 스택, URP의 Opaque Texture, Built-in의 GrabPass가 모두 여기에 걸린다. 둘째, 디퍼드가 불리한 것도 같은 이유다. G-버퍼 여러 장을 쓰고 다시 읽는 왕복이 타일 메모리에 담기 힘들다. 셋째, 프레임 시작에 화면을 제대로 클리어하는 편이 낫다. 클리어하지 않으면 GPU가 이전 내용을 타일로 불러와야 해서 오히려 비싸진다. 넷째, 알파 테스트(clip·discard)는 픽셀이 살아남을지 셰이더를 돌려야 알 수 있어 조기 깊이 판정을 무효화한다. 나뭇잎처럼 꼭 필요한 곳에만 쓴다.

그래픽스 API 쪽도 비슷하게 오버헤드 이야기다. OpenGL ES와 DX11은 상태 검증·동기화·메모리 관리를 드라이버가 알아서 해 줬고, 그 대가로 드로우 콜마다 CPU 비용이 붙고 렌더 명령을 한 스레드에서만 만들 수 있었다. Vulkan·DX12·Metal은 그 일을 앱이 직접 맡는 저수준 API다. 드라이버 오버헤드가 줄고 커맨드 버퍼를 여러 스레드에서 병렬로 기록할 수 있어, 드로우 콜이 많아 CPU가 병목인 씬에서 이득이 크다. 반대로 GPU가 병목이면 API를 바꿔도 프레임은 그대로다.

Unity에서는 Player Settings의 Graphics APIs 목록에서 고른다. Auto Graphics API를 끄고 순서를 직접 정하면 앞에 있는 것부터 시도한다. 안드로이드는 기기·드라이버 편차가 커서 Vulkan을 앞에 두되 OpenGL ES 3을 뒤에 남겨 두는 구성이 흔하다. iOS는 Metal만 쓴다. API를 바꾸면 셰이더가 그 API용으로 다시 컴파일되므로 빌드 시간과 배리언트 수에도 영향이 있다.

면접에서 이렇게 답한다

  • 모바일 GPU와 데스크톱 GPU의 차이 — 모바일은 대역폭과 전력이 한계라 화면을 타일로 쪼개 칩 안 메모리에서 그리고 끝난 타일만 내보낸다. 그래서 MSAA는 상대적으로 싸고, 렌더 타깃을 바꾸거나 그린 결과를 되읽는 동작이 비싸다.
  • 그래서 무엇을 피하나 — 불필요한 풀스크린 패스, 카메라 스택 남발, 그랩 패스, 모바일 디퍼드를 줄인다. 프레임 시작 클리어는 생략하지 않고, 알파 테스트는 꼭 필요한 머티리얼에만 쓴다.
  • Vulkan과 OpenGL ES 3 중 무엇을 쓰나 — 드로우 콜이 많아 CPU가 병목이면 Vulkan이 유리하다. 다만 안드로이드는 드라이버 편차가 있어 대상 기기에서 실제로 재 보고 정하고, Graphics APIs 목록에 ES 3을 폴백으로 남겨 둔다.
  • 저수준 API가 빠른 이유 — 드라이버가 하던 검증과 동기화를 앱이 맡아 드로우 콜당 CPU 비용이 줄고, 커맨드 버퍼를 여러 스레드에서 미리 기록할 수 있다. GPU 병목에는 도움이 되지 않는다는 점을 같이 말한다.

흔한 오해

  • 타일 기반은 드로우 콜이 오면 바로 그린다 — 지오메트리를 먼저 모아 타일별 목록을 만든 뒤 타일 단위로 그린다. 바로 그리는 쪽이 즉시 모드다.
  • 모바일에서는 MSAA가 무조건 비싸다 — 타일 안에서 해소되므로 상대적으로 싸다. 오히려 비싼 것은 풀스크린 후처리 계열이다.
  • Vulkan으로 바꾸면 프레임이 오른다 — CPU 드라이버 오버헤드가 병목일 때만 오른다. 픽셀 채우기나 셰이더가 병목이면 변화가 없다.
  • 저수준 API는 GPU 연산이 더 빠르다 — GPU가 하는 계산은 같다. 달라지는 것은 명령을 준비하는 CPU 쪽이다.
  • 화면을 클리어하지 않으면 그만큼 아낀다 — 타일 기반에서는 이전 프레임 내용을 타일로 불러와야 해서 오히려 손해다.

안 보이는 삼각형은 추측하지 않는다. 드로우 콜이 있는지부터 갈라 범위를 좁힌다

핵심 개념

렌더링 버그는 원인 후보가 많아 감으로 뒤지면 오래 걸린다. 그래서 먼저 그 드로우 콜이 아예 없는가, 있는데 화면에 안 남는가로 이분한다. 이 한 번의 분기로 CPU 쪽 문제와 GPU 쪽 문제가 갈리고 후보가 절반으로 준다. 이걸 보는 도구가 Frame Debugger다.

Frame Debugger는 한 프레임을 멈춰 드로우 콜을 순서대로 하나씩 되짚는다. 각 단계에서 그때까지 그려진 화면, 쓰인 셰이더와 머티리얼과 프로퍼티 값, 렌더 타깃, 그리고 이 드로우가 앞엣것과 왜 배칭되지 않았는지를 보여 준다. 대신 시간은 보여 주지 않는다. CPU 시간은 Profiler, 메모리는 Memory Profiler, GPU 단계별 타이밍은 RenderDoc이나 Xcode GPU Frame Capture 같은 외부 도구가 맡는다.

Frame Debugger에서의심할 곳구체적인 후보
드로우 콜이 없다CPU가 애초에 안 보냈다비활성 오브젝트, 프러스텀·오클루전 컬링, 카메라 Culling Mask, 스케일 0, 머티리얼 없음
있는데 화면에 안 남는다GPU가 버렸다백페이스 컬링(감는 순서·노멀 반전·음수 스케일), 깊이 테스트에 밀림, 알파 0, near·far 밖, 셰이더 컴파일 실패
있는데 순서가 이상하다정렬 문제렌더 큐, 반투명 정렬, ZWrite 설정

예를 들어 메시가 통째로 사라졌는데 드로우 콜은 찍혀 있다면 백페이스 컬링을 먼저 본다. 정점 감는 순서나 노멀이 뒤집힌 메시, 혹은 스케일에 음수가 들어간 오브젝트는 앞면이 뒷면으로 판정돼 잘려 나간다. 머티리얼에서 Cull Off로 켜 봤을 때 보이면 그 방향이 맞다. 분홍색으로 나오면 셰이더가 없거나 컴파일에 실패한 것이라 원인이 아예 다르다.

설계 질문도 같은 뼈대로 답한다. 조명 시스템을 설계한다면, 먼저 씬을 정적과 동적으로 가른다. 움직이지 않는 지형·건물은 라이트맵으로 굽고, 움직이는 캐릭터는 라이트 프로브로 간접광을 받는다. 실시간 그림자는 디렉셔널 라이트 하나에만 주고 나머지는 베이크하거나 블롭 섀도 같은 가짜로 대체한다. 기기 등급별로 그림자 거리·캐스케이드·해상도를 품질 티어로 묶어 두면 저사양 대응이 설정 교체로 끝난다. 시간대 변화가 필요하면 굽는 대신 라이트맵 세트를 여러 벌 만들어 섞는 식으로 범위를 제한한다.

거대한 도시를 렌더링한다면, 한 번에 다 들고 있지 않는 것이 핵심이다. 도시를 셀(청크)로 쪼개고 카메라 주변 셀만 비동기로 로드·언로드한다. Unity에서는 멀티 씬이나 Addressables로 구현하고, 로드 순간 히칭이 생기지 않게 프레임을 나눠 처리한다. 가까운 것만 자세히 그리기 위해 LOD를 쓰고, 먼 블록은 통째로 하나의 저해상도 메시나 임포스터로 대체한다. 실내·골목처럼 가림이 많은 구간은 오클루전 컬링이 특히 잘 듣고, 같은 건물·가로등이 반복되면 GPU 인스턴싱으로 드로우 콜을 묶는다. 월드가 아주 넓으면 좌표가 커져 float 정밀도가 떨어지므로 원점을 카메라 근처로 옮기는 처리도 같이 본다.

면접에서 이렇게 답한다

  • 렌더링 문제를 어떻게 디버깅하나 — Frame Debugger로 그 드로우 콜이 있는지부터 본다. 없으면 활성화·컬링·레이어 같은 CPU 쪽을, 있으면 백페이스 컬링·깊이·블렌딩 같은 GPU 쪽을 본다. 시간이 문제면 Profiler로, 메모리면 Memory Profiler로 옮겨 간다.
  • Frame Debugger로 무엇을 보나 — 드로우 순서, 각 드로우의 셰이더와 머티리얼과 렌더 타깃, 배칭이 깨진 이유를 본다. UI가 안 보이거나 배칭이 안 묶일 때 가장 먼저 켜는 도구다.
  • 삼각형 하나가 안 나온다면 — 감는 순서나 노멀이 뒤집혀 백페이스 컬링된 경우가 흔하다. 그 밖에 프러스텀·레이어 마스크 밖, 스케일 0, 깊이 테스트에 밀림, 셰이더 컴파일 실패를 순서대로 확인한다.
  • 조명 시스템을 설계한다면 — 정적은 라이트맵, 동적은 라이트 프로브로 나누고 실시간 그림자는 디렉셔널 하나로 제한한다. 기기 등급별 품질 티어를 만들어 그림자 거리와 해상도를 설정으로 갈아 끼울 수 있게 한다.
  • 거대한 도시를 다룬다면 — 셀 단위 스트리밍으로 주변만 로드하고, LOD와 임포스터로 정점을 줄이고, 오클루전 컬링과 GPU 인스턴싱으로 드로우 콜을 줄인다. 넓은 월드에서는 float 정밀도 때문에 원점 이동도 고려한다.

흔한 오해

  • Frame Debugger로 CPU 시간이나 메모리를 본다 — 드로우 콜 구성만 보여 준다. 시간은 Profiler, 메모리는 Memory Profiler다.
  • 안 보이면 카메라 문제다 — 카메라만큼 흔한 원인이 백페이스 컬링, 깊이 테스트, 레이어 마스크다. 먼저 드로우 콜 유무로 범위를 나눈다.
  • 오클루전 컬링을 켜면 항상 이득이다 — 굽는 데이터가 늘고 런타임 판정 비용도 있다. 가림이 많은 실내·도시형 씬에서 이득이 크다.
  • LOD만 넣으면 넓은 월드가 돌아간다 — LOD는 정점 수를 줄일 뿐 메모리에 올라온 에셋은 그대로다. 넓은 월드는 스트리밍으로 로드 자체를 줄인다.
