모바일과 상황형 질문

모바일은 발열과 메모리 한도가 먼저 온다. 지속 가능한 부하로 낮추고 피크를 관리한다

핵심 개념

모바일은 PC와 병목이 다르다. CPU와 GPU가 같은 메모리 대역폭을 나눠 쓰고, 전력 예산이 작아 부하가 계속되면 발열로 클럭을 스스로 낮춘다(서멀 스로틀링). 그래서 처음 2분의 프레임이 아니라 10분 뒤에도 유지되는 프레임이 진짜 성능이다. 최적화 기준도 피크가 아니라 지속 가능한 부하가 된다.

발열을 낮추는 방법은 결국 일을 덜 시키는 것이다. 목표 프레임을 고정해 남는 성능을 굳이 태우지 않고, 메뉴나 정지 화면에서는 프레임을 더 낮추며, 렌더 해상도와 오버드로·후처리·실시간 그림자를 줄인다. 반대로 매 프레임 GC.Collect()를 부르는 식의 처리는 CPU 일을 늘려 열을 더 낸다.

using UnityEngine;

public class MobilePerformanceSetup : MonoBehaviour
{
    void Start()
    {
        QualitySettings.vSyncCount = 0;       // 모바일에서 targetFrameRate가 먹도록 둔다
        Application.targetFrameRate = 30;     // 60을 못 지키면 30 고정이 체감이 낫다
        Time.fixedDeltaTime = 0.02f;          // 물리 호출 횟수를 늘리지 않는다
    }
}

메모리는 프레임과 다른 방식으로 앱을 죽인다. iOS는 앱이 기기별 한도를 넘으면 예외 없이 프로세스를 종료하므로, 시간이 지날수록 늘고 메모리가 적은 구형 기기에 몰리는 크래시는 누수나 과다 사용에 의한 강제 종료부터 의심한다. 해제하지 않은 에셋 번들, 참조가 남아 내려가지 않는 텍스처, 끝없이 커지는 캐시가 단골이다. Memory Profiler로 시작 직후와 10분 뒤 스냅샷을 비교해 무엇이 늘었는지 본다.

시야가 갑자기 트이는 상황(언덕 위에서 화면 회전)은 한 순간에 보이는 대상이 폭증하는 문제다. 가려져 있던 오브젝트가 한꺼번에 보이면서 드로우 콜이 뛰고 메시·텍스처가 몰려 로드되며 메모리 피크가 생긴다. 오브젝트 수를 줄이지 않고 푸는 정공법은 LOD로 먼 것을 가벼운 메시로 바꾸고, Layer Cull Distances와 오클루전 컬링으로 그릴 대상을 줄이고, 임포스터와 스트리밍으로 동시에 올라오는 양을 나누는 것이다.

물리는 호출 횟수와 충돌 쌍이 비용이다. Fixed Timestep을 줄이면 FixedUpdate와 시뮬레이션이 초당 더 여러 번 돌아 부담이 커지므로 모바일에서는 오히려 0.02~0.033초로 늘린다. 레이어 충돌 매트릭스에서 필요 없는 조합을 끄고, Mesh Collider 대신 기본 도형을 쓰며, 움직일 콜라이더에는 Kinematic Rigidbody를 붙인다. Rigidbody 없는 콜라이더를 움직이면 정적 충돌 구조를 다시 만들어 비싸기 때문이다.

면접에서 이렇게 답한다

  • 모바일에서 성능과 메모리를 어떻게 잡나 — 목표 기기에서 지속 프레임과 메모리 상한을 먼저 정한다. 프레임은 목표치로 고정해 열을 아끼고, 메모리는 텍스처 포맷과 해상도, 번들 언로드로 상한 안에 유지한다.
  • 발열은 왜 낮추나 — 발열이 심하면 OS가 클럭을 낮춰 프레임이 떨어지고 배터리와 사용자 경험도 나빠진다. 목표 프레임 고정, 해상도 스케일, 오버드로와 후처리 축소로 부하 총량을 줄인다.
  • 10분 뒤 크래시가 급증한다면 — 메모리 누수나 과다 사용으로 OS가 앱을 종료하는 경우를 먼저 본다. 시간대별 메모리 스냅샷을 비교하고 기기의 메모리 경고 로그를 확인한다.
  • 물리 오브젝트가 많은 모바일 게임은 — Fixed Timestep을 늘려 호출 횟수를 줄이고, 충돌 매트릭스로 불필요한 검사와 Mesh Collider를 걷어낸다. 움직이는 콜라이더에는 Kinematic Rigidbody를 붙인다.

흔한 오해

  • GC.Collect로 메모리를 비우면 발열이 준다 — 수집 자체가 CPU 작업이라 열과 끊김을 모두 늘린다.
  • 프레임은 높을수록 좋다 — 모바일에서는 남는 프레임이 열과 배터리로 나가고 결국 스로틀링으로 돌아온다.
  • Fixed Timestep을 촘촘하게 하면 최적화다 — 물리 정확도는 오르지만 CPU 부담이 커진다. 모바일에서는 반대로 늘린다.
  • 시야가 트일 때는 안개를 걷거나 그림자 거리를 늘려 본다 — 둘 다 그릴 양을 늘리는 방향이라 상황을 악화시킨다.
  • 크래시는 코드 예외 때문이다 — OOM 종료는 스택 트레이스 없이 죽는 경우가 많아 로그만 봐서는 원인을 못 찾는다.
