최적화·메모리

모바일과 상황형 질문

모바일은 발열과 메모리 한도가 먼저 온다. 10분 뒤 프레임이 진짜 성능이다

시연할 때는 60프레임이 잘 나왔다. 그런데 10분 넘게 이어서 플레이하면 같은 기기에서 프레임이 내려앉는다. 코드는 한 줄도 안 바뀌었는데 무엇이 달라졌을까?

기기가 뜨거워져 스스로 클럭을 낮춘 것이다. 모바일에서 처음 2분의 숫자는 성능이 아니다.

발열이 클럭을 깎는다. 지속 프레임으로 본다

모바일은 CPU와 GPU가 같은 메모리 대역폭을 나눠 쓴다. 전력 예산도 작아서 부하가 이어지면 발열 때문에 기기가 클럭을 스스로 낮춘다. 이것이 서멀 스로틀링이다.

기준은 피크가 아니라 지속 가능한 부하다. 목표 프레임을 고정해 남는 성능을 굳이 태우지 않는다. 메뉴나 정지 화면에서는 더 낮춰도 된다.

모바일에서 프레임과 물리 호출 횟수를 고정하는 코드다:

void Start()
{
    QualitySettings.vSyncCount = 0;    // 모바일에서 targetFrameRate가 먹도록
    Application.targetFrameRate = 30;  // 60을 못 지키면 30 고정이 체감이 낫다
    Time.fixedDeltaTime = 0.02f;       // 물리 호출 횟수를 늘리지 않는다
}

발열은 CPU와 GPU가 오랫동안 높은 부하로 도는 데서 온다. 그래서 손대는 곳도 한 방향이다. 프레임레이트 제한, 정적인 화면에서 프레임 낮추기, 후처리나 실시간 그림자 같은 무거운 효과 줄이기, 렌더 해상도 조절은 모두 부하를 낮춘다.

반대로 매 프레임 GC.Collect()로 메모리를 비운다면 오히려 CPU 일이 늘고 프레임마다 멈춤이 생긴다. 열도 끊김도 같이 는다.

메모리가 넘치면 무슨 일이 일어나나

프레임이 떨어지는 게 아니라 앱이 사라진다. iOS는 앱이 기기별 한도를 넘으면 프로세스를 그냥 종료한다. 시간이 갈수록 늘고 메모리가 적은 구형 기기에 몰리는 크래시라면 메모리부터 의심한다.

단골은 셋이다. 해제하지 않은 에셋 번들, 참조가 남아 내려가지 않는 텍스처, 끝없이 커지는 캐시. Memory Profiler로 시작 직후와 10분 뒤 스냅샷을 비교해 무엇이 늘었는지 본다.

시야가 트이면 보이는 대상이 한꺼번에 는다

언덕 위에서 화면을 한 바퀴 돌린다고 하자. 시야가 트이는 순간 가려져 있던 오브젝트가 한꺼번에 보이면서 드로우 콜과 메시·텍스처 로딩이 몰려 메모리가 터진다.

정공법은 한 번에 그릴 양을 줄이는 것이다. LOD로 먼 것은 가벼운 메시로 바꾸고, Layer Cull Distances의 컬링 거리로 작은 물체를 일찍 잘라 내고, 오클루전 컬링으로 가려진 후보를 미리 깎는다. 임포스터와 스트리밍으로 동시에 올라오는 양을 여러 프레임에 나누는 것까지가 한 벌이다.

반대로 안개를 걷거나 그림자 거리를 키우는 것은 부담을 더 키운다. 화면에 들어오는 대상이 늘어나는 쪽이기 때문이다.

물리는 호출 횟수와 충돌 쌍이 비용이다

Fixed Timestep을 줄이면 FixedUpdate와 시뮬레이션이 초당 더 여러 번 돈다. 모바일에서는 거꾸로 0.02~0.033초로 늘린다. 정확도를 조금 내주고 호출 횟수를 산다.

충돌 쌍은 레이어 충돌 매트릭스에서 필요 없는 조합을 꺼서 줄인다. Mesh Collider 대신 기본 도형을 쓰고, 움직일 콜라이더에는 Kinematic Rigidbody를 붙인다.

Rigidbody 없는 콜라이더를 움직이면 정적 충돌 구조를 통째로 다시 만든다. 그 값을 움직일 때마다 치른다.

면접에서 이렇게 답한다

  • 모바일에서 성능과 메모리를 어떻게 잡나 — 목표 기기에서 지속 프레임과 메모리 상한을 먼저 정한다고 말한다. 프레임은 목표치로 고정해 열을 아끼고, 메모리는 텍스처 포맷과 해상도, 번들 언로드로 상한 안에 유지한다.
  • 발열은 왜 낮추나 — 발열이 심하면 OS가 클럭을 낮춰 프레임이 떨어진다. 배터리와 사용자 경험도 같이 나빠진다. 목표 프레임 고정, 해상도 스케일, 오버드로 축소로 부하 총량을 줄인다고 이어 간다.
  • 10분 뒤 크래시가 급증한다면 — 메모리 누수나 과다 사용으로 OS가 앱을 종료하는 경우를 먼저 본다. 시간대별 메모리 스냅샷을 비교하고 기기의 메모리 경고 로그를 확인한다.
  • 물리 오브젝트가 많은 모바일 게임은 — Fixed Timestep을 늘려 호출 횟수를 줄인다. 충돌 매트릭스로 불필요한 검사와 Mesh Collider를 걷어낸다. 움직이는 콜라이더에는 Kinematic Rigidbody를 붙인다고 답한다.

이런 오해를 한다

  • “GC.Collect로 메모리를 비우면 발열이 준다” — 수집 자체가 CPU 작업이다. 열과 끊김을 모두 늘린다.
  • “프레임은 높을수록 좋다” — 모바일에서는 남는 프레임이 열과 배터리로 나간다. 결국 스로틀링으로 돌아온다.
  • “Fixed Timestep을 촘촘하게 하면 최적화다” — 물리 정확도는 오르지만 CPU 부담이 커진다. 모바일에서는 거꾸로 늘린다.
  • “시야가 트일 때는 안개를 걷어 본다” — 안개를 걷거나 그림자 거리를 늘리면 그릴 양이 는다. 상황이 더 나빠진다.
  • “크래시는 코드 예외 때문이다” — OOM 종료는 스택 트레이스 없이 죽는 일이 많다. 로그만 봐서는 원인을 못 찾는다.

3줄 정리

  • 10분 뒤에도 유지되는 프레임이 모바일의 진짜 성능
  • 목표 프레임을 고정해 남는 성능을 열로 태우지 않는다
  • 메모리 초과는 프레임이 아니라 앱 강제 종료로 나타난다
