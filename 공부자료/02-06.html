Unity 엔진

UI

UI 성능을 가르는 기준은 계층 구조가 아니라 무엇이 얼마나 자주 바뀌느냐다

기기마다 화면 크기도 비율도 다르다. 한 벌로 만든 UI를 그 전부에 맞추고, 손가락이 어디를 눌렀는지까지 알아내야 한다. uGUI는 이 일을 세 컴포넌트에 나눠 맡긴다.

버튼이 안 눌리면 무엇부터 보나

씬에 EventSystem이 있는지부터 본다. 입력이 들어오면 EventSystem이 Graphic Raycaster로 어떤 UI가 맞았는지 찾아 전달한다. 이게 없으면 화면은 멀쩡히 나오는데 클릭만 안 먹는다.

나머지 둘도 역할이 뚜렷하다. Canvas는 자식 UI의 사각형과 색을 모아 하나의 메시로 만들어 그리는 루트다. UI는 Canvas 밑에 있어야 화면에 나온다.

RectTransform은 UI 전용 트랜스폼이다. 앵커는 부모의 어디에 붙을지를, 피벗은 무엇을 기준으로 돌고 커질지를 정한다.

숫자 하나가 배경 100장을 다시 그리게 한다

Canvas는 자식 그래픽 하나만 바뀌어도 그 Canvas 전체의 메시를 다시 만든다. 정적인 배경 100장과 매 프레임 바뀌는 타이머가 한 Canvas에 있다고 하자. 숫자 한 자리 때문에 배경 100장이 매 프레임 다시 조립된다.

갱신 빈도가 다른 UI는 Canvas를 나눈다. 기준은 계층 구조가 아니라 얼마나 자주 바뀌는가다. 다만 배칭은 Canvas 경계를 넘지 못하니, 무작정 쪼개면 드로우 콜이 늘어난다.

요소가 아주 많으면 두 가지를 더 본다. 누를 일이 없는 이미지와 텍스트는 Raycast Target을 끈다. 긴 목록은 화면에 보이는 만큼만 만들어 돌려 쓴다.

크기는 CanvasScaler, 화면비는 앵커가 맡는다

크기는 CanvasScaler가 맡는다. Scale With Screen Size로 두고 기준 해상도를 정하면 화면이 커진 만큼 UI도 비례해 커진다. Match는 너비와 높이 중 어느 쪽을 따를지 정하는 값이다.

화면비 차이는 스케일로 풀리지 않는다.

남은 것은 앵커의 몫이다. 구석에 붙는 요소는 그 방향에 앵커를 두고, 늘어나야 하는 요소는 앵커를 벌려 스트레치로 만든다. 그래야 16:9에서 20:9로 넘어가도 쏠리거나 잘리지 않는다.

노치가 있는 기기는 Screen.safeArea를 읽는다. 그 값만큼 루트 RectTransform을 안쪽으로 밀면 카메라 구멍에 버튼이 가리지 않는다.

3D를 따라다니는 체력 바는 LateUpdate에서 옮긴다

머리 위 체력 바를 만드는 길은 둘이다. World Space Canvas로 캐릭터에 붙이면 멀어질수록 작아지고, Overlay Canvas에 두고 화면 좌표로 옮기면 거리와 상관없이 같은 크기다.

뒤쪽은 카메라가 움직인 뒤에 좌표를 잡아야 한다. 체력 바가 한 프레임씩 밀리지 않게 옮기는 코드다:

void LateUpdate()   // 카메라가 움직인 뒤에 잡아야 한 프레임 밀리지 않는다
{
    Vector3 world = target.position + offset;
    Vector3 view = Camera.main.WorldToViewportPoint(world);
    bool visible = view.z > 0f;   // z가 음수면 카메라 뒤라 좌표가 뒤집힌다

    if (bar.gameObject.activeSelf != visible) bar.gameObject.SetActive(visible);
    if (visible) bar.position = Camera.main.WorldToScreenPoint(world);
}

UI Toolkit은 구조가 아예 다르다. UI가 게임오브젝트가 아니라 VisualElement 트리라, 수천 개를 만들어도 씬 계층이 무거워지지 않는다. 다만 월드 스페이스 UI는 Unity 6에 와서 들어왔고, 런타임 게임 UI는 아직 uGUI가 기본이다.

면접에서 이렇게 답한다

  • Canvas, RectTransform, EventSystem의 역할 — Canvas는 자식 UI를 메시로 합쳐 그리는 루트라고 시작한다. RectTransform은 앵커와 피벗으로 위치와 크기를 정하고, EventSystem은 레이캐스트로 입력 대상을 찾는다. EventSystem을 지운 씬에서는 버튼이 하나도 안 눌린다는 예까지 붙인다.
  • 여러 해상도와 화면비를 어떻게 맞추나 — 크기는 CanvasScaler를 Scale With Screen Size로 두고 기준 해상도와 Match로 맞춘다. 화면비는 앵커로 흡수하고, 노치 기기는 Safe Area만큼 루트를 안쪽으로 민다.
  • UI 요소가 아주 많을 때 — 갱신 빈도로 Canvas를 나눠 리빌드 범위부터 줄인다. 누를 일 없는 이미지는 Raycast Target을 끄고, 목록은 보이는 만큼만 만들어 재활용한다.
  • NGUI와 uGUI의 차이 — NGUI는 에셋 스토어 서드파티 UI였고, uGUI는 그 개발자를 영입해 엔진에 내장한 공식 UI다. 손으로 관리하던 아틀라스가 스프라이트 패커와 Canvas 배칭으로 들어왔다.

이런 오해를 한다

  • “알파를 0으로 만들면 안 그려진다” — 투명해질 뿐 메시는 그대로 만들어진다. 정말 빼려면 Canvas 컴포넌트를 끄거나 게임오브젝트를 비활성화한다.
  • “Canvas는 하나로 두는 게 좋다” — 거꾸로다. 하나에 몰면 작은 변경 하나가 전체 리빌드를 부른다. 다만 잘게 쪼개면 배칭이 끊기니 갱신 빈도로 나눈다.
  • “CanvasScaler만 설정하면 화면비도 해결된다” — 스케일만 다룬다. 16:9와 20:9에서 남는 폭은 앵커로 처리해야 요소가 쏠리거나 잘리지 않는다.
  • “Raycast Target은 켜 둬도 공짜다” — 입력이 들어올 때마다 그래픽을 하나씩 검사한다. 배경과 텍스트는 꺼 둔다.

3줄 정리

  • Canvas는 자식 하나가 바뀌면 전체 메시를 다시 만든다
  • 그래서 계층이 아니라 갱신 빈도로 Canvas를 나눈다
  • 크기는 CanvasScaler, 화면비와 노치는 앵커와 Safe Area
