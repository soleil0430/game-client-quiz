최적화·메모리

프로파일링과 병목 진단

CPU와 GPU 중 느린 쪽이 프레임 시간이다. 실기기 개발 빌드에서 가른다

에디터에서 12ms로 돌던 씬을 폰에 올렸더니 34ms가 나온다. 게다가 에디터에서 제일 비싸 보이던 항목이 기기에서는 3등으로 내려가 있다. 무엇을 재느냐보다 어디서 재느냐가 먼저다.

느린 쪽이 프레임 시간을 정한다

한 프레임은 둘이 나눠 처리한다. CPU는 스크립트·물리·애니메이션·UI를 돌리고 렌더 명령을 준비한다. GPU는 그 명령대로 픽셀을 칠한다.

둘은 겹쳐 돈다. 프레임 시간은 더한 값이 아니라 느린 쪽이다. 빠른 쪽을 반으로 줄여도 숫자는 꿈쩍하지 않는다.

어느 쪽이 한계인가? 가장 싼 실험은 렌더 해상도를 절반으로 낮추는 것이다. 해상도를 낮추면 GPU가 처리할 픽셀이 줄어들 뿐, CPU가 하던 일은 그대로다.

해상도를 낮췄더니 프레임이 크게 좋아진다면 GPU 쪽 병목일 가능성이 크다. 픽셀 셰이더 처리량이나 오버드로가 풀리면서 숫자가 오른 것이니, 칠해야 할 픽셀이 많은 것이 한계라는 뜻에서 필 레이트 병목이라고 부른다. 모바일에서는 반투명 UI와 파티클이 겹쳐 쌓이는 오버드로가 가장 흔한 원인이다.

반대로 해상도를 바꿔도 그대로면 CPU나 정점 처리 쪽을 봐야 한다. 드로우 콜은 CPU가 렌더 명령을 준비하는 비용이라 CPU 병목의 흔한 원인이다. 프로파일러에서 Gfx.WaitForPresent처럼 CPU가 GPU를 기다리는 항목이 크면 GPU 부하나 수직 동기화 대기를 의심한다.

해상도 실험은 어디를 팔지 정하는 신호탄이지 판정이 아니다. 실제 진단은 프로파일러의 CPU·GPU 모듈과 Frame Debugger를 함께 본다.

에디터 말고 실기기 개발 빌드에서 잰다

맨 앞의 12ms와 34ms가 여기서 나온다. 에디터에는 에디터 자체의 오버헤드가 섞이고, PC의 하드웨어 특성도 폰과 다르다. 절대 수치는 믿을 것이 못 된다.

Development Build로 빌드해 Autoconnect Profiler로 실기기에 붙어 잰다.

Deep Profile은 모든 메서드에 계측을 붙여 호출 구조를 다 펼쳐 준다. 그 계측 비용이 수치 자체를 왜곡하는 것이 함정이다. 범위를 좁힐 때만 켜고, 평소에는 궁금한 구간에 마커를 직접 심는다.

적의 갱신 구간만 프로파일러에 따로 잡는 코드다:

using Unity.Profiling;

public class EnemyManager : MonoBehaviour
{
    // 마커는 static으로 한 번만 만든다. 매 프레임 만들면 그게 비용이다
    static readonly ProfilerMarker s_Tick = new ProfilerMarker("Enemy.Tick");
    void Update()
    {
        using (s_Tick.Auto())      // 이 블록만 프로파일러에 따로 잡힌다
            Tick(Time.deltaTime);
    }
}

평소에 느린 건가, 한 번 튀는 건가

둘은 원인도 해법도 다르다. 평소에 느린 것은 매 프레임 도는 비용의 문제고, 한 지점에서 튀는 것은 그 순간에 몰린 작업의 문제다. 갈라 놓지 않으면 엉뚱한 곳을 판다.

특정 순간에만 튀는 끊김(hitch)에서는 처음 쓰이는 셰이더 컴파일, 동기 에셋 로드, 대량 Instantiate, 큰 GC, 한 프레임에 몰린 초기화가 흔한 원인이다. 튄 프레임을 프로파일러에서 골라 무엇이 시간을 먹는지 본다. 반대로 프로젝트 전체의 스크립트 파일 수 같은 숫자는 여기 끼지 못한다. 런타임 끊김과 관계가 없는 값이다.

해법은 둘 중 하나다. 앞당기거나, 나누거나.

미리 로드하고 셰이더를 워밍업해 두면 첫 사용 비용이 로딩 화면으로 옮겨 간다. 생성은 여러 프레임에 나눠 편다. 무엇이 실제로 그려지는지는 Frame Debugger에서 드로우 콜을 하나씩 짚어 확인한다.

프로파일러 위쪽에 Transform이 올라온다면

진단을 하다 보면 짐작하지 못한 항목이 위로 올라올 때가 있다. 자주 나오는 것이 Transform 갱신이다.

부모 Transform이 바뀌면 자식들의 월드 행렬이 더럽혀졌다고 표시되고, 다음에 그 값을 읽을 때 다시 계산된다. 부모를 움직이면 자식들의 위치를 다시 계산한다는 뜻이다. 그래서 자식이 많고 깊은 계층을 자주 움직이면 비용이 커진다.

손보는 방향은 둘이다. 자주 움직이는 오브젝트는 계층을 얕게 두고, 한 프레임에 위치를 여러 번 고칠 때는 지역 변수에 모아 계산한 뒤 마지막에 한 번만 대입한다.

면접에서 이렇게 답한다

  • CPU 병목인지 GPU 병목인지 어떻게 가리나 — 해상도를 낮춰 보고 프레임이 크게 오르면 GPU의 픽셀 처리 쪽을 의심한다고 말한다. 그다음 프로파일러의 CPU·GPU 모듈과 Frame Debugger로 확정한다.
  • 모바일은 어떻게 프로파일링하나 — Development Build로 실기기에 올려 Autoconnect Profiler로 붙어 잰다. 에디터 수치는 경향만 보고, Deep Profile은 범위를 좁힐 때만 켠다고 덧붙인다.
  • 특정 지점에서 크게 끊긴다면 — 튄 프레임을 프로파일러에서 집어 그 순간 무엇이 실행됐는지 본다. 그다음 셰이더 워밍업, 비동기 로드, 생성 분산 중에서 그 작업에 맞는 것을 고른다.

이런 오해를 한다

  • “에디터 프로파일러 수치면 충분하다” — 에디터 오버헤드와 하드웨어 차이로 절대 수치가 다르다. 기기에서는 항목 순위까지 뒤집힌다.
  • “Deep Profile이 가장 정확하다” — 계측 비용이 커서 수치 자체가 틀어진다. 어디를 볼지 좁히는 용도다.
  • “스크립트 파일이 많아서 끊긴다” — 파일 수가 늘리는 것은 컴파일 시간이다. 런타임 프레임과는 무관하다.
  • “프레임이 일정하면 최적화가 끝났다” — 평균이 좋아도 스파이크 한 번이 체감을 깎는다. 최대 프레임 시간도 같이 본다.

3줄 정리

  • CPU와 GPU 중 느린 쪽이 프레임 시간을 정한다
  • 해상도를 반으로 낮춰 보면 어느 쪽인지 갈린다
  • 실기기 개발 빌드로 재고, 스파이크는 따로 본다
