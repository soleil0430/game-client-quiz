가상 메모리

프로세스마다 가짜 주소를 주고 필요한 페이지만 올린다. 모바일 메모리 크래시의 배경이다

핵심 개념

가상 메모리는 프로세스마다 "이 주소 공간은 네가 혼자 쓴다"고 거짓말을 해 주는 장치다. 프로그램이 다루는 주소는 전부 가상 주소이고, CPU 안의 MMU가 페이지 테이블을 보고 실제 물리 주소로 바꾼다. 한 겹을 끼워 넣어 얻는 것이 셋이다. 프로세스끼리 남의 메모리를 못 건드리게 격리하고, 물리 메모리보다 큰 프로그램을 돌리고, 같은 공유 라이브러리를 물리적으로 한 벌만 두고 여러 프로세스가 같이 쓴다.

주소 공간은 고정 크기 페이지(보통 4KB)로 잘라 관리한다. 접근한 페이지가 물리 메모리에 없으면 페이지 폴트가 나고, 운영체제가 그 페이지를 올린 뒤 멈췄던 명령을 다시 실행한다. 즉 페이지 폴트는 오류가 아니라 요구 페이징의 정상 동작이고, 유효하지 않은 주소일 때만 진짜 오류가 된다. 다만 저장 장치까지 내려가는 하드 폴트는 메모리 접근보다 자릿수로 느려서, 게임에서는 그 한 번이 프레임 스파이크로 보인다. 매번 페이지 테이블을 읽으면 메모리 접근이 두 번이 되므로, 최근 변환 결과를 담아 두는 작은 캐시가 TLB다. 문맥 전환 때 TLB가 무효화되는 것도 전환 비용이 커지는 이유 중 하나다.

페이징세그멘테이션
나누는 기준고정 크기(보통 4KB)코드·스택 같은 논리 단위
외부 단편화없다 — 빈 프레임 아무 곳에나 들어간다생긴다 — 크기가 제각각이다
내부 단편화마지막 페이지에 자투리가 남는다거의 없다

내부 단편화는 필요한 양보다 크게 떼어 준 탓에 블록 안에 남는 공간이고, 외부 단편화는 빈 공간이 흩어져 총량은 충분한데 연속된 큰 블록을 못 잡는 상황이다. 실제 시스템은 둘을 섞어 쓴다. 게임을 몇 시간 돌린 뒤 텍스처 한 장 할당이 실패하는 것이 외부 단편화의 전형이다.

필요한 페이지 수보다 물리 프레임이 모자라면 올리자마자 다시 내보내기를 반복하는 스래싱에 빠져, CPU가 대부분의 시간을 입출력 대기로 보낸다. 모바일 게임의 메모리 크래시가 여기 닿아 있다. iOS에는 스왑이 없어 메모리를 과하게 쓰면 페이징이 아니라 OS의 강제 종료로 끝나고, 안드로이드도 비슷하게 앱을 정리한다. 그래서 클라이언트의 답은 "교체를 잘한다"가 아니라 한 번에 참조하는 양(워킹 세트) 자체를 줄이는 것이다. 텍스처 해상도와 압축 포맷 정리, 안 쓰는 번들 언로드, 씬 단위 상주 메모리 예산이 그 수단이다.

교체가 필요할 때 무엇을 내보낼지가 페이지 교체 알고리즘이다. LRU는 가장 오래 참조되지 않은 것을, FIFO는 들어온 지 오래된 것을, LFU는 참조 횟수가 적은 것을 내보낸다. 앞으로 쓸 시점을 아는 OPT는 구현할 수 없는 이론적 기준이다. 참고로 32비트 프로세스가 4GB를 못 넘는 것도 가상 주소의 문제다. 포인터가 32비트면 서로 다른 번지를 2^32개, 바이트 단위로 4GB까지만 가리킬 수 있다.

면접에서 이렇게 답한다

  • 가상 메모리가 왜 필요한가 — 프로세스를 서로 격리하고, 물리 메모리보다 큰 프로그램을 돌리고, 공유 라이브러리를 물리 한 벌로 같이 쓰기 위해서다. 대가는 주소 변환 비용과 페이지 폴트 지연이고, TLB가 앞쪽 비용을 줄인다.
  • 페이지 폴트를 줄이려면 — 한 번에 참조하는 범위를 줄이고 접근을 순차적으로 만든다. 게임에서는 필요한 에셋을 로딩 구간에 몰아 올리고, 상주 메모리 예산을 정해 지키는 식이다.
  • 페이징과 세그멘테이션의 차이는 — 페이징은 고정 크기라 외부 단편화가 없고 내부 단편화가 남는다. 세그멘테이션은 논리 단위라 보호와 공유를 걸기 좋지만 크기가 달라 외부 단편화가 생긴다.
  • 모바일에서 메모리 한도를 넘기면 — 스왑이 없거나 제한적이라 스래싱 대신 OS가 앱을 종료시킨다. 그래서 기기별 상주 예산을 정하고 텍스처·번들 단위로 지키는 것이 실제 대응이다.

흔한 오해

  • 페이지 폴트는 버그다 — 요구 페이징의 정상 동작이다. 잘못된 주소 접근만 오류가 되고, 문제는 폴트의 존재가 아니라 빈도다.
  • 페이징에도 외부 단편화가 있다 — 크기가 모두 같아 빈 프레임 어디에나 들어가므로 외부 단편화가 없다. 남는 것은 페이지 안의 내부 단편화다.
  • TLB는 데이터를 캐시한다 — TLB가 담는 것은 데이터가 아니라 주소 변환 결과다. L1·L2 같은 데이터 캐시와는 다른 장치다.
  • 프레임을 늘리면 페이지 폴트는 반드시 준다 — FIFO에서는 늘렸는데 늘어나는 경우가 있다(벨라디의 역설). LRU 같은 스택 알고리즘에서는 이런 일이 없다.
  • 32비트 프로세스는 4GB를 다 쓴다 — 커널이 절반 안팎을 가져가므로 실제로 쓸 수 있는 양은 그보다 적다.
