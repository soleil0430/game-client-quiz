운영체제·동시성

가상 메모리

프로세스마다 가짜 주소를 주고 필요한 페이지만 올린다. 모바일 메모리 크래시의 배경이다

테스트 기기에서 멀쩡하던 빌드가 구형 단말에서만 죽는다. 로그에는 원인이 거의 안 남는다.

운영체제가 메모리를 어떻게 빌려주고 언제 뺏는지 알아야 이 죽음이 읽힌다.

모든 주소는 가짜이고 MMU가 물리 주소로 바꾼다

가상 메모리는 프로세스마다 이 주소 공간은 너 혼자 쓴다고 거짓말을 해 주는 장치다. 프로그램이 다루는 주소는 전부 가상 주소다. CPU 안의 MMU가 페이지 테이블을 보고 실제 물리 주소로 바꾼다.

한 겹을 끼워 넣어 얻는 것이 셋이다. 프로세스끼리 남의 메모리를 못 건드리게 격리하고, 물리 메모리보다 큰 프로그램을 돌리고, 같은 공유 라이브러리를 물리적으로 한 벌만 두고 같이 쓴다.

페이지 테이블을 매번 읽으면 메모리 접근이 두 번이 된다. 최근 변환 결과를 담아 두는 작은 캐시를 따로 두는 이유다. 이것이 TLB이고, 문맥 전환 때 이 TLB가 무효화되는 것도 전환이 비싸지는 까닭이다.

페이지 폴트는 버그가 아니라 정상 동작이다

주소 공간은 고정 크기 페이지(보통 4KB)로 잘라 관리한다. 접근한 페이지가 물리 메모리에 없으면 페이지 폴트가 난다. 운영체제가 그 페이지를 올린 뒤 멈췄던 명령을 다시 실행한다.

폴트 자체는 요구 페이징의 정상 동작이라는 말이다. 유효하지 않은 주소일 때만 진짜 오류가 된다.

다만 저장 장치까지 내려가는 하드 폴트는 자릿수로 느리다. 게임에서는 그 한 번이 프레임 스파이크로 보인다.

단편화는 안에서 남거나 밖에서 흩어진다

내부 단편화는 필요한 양보다 크게 떼어 준 탓에 블록 안에 남는 공간이다. 외부 단편화는 빈 공간이 흩어져, 총량은 충분한데 연속된 큰 블록을 못 잡는 상황이다.

페이징 세그멘테이션
나누는 기준 고정 크기(보통 4KB) 코드·스택 같은 논리 단위
외부 단편화 없다 — 빈 프레임 아무 곳에나 들어간다 생긴다 — 크기가 제각각이다
내부 단편화 마지막 페이지에 자투리가 남는다 거의 없다

게임을 몇 시간 돌린 뒤 텍스처 한 장 할당이 실패하는 것이 외부 단편화의 전형이다. 실제 시스템은 둘을 섞어 쓴다.

모바일에는 스왑이 없어 강제 종료로 끝난다

물리 프레임이 모자라면 올리자마자 다시 내보내기를 반복하는 스래싱에 빠진다. CPU가 대부분의 시간을 입출력 대기로 보낸다. iOS에는 스왑이 없어 이 단계 대신 OS의 강제 종료가 오고, 안드로이드도 비슷하게 앱을 정리한다.

그럼 클라이언트가 할 일은 교체를 잘하는 것인가. 아니다. 한 번에 참조하는 양, 곧 워킹 세트를 줄이는 것이 답이다. 텍스처 해상도와 압축 포맷 정리, 안 쓰는 번들 언로드, 씬 단위 상주 예산이 그 수단이다.

교체가 필요할 때 무엇을 내보낼지가 페이지 교체 알고리즘이다. LRU는 가장 오래 참조되지 않은 것을, FIFO는 들어온 지 오래된 것을 내보낸다. 앞으로 쓸 시점을 아는 OPT는 구현할 수 없는 이론적 기준이다.

면접에서 이렇게 답한다

  • 가상 메모리가 왜 필요한가 — 프로세스를 서로 격리하고, 물리 메모리보다 큰 프로그램을 돌리고, 공유 라이브러리를 한 벌로 같이 쓰기 위해서다. 대가는 주소 변환 비용과 페이지 폴트 지연이고 TLB가 앞쪽 비용을 줄인다고 덧붙인다.
  • 페이지 폴트를 줄이려면 — 한 번에 참조하는 범위를 줄이고 접근을 순차적으로 만든다. 게임에서는 필요한 에셋을 로딩 구간에 몰아 올린다. 상주 메모리 예산을 정해 지키는 것도 같은 이야기다.
  • 페이징과 세그멘테이션의 차이는 — 페이징은 고정 크기라 외부 단편화가 없고 내부 단편화가 남는다. 세그멘테이션은 논리 단위라 보호와 공유를 걸기 좋은 대신 크기가 달라 외부 단편화가 생긴다.
  • 모바일에서 메모리 한도를 넘기면 — 스왑이 없거나 제한적이라 스래싱 대신 OS가 앱을 종료시킨다. 기기별 상주 예산을 정하고 텍스처와 번들 단위로 지키는 것이 실제 대응이라고 답한다.

이런 오해를 한다

  • “페이지 폴트는 버그다” — 요구 페이징의 정상 동작이다. 문제는 폴트의 존재가 아니라 빈도다.
  • “페이징에도 외부 단편화가 있다” — 크기가 모두 같아 빈 프레임 어디에나 들어간다. 남는 것은 페이지 안의 내부 단편화다.
  • “TLB는 데이터를 캐시한다” — TLB가 담는 것은 주소 변환 결과다. L1·L2 같은 데이터 캐시와는 다른 장치다.
  • “프레임을 늘리면 폴트는 반드시 준다” — FIFO에서는 늘렸는데 폴트도 느는 경우가 있다(벨라디의 역설). LRU 같은 스택 알고리즘에서는 이런 일이 없다.
  • “32비트 프로세스는 4GB를 다 쓴다” — 포인터가 32비트라 4GB까지 가리키지만 커널이 절반 안팎을 가져간다. 실제로 쓸 수 있는 양은 그보다 적다.

3줄 정리

  • 가상 주소를 MMU가 페이지 테이블로 물리 주소에 이어 준다
  • 페이지 폴트는 정상 동작이고, 문제는 빈도와 하드 폴트다
  • 모바일은 스왑이 없어 한도를 넘기면 OS가 앱을 죽인다
