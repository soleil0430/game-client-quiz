스크립팅 백엔드

내가 쓴 C#이 기기에서 실제로 실행되기까지 — Mono의 JIT과 IL2CPP의 AOT가 갈리는 지점

핵심 개념

C# 소스는 그대로 실행되지 않는다. 먼저 IL(중간 언어)로 컴파일되고, 그 IL을 기기에서 어떻게 네이티브 명령으로 바꿔 돌릴지를 정하는 것이 스크립팅 백엔드다. Unity는 Mono와 IL2CPP 둘을 제공한다.

Mono는 JIT이다. IL을 앱에 담아 두고 실행 중에 필요한 메서드를 그때그때 네이티브로 번역해서 빌드가 빠르고 개발 반복에 좋다. IL2CPP는 AOT다. IL을 전부 C++ 소스로 변환한 뒤 플랫폼 네이티브 컴파일러로 미리 컴파일한다. 실행 시점에 번역할 것이 없어 빠르고, 실행 중 코드 생성을 금지하는 iOS에서는 선택이 아니라 필수다. 대신 C++ 변환과 컴파일이 통째로 들어가 빌드가 오래 걸린다.

변환 시점실행 중에 IL을 네이티브로빌드 때 IL을 C++로, 다시 네이티브로
빌드 시간짧다길다
실행 성능보통대체로 더 빠르다
런타임 코드 생성가능불가능
쓰이는 곳에디터·개발 빌드iOS는 필수, 안드로이드 출시에도 사실상 표준

AOT라는 성질에서 제약이 따라온다. 첫째, System.Reflection.Emit처럼 실행 중에 코드를 만드는 기능을 쓸 수 없다. 리플렉션으로 읽는 것은 되지만 새로 만드는 것이 안 된다. 둘째, 아무도 참조하지 않는 것처럼 보이는 타입을 잘라내는 코드 스트리핑이 돈다. 문자열 이름으로만 접근하는 코드는 잘려 나가므로 link.xml에 보존 대상을 적거나 [Preserve]를 붙인다. 셋째, 값 타입 제네릭은 빌드 때 쓰인 조합만 생성되어 런타임에 새 조합을 만들면 예외가 난다.

C# 문법 버전도 여기에 묶인다. Unity 2022 LTS는 C# 9와 .NET Standard 2.1 수준이라 그보다 최신 문법은 컴파일러가 거부하고, 통과하더라도 대응하는 런타임 API가 없으면 실행 시점에 깨진다. Unity 6부터 지원 범위가 올라가므로 팀이 쓰는 버전부터 확인한다.

개발 편의 쪽에는 도메인 리로드가 있다. 에디터에서 플레이를 누르면 Unity가 매니지드 도메인을 다시 올려 static 필드를 초기값으로 되돌리고 이벤트 구독을 끊는다. 매번 새로 켠 상태가 되지만 프로젝트가 커지면 그만큼 기다린다. Reload Domain을 끄면 진입이 빨라지는 대신 static 값과 이벤트 구독이 이전 플레이 상태 그대로 남는다. 에디터 전용 설정이라 빌드에는 영향이 없다.

public static class ScoreBoard
{
    private static int total;

    // 도메인 리로드를 꺼도 플레이를 시작할 때마다 static을 되돌린다
    [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
    private static void ResetStatics() => total = 0;
}

면접에서 이렇게 답한다

  • Mono와 IL2CPP의 차이는 — Mono는 IL을 실행 중에 번역하는 JIT이고 IL2CPP는 IL을 C++로 바꿔 미리 컴파일하는 AOT다. IL2CPP가 실행은 빠르지만 빌드가 길고, iOS처럼 JIT이 금지된 플랫폼에서는 필수다.
  • IL2CPP로 바꾸면 무엇을 조심하나 — 런타임 코드 생성이 막히고 코드 스트리핑이 돈다. 문자열로만 접근하는 타입은 잘릴 수 있어 link.xml이나 [Preserve]로 보존한다. 제네릭도 빌드 때 쓰인 조합만 생성된다.
  • 최신 C# 문법을 쓰면 — 에디터 버전이 지원하는 C# 버전까지만 쓸 수 있고 2022 LTS는 C# 9다. 문법이 통과해도 런타임 API가 없으면 실행 시점에 깨지므로 지원 범위를 먼저 확인한다.
  • 도메인 리로드는 왜 신경 쓰나 — 진입 시간을 줄이려고 끄면 static 값과 이벤트 구독이 남아 두 번째 플레이부터 동작이 달라진다. RuntimeInitializeOnLoadMethod로 static을 직접 초기화해 두면 안전하다.

흔한 오해

  • IL2CPP는 C++로 바꿔 주니 그 C++을 읽고 고치면 된다 — 사람이 읽으라고 만든 코드가 아니다. 최적화와 디버깅은 C# 쪽에서 한다.
  • IL2CPP에서는 리플렉션을 아예 못 쓴다 — 읽는 리플렉션은 된다. 막히는 것은 Reflection.Emit 같은 실행 중 코드 생성이고, 나머지는 스트리핑에 잘리지 않게 보존하면 쓸 수 있다.
  • IL2CPP로 바꾸면 항상 빨라진다 — 스크립트 실행은 대체로 빨라지지만 GPU나 로드가 병목이면 체감 차이가 없다. 빌드 시간은 확실히 늘어난다.
  • 에디터에서 잘 돌면 IL2CPP 빌드도 똑같이 돈다 — 에디터는 Mono라 스트리핑도 AOT 제약도 없다. 리플렉션이나 제네릭이 많은 코드는 IL2CPP 빌드로 따로 확인해야 한다.
