C# 언어

런타임과 컴파일

C#이 IL을 거쳐 기계어가 되는 두 단계가 Mono와 IL2CPP의 차이를 만든다

에디터에서는 잘 돌던 코드가 iOS 빌드에서만 죽는다. 리플렉션으로 찾던 타입이 빌드에는 없었다.

같은 C#인데 Mono에서는 왜 멀쩡할까. 번역을 언제 하느냐를 알면 풀린다.

C# 코드는 두 번 번역된다

빌드할 때 컴파일러가 하는 일은 기계어를 만드는 것이 아니다. 소스를 IL(중간 언어)과 메타데이터로 바꿔 어셈블리에 넣는다. 기계어로 바꾸는 일은 뒤로 미룬다.

굳이 둘로 나눈 이유가 둘 있다. IL은 CPU에 독립적이라 같은 어셈블리를 여러 아키텍처에서 쓸 수 있다. 함께 실린 메타데이터 덕분에 런타임이 타입 정보를 읽는다.

GC와 리플렉션, 직렬화가 전부 이 메타데이터에 기댄다. 메타데이터가 없으면 런타임은 객체 안에 무엇이 들었는지 알 길이 없다.

언제 번역하느냐가 JIT와 AOT를 가른다

세 방식의 차이는 한 가지 질문으로 압축된다. 언제 번역하는가.

방식 번역 시점 대가
JIT 실행 중, 메서드가 처음 호출될 때 그 메서드만 첫 호출이 느리고, 실행 중 코드를 만들 권한이 필요하다
AOT 빌드할 때 전부 미리 빌드가 오래 걸리고, 실행 중 새 타입을 만들 수 없다
인터프리터 번역하지 않고 한 줄씩 해석 결과를 남기지 않아 같은 줄을 돌 때마다 다시 해석한다

JIT는 실행 중에 필요한 부분을 기계어로 번역하고 그 결과를 캐싱한다. 첫 호출이 느린 대신 실제 실행 환경에 맞춰 최적화할 수 있다. AOT는 빌드 때 미리 네이티브 코드로 번역해 두므로 시작이 빠르고, 런타임 코드 생성이 금지된 iOS 같은 플랫폼에서는 필수다. 인터프리터는 번역 결과를 남기지 않고 한 줄씩 해석해 실행한다.

Unity에서는 Mono가 JIT, IL2CPP가 AOT다. IL2CPP는 IL을 C++ 소스로 변환한 뒤 플랫폼 네이티브 컴파일러로 빌드하는 방식이라, JIT가 금지된 iOS에서는 선택지가 이것뿐이고 보통 실행 속도도 더 빠르다.

대가는 빌드 시간과 제약이다. AOT 특성상 코드 스트리핑이나 동적 제네릭·리플렉션 때문에 런타임에 실패할 수 있어 link.xml 설정이 필요할 때가 있다. 맨 앞의 iOS 빌드가 그 이야기였고, 그때 link.xml이나 [Preserve]로 지킬 타입을 표시한다.

Mono는 JIT라 빌드가 빨라 에디터와 개발 빌드에 쓴다.

.NET과 C#은 이름이 비슷해 섞이기 쉽다. .NET은 런타임과 클래스 라이브러리, 도구를 묶은 플랫폼이고 C#은 그 위에서 도는 언어다. Unity는 Microsoft의 CLR 대신 자체 포크한 Mono나 IL2CPP를 쓴다.

리플렉션은 왜 느린가

리플렉션은 실행 중에 Type 정보를 뒤져 필드나 메서드를 찾아 호출하는 기능이다. 실행 중에 타입 정보를 읽어 멤버를 부를 수 있다는 뜻이고, 인스펙터와 직렬화기, 테스트 러너가 이것으로 돈다.

느린 이유는 '뒤져서'에 있다. 이름을 문자열로 찾고, 인자는 object[]에 싸서 넘긴다. 문자열 탐색과 동적 호출이라 직접 호출보다 수십 배 이상 느리고 할당도 생긴다.

매번 뒤지는 방식과 한 번만 찾아 두는 방식을 나란히 둔 코드다:

// 매번 메타데이터를 문자열로 뒤진다. 인자도 object[]로 싸서 박싱된다
typeof(Enemy).GetMethod("TakeDamage").Invoke(enemy, new object[] { 10 });

// 한 번만 찾아 델리게이트로 만들어 두면 그 뒤로는 직접 호출과 비슷하다
static readonly Dictionary<string, Action<Enemy, int>> Table = new();

static Action<Enemy, int> GetCall(string name)
{
    if (!Table.TryGetValue(name, out var call))
        Table[name] = call = (Action<Enemy, int>)Delegate.CreateDelegate(
            typeof(Action<Enemy, int>), typeof(Enemy).GetMethod(name));
    return call;
}

IL2CPP 같은 AOT 빌드에서는 쓰이지 않는 코드가 스트리핑돼 리플렉션이 실패하기도 한다. 반복 호출은 위처럼 델리게이트로 캐싱하거나 소스 생성기로 대체한다.

더 나은 답은 아예 빌드할 때 코드를 만들어 두는 것이다. Roslyn 소스 생성기는 컴파일 시점에 호출 코드를 생성한다. 런타임 탐색이 사라지고, 이름이 틀리면 컴파일 단계에서 걸리며, 스트리핑에도 살아남는다.

직렬화는 주소를 버리고 값과 구조만 적는다

메모리에 흩어져 있는 객체를 JSON이나 바이너리처럼 연속된 데이터로 바꿔 파일 저장이나 네트워크 전송이 가능하게 만드는 것이 직렬화다. 역직렬화는 그 데이터를 다시 객체로 되돌리는 것이고, 둘은 한 쌍이다.

참조 주소는 프로세스마다 달라 저장해도 의미가 없으므로 값과 구조만 기록한다. Unity는 [SerializeField]로 인스펙터와 프리팹 직렬화를 처리하며, 프로퍼티는 기본적으로 직렬화되지 않는다.

면접에서 이렇게 답한다

  • C#은 C++보다 느린가 — 같은 알고리즘이면 차이는 대개 작다고 답한다. GC와 경계 검사 같은 안전장치 비용을 내는 대신 JIT는 실제 실행 중인 CPU에 맞춰 최적화한다. 게임에서 체감하는 느림은 언어보다 매 프레임 할당과 캐시를 무시한 데이터 배치에서 온다고 덧붙인다.
  • JIT, AOT, 인터프리터의 차이 — JIT는 실행 중 메서드 단위로 번역해 캐싱한다. AOT는 빌드 때 전부 미리 번역하고, 인터프리터는 결과를 남기지 않고 한 줄씩 해석한다. Unity에서는 Mono가 JIT, IL2CPP가 AOT라고 예를 붙인다.
  • 리플렉션을 지양하는 이유 — 느리고 할당이 생긴다. IL2CPP에서는 스트리핑에 지워져 런타임에 가서야 실패가 드러난다. 반복 호출은 델리게이트로 캐싱하고, 구조가 고정적이면 소스 생성기로 옮긴다.
  • 텍스트에 적힌 이름으로 메서드 100여 개를 호출해야 한다면 — 이름과 델리게이트를 짝지은 사전을 시작할 때 한 번 만들어 두고 호출은 조회만 하게 만든다. 등록을 어트리뷰트 스캔이나 소스 생성기로 자동화하면 없는 이름을 로딩 시점에 걸러낼 수 있다.
  • IL을 보면 무엇이 도움 되나 — 박싱이 일어난 지점이나 클로저 때문에 생긴 클래스가 드러난다. 소스만 봐서는 보이지 않는 비용이다.

이런 오해를 한다

  • “IL2CPP를 쓰면 C++로 코드를 짜야 한다” — 작성하는 코드는 그대로 C#이다. 변환된 C++는 사람이 읽으라고 만든 결과물이 아니다.
  • “JIT는 시작할 때 프로그램 전체를 번역한다” — 메서드가 처음 호출될 때 그 메서드만 번역하고 캐싱한다. 첫 진입에서만 끊김이 생기는 것도 그 때문이다.
  • “인터프리터도 번역 결과를 캐싱한다” — 캐싱하는 순간 그것이 JIT다. 인터프리터는 남기지 않기 때문에 느리다.
  • “IL2CPP에서는 리플렉션이 아예 안 된다” — 동작한다. 문제는 코드에서 참조가 보이지 않아 스트리핑에 지워지는 것이므로 보존 설정으로 남긴다.
  • “직렬화는 파일 저장에만 쓴다” — 네트워크 전송과 프리팹·씬 저장, 인스펙터 표시가 모두 같은 구조 위에 있다.

3줄 정리

  • C#은 빌드 때 IL로, 나중에 기계어로 두 번 번역된다
  • Mono는 JIT라 실행 중에, IL2CPP는 AOT라 빌드 때 번역한다
  • 리플렉션은 매번 뒤져서 느리다. 캐싱하거나 생성기로 옮긴다
