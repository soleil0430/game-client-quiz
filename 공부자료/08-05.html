컴퓨터 구조

캐시 라인·엔디언·float 정밀도는 프레임 튐과 좌표 떨림으로 눈앞에 나타난다

핵심 개념

메모리 계층은 빠르고 작고 비싼 것에서 느리고 크고 싼 것으로 내려간다. 레지스터에서 L1, L2, L3, 메인 메모리, 저장 장치 순이고 L1은 코어마다 붙어 있으며 L3는 보통 코어들이 공유한다. L1과 메인 메모리의 지연 차이가 100배쯤 되기 때문에, 요즘 게임 코드의 속도는 연산 횟수보다 메모리 접근 패턴이 정한다.

계층대략 크기대략 지연
L1(코어 전용)수십 KB수 사이클
L2수백 KB ~ 수 MB십수 사이클
L3(코어 공유)수 MB 이상수십 사이클
메인 메모리GB 단위수백 사이클

캐시는 바이트 하나가 아니라 캐시 라인(보통 64바이트) 단위로 퍼 온다. 여기서 두 가지 지역성이 나온다. 방금 쓴 데이터를 곧 다시 쓰는 시간 지역성과, 가까운 주소를 잇따라 쓰는 공간 지역성이다. C/C++의 2차원 배열은 행 우선으로 저장되므로 안쪽 반복이 열을 도는 순회는 한 번 퍼 온 라인을 끝까지 쓰고, 열을 바깥에 두면 매 접근마다 새 라인을 읽어 미스가 난다. 연산 횟수는 같은데 몇 배가 차이 나는 이유다.

// 캐시 친화: 안쪽 반복이 이어 붙은 주소를 훑는다
for (int y = 0; y < H; y++)
    for (int x = 0; x < W; x++)
        sum += grid[y][x];

// 캐시 적대: 한 번 읽을 때마다 새 캐시 라인
for (int x = 0; x < W; x++)
    for (int y = 0; y < H; y++)
        sum += grid[y][x];

클라이언트에서 이 이야기는 데이터 배치로 이어진다. 파티클 1만 개의 위치만 갱신하는데 구조체 하나에 색·수명·머티리얼까지 들어 있으면 라인마다 쓰지 않을 값이 딸려 와 대역폭을 버린다. 필요한 필드만 따로 배열로 모으는 배치(SoA)가 빠른 이유이고, 유니티 DOTS가 컴포넌트 조합별로 메모리를 묶는 것도 같은 계산이다.

엔디언은 여러 바이트로 된 수를 메모리에 놓는 순서다. 리틀 엔디언은 낮은 자리 바이트를 낮은 주소에 두고 x86과 대부분의 ARM이 쓴다. 네트워크 바이트 순서는 빅 엔디언으로 정해져 있어서, 정수를 그대로 패킷에 실으면 기종이 다를 때 값이 뒤집힌다. 바이트 단위인 문자열은 영향이 없고 여러 바이트 수를 보낼 때만 변환한다. 음수를 담는 2의 보수도 같은 결의 약속이다. 양수의 비트를 뒤집고 1을 더하므로 8비트에서 -3은 11111101이 되고, 덕분에 뺄셈을 덧셈 회로로 처리할 수 있다.

float은 부호·지수·가수로 나뉘고 단정밀도의 가수는 암시 비트를 포함해 24비트뿐이다. 그래서 값이 커질수록 표현할 수 있는 간격이 넓어진다. 좌표가 수십만 단위가 되면 작은 이동이 아예 반영되지 않거나 값이 튀어 오브젝트가 떨린다. 오픈 월드에서 플레이어가 멀어지면 월드 전체를 원점 쪽으로 되돌리는 원점 이동을 쓰는 이유다. 64비트 빌드로 바꿔도 해결되지 않는다. 포인터가 8바이트가 될 뿐 float은 여전히 4바이트다.

면접에서 이렇게 답한다

  • 캐시 지역성이란 — 시간 지역성은 방금 쓴 데이터를 곧 다시 쓰는 성질, 공간 지역성은 가까운 주소를 잇따라 쓰는 성질이다. 캐시는 라인 단위로 퍼 오므로 붙어 있는 데이터를 순서대로 훑으면 미스가 줄고, 찾으면 히트, 없어서 아래 계층까지 내려가면 미스다.
  • 행 우선과 열 우선 순회의 성능이 왜 다른가 — 배열이 행 단위로 이어 붙어 있어서다. 행을 따라 돌면 한 캐시 라인을 여러 번 쓰고, 열을 따라 돌면 매 접근이 새 라인이라 미스가 난다.
  • 엔디언을 언제 신경 쓰나 — 여러 바이트 정수를 네트워크나 파일로 주고받을 때다. 네트워크 바이트 순서는 빅 엔디언이라 보낼 때 변환하거나, 직렬화 포맷의 규약을 맞춘다.
  • 먼 좌표에서 오브젝트가 떨리는 이유는 — float의 가수가 24비트라 값이 클수록 표현 간격이 넓어지기 때문이다. 원점 이동으로 좌표 크기 자체를 줄이거나, 꼭 필요한 계산만 double로 다룬다.

흔한 오해

  • L1이 L3보다 크다 — 반대다. 코어에 가까울수록 작고 빠르다. L1은 코어 전용이고 L3는 보통 코어들이 공유한다.
  • 캐시는 필요한 바이트만 가져온다 — 라인(보통 64바이트) 단위로 가져온다. 쓰지 않는 필드가 섞여 있으면 그만큼 대역폭이 버려진다.
  • 64비트로 빌드하면 float 정밀도가 올라간다 — 달라지는 것은 포인터 크기와 주소 한계다. float은 그대로 4바이트이고 C#의 int도 플랫폼과 무관하게 4바이트다.
  • -3은 부호 비트만 1로 세우면 된다 — 그것은 부호-크기 표현이다. 2의 보수에서는 비트를 뒤집고 1을 더해 11111101이 된다.
  • 64비트가 무조건 빠르다 — 포인터가 커져 참조가 많은 자료구조는 캐시에 덜 담긴다. 주소 공간과 레지스터를 얻는 대신 치르는 비용이다.
