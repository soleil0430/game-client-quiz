컴퓨터 구조

속도는 연산 횟수가 아니라 메모리 접근 순서가 정한다. 캐시 라인 64바이트가 기준이다

연산 횟수는 똑같은데 실행 시간만 몇 배 차이 나는 코드가 있다. 원인은 계산이 아니라 메모리를 훑는 순서다. 캐시가 어떻게 퍼 오는지 알면 그 차이가 설명된다.

메모리 계층은 아래로 갈수록 느리고 크다

레지스터에서 시작해 L1, L2, L3, 메인 메모리, 저장 장치 순으로 내려간다. L1은 코어마다 붙어 있고 L3는 보통 코어들이 공유한다. 아래로 갈수록 크고 싸지는 대신 느려진다.

캐시는 64바이트 라인 단위로 퍼 온다

캐시는 바이트 하나가 아니라 캐시 라인(보통 64바이트) 통째로 읽어 온다. 여기서 두 가지 지역성이 나온다. 방금 쓴 데이터를 곧 다시 쓰는 시간 지역성과, 가까운 주소를 잇따라 쓰는 공간 지역성이다.

2차원 배열은 행 우선으로 저장된다. 안쪽 반복이 열을 도는 순회는 한 번 퍼 온 라인을 끝까지 쓴다. 열을 바깥에 두면 접근마다 새 라인을 읽어 미스가 난다.

격자 맵을 훑는 두 순회의 차이:

// 캐시 친화: 안쪽 반복이 이어 붙은 주소를 훑는다
for (int y = 0; y < H; y++)
    for (int x = 0; x < W; x++)
        sum += grid[y][x];      // 한 번 퍼 온 라인을 끝까지 쓴다

// 캐시 적대: 연산 횟수는 같은데 몇 배 느리다
for (int x = 0; x < W; x++)
    for (int y = 0; y < H; y++)
        sum += grid[y][x];      // 한 번 읽을 때마다 새 캐시 라인

데이터 배치도 같은 이야기다. 파티클 1만 개의 위치만 갱신하는데 구조체에 색·수명·머티리얼이 함께 들어 있으면, 라인마다 쓰지 않을 값이 딸려 와 대역폭을 버린다. 필요한 필드만 따로 배열로 모으는 배치가 빠른 이유이고, Unity DOTS도 같은 계산이다.

엔디언은 여러 바이트 수를 주고받을 때만 문제다

엔디언은 여러 바이트로 된 수를 메모리에 놓는 순서다. 리틀 엔디언은 낮은 자리 바이트를 낮은 주소에 두고 x86과 대부분의 ARM이 쓴다. 네트워크 바이트 순서는 빅 엔디언이라, 정수를 그대로 패킷에 실으면 기종이 다를 때 값이 뒤집힌다.

바이트 단위인 문자열은 영향이 없다. 음수를 담는 2의 보수도 같은 결의 약속이다. 양수의 비트를 뒤집고 1을 더하므로 8비트에서 -3은 11111101이 되고, 덕분에 뺄셈을 덧셈 회로로 처리한다.

먼 좌표에서 오브젝트가 떨리는 이유

float은 부호·지수·가수로 나뉘고, 단정밀도의 가수는 암시 비트를 포함해 24비트뿐이다. 그래서 값이 커질수록 표현할 수 있는 간격이 넓어진다. 좌표가 수십만 단위가 되면 작은 이동이 아예 반영되지 않거나 값이 튄다.

오픈 월드에서 월드 전체를 원점 쪽으로 되돌리는 원점 이동을 쓰는 이유가 이것이다. 64비트 빌드로 바꿔도 해결되지 않는다. 포인터가 8바이트가 될 뿐 float은 여전히 4바이트다.

면접에서 이렇게 답한다

  • 캐시 지역성이란 — 시간 지역성은 방금 쓴 데이터를 곧 다시 쓰는 성질, 공간 지역성은 가까운 주소를 잇따라 쓰는 성질이다. 캐시는 라인 단위로 퍼 오므로 붙어 있는 데이터를 순서대로 훑으면 미스가 준다.
  • 행 우선과 열 우선 순회의 성능이 왜 다른가 — 배열이 행 단위로 이어 붙어 있어서다. 행을 따라 돌면 한 캐시 라인을 여러 번 쓴다. 열을 따라 돌면 접근마다 새 라인이라 미스가 난다.
  • 엔디언을 언제 신경 쓰나 — 여러 바이트 정수를 네트워크나 파일로 주고받을 때다. 네트워크 바이트 순서는 빅 엔디언이라 보낼 때 변환하거나 직렬화 포맷의 규약을 맞춘다.
  • 먼 좌표에서 오브젝트가 떨리는 이유는 — float의 가수가 24비트라 값이 클수록 표현 간격이 넓어지기 때문이다. 원점 이동으로 좌표 크기를 줄이거나 꼭 필요한 계산만 double로 다룬다.

이런 오해를 한다

  • L1이 L3보다 크다 — 반대다. 코어에 가까울수록 작고 빠르다. L1은 코어 전용이고 L3는 보통 공유한다.
  • 캐시는 필요한 바이트만 가져온다 — 라인(보통 64바이트) 단위로 가져온다. 쓰지 않는 필드가 섞여 있으면 그만큼 대역폭이 버려진다.
  • 64비트로 빌드하면 float 정밀도가 올라간다 — 달라지는 것은 포인터 크기와 주소 한계다. float은 그대로 4바이트이고 C#의 int도 플랫폼과 무관하게 4바이트다.
  • -3은 부호 비트만 1로 세우면 된다 — 그것은 부호-크기 표현이다. 2의 보수에서는 비트를 뒤집고 1을 더해 11111101이 된다.
  • 64비트가 무조건 빠르다 — 포인터가 커져 참조가 많은 자료구조는 캐시에 덜 담긴다. 주소 공간과 레지스터를 얻는 대신 치르는 비용이다.

3줄 정리

  • 캐시는 64바이트 라인 단위라 접근 순서가 속도를 정한다
  • 엔디언은 여러 바이트 수를 네트워크로 보낼 때만 문제다
  • float 가수는 24비트라 좌표가 커지면 값이 떨린다
