운영체제·동시성

비동기

async는 스레드를 만들지 않는다. 기다리는 동안 스레드를 놓아주는 장치다

다운로드가 끝날 때까지 프로그레스 바가 멈춰 있다. 기다리는 동안 스레드를 붙잡고 있어서다.

그 시간에 스레드를 놓아주면 같은 1초 동안 화면이 계속 돈다.

블로킹과 동기는 서로 다른 축이다

블로킹 여부는 제어권을 언제 돌려주느냐의 문제다. 블로킹·논블로킹은 호출한 함수가 제어권을 바로 돌려주는지의 문제이고, 동기·비동기는 작업 완료를 호출자가 직접 기다려 확인하는지 통보받는지의 문제다.

논블로킹은 바로 돌아오지만 아직 안 됐다는 응답일 수 있어, 결과가 완성되어 오는 것과는 다르다. 비동기가 곧 새 스레드를 뜻하지도 않는다. 완료 통지는 스레드 없이도 처리된다.

Thread.Sleep은 그 스레드를 통째로 재우므로 메인 스레드에서 부르면 화면이 멈추고, await Task.Delay는 타이머를 걸고 제어권을 돌려줘 그동안 다른 작업이 돈다.

Unity에서 한 프레임만 쉬려면 코루틴의 yield return null이나 UniTask의 Yield가 더 알맞다. Task.Delay도 타이머 해상도만큼 오차가 있다.

컴파일러가 메서드를 상태 기계로 쪼갠다

async/await는 기다림을 상태 기계로 해낸다. 컴파일러는 async 메서드를 await 지점마다 멈췄다 이어갈 수 있는 상태 기계로 바꾸고, 완료되면 이어서 실행할 부분을 콜백으로 등록한다. 컴파일러가 메서드를 상태 기계로 바꿔서 처리한다는 뜻이다.

그래서 await 중에는 스레드가 풀려 다른 일을 할 수 있다. async는 스레드를 새로 만들지 않는다. 계산을 다른 스레드로 옮기려면 Task.Run을 명시해야 한다.

Unity에서는 await 뒤가 다시 메인 스레드다

이어 실행할 조각을 어디서 돌릴지는 동기화 컨텍스트가 정한다. Unity는 UnitySynchronizationContext를 걸어 둔다. 그 덕분에 await 뒤 코드가 메인 스레드에서 이어지며 Unity API를 그대로 쓸 수 있다.

다만 Task는 참조 형식이라 호출마다 할당이 생긴다. 매 프레임 도는 경로라면 이 할당이 GC 부담으로 쌓인다. 모바일에서는 할당을 줄이려고 UniTask를 많이 쓰고, Unity 2023 이후면 Awaitable도 쓴다.

팝업 버튼이 눌릴 때까지 한 함수 안에서 기다리는 모습이다: 

private TaskCompletionSource<bool> _tcs;   // 버튼을 기다릴 손잡이

public Task<bool> WaitForAnswerAsync()     // await할 Task만 돌려준다
{
    _tcs = new TaskCompletionSource<bool>();
    return _tcs.Task;
}
public void OnYesClicked() => _tcs?.TrySetResult(true);   // 대기가 풀린다

private async Task ShowAsync()
{
    bool ok = await WaitForAnswerAsync();  // 기다려도 프레임은 계속 돈다
    if (ok) transform.position = Vector3.zero;   // 여기는 메인 스레드다
}

async void는 왜 피하나

async void의 문제는 돌려줄 Task가 없다는 한 가지에서 다 나온다. async Task는 호출한 쪽이 await로 완료를 기다리고 예외도 받을 수 있지만, async void는 돌려받을 Task가 없어 끝났는지 알 수 없고 예외가 호출한 쪽 try-catch에 잡히지 않는다.

호출한 쪽이 완료를 기다리거나 예외를 try-catch로 잡을 수 없어서다. 이벤트 핸들러처럼 시그니처가 void로 정해진 곳에서만 쓰고, 그 안에서 예외를 직접 처리하는 것이 좋다. async 자체는 새 스레드를 만들지 않는다.

ValueTask는 구조체라 캐시 히트처럼 값이 이미 준비된 경로에서 Task 객체 할당을 피할 수 있다. 동기 완료가 잦을 때 할당을 줄여 준다는 말이다.

대신 두 번 await하거나 저장해 두고 돌려쓰면 안 되고, 실제로 비동기로 진행되는 경우가 대부분이면 이득이 없다. 그래서 기본은 Task, 호출이 아주 잦고 대개 동기로 끝나는 API에만 ValueTask를 고려한다.

면접에서 이렇게 답한다

  • 동기·비동기와 블로킹·논블로킹 — 블로킹 여부는 제어권을 언제 돌려주느냐, 동기 여부는 완료를 직접 확인하느냐 통보받느냐다. 축이 달라서 논블로킹이면서 동기인 폴링 같은 조합도 있다고 예를 든다.
  • async/await 내부 동작 — 컴파일러가 메서드를 await마다 멈췄다 이어갈 수 있는 상태 기계로 바꾼다. 완료되면 이어갈 조각을 콜백으로 등록한다. 대기 중에는 스레드가 풀리며 async 자체가 스레드를 만들지는 않는다고 못을 박는다.
  • Unity에서 언제 쓰나 — 네트워크 요청이나 에셋 로드처럼 대기가 있는 흐름에 쓴다. 동기화 컨텍스트 덕에 await 뒤가 메인 스레드라 Unity API를 그대로 쓴다. 할당이 문제면 UniTask로 바꾼다.
  • async void를 피하는 이유 — 반환할 Task가 없어 완료를 기다릴 수도, 예외를 호출자가 잡을 수도 없다. 시그니처가 void로 고정된 이벤트 핸들러에서만 쓴다.
  • 버튼이 눌릴 때까지 기다리는 로직 — Update 폴링은 상태 변수가 흩어지고 콜백은 단계가 늘수록 중첩된다. TaskCompletionSource로 감싸 await하면 흐름이 한 함수에 남는다. 수 프레임짜리 연출이면 코루틴도 괜찮다.

이런 오해를 한다

  • “async를 붙이면 별도 스레드에서 돈다” — 대기 지점에서 제어권을 돌려줄 뿐이다. 계산을 옮기려면 Task.Run이 필요하다.
  • “await 뒤 코드는 다른 스레드다” — 동기화 컨텍스트가 있으면 원래 컨텍스트로 돌아온다. Unity에서는 메인 스레드로 복귀한다.
  • “Task.Delay와 Thread.Sleep은 같다” — Sleep은 스레드를 붙잡고 자고 Delay는 놓아준다.
  • “ValueTask가 언제나 빠르다” — 실제로 비동기로 진행되는 경로가 대부분이면 이득이 없다.
  • “결과는 .Result로 받으면 된다” — 메인 스레드에서 블로킹하면 컨텍스트가 묶여 데드락이 나기 쉽다.

3줄 정리

  • async는 스레드를 만들지 않고 대기 중에 놓아줄 뿐이다
  • 컴파일러가 await마다 끊어 상태 기계로 바꿔 준다
  • Unity에서는 await 뒤가 메인 스레드라 API를 그대로 쓴다
