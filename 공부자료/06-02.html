디자인 패턴

패턴은 문제가 있을 때만 꺼낸다. 어디에 썼는지를 말할 수 있어야 한다

보스 페이즈가 늘 때마다 Update의 if-else가 한 단씩 깊어지는 코드를 누구나 본다. 이런 문제는 이미 남들이 다 겪었고, 해결책에는 이름이 붙어 있다.

디자인 패턴은 자주 나오는 설계 문제의 이름 붙은 해결책이다. 이름을 대면 팀이 같은 그림을 떠올린다. 문제가 없는데 꺼내면 클래스만 는다.

생성·구조·행위 세 갈래로 나눠 외운다

GoF 분류는 만드는 것, 엮는 것, 주고받는 것이다. 갈래를 먼저 말하고 갈래마다 써 본 패턴을 대면 답이 정리된다.

추상 팩토리와 플라이웨이트는 각각 생성·구조, 템플릿 메서드는 행위다. 목록을 외우는 것이 목적은 아니다. 지금 겪는 문제가 어느 갈래인지 짚는 것이 목적이다.

싱글톤인데 왜 둘이 되나

DontDestroyOnLoad로 남긴 매니저가 그 씬을 다시 로드하면 새로 생긴 같은 매니저와 겹치기 때문이다. 싱글톤 코드의 핵심이 Awake의 중복 처리인 것도 그래서다.

먼저 자리를 잡은 쪽을 남기고 늦게 온 쪽을 지우는 코드다:

public class SoundManager : MonoBehaviour
{
    public static SoundManager Instance { get; private set; }

    private void Awake()
    {
        // 이미 살아 있는 인스턴스가 있으면 늦게 온 자신을 지운다
        if (Instance != null && Instance != this) { Destroy(gameObject); return; }

        Instance = this;
        DontDestroyOnLoad(gameObject);  // 씬이 바뀌어도 살아남는다
    }
}

if 더미를 상태 객체로 나누는 상태 패턴

bool 몇 개로 상태를 관리하면 “죽었는데 공격 중” 같은 불가능한 조합이 생긴다. 상태 패턴은 상태마다 클래스를 두어 한 번에 하나만 켜지게 만든다.

진입·갱신·퇴장을 상태마다 모아 두고, 전환은 한 메서드에서만 하는 코드다:

public interface IState { void Enter(); void Tick(); void Exit(); }

public class StateMachine
{
    private IState current;

    public void Change(IState next)
    {
        current?.Exit();   // 나가는 상태 정리 (연출 끄기, 코루틴 중단)
        current = next;
        current.Enter();   // 들어오는 상태 준비 (애니메이션, 타이머)
    }

    public void Tick() => current?.Tick();  // 매 프레임은 현재 상태에만 맡긴다
}

옵저버는 C#에서 event가 곧 구현이다

알리는 쪽이 누가 듣는지 모르니, 반응을 추가해도 알리는 쪽은 안 바뀐다. 체력이 줄었다는 사실 하나에 체력바와 피격 연출과 업적이 각자 반응한다.

구독과 해제는 짝을 맞춘다. OnEnable에서 +=, OnDisable에서 -=다. 빠뜨리면 파괴된 구독자를 붙들어 누수와 예외가 난다.

전략 패턴도 같은 뼈대 위에 서 있다. 그럼 둘은 뭐가 다를까? 갈아 끼울 대상이 반응이면 옵저버, 알고리즘이면 전략이라고 부른다.

면접에서 이렇게 답한다

  • 아는 패턴을 말해 보라 — 세 갈래를 나누고 갈래마다 써 본 것을 든다. “보스 페이즈를 상태 패턴으로 나눴다”처럼 쓴 자리를 댄다.
  • 싱글톤의 문제와 대안 — 전역 접근이라 결합이 커지고, 가짜 구현을 못 끼워 테스트가 막힌다. 초기화 순서와 씬 수명도 걸린다. 대안은 주입이다.
  • 멀티스레드에서 하나임을 보장 — 널 검사와 생성 사이에 다른 스레드가 끼어들 수 있다. lock이나 Lazy에 맡긴다고 답한다.
  • 전략과 의존성 주입의 차이 — 전략은 알고리즘을 인터페이스 뒤로 빼는 설계, 주입은 구현을 누가 넣느냐는 기법이다. 층위가 달라 같이 쓴다.

이런 오해를 한다

  • “싱글톤은 접근할 때마다 객체가 생긴다” — 하나를 재사용하니 할당이 없다. 비용은 성능이 아니라 결합도와 테스트다.
  • “volatile이면 인스턴스가 하나가 된다” — 값이 제때 보이게 할 뿐이다. 생성이 한 번임은 보장하지 않는다.
  • “옵저버는 등록 순서대로 돈다” — 기대면 안 된다. 순서가 중요하면 이벤트 대신 직접 호출로 푼다.
  • “C# event와 UnityEvent는 같다” — UnityEvent는 인스펙터 연결을 얻는 대신 더 무겁다.

3줄 정리

  • 패턴은 갈래를 말하고 쓴 자리를 대야 답이 된다.
  • 싱글톤은 씬 재로드 중복을 Awake에서 처리한다.
  • 상태 패턴은 if 더미를, 옵저버는 직접 참조를 없앤다.
