자료구조·알고리즘

공간 분할

n제곱 비교를 없애는 구조다. 그리드·쿼드트리·BVH는 약점이 서로 다르다

유닛 1,000마리가 서로 주변을 살피면 비교가 50만 번이다. 정작 확인하고 싶은 이웃은 반경 안의 몇 마리뿐이다. 나머지는 버려지는 계산이다.

공간을 미리 칸으로 나눠 두면 그 낭비가 사라진다.

칸으로 나누면 후보가 주변 밀도만큼으로 준다

공간 분할은 내 주변에 무엇이 있나를 전수 검사 없이 답하는 구조다. 모든 유닛과 거리를 비교하면 질의마다 O(n)이고, 유닛끼리 서로 찾으면 O(n²)이 된다.

공간을 칸으로 나눠 칸별로 유닛을 담아 두면 주변 칸의 유닛만 보면 된다. 그리드나 쿼드트리로 나누는 것이 그 방법이고, 질의 반경이 닿는 칸만 본다.

물리의 브로드페이즈와 렌더링의 컬링이 같은 발상이다. 둘 다 정밀 검사에 들어가기 전에 후보를 먼저 쳐내는 단계다.

줄어드는 폭이 크다. 1,000마리를 40칸에 고르게 나누면 한 칸에 25마리다. 한 유닛이 보는 후보가 200여 개로 준다.

다만 이것은 후보를 줄이는 단계일 뿐이다. 칸 안에 들어온 것들끼리는 실제 거리로 다시 검사해야 한다.

그리드·쿼드트리·BVH는 약점이 다르다

구조 유리한 상황 약점
균일 그리드 고르게 퍼지고 크기가 비슷할 때. 갱신이 싸다 한곳에 몰리면 한 칸에 다 들어가 다시 O(n)
쿼드트리·옥트리 밀도가 들쭉날쭉할 때. 붐비는 칸만 더 쪼갠다 움직이는 객체는 칸을 넘을 때마다 다시 넣는다
BVH 레이·프러스텀 질의. 객체를 상자로 묶는다 트리를 짓는 비용이 크다

쿼드트리는 칸 하나에 원소가 기준을 넘으면 그 칸만 넷으로 쪼갠다. 3D에서 여덟으로 쪼개면 옥트리다. 빈 공간은 큰 칸 하나로 남아 밀도에 맞춰 해상도가 달라진다.

BVH가 레이캐스트에 강한 이유는 건너뛰기다. 물체를 감싸는 경계 상자(AABB)를 계층으로 묶은 트리라, 레이가 상위 경계 볼륨에 안 맞으면 그 안의 자식과 삼각형을 전부, 곧 그 아래 전체를 건너뛴다. 덕분에 평균 판정 비용이 O(log N) 수준으로 떨어진다.

유닛이 고르게 퍼져 있으면 균일 그리드가 단순하고 빠르며, 한곳에 몰리거나 크기 차이가 크면 쿼드트리나 BVH가 유리하다. 이름 기준 정렬이나 해시는 위치 질의에 도움이 되지 않는다.

균일 그리드는 물체가 고르게 퍼져 있을 때 단순하고 빠르지만, 밀집도가 들쭉날쭉한 장면에서는 BVH가 유리하다. 물리 엔진의 레이캐스트와 레이 트레이싱 모두 이런 가속 구조를 쓴다.

셀 크기를 질의 반경에 맞춘다

직접 짜는 것은 대개 균일 그리드다. 셀은 작을수록 좋을까. 너무 작으면 훑을 칸 수가 늘고, 너무 크면 한 칸에 다 들어와 이득이 사라진다. 질의 반경과 비슷하게 잡는 것이 기준이다: 

Vector2Int Key(Vector3 p)   // 좌표를 셀 크기로 나눈 것이 칸 번호다
    => new Vector2Int(Mathf.FloorToInt(p.x / _cell), Mathf.FloorToInt(p.z / _cell));

// 결과 리스트를 재사용해 매 프레임 불러도 할당이 없다
public void Query(Vector3 center, float radius, List<Transform> result)
{
    result.Clear();
    Vector2Int c = Key(center);
    int r = Mathf.CeilToInt(radius / _cell);   // 반경이 닿는 칸 범위
    float sqr = radius * radius;               // 제곱끼리 비교해 루트를 뺀다

    for (int dx = -r; dx <= r; dx++)
        for (int dy = -r; dy <= r; dy++)
            if (_cells.TryGetValue(new Vector2Int(c.x + dx, c.y + dy), out var list))
                foreach (Transform tr in list)   // 칸 안에서만 실제 거리 검사
                    if ((tr.position - center).sqrMagnitude <= sqr) result.Add(tr);
}

Unity도 안에서 같은 일을 한다

Unity 물리는 프로젝트 설정의 브로드페이즈 방식으로 후보를 추린다. Sweep and Prune이나 Multibox Pruning 같은 선택지가 거기 있다.

범위 질의는 Physics.OverlapSphereNonAlloc처럼 미리 잡은 배열에 담아 할당을 없앤다. LayerMask로 후보를 좁히는 것도 결국 같은 목적이다.

면접에서 이렇게 답한다

  • 주변 유닛을 빠르게 찾으려면 — 전수 비교는 질의마다 O(n), 서로 찾으면 O(n²)이라 공간을 칸으로 나눈다. 반경이 닿는 칸만 검사하면 후보가 주변 밀도에 비례하는 수준으로 준다고 설명한다.
  • 그리드와 쿼드트리 중 무엇을 쓰나 — 고르게 퍼지고 크기가 비슷하면 갱신이 싼 균일 그리드다. 한곳에 몰리면 밀도에 맞춰 쪼개는 쿼드트리나 옥트리를 쓴다. 셀 크기를 질의 반경에 맞추는 것이 그리드 성능의 핵심이라고 덧붙인다.
  • BVH가 레이 판정을 빠르게 하는 원리 — 물체를 감싼 경계 상자를 계층으로 묶는다. 레이가 부모 상자와 만나지 않으면 그 아래 전체를 건너뛴다.

이런 오해를 한다

  • “ID나 이름으로 정렬해 두면 주변 검색도 빨라진다” — 기준이 위치가 아니면 위치 질의에는 쓸 수 없다.
  • “BVH는 레이가 지나는 모든 삼각형을 검사한다” — 상자에 안 맞은 가지는 통째로 버린다.
  • “공간 분할을 하면 정밀 검사가 필요 없다” — 후보를 줄일 뿐이라 칸 안에서는 실제 거리로 다시 검사한다.
  • “셀은 작을수록 좋다” — 훑을 칸 수가 반경 제곱으로 늘어 오히려 느려진다.

3줄 정리

  • 공간을 칸으로 나눠 n² 비교를 주변 밀도로 바꾼다
  • 고르면 그리드, 몰리면 쿼드트리, 레이면 BVH다
  • 후보만 줄일 뿐이라 칸 안에서는 다시 재야 한다
