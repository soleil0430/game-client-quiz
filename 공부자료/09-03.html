네트워크

소켓과 HTTP

소켓은 연결을 열어 두고 HTTP는 매번 새로 묻는다. 게임은 용도로 나눈다

대전 상대가 잡혔다고 서버가 먼저 알려 줘야 하는데, HTTP로는 그 말을 걸 방법이 없다. 클라이언트가 묻지 않으면 서버는 입을 못 뗀다.

소켓과 HTTP를 어디에 쓸지는 여기서 갈린다.

포트는 번호표, 소켓은 그 번호로 뚫린 통로

포트는 도착한 데이터를 어느 프로세스로 보낼지 구분하는 16비트 번호(0~65535)이고, 소켓은 그 포트와 IP를 묶어 프로그램이 읽고 쓰는 통신 종단점이자 운영체제가 관리하는 자원이다. 서버 소켓 하나가 같은 포트에서 연결마다 소켓을 따로 만들며 여러 연결을 받는다.

포트 하나에 수천 명이 붙어도 대화가 섞이지 않는다. 연결이 출발지 IP·포트와 목적지 IP·포트, 이 네 값의 조합으로 구분되기 때문이다. UDP도 소켓을 쓰되 연결 없이 주소를 지정해 보낸다.

HTTP가 로그인 상태를 기억하지 못하는 이유

HTTP는 무상태다. 요청 하나하나가 독립적이라 서버가 이전 요청을 기억하지 않는다. 응답이 끝나면 대화도 끝나고, 다음 요청은 초면으로 시작한다.

그럼 서버는 나를 어떻게 알아보나. 쿠키에 담은 세션 ID나 요청 헤더에 넣는 액세스 토큰으로 매번 알려 주기 때문이다. 무상태를 쿠키와 토큰으로 보완한다는 말이 이것이다.

불편해 보이지만 이 성질이 증설을 쉽게 만든다. 어느 서버가 받아도 처리가 같으니 서버를 여러 대로 늘리기 쉬운 장점이 있다. 비연결 특징 탓에 생기는 연결 비용은 keep-alive로 줄인다.

버전핵심 변화남는 문제
HTTP/1.1keep-alive로 연결 재사용응답이 앞 요청 순서에 묶인다
HTTP/2멀티플렉싱, 헤더 압축TCP 위라 한 패킷을 잃으면 다 밀린다
HTTP/3UDP 기반 QUIC, 빠른 연결환경에 따라 UDP가 막히기도 한다

HTTP/2가 푼 것은 대기 문제다. 요청을 스트림으로 나눠 한 연결에서 동시에 처리하는 멀티플렉싱과 바이너리 프레이밍, 헤더 압축(HPACK)을 도입해 1.1의 요청 대기를 줄였다. HTTP/3은 TCP 대신 UDP 기반 QUIC을 써서 한 스트림의 손실이 다른 스트림을 막지 않게 하고 연결 수립도 빠르다.

HTTPS는 오가는 구간까지만 지킨다

TLS 핸드셰이크에서 인증서로 서버 신원을 확인한다. 이어서 키 교환으로 세션 키를 만들고, 본 통신은 대칭키로 암호화한다.

공개키 방식은 느리지만 키를 안전하게 나눌 수 있어 인증서 검증과 세션키 합의에 쓰인다. 즉 대칭키가 공개키보다 빠르며 본 통신을 담당한다. 인증서는 CA의 서명으로 신뢰를 확인하므로, 인증서 검증을 끄는 코드는 중간자 공격에 그대로 노출된다.

지키는 범위는 딱 오가는 구간까지다. 전송 구간의 도청과 변조를 막을 뿐, 사용자 기기의 앱이나 메모리 조작은 막지 못한다. 그래서 중요한 판정은 서버에서 검증한다.

주소창에 URL을 치면 무슨 순서로 도는가

도메인만으로는 통신할 수 없으므로 먼저 DNS로 IP를 알아낸다. 캐시가 있으면 이 조회는 생략된다. 그 IP와 TCP 3-way handshake로 연결한 뒤 HTTPS면 TLS 핸드셰이크를 거쳐 HTTP 요청을 보낸다.

응답으로 받은 HTML을 파싱하며 필요한 리소스를 추가로 요청해 화면을 그린다. 중간에 ARP로 게이트웨이의 MAC 주소를 찾는 과정이 들어가지만, 순서를 물으면 DNS가 가장 앞이라고 답하면 된다.

메타 통신은 REST, 인게임은 소켓

REST는 요청과 응답이 뚜렷하고 빈도가 낮은 조회·저장에 맞고, 소켓은 연결을 유지한 채 양방향으로 자주 오가는 실시간 통신에 맞는다. 그래서 로그인·상점·랭킹은 HTTPS로, 초당 여러 번 오가거나 서버가 먼저 말을 걸어야 하는 대전 중 통신은 소켓 연결이 알맞다.

RPC는 원격 호출을 함수 호출처럼 감싸는 방식이라 응답을 받을 수 있고, HTTP나 소켓 위에 얹어 쓴다. 실제 게임은 메타 데이터는 REST, 인게임은 소켓으로 나누는 구성이 흔하다.

랭킹을 받아 오는 최소 형태다. UnityWebRequest.Get이나 UnityWebRequest.Post로 요청 객체를 만들고 SendWebRequest()를 코루틴에서 yield하거나 await해서 완료될 때까지 기다린 뒤, 성공 여부는 result가 Success인지로 확인하고 본문은 downloadHandler.text에서 읽는다.

error 속성에는 실패 사유만 들어간다. 요청 객체는 네이티브 자원을 쥐므로 using이나 Dispose로 정리하고, 동기 대기는 프레임을 멈추므로 쓰지 않는다:

IEnumerator GetRanking(string url)
{
    using (UnityWebRequest req = UnityWebRequest.Get(url))
    {
        yield return req.SendWebRequest();  // 프레임을 막지 않고 기다린다
        if (req.result != UnityWebRequest.Result.Success)
        {
            Debug.LogError(req.error);      // error 문자열만 보고 판단하지 않는다
            yield break;
        }
        Debug.Log(req.downloadHandler.text);  // 본문은 downloadHandler에서 읽는다
    }                                         // 네이티브 자원이라 using으로 정리
}

직렬화도 같은 저울에 올린다. JSON 같은 텍스트 포맷은 사람이 바로 읽어 디버깅과 연동이 쉽지만, 숫자를 문자열로 적어 크기가 크고 파싱 비용도 높다. Protobuf나 FlatBuffers 같은 바이너리 포맷은 크기와 속도에서 유리한 대신 별도 도구와 스키마 관리가 필요하다.

어느 쪽이든 필드를 추가하거나 지울 때 구버전 클라이언트와의 호환 규칙은 미리 정해 두어야 한다.

면접에서 이렇게 답한다

  • 소켓과 포트의 차이 — 포트는 프로세스를 구분하는 번호고 소켓은 IP와 포트로 식별되는 종단점이다. 연결은 네 값의 조합으로 구분되니 포트 하나로 여러 연결을 다룬다고 이어 말한다.
  • HTTP와 HTTPS, TLS 핸드셰이크 — 인증서로 서버 신원을 확인하고 공개키로 세션 키를 합의한다. 본 통신은 대칭키로 암호화하며 보호 범위는 전송 구간까지라고 선을 긋는다.
  • 무상태를 어떻게 보완하나 — 세션 ID 쿠키나 액세스 토큰을 요청마다 실어 보낸다. 상태가 필요하면 서버 메모리 대신 공용 저장소에 둔다.
  • URL 입력부터 화면까지 — DNS로 IP를 얻고 TCP와 TLS 핸드셰이크를 거쳐 요청을 보낸다. 응답을 파싱하며 부족한 리소스를 추가로 받아 그린다.
  • Unity에서 HTTP 호출 — UnityWebRequest로 요청을 만들고 코루틴이나 await로 기다린다. 성공 판정은 result로 하고, 네이티브 자원이라 using으로 정리한다는 것까지 말한다.

이런 오해를 한다

  • “HTTPS를 쓰면 치트를 막는다” — 지켜지는 것은 전송 구간뿐이다. 변조된 클라이언트가 보낸 값은 서버 검증으로만 걸러진다.
  • “공개키가 대칭키보다 빠르다” — 반대다. 느린 쪽이라 키 합의에만 쓴다.
  • “error가 비어 있으면 성공이다” — 성공 판정은 result가 Success인지로 한다.
  • “실시간 대전도 REST로 된다” — 요청마다 왕복이 필요하다. 서버가 먼저 보내는 메시지도 받을 수 없다.

3줄 정리

  • 포트는 번호, 소켓은 IP와 포트를 묶은 종단점
  • HTTP는 무상태라 토큰을 매번 실어 보낸다
  • 메타는 HTTPS, 인게임은 소켓으로 나눈다
