소켓과 HTTP

소켓은 연결을 열어 두고 HTTP는 매번 새로 묻는다. 게임은 용도로 나눈다

HTTP로만 통신하면 서버가 먼저 말을 걸 수 없다. 클라이언트가 묻지 않는 한 대전 상대가 잡혔다는 사실도 전할 방법이 없다. 소켓과 HTTP를 어디에 쓸지는 여기서 갈린다.

포트는 번호표, 소켓은 그 번호로 뚫린 통로

포트는 어느 프로세스에 줄지 고르는 16비트 번호다. 소켓은 IP와 포트를 묶은 통신 종단점이자 OS가 관리하는 자원이다. 서버는 리스닝 소켓 하나로 받고 연결마다 별도 소켓을 만든다.

포트 하나에 수천 명이 붙어도 섞이지 않는다. 연결을 출발지와 목적지의 IP·포트 네 값으로 구분하기 때문이다. 그래서 서버는 포트 하나로 여러 연결을 다룬다.

HTTP가 로그인 상태를 기억하지 못하는 이유

HTTP는 무상태라 이전 요청을 기억하지 않는다. 응답이 끝나면 대화도 끝난다. 그래서 로그인 상태는 쿠키 속 세션 ID나 액세스 토큰으로 매번 알려 준다.

불편해 보이지만 이 성질이 증설을 쉽게 한다. 어느 서버가 받아도 처리가 같아 앞에 서버를 더 붙이면 그만이다. 연결을 새로 여는 비용은 keep-alive로 줄인다.

버전핵심 변화남는 문제
HTTP/1.1keep-alive로 연결 재사용응답이 앞 요청 순서에 묶인다
HTTP/2멀티플렉싱, 헤더 압축TCP 위라 한 패킷을 잃으면 다 밀린다
HTTP/3UDP 기반 QUIC, 빠른 연결환경에 따라 UDP가 막히기도 한다

HTTPS가 지키는 구간은 전송 구간뿐

TLS 핸드셰이크에서 인증서로 서버 신원을 확인한다. 이어서 공개키로 세션 키를 합의하고 본 통신은 대칭키로 암호화한다. 공개키는 느려서 키 합의에만 쓰고 데이터는 빠른 대칭키가 맡는다.

보호 범위는 오가는 구간까지다. 기기 안에서 암호가 풀리므로 변조된 클라이언트는 막지 못한다. 그쪽은 서버 검증의 몫이다.

메타 통신은 REST, 인게임은 소켓

로그인·상점·랭킹처럼 빈도가 낮은 통신은 HTTPS로 간다. 초당 여러 번 오가거나 서버가 먼저 보내야 하는 통신은 소켓으로 간다. RPC는 원격 호출을 함수처럼 감싸는 방식이라 둘 위에 모두 얹는다.

랭킹을 받아 오는 최소 형태다. 프레임을 막지 않고 기다리는 부분을 본다:

IEnumerator GetRanking(string url)
{
    using (UnityWebRequest req = UnityWebRequest.Get(url))
    {
        yield return req.SendWebRequest();  // 프레임을 막지 않고 기다린다
        if (req.result != UnityWebRequest.Result.Success)
        {
            Debug.LogError(req.error);      // error 문자열만 보고 판단하지 않는다
            yield break;
        }
        Debug.Log(req.downloadHandler.text);  // 본문은 downloadHandler에서 읽는다
    }                                         // 네이티브 자원이라 using으로 정리
}

직렬화도 같은 저울이다. JSON은 읽기 쉬워 디버깅이 편한 대신 크고 느리다. Protobuf 같은 바이너리는 작고 빠른 대신 스키마 관리가 따라온다.

면접에서 이렇게 답한다

  • 소켓과 포트의 차이 — 포트는 프로세스를 구분하는 번호고 소켓은 IP와 포트로 식별되는 종단점이다. 연결은 네 값의 조합으로 구분되므로 포트 하나로 여러 연결을 다룬다.
  • HTTP와 HTTPS, TLS 핸드셰이크 — 인증서로 서버 신원을 확인하고 공개키로 세션 키를 합의한다. 본 통신은 대칭키로 암호화하며 보호 범위는 전송 구간뿐이다.
  • 무상태를 어떻게 보완하나 — 세션 ID 쿠키나 액세스 토큰을 요청마다 실어 보낸다. 상태가 필요하면 서버 메모리 대신 공용 저장소에 둔다.
  • URL 입력부터 화면까지 — DNS로 IP를 얻고 TCP와 TLS 핸드셰이크를 거쳐 요청을 보낸다. 응답을 파싱하며 부족한 리소스를 추가로 받아 그린다.
  • Unity에서 HTTP 호출 — UnityWebRequest로 요청을 만들고 코루틴이나 await로 기다린다. 성공 판정은 result로 하고 네이티브 자원이라 using으로 정리한다.

이런 오해를 한다

  • HTTPS를 쓰면 치트를 막는다 — 전송 구간만 보호한다. 변조된 클라이언트가 보낸 값은 서버 검증으로만 걸러진다.
  • 공개키가 대칭키보다 빠르다 — 반대다. 느린 공개키는 키 합의에만 쓴다.
  • error가 비어 있으면 성공이다 — 성공 판정은 result가 Success인지로 한다.
  • 실시간 대전도 REST로 된다 — 요청마다 왕복이 필요하다. 서버가 먼저 보내는 메시지도 받을 수 없다.

3줄 정리

  • 포트는 번호, 소켓은 IP와 포트를 묶은 종단점
  • HTTP는 무상태라 토큰을 매번 실어 보낸다
  • 메타는 HTTPS, 인게임은 소켓으로 나눈다
