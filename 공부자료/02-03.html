직렬화와 데이터

인스펙터에 보이는 값이 곧 저장되는 값이다. 그 규칙이 씬·프리팹·세이브 파일로 이어진다

인스펙터에서 맞춰 둔 값이 실행하면 사라진다. 프리팹마다 같은 스탯을 복사해 둬서 밸런스를 고칠 때마다 전부 손댄다. 둘 다 무엇이 저장되는지를 모르면 생기는 일이다.

인스펙터에 보이는 값이 곧 저장되는 값이다

직렬화는 메모리 위의 객체를 저장하고 되살릴 수 있는 형태로 펴는 일이다. Unity에서는 씬, 프리팹, ScriptableObject 에셋, 인스펙터 표시가 전부 같은 직렬화 하나를 쓴다. 그래서 인스펙터에 안 보이는 값은 씬에도 저장되지 않는다.

대상이 되는 조건은 단순하다. public 필드이거나 [SerializeField]가 붙은 private 필드여야 하고 타입도 직렬화 가능해야 한다. 프로퍼티와 static 필드와 Dictionary는 대상이 아니다.

클래스나 구조체를 통째로 저장하려면 [System.Serializable]을 붙인다. 캡슐화를 깨며 public으로 여는 대신 private 필드에 [SerializeField]를 붙이는 방식을 실무에서 흔히 쓴다.

무기 스탯을 에셋으로 빼 둔 코드다: 

[CreateAssetMenu(menuName = "Game/Weapon Data")]
public class WeaponData : ScriptableObject
{
    [SerializeField] private int damage = 10;  // private이어도 인스펙터에 뜬다
    public int Damage => damage;               // 프로퍼티는 저장되지 않는다
}

Dictionary가 인스펙터에 안 나오는 이유

Unity 직렬화기는 필드를 순서대로 늘어놓는 단순한 형식이다. 키와 값이 짝을 이루는 구조를 그대로 표현하지 못한다. 그래서 Dictionary가 대상에서 빠진다.

꼭 필요하면 ISerializationCallbackReceiver를 구현한다. 저장 직전에 키 리스트와 값 리스트로 폈다가 로드 직후에 다시 Dictionary로 조립한다.

무기 스탯을 프리팹마다 복사하지 않으려면

ScriptableObject는 씬에 붙지 않는 데이터 그릇이다. 에셋 파일로 두면 여러 프리팹이 복사본이 아니라 같은 참조를 공유한다. 스탯 하나를 고치면 그것을 쓰는 전부가 바뀌고 메모리에도 한 벌만 올라간다.

대신 MonoBehaviour와 달리 Update 같은 엔진 호출을 받지 않는다. 갱신이 필요하면 MonoBehaviour가 불러 줘야 한다.

에디터와 빌드의 차이가 함정이다. 에디터에서는 프로젝트의 에셋 파일을 그대로 가리켜 플레이 중 바꾼 값이 다음 실행까지 남는다. 빌드에서는 읽기 전용으로 패키징되어 앱을 다시 켜면 원래 값으로 돌아온다.

그래서 ScriptableObject는 변하지 않는 설정과 원본 데이터에만 쓴다. 변하는 상태는 세이브로 따로 저장한다.

세이브는 어디에 어떤 형식으로 두나

PlayerPrefs는 int·float·string만 다루는 키-값 저장소다. 윈도우는 레지스트리, iOS는 plist, 안드로이드는 SharedPreferences에 평문으로 남는다. 누구나 열어 고칠 수 있어 옵션 값 정도에만 쓴다.

구조가 있는 데이터는 JSON으로 만들어 persistentDataPath에 파일로 쓴다. JsonUtility는 Unity 직렬화를 그대로 쓰므로 위 규칙을 똑같이 따른다. Dictionary와 다형성과 최상위 배열을 못 다루는 대신 가볍고 빠르다.

Newtonsoft.Json에는 그 제약이 없다. 대신 리플렉션을 써서 느리고 IL2CPP에서 코드 스트리핑에 걸릴 수 있다.

세이브 시스템은 버전과 손상을 전제로 만든다. 데이터에 version 필드를 두고 읽을 때 옛 버전이면 마이그레이션을 태운다. 쓰는 중에 앱이 죽으면 파일이 반만 남으므로 임시 파일에 먼저 쓰고 성공하면 이름을 바꿔 교체한다.

면접에서 이렇게 답한다

  • public 필드와 [SerializeField]의 차이 — 둘 다 직렬화되어 인스펙터에 나옵니다. 다른 점은 접근 제한자뿐이라, 값은 인스펙터에서 조정하되 코드에서는 외부가 못 건드리게 하려고 [SerializeField]를 씁니다.
  • ScriptableObject는 어디에 쓰나 — 여러 오브젝트가 공유하는 설정 데이터의 원본으로 씁니다. 프리팹마다 복사하지 않아 수정 지점이 하나고 메모리도 한 벌입니다. 빌드에서는 읽기 전용이라 세이브로는 못 씁니다.
  • 세이브 구조가 바뀌면 — 파일에 버전 번호를 같이 저장하고 읽을 때 버전별 마이그레이션을 태웁니다. 쓰기는 임시 파일에 한 뒤 이름을 바꿔 교체해서 도중에 죽어도 이전 파일이 남게 합니다.

이런 오해를 한다

  • 프로퍼티도 인스펙터에 나온다 — 직렬화 대상이 아니다. 백킹 필드를 private으로 두고 [SerializeField]를 붙여야 저장되고 보인다.
  • ScriptableObject에 값을 써 두면 세이브가 된다 — 에디터에서만 에셋에 남는다. 빌드에서는 앱을 끄면 사라진다.
  • ScriptableObject도 Update를 받는다 — 씬의 오브젝트가 아니라 엔진 콜백을 받지 않는다. 갱신은 MonoBehaviour가 불러 준다.
  • PlayerPrefs는 앱 안에 숨겨져 있어 안전하다 — 평문으로 남아 사용자가 열어 고칠 수 있다.

3줄 정리

  • 저장되는 값은 public이나 [SerializeField]가 붙은 필드뿐
  • 공유 데이터의 원본은 ScriptableObject, 세이브는 아니다
  • 세이브는 JSON을 persistentDataPath에, 버전을 같이 쓴다
