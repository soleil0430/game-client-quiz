설계·아키텍처

아키텍처

시스템끼리 어떻게 찾고 부르는지가 다음 기능을 넣는 비용을 정한다

버튼 하나를 더하는 데 매니저 다섯 개를 따라 고쳐야 한다면, 설계가 아니라 배선이 잘못된 것이다. 배선이 잘못된 집은 스위치 하나를 옮기려고 벽을 뜯는다. 코드도 똑같고, 다른 점은 벽이 눈에 안 보인다는 것뿐이다.

아키텍처의 목적은 멋진 그림이 아니라 다음 기능을 넣는 비용을 낮추는 것이다. 그 비용은 대개 한 가지가 정한다. 시스템끼리 서로를 어떻게 찾고 부르는가다.

시스템을 잇는 방법은 세 가지뿐이다

셋은 결합도와 흐름 추적을 맞바꾼다. 느슨해질수록 고치기는 쉽고 따라가기는 어렵다.

방식결합도흐름 추적어디에 쓰나
구체 클래스 직접 참조높다가장 쉽다늘 붙어 다니는 관계
인터페이스 + 주입중간코드에 보인다교체·테스트가 필요한 협력
이벤트·메시지 버스낮다어렵다먼 시스템에 던지는 알림

가까운 관계는 주입으로, 먼 시스템 알림은 버스로 나눈다. 그럼 전부 버스로 묶으면 되지 않을까? 그러면 호출 흐름이 코드에 남지 않아 원인을 찾을 실마리가 사라진다.

주입이란 컨테이너를 붙이는 일인가

아니다. 쓸 협력 객체를 스스로 new하지 않고 밖에서 받으면 그게 주입이다. 생성자나 메서드 인자로 넘기기만 해도 주입이고, 인스펙터 연결도 넓게 보면 같은 일이다.

점수 서비스가 저장 위치를 모르는 채로 기록하는 코드다:

public interface ISaveStore { void Save(string json); }  // 계약만 남긴다

public class ScoreService
{
    private readonly ISaveStore store;

    // 파일인지 서버인지는 밖에서 정해 넣어 준다 (생성자 주입)
    public ScoreService(ISaveStore store) => this.store = store;

    public void Record(int score) => store.Save(score.ToString());
}

// MonoBehaviour는 생성자를 쓸 수 없어 초기화 메서드로 받는다
public class ScoreView : MonoBehaviour
{
    private ScoreService service;
    public void Init(ScoreService service) => this.service = service;
}

UI는 모델이 뷰를 모르게 잘라 둔다

모델은 데이터와 규칙, 뷰는 표시와 입력 전달, 컨트롤러는 입력을 받아 모델을 고친다. 핵심은 모델이 뷰를 모르게 해서, 화면을 갈아엎어도 규칙 코드를 안 건드리는 것이다.

MVP는 뷰를 더 얇게 두고 프레젠터가 중개한다. MVVM은 그 연결을 바인딩으로 자동화한다. 대신 클래스가 늘어 작은 팝업에는 과하다.

ECS는 같은 처리를 수만 번 반복할 때 유리하다

ECS는 방향 자체가 다르다. 엔티티에 순수 데이터인 컴포넌트를 붙이고 로직은 시스템에 두며, 같은 컴포넌트를 가진 엔티티를 메모리에 촘촘히 모아 한 번에 훑는다.

덕분에 캐시 적중률이 높고 일감을 나누기 쉽다.

상속 기반 구조는 데이터와 로직이 객체마다 흩어져 있고 호출마다 가상 함수 테이블을 탄다.

면접에서 이렇게 답한다

  • 전 회사 아키텍처를 설명하라 — 레이어를 나열하지 않는다. 무엇이 자주 바뀌었고 그래서 어디를 갈아 끼울 수 있게 뒀는지로 말한다. 콘텐츠 데이터, UI, 서버 통신 중 무엇이 가장 자주 바뀌었는지부터 꺼낸다.
  • 의존성 주입이 왜 필요한가 — 구체 클래스를 직접 new하면 교체할 수 없고 테스트에서 가짜를 넣을 수 없다. 계약만 남기면 서버 연동을 로컬 스텁으로 바꿔 끼우는 일이 호출부 수정 없이 끝난다.
  • 이벤트가 많아지면 — 연쇄 호출과 구독 순서 의존으로 추적이 어려워지고, 해제 누락이 누수로 이어진다. 이벤트의 범위를 정하고 중요한 흐름은 직접 호출로 남긴다.
  • 레거시 리팩터링 — 한 번에 갈아엎지 않는다. 바꿀 곳 주변에 재현 절차를 먼저 만들고, 인터페이스로 경계를 그은 뒤 그 안에서 조금씩 교체한다.
  • 프레임워크와 라이브러리의 차이 — 누가 누구를 부르는지로 갈린다. Update가 엔진에 의해 불리면 프레임워크, 내가 부르는 수학 유틸리티는 라이브러리다.
  • Lua 같은 스크립트를 왜 붙이나 — 콘텐츠 규칙을 빼 두면 앱 재심사 없이 고칠 수 있다. 대신 인터프리터 비용 때문에 매 프레임 도는 계산은 C#에 남긴다.

이런 오해를 한다

  • “의존성 주입은 성능 최적화” — 목적은 결합도를 낮추는 설계다. 성능만 보면 간접 호출이 한 겹 늘어난다.
  • “이벤트 버스를 쓰면 결합이 사라진다” — 직접 참조가 없어질 뿐이다. 메시지 형식이라는 계약이 남고, 디버깅 비용은 올라간다.
  • “뷰가 데이터를 직접 읽고 써도 MVC” — 그 순간 분리가 무너진다. 모델이 뷰를 모르게 하는 것이 목적이다.
  • “ECS로 바꾸면 무조건 빨라진다” — 같은 처리를 대량 반복할 때 유리하다. 종류가 제각각인 소수 오브젝트는 이득이 적고 전환 비용이 크다.
  • “순수 함수는 static 함수” — 상관없다. 기준은 같은 입력에 같은 결과인지, 부수 효과가 없는지다.

3줄 정리

  • 연결 방식이 다음 기능을 넣는 비용을 정한다.
  • 가까운 협력은 주입, 먼 알림은 이벤트로 나눈다.
  • 모델이 뷰를 모르게, ECS는 대량 반복일 때만.
