Unity 엔진

빌드와 플랫폼

빌드 용량은 텍스처에서 갈리고, 설치 실패는 대개 ARM64와 API 레벨에서 갈린다

용량이 큰 앱은 설치 화면에서 사람을 잃는다. 스토어는 App Bundle 크기에 상한을 둬서, 넘기면 아예 올리지도 못한다.

빌드 줄이기가 취향이 아니라 지표 문제인 이유다.

무엇부터 줄일지는 감이 아니라 빌드 리포트가 정한다

빌드 용량은 대개 텍스처와 오디오가 대부분이다. 빌드 직후 Editor.log에 에셋 종류별 용량이 남으니, 그걸 열어 큰 것부터 손댄다. 효과 순서는 대개 아래와 같다.

항목방법보통 효과
텍스처ASTC 등 플랫폼 압축, Max Size 하향, 밉맵과 알파 정리가장 크다
오디오BGM은 Vorbis와 Streaming, 짧은 효과음은 ADPCM크다
코드Managed Stripping Level 상향, 안 쓰는 패키지 제거중간
배포 구조Addressables로 빼서 나중에 내려받기초기 용량만 준다

텍스처를 플랫폼별 압축 포맷으로 굽고 크기를 줄이는 쪽이 1등인 이유는 포맷 하나로 몇 배가 갈리기 때문이다. 같은 2048 크기라도 무압축 RGBA32는 16MB, ASTC 6x6은 1MB 수준이다. ASTC 같은 압축 포맷과 알맞은 Max Size 지정이 효과가 가장 크다.

그다음이 Managed Stripping Level을 올려 안 쓰는 코드를 걷어내는 것과, 당장 필요 없는 에셋을 Addressables로 빼서 나중에 내려받게 하는 것이다.

Managed Stripping은 진입점에서 도달 가능한 코드만 남긴다. 리플렉션으로만 부르는 타입은 도달 불가로 보여 같이 잘린다. 그걸 막는 것이 link.xml이다.

Resources 폴더는 참조가 없어도 전부 들어간다

Resources 폴더 안의 에셋은 아무도 참조하지 않아도 빌드에 들어간다. 한때 쓰고 버린 프로토타입 텍스처까지 그대로 앱에 실린다. 앱 시작 시 인덱스를 만드느라 기동도 느려진다.

필요한 것만 그때 불러오려면 Addressables를 쓴다. 초기 설치 용량을 줄이고 나머지는 나중에 내려받는 구조다.

Resources에 넣으면 참조가 없어도 전부 빌드에 들어가 오히려 늘어난다는 뜻이다. 반대로 주석은 컴파일 결과에 남지 않으니, 주석이나 변수 이름을 줄이는 쪽은 아무 소용이 없다.

설치가 안 되면 ARM64와 Target API부터 본다

ARMv7은 32비트, ARM64는 64비트 명령어 집합이다. 구글 플레이 배포에는 ARM64 지원이 필수다. 2019년 8월부터 64비트 지원을 요구해서, ARM64 없이 ARMv7만 올리면 등록이 거부된다.

ARM64는 IL2CPP 백엔드에서만 빌드된다. Mono로 두면 Player Settings에서 ARM64 체크박스 자체가 눌리지 않는다.

최신 기기에 APK가 설치되지 않는 문제도 대개 여기서 온다. 원인은 둘 중 하나다. ARM64가 빠졌거나, Target API Level이 스토어 요구치보다 낮다.

Player Settings에서 둘 다 체크하면 하나의 APK에 두 벌이 담겨 그만큼 커진다. 스토어에는 App Bundle로 올려 기기에 맞게 분할 배포되게 한다.

기기에서만 나는 버그는 어떻게 보나

USB나 무선 디버깅으로 연결한 기기는 adb logcat으로 로그를 볼 수 있다. Unity의 Android Logcat 패키지를 설치하면 에디터 창에서 패키지 이름과 로그 레벨로 걸러 볼 수 있다.

Development Build를 켜면 스택 트레이스가 온전히 남고 프로파일러도 붙는다. 대신 오버헤드가 있으니 성능 수치는 상대 비교로만 쓴다.

출시 뒤 재현이 어려운 문제는 게임 안에서 로그를 모아 서버로 보내는 방식으로 잡는다.

서드파티 SDK는 대개 Gradle 의존성 충돌과 매니페스트 병합에서 사고가 난다. 결제는 영수증 검증을 반드시 서버에서 한다. 클라이언트만 믿으면 변조된 영수증으로 아이템이 나간다.

면접에서 이렇게 답한다

  • 빌드 크기를 왜, 어떻게 줄이나 — 설치 전환율과 스토어 상한 때문이라고 이유부터 댄다. 먼저 빌드 리포트로 무엇이 큰지 보고, 대개 텍스처 압축 포맷과 Max Size에서 가장 큰 폭이 나온다. 그다음이 오디오 설정, 코드 스트리핑, Addressables 분리다.
  • ARMv7과 ARM64의 차이 — 32비트와 64비트 명령어 집합이고, 구글 플레이가 64비트를 필수로 요구한다. ARM64는 IL2CPP에서만 빌드되므로 백엔드를 바꾸고 App Bundle로 배포한다.
  • 최신 기기에 설치가 안 된다면 — ARM64가 빠졌는지, Target API Level이 요구치보다 낮은지부터 본다. 그다음 minSdkVersion과 서명, 설치 로그를 adb logcat으로 확인한다.
  • 서드파티 SDK와 결제는 — Gradle 의존성 충돌과 매니페스트 병합이 주된 사고 지점이라 버전을 맞추고 병합 결과를 본다. 결제는 영수증을 서버에서 검증해 변조로 아이템이 나가지 않게 한다.

이런 오해를 한다

  • “주석과 변수 이름을 줄이면 빌드가 작아진다” — 컴파일 결과에 남지 않는다. 용량은 에셋과 컴파일된 코드가 차지한다.
  • “Resources 폴더에 넣으면 관리가 편하다” — 참조가 없어도 전부 빌드에 들어가고 시작 속도까지 느려진다. 동적 로딩은 Addressables로 한다.
  • “IL2CPP로 바꾸면 빌드가 작아진다” — 네이티브 코드로 변환하므로 오히려 커질 수 있다. 얻는 것은 실행 속도와 ARM64 지원이다.
  • “빌드 크기를 줄이면 프레임도 오른다” — 용량은 다운로드와 로딩 시간에 영향을 줄 뿐이다. 한 프레임의 계산량과는 다른 축이다.
  • “ARMv7만 올려도 요즘 기기는 다 돌아간다” — 기기가 실행은 해도 구글 플레이가 등록을 거부한다.

3줄 정리

  • 무엇부터 줄일지는 빌드 리포트를 보고 정한다
  • 텍스처 압축이 가장 크고, Resources 폴더는 통째로 들어간다
  • 설치가 안 되면 ARM64와 Target API Level부터 본다
