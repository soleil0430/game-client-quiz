타입과 메모리

값 형식과 참조 형식의 차이는 저장 위치가 아니라 복사 방식이고, 박싱은 그 경계에서 생긴다

핵심 개념

값 형식과 참조 형식을 가르는 기준은 변수가 값을 직접 담느냐, 값이 있는 곳의 주소를 담느냐다. int나 struct 같은 값 형식은 변수 안에 값 자체가 들어 있고, class·배열·string 같은 참조 형식은 힙에 있는 객체를 가리키는 주소가 들어 있다.

그래서 “값 형식은 스택에 있다”는 말은 절반만 맞다. 값 형식은 선언된 자리에 얹혀서 산다. 지역 변수면 그 메서드의 스택 프레임에, 클래스 필드면 그 객체와 함께 힙에, 배열 요소면 배열 안에 있다. 반대로 struct 안에 string 필드가 있으면 주소만 struct 안에 있고 문자열 객체는 힙에 있다.

struct Point { public int X; }

class Box
{
    public Point P;                 // P는 Box 객체와 함께 힙에 있다
}

static class Demo
{
    static void Move(in Point p) { }    // 읽기 전용 참조 - 복사가 없다

    static void Run()
    {
        Point a = new Point { X = 1 };  // 지역 변수라 스택, 힙 할당은 없다
        Point b = a;                    // 값 전체가 복사된다
        b.X = 2;                        // a.X는 그대로 1

        object o = a;                   // 박싱: 힙에 상자를 만들고 값을 복사
        Point c = (Point)o;             // 언박싱: 꺼내면서 또 복사
        Move(in a);
    }
}

이 차이가 실제로 문제를 일으키는 지점은 복사다. struct는 대입하거나 인자로 넘길 때마다 필드 전체가 복사되므로, 필드가 많은 struct를 매 프레임 넘기면 복사 비용이 쌓인다. 이때 in을 붙이면 읽기 전용 참조로 넘겨 복사를 피하고, 타입 자체를 readonly struct로 선언하면 컴파일러가 안전을 위해 넣는 방어적 복사까지 사라진다. ref도 복사를 피하지만 호출된 쪽이 원본을 고칠 수 있다는 점이 다르다.

박싱은 값 형식을 object나 인터페이스로 올릴 때 힙에 상자를 만들고 값을 복사하는 일이다. 할당이 생기니 GC 부담으로 이어진다. 제네릭 컬렉션(List<int>)은 박싱 없이 값을 담지만, object를 받는 옛 API에 값 형식을 넘기면 박싱이 난다. 어느 자리에서 박싱이 나는지는 런타임 버전에 따라 달라졌으므로(enum 키 Dictionary가 대표적이다) 외우기보다 프로파일러로 할당을 확인하는 편이 낫다.

면접에서 이렇게 답한다

  • 값 형식과 참조 형식의 차이 — 변수가 값을 직접 담느냐 주소를 담느냐의 차이고, 그래서 대입할 때 값 전체가 복사되느냐 같은 객체를 공유하느냐가 갈린다. 저장 위치는 “값 형식은 스택”이 아니라 선언된 자리를 따라간다고 덧붙인다.
  • class 대신 struct를 쓰는 기준 — 좌표나 색처럼 작고 의미가 값 하나에 가까운 데이터에 쓴다. 상속·다형성·null 표현이 필요하거나 여럿이 같은 인스턴스를 공유해야 하면 class를 쓴다. 필드가 많아지면 복사 비용 때문에 오히려 손해다.
  • 박싱이 왜 문제인가 — 힙 할당과 값 복사가 함께 일어나 매 프레임 도는 코드에서는 GC를 자주 부른다. 제네릭과 in, readonly struct로 값 형식을 값 형식인 채로 다루는 것이 해법이다.
  • ref, out, in의 차이 — 셋 다 참조로 넘긴다. ref는 넘기기 전에 초기화돼 있어야 하고 메서드가 고칠 수 있으며, out은 초기화 없이 넘기는 대신 메서드가 끝나기 전에 반드시 값을 넣어야 하고, in은 읽기 전용이라 큰 struct의 복사를 피하는 용도다.

흔한 오해

  • 값 형식은 항상 스택에 있다 — 클래스 필드나 배열 요소인 값 형식은 그 객체와 함께 힙에 있다. 스택이냐 힙이냐는 타입이 아니라 어디에 선언됐는지가 정한다.
  • new를 쓰면 반드시 힙 할당이 일어난다 — new Vector3(0, 0, 0)처럼 값 형식의 new는 그 자리에서 생성자를 돌릴 뿐 힙을 건드리지 않는다.
  • string을 object로 캐스팅하면 박싱이 일어난다 — string은 이미 참조 형식이라 주소만 옮겨 담는다. 박싱은 값 형식에서만 일어난다.
  • readonly로 선언한 List는 내용도 못 바꾼다 — 고정되는 것은 어느 리스트를 가리키는지뿐이라 Add나 원소 수정은 그대로 된다. const는 한술 더 떠 값이 사용하는 쪽 코드에 박혀 들어가므로, 라이브러리의 const를 바꾸면 쓰는 쪽도 다시 빌드해야 한다.
  • 얕은 복사만으로 원본과 분리된다 — MemberwiseClone은 얕은 복사라 참조 멤버는 원본과 같은 객체를 가리킨다. 세이브 데이터나 되돌리기처럼 원본이 바뀌면 안 되는 곳에서는 깊은 복사가 필요하다.

객체지향 문법

호출하는 쪽이 구체 타입을 몰라도 되게 만드는 장치들과, 그것이 실제로 동작하는 원리

핵심 개념

상속, 인터페이스, 가상 메서드는 결국 부르는 쪽이 구체 타입을 모른 채로 일을 시키기 위한 장치다. 적 100마리를 돌면서 Attack()을 부를 때 그것이 슬라임인지 보스인지 호출하는 쪽이 알 필요가 없게 만드는 것이 목적이고, 문법은 그 목적을 위한 수단이다.

고를 때의 기준은 간단하다. 물려줄 상태와 기본 구현이 있으면 추상 클래스, 서로 상관없는 타입들이 같은 약속만 지키면 되면 인터페이스다. C#은 클래스 다중 상속을 막고(같은 멤버를 양쪽에서 물려받는 다이아몬드 문제를 피하려고) 인터페이스는 여러 개 구현하게 한다. 구현할 두 인터페이스에 이름이 같은 메서드가 있으면 명시적 인터페이스 구현(void IA.Attack())으로 각각 따로 정의한다.

가상 메서드가 변수 타입이 아니라 실제 객체 타입에 맞게 불리는 이유는 타입마다 가상 메서드 표(vtable)를 하나씩 두고 호출이 그 표를 한 번 더 거치기 때문이다. 그래서 부모 타입 변수로 다뤄도 override한 구현이 실행된다. 반면 new는 표를 고치지 않고 이름만 가리므로 변수 타입 기준으로 불린다. 다형성이 끊기는 것이다.

class Enemy
{
    public virtual void Attack() => Console.Write("적");
}

class Boss : Enemy
{
    public override void Attack() => Console.Write("보스");   // 표를 덮어쓴다
}

class Slime : Enemy
{
    public new void Attack() => Console.Write("슬라임");      // 이름만 가린다
}

Enemy a = new Boss();
Enemy b = new Slime();
a.Attack();   // 보스 - 실제 객체 타입의 구현이 불린다
b.Attack();   // 적   - 변수 타입 기준으로 불린다

나머지는 범위와 시점의 문제다. 오버로딩은 같은 이름에 매개변수 구성을 다르게 둔 것이라 컴파일 시점에 어느 것을 부를지 정해지고, 오버라이딩은 실행 중에 실제 타입을 보고 정해진다. 접근 제한자 중 protected internal은 합집합(같은 어셈블리 전체와 다른 어셈블리의 파생 클래스), private protected는 교집합(같은 어셈블리 안의 파생 클래스)이다. static 생성자는 그 타입을 처음 쓰는 시점에 런타임이 딱 한 번 부르므로 호출 시점을 프로그래머가 정할 수 없고, 그래서 무거운 초기화를 넣지 않는다. 제네릭 제약(where T : IDamageable)은 컴파일러에게 “T는 적어도 이건 한다”를 알려 캐스팅 없이 그 멤버를 쓰게 해 준다.

면접에서 이렇게 답한다

  • 인터페이스와 추상 클래스 중 무엇을 쓰나 — 공통 상태와 기본 동작을 물려줄 것이 있으면 추상 클래스, 상속 계층이 다른 타입들이 같은 기능을 약속하게 하려면 인터페이스를 쓴다. C#은 클래스 상속이 하나뿐이므로 확장 지점은 인터페이스로 여는 편이 안전하다.
  • 가상 메서드는 어떻게 동작하나 — 타입마다 가상 메서드 표가 있고 호출이 그 표를 거쳐 실제 구현으로 간다. 간접 호출이라 아주 약간 느리고, 그래서 더 재정의할 일이 없으면 sealed를 붙여 최적화 여지를 준다.
  • 오버로딩과 오버라이딩의 차이 — 오버로딩은 한 클래스 안에서 이름이 같고 매개변수가 다른 메서드를 여러 개 두는 것으로 컴파일 시점에 결정되고, 오버라이딩은 상속 관계에서 가상 메서드를 다시 구현하는 것으로 실행 중에 결정된다.
  • 상속은 허용하되 재정의만 막으려면 — 그 메서드를 sealed override로 선언한다. sealed class는 상속 자체를 막아 조건을 넘어선다.

흔한 오해

  • new로 재정의해도 override와 결과가 같다 — new는 가리기일 뿐이라 부모 타입 변수로 부르면 부모 구현이 실행된다. 의도한 재정의라면 override를 쓴다.
  • protected internal은 같은 어셈블리의 파생 클래스만 — 그것은 private protected다. protected internal은 둘의 합집합이라 같은 어셈블리면 상속 관계가 아니어도 접근된다.
  • 반환 타입만 다르면 오버로딩이 된다 — 오버로딩 판별에 반환 타입은 쓰이지 않아 컴파일 오류가 난다.
  • 인터페이스는 구현을 전혀 가질 수 없다 — C# 8부터 기본 구현을 넣을 수 있다(Unity는 2021.2 이후 C# 9 기준). 다만 인스턴스 필드는 여전히 못 가지므로 상태를 물려주려면 추상 클래스가 필요하다.
  • 어트리뷰트를 붙이면 코드가 실행된다 — 어트리뷰트는 메타데이터일 뿐이고, 그것을 리플렉션으로 읽는 쪽(직렬화기, 에디터, 테스트 러너)이 동작을 바꾼다.

델리게이트·이벤트·람다

메서드를 값처럼 넘기는 문법과, 그 때문에 생기는 힙 할당·구독 해제 누수를 함께 본다

핵심 개념

델리게이트는 메서드를 담는 변수다. 타입이 맞는 메서드를 담아 두었다가 나중에 호출하므로, “무슨 일이 생기면 누가 처리할지”를 실행 중에 갈아 끼울 수 있다. Action은 반환값이 없는 델리게이트, Func는 마지막 타입 인자가 반환 타입인 델리게이트로, 매개변수 개수별 오버로드가 미리 준비돼 있어 직접 delegate 타입을 선언할 일이 거의 없다.

event는 새로운 타입이 아니라 델리게이트 필드에 붙는 한정자다. 붙이면 밖에서는 +=와 -=만 할 수 있고, 통째로 대입하거나 직접 호출하는 것은 선언한 클래스만 할 수 있다. 남이 내 이벤트를 대신 발생시키거나 다른 구독자를 실수로 날려 버리는 일을 문법으로 막는 장치다.

델리게이트 하나에 +=로 여러 메서드를 담을 수 있는데(멀티캐스트) 등록한 순서대로 불리고, 반환값은 마지막 호출의 결과만 남는다. 중간에서 예외가 나면 그 뒤에 등록된 대상은 호출되지 않으므로, 각각의 결과나 예외가 중요하면 GetInvocationList()로 직접 순회한다.

static class GameEvents
{
    public static event Action<int> ScoreChanged;   // 밖에서는 += , -= 만 된다

    // 델리게이트를 한 번만 읽어 호출하므로 검사와 호출 사이에 null이 되는 틈이 없다
    public static void Raise(int score) => ScoreChanged?.Invoke(score);
}

var actions = new List<Action>();
for (int i = 0; i < 3; i++)
{
    int copy = i;                            // 복사본을 캡처해야 0 1 2가 나온다
    actions.Add(() => Console.Write(copy));  // i를 그대로 캡처하면 3 3 3이 나온다
}

람다는 그 자리에서 만드는 이름 없는 메서드다. 주의할 것은 캡처가 값이 아니라 변수 자체를 붙잡는다는 점이다. for의 루프 변수는 루프 전체에서 하나뿐이라 그것을 캡처한 람다들은 모두 마지막 값을 본다(foreach의 반복 변수는 C# 5부터 반복마다 새로 만들어져 이 문제가 없다). 캡처가 있으면 컴파일러가 만든 클로저 객체가 힙에 생겨 호출할 때마다 할당이 쌓인다. 반대로 캡처가 없는 람다는 컴파일러가 델리게이트 인스턴스를 정적 필드에 캐싱해 사실상 한 번만 할당하므로, 매 프레임 도는 코드에서는 캡처를 피하거나 델리게이트를 필드에 담아 재사용한다.

면접에서 이렇게 답한다

  • delegate와 event의 차이 — event는 델리게이트 필드에 접근 제한을 거는 한정자다. 밖에서는 구독과 해제만 되고 발생은 선언한 클래스만 할 수 있어, 알림을 공개하되 통제권은 발행자가 쥐는 구조를 만든다.
  • 이벤트로 메모리 누수가 나는 이유 — 이벤트가 구독자 메서드와 그 객체를 참조하므로, 해제하지 않으면 구독자는 루트에 매달려 수거되지 않는다. 구독한 곳과 대칭이 되는 지점에서 반드시 -= 한다.
  • 클로저의 단점 — 캡처한 변수를 담을 객체가 힙에 생겨 할당이 되고, 캡처한 대상의 수명이 람다만큼 늘어난다. 매 프레임 도는 코드에서는 캡처 없는 람다나 미리 만들어 둔 델리게이트를 쓴다.
  • 델리게이트를 안전하게 호출하려면 — OnDie?.Invoke()를 쓴다. null 검사와 호출 사이에 마지막 구독자가 해제되면 예외가 나는데, ?.는 델리게이트를 한 번만 읽어 임시 변수로 호출하므로 그 틈이 없다.

흔한 오해

  • event는 델리게이트와 다른 별개의 타입이다 — 타입이 아니라 필드에 붙는 한정자다. 내부는 그대로 델리게이트다.
  • 멀티캐스트 델리게이트는 모든 반환값을 받을 수 있다 — 마지막 호출의 결과만 남는다. 전부 필요하면 GetInvocationList()로 하나씩 부른다.
  • if (e != null) e();면 충분하다 — 검사와 호출 사이에 구독이 해제되면 그대로 NullReferenceException이다. ?.Invoke()가 안전하다.
  • 람다는 가벼우니 할당이 없다 — 바깥 지역 변수나 this를 캡처하면 클로저 객체가 힙에 생긴다. C# 9의 static 람다는 캡처 자체를 막아 이 실수를 컴파일 오류로 잡아 준다.

컬렉션·문자열·LINQ

컬렉션의 내부 자료구조를 알아야 무엇이 O(1)이고 어디서 할당이 생기는지 보인다

핵심 개념

컬렉션 질문은 사실상 내부 자료구조를 아느냐를 묻는 것이다. 배열은 길이가 고정된 연속 메모리라 인덱스 접근이 가장 빠르고, List<T>는 그 배열을 안에 품고 크기가 모자라면 보통 두 배짜리 새 배열로 옮겨 담는다. 그래서 Add는 평균 O(1)이지만 늘어나는 순간에는 복사 비용과 버려진 배열만큼의 가비지가 생긴다. 개수를 대충이라도 알면 생성자에 용량을 넘겨 재할당을 줄인다. 참고로 Remove를 해도 Capacity는 줄지 않는다.

Dictionary<TKey, TValue>는 키의 GetHashCode()로 버킷을 정하고 그 안에서 Equals로 비교한다. 그래서 평균 O(1)이고, 해시가 한쪽으로 몰리면 최악 O(n)이다. 열거 순서는 보장되지 않으며, 커스텀 타입을 키로 쓰면 GetHashCode와 Equals를 함께 재정의해야 하고 그 기준 필드는 넣은 뒤에 바뀌지 않아야 한다. 정렬된 순회가 필요하면 균형 이진 탐색 트리인 SortedDictionary·SortedSet을 쓰는 대신 조회가 O(log n)이 된다는 것을 감수한다.

var names = new List<string>(capacity: 64);   // 재할당과 복사를 미리 줄인다

var sb = new StringBuilder();
foreach (var n in names)
{
    sb.Append(n).Append(", ");   // 이어 붙일 때마다 새 문자열을 만들지 않는다
}
string line = sb.ToString();

string s = "hello";
s.ToUpper();        // 반환값을 버렸으므로 s는 그대로 "hello"
s = s.ToUpper();    // 새 문자열을 다시 담아야 바뀐다

string은 불변이다. Replace나 ToUpper는 원본을 고치지 않고 바뀐 새 문자열을 돌려주므로 반환값을 다시 담지 않으면 아무 일도 일어나지 않는다. 같은 이유로 반복문에서 +=로 이어 붙이면 매번 새 문자열이 생기고 이전 것은 가비지가 된다. 조각이 많으면 StringBuilder로 버퍼에 이어 쓰고, Split처럼 배열과 문자열을 한꺼번에 만드는 메서드는 매 프레임 도는 코드에서 피한다.

LINQ는 대부분 지연 실행이다. Where나 Select는 호출하는 순간 계산하지 않고, foreach로 돌리거나 ToList(), Count()처럼 결과를 요구할 때 비로소 계산된다. 원본은 바뀌지 않고 새 시퀀스가 나온다. 읽기 좋은 대신 이터레이터 객체와 람다(캡처가 있으면 클로저)가 힙에 생기므로, 초기화나 로딩처럼 가끔 도는 코드에는 마음껏 쓰고 매 프레임 도는 코드에서는 for 문으로 풀어 쓰는 편이 안전하다.

면접에서 이렇게 답한다

  • 배열과 List의 차이 — List는 내부에 배열을 두고 자동으로 늘리는 동적 배열이다. 크기가 고정이고 성능이 예민한 자리는 배열, 개수가 변하는 자리는 List를 쓰되 예상 개수를 용량으로 미리 준다.
  • Dictionary는 어떻게 O(1)인가 — 키의 해시로 버킷을 바로 찾고 그 안에서만 비교하기 때문이다. 해시가 몰리면 한 버킷을 훑게 돼 최악 O(n)이고, 그래서 키 타입의 GetHashCode 품질이 성능을 좌우한다.
  • 문자열 연결이 왜 문제인가 — string이 불변이라 이어 붙일 때마다 새 객체가 생기고 이전 것이 가비지가 된다. 매 프레임 UI 텍스트를 이렇게 만들면 GC 끊김의 원인이 되므로 StringBuilder나 보간을 쓴다.
  • LINQ를 실무에서 쓰나 — 읽기 쉬워서 초기화·에디터 도구·로딩 코드에는 적극적으로 쓰고, 매 프레임 도는 경로에서는 할당 때문에 걷어낸다고 답한다. 판단 근거는 프로파일러의 GC Alloc 수치다.

흔한 오해

  • s.ToUpper();를 호출하면 s가 바뀐다 — string은 불변이라 새 문자열이 반환될 뿐이다. s = s.ToUpper();처럼 다시 담아야 한다.
  • List는 연결 리스트다 — List<T>는 내부가 배열인 동적 배열이다. 중간 삽입·삭제가 잦으면 뒤 원소를 밀어야 해서 오히려 비싸다.
  • Dictionary는 넣은 순서대로 열거된다 — 순서는 보장되지 않는다. 순서가 필요하면 SortedDictionary나 별도의 리스트를 함께 둔다.
  • LINQ는 호출하는 순간 결과가 만들어진다 — 대부분 지연 실행이라 열거할 때 계산된다. 원본을 바꾼 뒤에 열거하면 결과가 달라지는 것도 이 때문이다.

가비지 컬렉션

도달 가능성으로 수거하는 원리와, Unity의 GC가 .NET의 GC와 다른 점을 나눠 본다

핵심 개념

GC의 판단 기준은 “참조가 몇 개인가”가 아니라 루트에서 닿을 수 있는가다. 스택의 지역 변수, 정적 필드, 레지스터 같은 루트에서 출발해 참조를 따라가며 도달한 객체에 표시하고(mark), 표시되지 않은 것을 회수한다(sweep). 그래서 서로만 참조하는 객체 무리(순환 참조)도 루트에서 끊기면 통째로 수거된다. 반대로 말하면 누수는 안 쓰는데도 루트에서 닿는 것이다. 정적 컬렉션에 계속 담아 두거나 이벤트 구독을 해제하지 않은 경우가 전부 여기에 해당한다.

static class GameEvents
{
    public static event Action Died;
}

class HudPanel
{
    public void Show() => GameEvents.Died += OnDied;
    public void Hide() => GameEvents.Died -= OnDied;
    // Hide를 빼먹으면 정적 이벤트가 이 패널을 계속 참조해 영원히 수거되지 않는다

    void OnDied() { }
}

// using은 try-finally로 컴파일되므로 예외가 나도 Dispose가 불린다
using (var stream = File.OpenRead("save.dat"))
{
}

.NET의 GC는 여기에 세대를 더한다. 대부분의 객체는 금방 죽는다는 관찰에 기대어 힙을 0·1·2세대로 나누고, 0세대만 자주 싸게 훑는다. 0세대 수집에서 살아남은 객체는 1세대로, 또 살아남으면 2세대로 승격된다. 2세대 수집은 힙 전체를 훑기 때문에 드물게 일어나고 비싸다. 약 85,000바이트 이상인 큰 객체는 따로 LOH에 할당되는데, 복사 비용이 커서 기본적으로 압축하지 않으므로 단편화가 생기기 쉽고 2세대와 함께 수집돼 비싸다. 큰 배열은 새로 만들기보다 풀에 넣고 재사용하는 이유가 이것이다.

중요한 점은 Unity가 이 세대별 GC를 쓰지 않는다는 것이다. Mono든 IL2CPP든 Boehm GC를 쓰며, 세대 구분이 없고 객체를 옮기지 않아(비압축) 힙이 단편화될 수 있다. 증분 GC를 켜면 수집 작업을 여러 프레임에 나눠 한 번에 멈추는 시간을 줄여 주지만, 할당 자체를 줄여 주지는 않는다. 결국 게임에서 할 일은 GC를 튜닝하는 것이 아니라 매 프레임 생기는 할당을 없애는 것이다. Unity 2022 LTS 기준으로 증분 GC는 기본으로 켜져 있다.

마지막으로 GC가 모르는 자원이 있다. 파일 핸들, 소켓, 네이티브 플러그인이 잡은 메모리는 IDisposable로 직접 풀어야 한다. using은 try-finally로 컴파일되므로 예외가 나도 Dispose가 반드시 불린다. 소멸자(Finalize)는 불리는 시점이 정해져 있지 않고 파이널라이저 큐를 한 번 거치느라 객체 수거가 오히려 한 번 더 미뤄지므로, 안전망으로만 두고 평소에는 Dispose로 명시적으로 해제한다.

면접에서 이렇게 답한다

  • C#의 GC는 어떻게 동작하나 — 루트에서 도달 가능한 객체를 표시하고 나머지를 회수하는 마크 앤 스윕이다. 참조 카운팅이 아니므로 순환 참조도 수거되고, 대신 정적 필드나 이벤트로 루트에 매달린 객체는 영원히 남는다.
  • 세대를 나누는 근거 — 대부분의 객체가 금방 죽는다는 경험칙이다. 갓 만든 객체만 모아 자주 싸게 수집하면 전체 힙을 훑는 비싼 수집을 덜 하게 된다.
  • Unity의 GC는 무엇이 다른가 — Boehm GC라 세대가 없고 객체를 옮기지 않아 단편화가 생긴다. 증분 GC는 멈춤 시간을 여러 프레임에 나눌 뿐이므로, 대책은 풀링과 캐싱으로 할당을 줄이는 쪽이다.
  • Dispose와 Finalize의 차이 — Dispose는 내가 시점을 정해 부르는 해제이고 Finalize는 GC가 언젠가 부르는 안전망이다. unmanaged 자원은 using으로 Dispose를 보장하는 것이 원칙이다.

흔한 오해

  • 2세대 수집이 0세대보다 자주 일어나고 싸다 — 반대다. 0세대가 자주·싸게 돌고, 2세대는 힙 전체를 훑어 드물게 일어나며 비싸다.
  • 순환 참조는 수거되지 않는다 — 참조 카운팅을 쓰던 COM 시절의 이야기다. 도달 가능성으로 판단하므로 루트에서 끊기면 함께 수거된다.
  • Unity도 세대별 GC를 쓴다 — Boehm GC라 세대 구분이 없다. LOH 같은 .NET의 구분도 그대로 적용되지 않는다.
  • 증분 GC를 켜면 할당을 신경 쓰지 않아도 된다 — 한 번에 멈추는 시간을 나눌 뿐 총량은 그대로다. 할당이 많으면 수집도 그만큼 자주 돈다.
  • 소멸자를 만들어 두면 자원이 제때 풀린다 — 호출 시점이 정해져 있지 않고 수거만 늦춘다. 명시적으로 Dispose를 부르는 것이 원칙이다.

런타임과 컴파일

C# 소스가 IL을 거쳐 기계어가 되는 두 단계를 알면 Mono와 IL2CPP의 차이가 보인다

핵심 개념

C# 코드는 두 번 번역된다. 빌드할 때 컴파일러가 소스를 IL(중간 언어)과 메타데이터로 바꿔 어셈블리에 넣고, 그 IL을 기계어로 바꾸는 일은 나중에 한다. 이렇게 나눈 이유는 IL이 CPU에 독립적이어서 같은 어셈블리를 여러 아키텍처에서 쓸 수 있고, 함께 실린 메타데이터 덕분에 런타임이 타입 정보를 읽을 수 있기 때문이다. GC와 리플렉션, 직렬화가 모두 이 메타데이터에 기댄다.

두 번째 번역을 언제 하느냐가 JIT와 AOT를 가른다.

방식번역 시점대가
JIT실행 중, 메서드가 처음 호출될 때 그 메서드만첫 호출이 느리고, 실행 중 코드를 만들 권한이 필요하다
AOT빌드할 때 전부 미리빌드가 오래 걸리고, 실행 중 새 타입을 만들 수 없다
인터프리터번역하지 않고 한 줄씩 해석결과를 남기지 않아 같은 줄을 돌 때마다 다시 해석한다

Unity의 Mono는 JIT, IL2CPP는 AOT다. IL2CPP는 IL을 기계가 만든 C++ 소스로 옮긴 뒤 플랫폼 네이티브 컴파일러로 빌드한다. iOS는 실행 중 코드 생성을 막기 때문에 JIT를 쓸 수 없어 IL2CPP가 사실상 유일한 선택이고, 보통 실행 속도도 더 빠르다. 대신 빌드가 오래 걸리고, 쓰이지 않아 보이는 코드를 지우는 스트리핑과 AOT 제약 탓에 리플렉션이나 동적 제네릭이 런타임에 실패할 수 있다. 그때는 link.xml이나 [Preserve]로 지킬 타입을 표시한다.

.NET은 런타임과 클래스 라이브러리, 도구를 묶은 플랫폼이고 C#은 그 위에서 도는 언어다. Unity는 Microsoft의 CLR 대신 자체 포크한 Mono 런타임이나 IL2CPP를 쓰고, 쓸 수 있는 라이브러리 범위는 프로젝트 설정의 API 호환성 레벨로 정한다.

리플렉션은 실행 중에 Type을 뒤져 필드나 메서드를 찾아 호출하는 기능이다. 인스펙터와 직렬화기, 테스트 러너가 이것으로 돈다. 다만 이름을 문자열로 찾고 인자를 object[]에 싸서 넘기므로 탐색 비용과 박싱이 매번 생겨 직접 호출보다 훨씬 느리다. 한 번 찾은 결과를 델리게이트로 캐싱하면 그 비용은 첫 호출 한 번으로 줄어든다.

// 매번 메타데이터를 문자열로 뒤진다. 인자도 object[]로 싸서 박싱된다
var mi = typeof(Enemy).GetMethod("TakeDamage");
mi.Invoke(enemy, new object[] { 10 });

// 한 번만 찾아 델리게이트로 만들어 두면 그 뒤로는 직접 호출과 비슷하다
static readonly Dictionary<string, Action<Enemy, int>> Table = new();

static Action<Enemy, int> GetCall(string name)
{
    if (!Table.TryGetValue(name, out var call))
    {
        var method = typeof(Enemy).GetMethod(name);
        call = (Action<Enemy, int>)Delegate.CreateDelegate(
            typeof(Action<Enemy, int>), method);
        Table[name] = call;
    }
    return call;
}

더 나은 답은 아예 빌드할 때 코드를 만들어 두는 것이다. Roslyn 소스 생성기는 컴파일 시점에 호출 코드를 생성하므로 런타임 탐색이 사라지고, 이름이 틀리면 컴파일 단계에서 걸리며, 스트리핑에도 살아남는다.

직렬화는 메모리에 흩어진 객체를 저장하거나 보낼 수 있는 연속된 데이터로 바꾸는 일이고, 역직렬화는 그 반대다. 참조 주소는 프로세스마다 달라 적어 두어도 의미가 없으므로 값과 구조만 기록한다. Unity는 [SerializeField]가 붙은 필드를 인스펙터와 프리팹에 저장하고 프로퍼티는 기본적으로 저장하지 않는다.

면접에서 이렇게 답한다

  • C#은 C++보다 느린가 — 같은 알고리즘이면 차이는 대개 작다. GC와 경계 검사 같은 안전장치 비용을 내는 대신 JIT는 실제 실행 중인 CPU에 맞춰 최적화한다. 게임에서 체감하는 느림은 언어보다 매 프레임 생기는 할당과 캐시를 무시한 데이터 배치에서 온다.
  • JIT, AOT, 인터프리터의 차이 — JIT는 실행 중 메서드 단위로 번역해 캐싱하고, AOT는 빌드 때 전부 미리 번역하며, 인터프리터는 번역 결과를 남기지 않고 한 줄씩 해석한다. Unity에서는 Mono가 JIT, IL2CPP가 AOT에 해당한다.
  • 리플렉션을 지양하는 이유 — 느리고 할당이 생기며, IL2CPP에서는 스트리핑에 지워져 런타임에 가서야 실패가 드러난다. 반복 호출은 델리게이트로 캐싱하고, 구조가 고정적이면 소스 생성기로 옮겨 컴파일 시점에 오류를 잡는다.
  • 텍스트에 적힌 이름으로 메서드 100여 개를 호출해야 한다면 — 이름과 델리게이트를 짝지은 사전을 시작할 때 한 번 만들어 두고 호출은 조회만 한다. 등록은 어트리뷰트 스캔이나 소스 생성기로 자동화해 메서드를 추가할 때 사전을 손대지 않게 한다. 없는 이름은 로딩 시점에 걸러낼 수 있다.
  • IL을 보면 무엇이 도움 되나 — 박싱이 일어난 지점, 클로저 때문에 생긴 클래스처럼 소스만 봐서는 안 보이는 비용이 드러난다.

흔한 오해

  • IL2CPP를 쓰면 C++로 코드를 짜야 한다 — 아니다. 작성하는 코드는 그대로 C#이고, 변환된 C++는 사람이 읽으라고 만든 결과물이 아니다.
  • JIT는 시작할 때 프로그램 전체를 번역한다 — 메서드가 처음 호출될 때 그 메서드만 번역하고 결과를 캐싱한다. 그래서 첫 진입에서만 끊김이 생긴다.
  • 인터프리터도 번역 결과를 캐싱한다 — 캐싱하는 순간 그것이 JIT다. 인터프리터는 남기지 않기 때문에 느리다.
  • IL2CPP에서는 리플렉션이 아예 안 된다 — 동작한다. 문제는 코드에서 참조가 보이지 않아 스트리핑에 지워지는 것이므로 보존 설정으로 남긴다.
  • 직렬화는 파일 저장에만 쓴다 — 네트워크 전송, 프리팹과 씬 저장, 인스펙터 표시가 모두 같은 구조 위에 있다.

예외 처리

throw와 throw ex는 스택 추적이 다르고, catch는 하나만 골라 실행되며 finally는 거의 언제나 실행된다

핵심 개념

예외는 '여기서는 더 못 한다'를 호출 스택 위로 올려 보내는 장치다. 예외가 던져지면 런타임은 현재 메서드에 맞는 catch가 있는지 보고, 없으면 자신을 부른 메서드로 올라가며 계속 찾는다. 끝까지 못 찾으면 그 스레드가 죽는다.

여기서 중요한 사실 하나. StackTrace는 예외 객체가 만들어질 때가 아니라 throw 문이 실행되는 지점에서 런타임이 채운다. 그래서 catch 안에서 throw;라고만 쓰면 잡은 예외가 원래 스택 추적을 그대로 달고 다시 올라가지만, throw ex;라고 쓰면 그 줄이 새 출발점이 되어 진짜 원인이 있던 위치가 지워진다. 로그만 보고 디버깅해야 하는 라이브 빌드에서는 이 차이가 크다. 원인을 감싸 올리고 싶으면 throw new XxxException(message, ex)로 InnerException에 원본을 담는다.

catch 절은 위에서부터 차례로 검사해 타입이 맞는 첫 하나만 실행된다. 여러 개가 연달아 실행되는 일은 없다. 그래서 파생 예외를 위에, Exception 같은 기반 예외를 아래에 적어야 한다. 순서를 뒤집으면 아래 절이 영원히 도달할 수 없으므로 컴파일 오류가 난다. finally는 예외가 났든 안 났든, catch에서 다시 던졌든, try 안에서 return했든 제어가 블록을 떠날 때 실행된다. 그래서 자원 해제를 여기에 둔다.

static void Load(string path)
{
    var file = File.OpenRead(path);
    try
    {
        Parse(file);            // 여기서 FormatException이 났다고 하자
    }
    catch (FormatException ex)  // 구체적인 예외가 위
    {
        Debug.LogException(ex);
        throw;                  // O: 원래 발생 위치가 StackTrace에 남는다
        // throw ex;            // X: 스택 추적이 이 줄부터 다시 쌓인다
    }
    catch (Exception ex)        // 기반 예외가 아래
    {
        // 원인을 감싸 올린다. 원본은 InnerException에 남는다
        throw new InvalidOperationException($"{path} 로드 실패", ex);
    }
    finally
    {
        file.Dispose();         // 예외가 나든, return을 하든 실행된다
    }
}

같은 예외 타입을 조건으로 나누고 싶으면 catch (IOException e) when (조건) 형태의 예외 필터를 쓴다. 필터 식은 스택을 되감기 전에 평가되므로, 조건이 맞지 않아 지나갈 때 원래 호출 스택과 지역 변수가 그대로 남는다. 잡아 놓고 if로 걸러 다시 던지는 방식보다 디버깅에 유리한 이유가 이것이다.

게임 클라이언트에서는 예외를 흐름 제어로 쓰지 않는다. 던지는 순간 스택 정보를 모으는 비용이 들어 매 프레임 도는 코드에서 반복되면 그대로 스파이크가 된다. 자주 일어나는 실패는 int.TryParse나 Dictionary.TryGetValue처럼 예외 없이 결과를 알려주는 형태로 처리한다.

면접에서 이렇게 답한다

  • throw와 throw ex의 차이 — throw;는 잡은 예외를 그대로 다시 올려 원래 발생 위치의 스택 추적을 유지한다. throw ex;는 스택 추적이 그 catch 위치에서 다시 시작돼 진짜 원인을 잃어버린다. 재던질 때는 throw;를 쓰고, 문맥을 덧붙이고 싶으면 새 예외로 감싸 InnerException에 원본을 남긴다.
  • try-catch-finally의 실행 순서 — try에서 예외가 나면 위에서부터 타입이 맞는 catch 하나만 실행되고, 그다음 finally가 실행된다. 여러 catch가 함께 실행되는 일은 없다.
  • catch 순서를 왜 신경 쓰나 — 기반 예외를 위에 두면 아래 절이 절대 실행될 수 없어 컴파일러가 막는다. 구체적인 것부터 위에 쓴다.
  • finally가 실행되지 않는 경우가 있나 — 거의 없다. Environment.FailFast처럼 프로세스가 그 자리에서 끝나는 경우뿐이라 자원 해제는 finally나 using에 맡겨도 된다. using은 컴파일러가 try-finally로 바꿔 준다.

흔한 오해

  • 타입이 맞는 catch가 여러 개면 전부 실행된다 — 위에서부터 검사해 처음 맞는 하나만 실행하고 나머지는 건너뛴다.
  • throw ex;가 무엇을 던지는지 명시해서 더 낫다 — 명시적으로 보일 뿐 스택 추적을 날린다. 같은 예외를 다시 올릴 거라면 throw;가 맞다.
  • try나 catch 안에서 return하면 finally를 건너뛴다 — 반환값을 계산한 뒤 finally를 실행하고 나서 돌아간다.
  • Exception 하나로 다 잡아 두면 안전하다 — 복구할 수 없는 예외까지 삼키면 잘못된 상태로 계속 돌다 엉뚱한 곳에서 터진다.
  • try 블록은 그 자체로 느리다 — 예외가 나지 않으면 진입 비용은 사실상 없다. 비싼 것은 실제로 던지는 순간이다.

코드 문제

출력 예측 문제는 기본값과 초기화 순서, 클로저 캡처 이 세 군데에서 답이 갈린다

핵심 개념

출력을 맞히는 문제는 문법 지식이 아니라 '언어가 언제 무엇을 하는가'를 묻는다. 실무에서 버그를 만드는 지점이 그대로 문제가 된다. 함정은 대개 세 갈래다.

첫째, 초기화하지 않은 필드의 기본값. 참조 형식은 null이지만 값 형식은 null이 될 수 없고 모든 필드가 0으로 채워진 값을 갖는다. DateTime의 기본값은 DateTime.MinValue다.

class A { public string S; public DateTime D; }

var a = new A();
Console.WriteLine(a.S == null);     // True  - 참조 형식의 기본값은 null
Console.WriteLine(a.D == null);     // False - 값 형식은 null이 될 수 없다
Console.WriteLine(a.D == default);  // True  - "설정 안 됨"은 이렇게 본다

두 번째 줄이 컴파일되는 이유는 a.D == null이 DateTime? 비교로 승격되기 때문이다. 문법은 통과하지만 결과가 언제나 False라 컴파일러가 '항상 false'라는 경고를 붙인다. 값이 들어왔는지를 정말 구분하려면 필드를 DateTime?로 선언한다.

둘째, 초기화 순서. 정적 필드 이니셜라이저 → 정적 생성자 → 인스턴스 필드 이니셜라이저 → 인스턴스 생성자 순이다. 정적 쪽은 타입을 처음 쓸 때 한 번 돌고, 인스턴스 쪽은 객체를 만들 때마다 돈다.

class Counter
{
    static int total = Log("1 정적 필드 이니셜라이저");
    int id = Log("3 인스턴스 필드 이니셜라이저");

    static Counter() { Console.WriteLine("2 정적 생성자"); }
    public Counter() { Console.WriteLine("4 인스턴스 생성자"); }

    static int Log(string what) { Console.WriteLine(what); return 0; }
}

new Counter();   // 1, 2, 3, 4가 차례로 찍힌다
new Counter();   // 3, 4만 찍힌다. 정적 초기화는 한 번뿐이다

셋째, 클로저 캡처. 람다는 변수의 값이 아니라 변수 자체를 잡는다. for의 반복 변수는 루프 전체에서 하나뿐이라 모든 람다가 같은 변수를 보고, 나중에 호출하면 루프가 끝난 뒤의 값을 읽는다. foreach의 반복 변수는 매 반복 새로 만들어지도록 언어가 바뀌어 기대한 대로 나온다.

var actions = new List<Action>();

for (int i = 0; i < 3; i++)
    actions.Add(() => Console.Write(i));   // 3 3 3 - i는 루프 전체에서 변수 하나다

foreach (var n in new[] { 0, 1, 2 })
    actions.Add(() => Console.Write(n));   // 0 1 2 - n은 반복마다 새로 만들어진다

for (int i = 0; i < 3; i++)
{
    int captured = i;                      // 반복 안에서 새 변수를 만들어 고친다
    actions.Add(() => Console.Write(captured));   // 0 1 2
}

캡처는 성능 문제이기도 하다. 변수를 잡는 람다는 그 변수를 담을 클래스를 힙에 만든다. 잡을 것이 없으면 static 람다로 선언해 실수로 캡처하는 것을 컴파일러가 막게 한다.

짧은 메서드를 써 보라는 문제도 같이 나온다. 답보다 경계 조건을 챙기는지를 본다.

static int SumEven(int[] numbers)
{
    int sum = 0;
    foreach (int n in numbers)
        if (n % 2 == 0) sum += n;   // n % 2 == 1로 홀수를 찾으면 음수에서 틀린다
    return sum;
}

static string KeepFirstDollar(string s)
{
    int first = s.IndexOf('$');
    if (first < 0) return s;
    return s.Substring(0, first + 1)
         + s.Substring(first + 1).Replace("$", string.Empty);
}

면접에서 이렇게 답한다

  • 초기화하지 않은 string과 DateTime을 null과 비교하면 — string은 참조 형식이라 True, DateTime은 값 형식이라 False다. 값 형식 비교는 DateTime?로 승격돼 컴파일은 되지만 결과가 항상 false라서 경고가 붙는다.
  • 정적 생성자와 인스턴스 생성자 중 무엇이 먼저인가 — 정적 쪽이 먼저다. 타입을 처음 쓰는 시점에 정적 필드 이니셜라이저와 정적 생성자가 한 번 돌고, 이후 객체를 만들 때마다 인스턴스 필드 이니셜라이저와 인스턴스 생성자가 돈다.
  • 루프에서 만든 람다가 전부 같은 값을 출력하는 이유 — 값을 복사하는 게 아니라 변수를 붙잡고 있기 때문이다. for의 반복 변수는 루프에 하나뿐이라 모두 같은 것을 본다. 반복 안에서 지역 변수를 새로 만들어 캡처하면 해결된다. 버튼을 루프로 만들며 인덱스를 캡처한 콜백을 붙일 때 실무에서 그대로 나온다.

흔한 오해

  • 값 형식도 초기화 전에는 null이다 — 값 형식에 null 상태는 없다. 0으로 채워진 기본값이 들어 있다.
  • a.D == null은 컴파일 오류다 — DateTime?로 승격돼 컴파일된다. 경고만 나고 결과는 항상 False다.
  • 정적 생성자는 프로그램이 시작할 때 실행된다 — 타입을 처음 쓰는 시점에 실행된다. 시점을 코드로 제어할 수 없으므로 무거운 작업을 넣지 않는다.
  • 홀짝 판정은 n % 2 == 1로 하면 된다 — 음수에서 -1이 나와 홀수를 놓친다. == 0이나 != 0으로 쓴다.
