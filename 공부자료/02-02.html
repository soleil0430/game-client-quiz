생명주기와 스크립팅

엔진이 내 함수를 언제 부르는지 알면 초기화·물리·파괴에서 나는 버그가 대부분 사라진다

Start에서 매니저를 찾았는데 null이 나온다. 물리를 Update에 뒀더니 기기마다 점프 높이가 다르다. 둘 다 엔진이 언제 부르는지를 모르면 생기는 버그다.

한 프레임 안에서 내 함수가 불리는 순서

Unity 스크립트에는 main이 없다. 게임 루프는 엔진이 들고 있고 내 함수는 엔진이 부르는 콜백이다. 언제 몇 번 불리는가가 그대로 설계 제약이 된다.

순서만큼 중요한 것이 자리 배치다. 어느 함수에 무엇을 두는지는 대체로 정해져 있다.

함수여기에 두는 일
Awake자기 초기화, 컴포넌트 캐싱
OnEnable이벤트 구독
Start다른 오브젝트를 찾는 초기화
FixedUpdate힘과 속도 같은 물리 처리
Update입력과 일반 로직
LateUpdate카메라 추적, 본 보정
OnDisable이벤트 해제
OnDestroy마지막 정리

Awake에서 남을 찾으면 null이 나온다

Awake와 Start가 따로 있는 이유는 순서 보장이다. 함께 로드된 오브젝트 전부의 Awake가 끝난 뒤에야 Start가 시작한다. Awake 시점에는 다른 오브젝트가 아직 준비되지 않았을 수 있다.

그래서 자기 초기화는 Awake, 남을 찾는 초기화는 Start에 둔다. Awake는 오브젝트가 꺼져 있어도 불리고 Start는 켜진 뒤에야 불린다. OnEnable은 켜질 때마다 불려서 이벤트 구독 자리로 쓴다.

종료는 OnApplicationQuit, OnDisable, OnDestroy 순이다. 다만 모바일에서 강제 종료되면 셋 다 불리지 않는다. 저장은 OnApplicationPause(true)에 두는 편이 안전하다.

물리를 Update에 두면 기기마다 결과가 달라진다

물리는 일정한 간격으로 적분해야 같은 결과가 나온다. FixedUpdate가 따로 있는 이유가 그것이다. 간격은 기본 0.02초고 Time.fixedDeltaTime으로 읽는다.

반면 Update는 호출 횟수가 기기 성능을 탄다. 시간에 비례하는 값에는 Time.deltaTime을 곱해야 어느 기기에서나 같은 속도가 된다. 입력은 Update에서 받아 플래그로 넘기고 힘은 FixedUpdate에서 준다.

timeScale을 0으로 두면 FixedUpdate가 멈추고 deltaTime이 0이 된다. Update 자체는 계속 불린다. 그래서 일시정지 화면의 연출에는 unscaledDeltaTime을 쓴다.

코루틴도 Destroy도 프레임 단위로 미뤄진다

코루틴은 스레드가 아니다. yield가 든 메서드를 컴파일러가 IEnumerator 상태 머신으로 바꾼다. Unity가 매 프레임 MoveNext를 불러 다음 yield까지만 진행시킨다.

메인 스레드에서 도니 Unity API를 그대로 쓸 수 있다. 대신 무거운 계산을 넣으면 그 프레임이 통째로 끊긴다. 오브젝트가 꺼지면 코루틴도 멈추지만 async/await는 CancellationToken으로 직접 끊어야 한다.

Destroy도 즉시 지우지 않는다. 그 프레임의 Update가 끝난 뒤 렌더링 전에 지워진다. 게다가 UnityEngine.Object는 네이티브 객체를 감싼 껍데기라 파괴 뒤에도 C# 객체가 남는다.

파괴된 적을 참조할 때 문법마다 결과가 갈린다: 

Enemy target = FindNearestEnemy();
Destroy(target.gameObject);   // 이 프레임 끝, 렌더링 직전에 지워진다

if (target == null) { }       // true. Unity가 ==를 재정의해 뒀다
if (target is null) { }       // false. 재정의를 타지 않는다
target?.Hit(10);              // 파괴된 껍데기에 그대로 접근한다

그래서 파괴될 수 있는 참조는 ==로만 검사한다. is null과 ?.와 ReferenceEquals는 재정의를 타지 않아 예외를 낸다.

면접에서 이렇게 답한다

  • 생명주기를 설명하라 — Awake, OnEnable, Start로 초기화합니다. 한 프레임은 FixedUpdate, Update, LateUpdate, 렌더링 순이고 FixedUpdate는 프레임마다 횟수가 다릅니다. 끝날 때 OnDisable과 OnDestroy가 불립니다.
  • Awake와 Start를 어떻게 나누나 — 모든 Awake가 끝난 뒤 Start가 불립니다. 그래서 자기 초기화는 Awake에, 남을 참조하는 초기화는 Start에 둡니다.
  • Update 1000개와 매니저 하나 중 무엇이 빠른가 — 매니저입니다. 네이티브에서 매니지드로 넘어오는 비용이 호출마다 붙어서, 한 번 넘어가 반복문을 도는 편이 쌉니다. 빈 Update도 지웁니다.

이런 오해를 한다

  • timeScale이 0이면 Update도 멈춘다 — Update는 계속 불린다. 멈추는 것은 FixedUpdate와 deltaTime을 쓰는 시간 기반 로직이다.
  • 코루틴은 별도 스레드에서 돈다 — 메인 스레드다. 진짜 병렬이 필요하면 스레드나 Job System을 쓴다.
  • 파괴된 오브젝트에 ?.를 쓰면 안전하다 — 오히려 위험하다. 재정의된 ==를 타지 않아 파괴된 껍데기에 그대로 접근한다.
  • transform.position.y = 0f가 막힌 것은 Unity 탓이다 — C# 문법이다. Vector3가 구조체라 프로퍼티가 복사본을 돌려준다.

3줄 정리

  • 한 프레임은 FixedUpdate, Update, LateUpdate, 렌더링 순
  • 자기 초기화는 Awake, 남을 찾는 초기화는 Start
  • 코루틴은 메인 스레드, Destroy는 프레임 끝에 실행
