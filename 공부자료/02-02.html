Unity 엔진

생명주기와 스크립팅

엔진이 내 함수를 언제 부르는지 알면 초기화·물리·파괴에서 나는 버그가 대부분 사라진다

Awake에서 매니저를 찾았는데 null이 돌아온다. 물리를 Update에 뒀더니 기기마다 점프 높이가 다르다. 로직이 틀린 게 아니라, 엔진이 내 함수를 언제 부르는지 몰라서 나는 버그다.

한 프레임 안에서 내 함수가 불리는 순서

Unity 스크립트에는 main이 없다. 게임 루프는 엔진이 들고 있고, 내가 쓴 함수는 엔진이 때맞춰 부르는 콜백이다.

순서만큼 중요한 것이 자리 배치다.

함수여기에 두는 일
Awake자기 초기화, 컴포넌트 캐싱
OnEnable이벤트 구독
Start다른 오브젝트를 찾는 초기화
FixedUpdate힘과 속도 같은 물리 처리
Update입력과 일반 로직
LateUpdate카메라 추적, 본 보정
OnDisable이벤트 해제
OnDestroy마지막 정리

Awake와 Start는 왜 따로 있나

순서를 보장하려고 그렇다. 함께 로드된 오브젝트들은 모든 Awake가 끝난 뒤 Start가 불리므로, Awake 시점에는 남이 아직 준비되지 않았을 수 있다.

자기 것은 Awake에서, 남의 것은 Start에서. 이 한 줄이면 절반은 끝난다.

순서를 꼭 정해야 하면 Project Settings의 Script Execution Order를 쓴다. 값이 작을수록 먼저 실행되고, 설정하지 않은 스크립트는 기본 그룹(0)에 들어가 그 사이에 놓인다. 이벤트 함수 전체에 적용되지만, 같은 스크립트를 붙인 인스턴스끼리의 순서는 보장되지 않는다.

실행 순서에 기대는 코드는 깨지기 쉽다. 이벤트로 순서를 설계에서 없애는 편이 낫다.

나머지 절반은 켜짐 여부다. Awake는 오브젝트가 꺼져 있어도 한 번 불리고, Start는 켜진 뒤 첫 Update 직전에 불린다. OnEnable과 OnDisable은 활성화·비활성화와 파괴 시점에 짝으로 불려서, C# 이벤트를 OnEnable에서 구독하고 OnDisable에서 해제하면 구독과 해제가 항상 맞는다.

해제를 빼먹으면 파괴된 오브젝트를 붙잡은 델리게이트가 이벤트에 남아 메모리 누수와 MissingReferenceException을 일으킨다. static 이벤트일수록 더 위험하다.

종료는 OnApplicationQuit, OnDisable, OnDestroy 순서로 온다. 다만 모바일에서 앱이 강제로 내려가면 셋 다 불리지 않는다. 저장을 OnApplicationPause(true)에 두는 이유가 그것이다.

물리를 Update에 두면 기기마다 결과가 달라진다

물리는 일정한 간격으로 적분해야 같은 결과가 나온다. 그 간격이 Fixed Timestep(Project Settings의 Time)이고 기본 0.02초, 초당 50회다. 프레임 레이트와 무관하게 정해진 간격으로 물리를 돌린다. Time.fixedDeltaTime으로 읽고 런타임에 대입해 바꿀 수도 있다.

프레임이 길어지면 밀린 만큼 FixedUpdate가 한 프레임에 여러 번 불리고, 프레임이 아주 빠르면 한 번도 안 불릴 수 있다.

Update는 다르다. 프레임마다 한 번 호출되니 transform.position += Vector3.forward * speed;만 적으면 매 프레임 같은 거리를 가서, 60fps 기기에서는 30fps 기기보다 두 배 빨리 움직인다.

프레임 사이 경과 시간인 Time.deltaTime을 곱하면 프레임레이트에 따라 속도가 달라지지 않고 초당 speed만큼 일정하게 움직인다.

입력은 Update에서 받아 플래그로 넘기고, 힘은 FixedUpdate에서 준다.

호출 횟수는 비용이기도 하다. 엔진은 Update를 가진 컴포넌트 목록을 돌며 네이티브에서 매니지드로 넘어가 호출한다. 이 경계를 넘는 비용이 호출마다 붙어서, 1000개가 각자 Update를 갖기보다 매니저 하나가 한 번만 넘어가 반복문을 도는 쪽이 빠르다.

timeScale은 게임 시간이 흐르는 속도만 바꾼다. Update는 프레임마다 그대로 호출되지만 deltaTime이 0이라 시간에 비례하는 로직이 멈추고, 물리 시간이 흐르지 않아 FixedUpdate는 호출되지 않는다. 일시정지 메뉴의 연출이나 애니메이션은 timeScale 영향을 받지 않는 unscaledDeltaTime과 WaitForSecondsRealtime을 쓴다.

코루틴도 Destroy도 프레임 단위로 미뤄진다

코루틴은 스레드가 아니다. yield가 들어간 메서드는 컴파일러가 IEnumerator를 구현한 상태 머신 클래스로 바꾸고, Unity가 매 프레임 이 열거자의 MoveNext를 불러 다음 yield까지만 진행시킨다.

yield return null은 다음 프레임 Update 시점에 그 자리부터 이어서 실행하고, WaitForFixedUpdate는 물리 갱신 뒤에, WaitForSeconds는 지정 시간이 지난 뒤에 재개한다. WaitForSeconds는 timeScale 영향을 받으니, 받지 않으려면 WaitForSecondsRealtime을 쓴다.

실행은 모두 메인 스레드에서 일어나 Unity API를 자유롭게 쓸 수 있다. 대신 CPU 부하 자체를 나누지는 못해서, 무거운 계산을 넣으면 그 프레임이 통째로 끊긴다. 그런 계산은 스레드나 Job System으로 넘기고 결과만 메인 스레드에서 반영한다.

코루틴은 돌리던 GameObject가 비활성화되거나 파괴되면 같이 멈춘다. async/await는 멈추지 않으므로 CancellationToken으로 직접 취소해야 한다.

Destroy도 부른 자리에서 지우지 않는다. 지연 파괴라 현재 프레임의 Update가 모두 끝난 뒤 렌더링 전에 실제로 제거된다.

DestroyImmediate는 즉시 지우지만, 순회 중인 내부 배열을 흔들 수 있어 런타임에서는 쓰지 말라고 문서에 명시돼 있고 에셋이나 에디터 툴에서만 쓴다.

씬이 바뀌어도 살아남게 하는 것은 DontDestroyOnLoad다. 대상을 파괴되지 않는 전용 씬으로 옮기므로, 자식에 호출하면 Unity가 루트로 끌어올린 뒤 옮겨 계층이 깨질 수 있다. 루트 오브젝트에만 적용되니 부모째로 옮겨야 하고, 되돌리려면 SceneManager.MoveGameObjectToScene으로 다시 씬에 넣는다.

씬을 다시 로드하면 매니저가 중복 생성되기 쉽다. 싱글턴에서 인스턴스가 있으면 스스로를 Destroy하게 만든다.

죽은 적을 참조할 때 문법마다 답이 갈린다:

Destroy(target.gameObject);   // 이 프레임 끝, 렌더링 직전에 지워진다

if (target == null) { }       // true. Unity가 ==를 재정의해 뒀다
if (target is null) { }       // false. 재정의를 타지 않는다
target?.Hit(10);              // 파괴된 껍데기에 그대로 접근한다

UnityEngine.Object는 네이티브 객체를 감싼 껍데기라, 파괴된 뒤에도 C# 객체는 남아 있다. 그래서 ==를 오버로드해 이런 객체를 null처럼 보이게 한다(fake null).

반면 ?.와 is null과 ReferenceEquals는 오버로드를 타지 않고 실제 참조만 보므로, 파괴된 객체를 null이 아니라고 판단해 그대로 접근하다 MissingReferenceException이 난다. 파괴될 수 있는 참조에는 == null과 != null만 쓴다.

Vector3는 구조체라 transform.position은 값 복사본을 돌려주는 프로퍼티다. 복사본의 필드를 고쳐 봐야 원본에 반영되지 않으니, C# 컴파일러가 transform.position.x = 5f;를 아예 막는다.

var p = transform.position; p.x = 5f; transform.position = p;처럼 지역 변수에 받아 고친 뒤 전체를 다시 대입한다.

SendMessage로 부르면 오타를 컴파일러가 못 잡는다

SendMessage는 자기 GameObject에 붙은 컴포넌트에서, BroadcastMessage는 자신과 모든 자식까지, SendMessageUpwards는 부모 쪽으로 올라가며 같은 이름의 메서드를 찾아 호출한다.

접근 제한자와 무관하게 호출되지만, 이름을 문자열로 찾는 리플렉션 방식이라 느리고 오타를 컴파일러가 잡아 주지 못한다. 실무에서는 C# 이벤트, UnityEvent, 인터페이스 호출로 대체한다.

면접에서 이렇게 답한다

  • 생명주기를 설명하라 — 초기화는 Awake, OnEnable, Start 순서라고 시작한다. 한 프레임은 FixedUpdate, Update, LateUpdate, 렌더링 순이고 FixedUpdate만 프레임마다 횟수가 다르다. 끝날 때는 OnDisable과 OnDestroy가 불린다.
  • Awake와 Start를 어떻게 나누나 — 모든 오브젝트의 Awake가 끝난 뒤에 Start가 불린다는 순서부터 말한다. 그래서 자기 초기화는 Awake에, 남을 참조하는 초기화는 Start에 둔다.
  • Update 1000개와 매니저 하나 중 무엇이 빠른가 — 매니저 하나다. 네이티브에서 매니지드로 넘어오는 비용이 호출마다 붙으니, 한 번 넘어가 반복문을 도는 편이 싸다. 빈 Update도 지운다는 말까지 덧붙인다.

이런 오해를 한다

  • “timeScale이 0이면 Update도 멈춘다” — Update는 멀쩡히 계속 불린다. 멈추는 것은 FixedUpdate와 deltaTime을 쓰는 시간 기반 로직이다.
  • “코루틴은 별도 스레드에서 돈다” — 메인 스레드다. 진짜 병렬이 필요하면 스레드나 Job System을 쓴다.
  • “파괴된 오브젝트에 ?.를 쓰면 안전하다” — 오히려 위험하다. 재정의된 ==를 타지 않아 이미 파괴된 껍데기를 살아 있다고 보고 접근한다.
  • “transform.position.y = 0f가 막힌 것은 Unity 탓이다” — C# 문법이다. Vector3가 구조체라 프로퍼티가 복사본을 돌려준다. 그 복사본을 고쳐 봐야 원본은 그대로다.

3줄 정리

  • 한 프레임은 FixedUpdate, Update, LateUpdate, 렌더링 순
  • 자기 초기화는 Awake, 남을 찾는 초기화는 Start
  • 코루틴은 메인 스레드, Destroy는 프레임 끝에 실행
