클래스와 가상 함수

vtable이 무엇을 대가로 다형성을 주는지 알면 가상 소멸자와 생성 순서가 따라온다

핵심 개념

C++에서 C#과 크게 갈리는 지점은 기본이 정적 바인딩이라는 것이다. virtual을 붙이지 않으면 호출 대상이 컴파일 시점에 포인터·참조의 타입으로 정해진다. 자식이 같은 이름의 함수를 만들어도 그것은 재정의가 아니라 부모 함수를 가리는 것(name hiding)이라, 부모 포인터로 부르면 부모 버전이 불린다.

virtual을 붙이면 컴파일러는 클래스마다 함수 주소 표(vtable)를 하나 만들고 객체에는 그 표를 가리키는 포인터(vptr)를 심는다. 호출할 때 vptr → vtable → 실제 함수로 한 번 더 건너뛰므로 부모 포인터로도 실제 객체의 함수가 불린다. 비용은 객체마다 포인터 하나(64비트에서 8바이트)와 간접 호출 한 번, 그리고 인라인이 안 된다는 점이다. 표는 클래스당 하나라 객체 수만큼 복사되지 않는다.

이 구조가 나머지를 설명한다. 생성자는 vptr을 세우는 주체라 virtual일 수 없고, Base 생성자가 도는 동안 vptr은 아직 Base를 가리키므로 생성자 안에서 부른 가상 함수는 Derived 버전이 불리지 않는다. 생성은 Base → Derived 멤버 → Derived 생성자 순이고 소멸은 그 역순이다. 가상 소멸자가 필요한 이유도 같다. 부모 포인터로 delete할 때 소멸자가 virtual이 아니면 정의되지 않은 동작이고, 보통 Base 소멸자만 불려 Derived가 들고 있던 자원이 샌다.

struct Base {
    virtual ~Base() = default;   // 다형적으로 쓸 기반 클래스의 규칙
    virtual void Update() {}
};
struct Derived : Base {
    void Update() override {}    // override를 적어야 오타를 컴파일러가 잡는다
};
Base* p = new Derived();
p->Update();                     // Derived::Update
delete p;                        // Derived → Base 순으로 소멸

vtable에는 타입 정보(RTTI)도 달려 있어 dynamic_cast와 typeid가 실행 중에 실제 타입을 확인한다. 그래서 부모에 가상 함수가 하나도 없으면 다운캐스트용 dynamic_cast를 쓸 수 없고, 검사 비용도 든다.

나머지는 C#과 짝지으면 정리된다. 순수 가상 함수(virtual void F() = 0;)가 하나라도 있으면 추상 클래스라 객체를 만들 수 없고, C#의 abstract 메서드와 같다. struct와 class는 기본 접근 지정자만 다르다(struct는 public). 다중 상속에서 A를 상속한 B와 C를 D가 함께 상속하면 A가 두 벌 생겨 모호해지는데(다이아몬드), class B : virtual public A로 가상 상속하면 한 벌만 남는다. C#은 클래스 다중 상속을 막아 이 문제를 피한다.

면접에서 이렇게 답한다

  • 가상 함수는 어떻게 동작하나 — 클래스마다 함수 주소 표인 vtable이 하나 생기고 객체에는 그 표를 가리키는 vptr이 들어간다. 호출할 때 vptr을 따라가 실제 함수로 가므로 부모 포인터로도 자식 구현이 불린다. 대신 간접 호출이라 인라인이 안 되고 객체가 포인터 하나만큼 커진다.
  • 가상 소멸자는 왜 필요한가 — 부모 포인터로 delete할 때 소멸자가 virtual이 아니면 정의되지 않은 동작이고 자식 소멸자가 불리지 않아 자원이 샌다. 다형적으로 쓸 기반 클래스는 소멸자를 public virtual로 두고, 그럴 일이 없으면 protected non-virtual로 막는다.
  • struct와 class의 차이는 — C++에서는 기본 접근 지정자만 다르고 기능은 같다. 스택인지 힙인지는 지역 변수로 선언했는지 new로 만들었는지가 정하며, C#의 값 형식·참조 형식 구분과는 다른 이야기다.
  • 생성과 소멸 순서는 — 생성은 부모부터, 소멸은 자식부터다. 부모 생성자가 도는 동안에는 자식이 아직 없어 그 안에서 부른 가상 함수는 부모 버전이 불린다. 멤버는 초기화 리스트에 적은 순서가 아니라 선언 순서로 초기화된다.

흔한 오해

  • vtable은 객체마다 하나씩 들어간다 — 표는 클래스당 하나이고 객체가 갖는 것은 그 표를 가리키는 포인터 하나다.
  • 자식에 같은 이름 함수를 만들면 재정의된다 — 부모에 virtual이 없으면 가리기일 뿐이라 부모 포인터로는 부모 함수가 불린다.
  • 생성자에서 가상 함수를 부르면 자식 버전이 불린다 — 그 시점에는 자식이 만들어지지 않았다. 초기화가 끝난 뒤 따로 부르게 설계한다.
  • C++ struct는 값 형식이라 스택에 잡힌다 — C#과 섞은 오해다. new로 만들면 struct도 힙에 잡힌다.
  • static_cast로 다운캐스트하면 안전하다 — 실제 타입이 달라도 조용히 통과해 잘못된 포인터가 된다. 확인이 필요하면 dynamic_cast의 결과가 nullptr인지 본다.

메모리와 포인터

GC가 없는 대신 소유권을 코드로 적는다. RAII와 스마트 포인터가 그 문법이다

핵심 개념

C#에서는 GC가 메모리를 걷어 가므로 이 객체를 누가 책임지는지 코드에 적을 일이 거의 없다. C++에는 그 담당자가 없어 소유권과 수명을 코드로 표현한다. 그 방식이 RAII다. 자원을 생성자에서 얻고 소멸자에서 놓으면 자원의 수명이 객체의 수명에 묶인다. 스택 객체는 스코프를 벗어날 때 반드시 소멸자가 불리므로 예외가 나거나 일찍 return해도 해제가 빠지지 않는다. C#의 IDisposable과 using이 같은 목적이지만 using은 적어야 하고, C++은 스코프가 알아서 한다. 메모리뿐 아니라 파일 핸들과 락에도 그대로 쓴다.

void Load() {
    auto tex = std::make_unique<Texture>("hero.png");  // 생성자에서 열고
    if (!tex->IsValid())
        return;                                          // 여기서 나가도
    Use(*tex);
}                                                        // 소멸자에서 닫는다

new와 malloc의 차이도 여기서 나온다. new는 타입에서 크기를 계산해 할당하고 생성자까지 부르며 실패하면 std::bad_alloc 예외를 던진다. malloc은 바이트 수만큼 메모리를 줄 뿐 생성자를 모르고 실패하면 NULL을 돌려준다. 그래서 new로 잡고 free로 놓거나 new[]를 delete로 놓으면 소멸자 호출과 해제 방식이 어긋나 정의되지 않은 동작이 된다.

스마트 포인터는 RAII를 포인터에 적용한 것이다. 셋 중 무엇을 쓸지는 소유자가 몇 명인가로 정한다.

종류소유쓰는 자리
unique_ptr혼자기본 선택. 복사가 막혀 있고 std::move로 소유권을 넘긴다
shared_ptr여럿(참조 카운트)수명을 진짜로 나눠 가질 때. 카운트가 0이 되면 해제한다
weak_ptr없음(관찰만)카운트를 올리지 않는 참조. lock()으로 살아 있는지 보고 쓴다

shared_ptr끼리 서로를 가리키면 카운트가 1 아래로 내려가지 않아 둘 다 영영 해제되지 않는다. 참조 카운트는 순환을 스스로 풀지 못한다. C#의 GC는 루트에서 닿을 수 있는지를 보므로 서로만 가리키는 섬도 수거하지만 shared_ptr은 그렇지 않다. 부모가 자식을 shared_ptr로, 자식이 부모를 weak_ptr로 갖는 식으로 한쪽 고리를 끊는다.

기초 문법도 C#과 대비하면 정리된다. 참조는 선언할 때 대상을 정하고 바꿀 수 없어 늘 유효한 객체를 가리킨다고 보고 쓰며, 포인터는 nullptr일 수 있고 다른 주소로 바꿀 수 있으며 산술 연산도 된다. 값이 없을 수 있으면 포인터, 반드시 있으면 참조로 받아 의도를 드러낸다. 포인터 멤버가 있는 클래스를 컴파일러가 만든 복사 생성자로 복사하면 얕은 복사라 두 객체가 같은 메모리를 가리켜 이중 해제가 난다. 새 메모리를 잡아 내용을 옮기는 깊은 복사를 직접 쓰거나 소유권이 분명한 스마트 포인터로 바꾼다. 배열은 범위를 검사하지 않아 넘어가면 예외가 아니라 정의되지 않은 동작이고, 남의 메모리를 조용히 덮어써 한참 뒤 엉뚱한 곳에서 터지는 쪽이 더 흔하다.

구조체 크기는 정렬 때문에 멤버 크기의 합보다 클 수 있다. struct A { char c; int i; char d; };는 int가 4바이트 경계에 놓여야 해 c 뒤에 3바이트가 들어가고, 전체가 4의 배수가 되도록 d 뒤에 3바이트가 더 붙어 12바이트다. int i; char c; char d; 순서면 8바이트다.

면접에서 이렇게 답한다

  • RAII란 — 자원의 수명을 객체의 수명에 묶는 기법이다. 생성자에서 얻고 소멸자에서 놓으면 스코프를 벗어날 때 반드시 해제되므로 예외나 조기 반환에도 새지 않는다. unique_ptr과 lock_guard가 그 예이고 C#의 using 문과 목적이 같다.
  • 스마트 포인터는 어떻게 고르나 — 소유자가 하나면 unique_ptr을 기본으로 쓰고, 수명을 여러 곳이 정말 나눠 가져야 할 때만 shared_ptr을 쓴다. 고리가 생길 수 있는 역방향 참조는 weak_ptr로 두고 쓸 때 lock()으로 확인한다.
  • malloc과 new의 차이는 — new는 크기 계산과 생성자 호출까지 하고 실패하면 예외를 던지며, malloc은 할당만 하고 실패하면 NULL을 준다. 섞어 쓰면 소멸자가 빠지거나 해제 방식이 어긋나 정의되지 않은 동작이 된다.
  • 얕은 복사와 깊은 복사는 — 얕은 복사는 포인터 값만 복사해 두 객체가 같은 메모리를 공유하므로 이중 해제와 의도치 않은 공유가 생긴다. 깊은 복사는 새 메모리를 잡아 내용을 옮긴다. 요즘은 소유권이 분명한 타입으로 설계해 문제 자체를 없앤다.

흔한 오해

  • shared_ptr을 쓰면 누수가 없다 — 서로 가리키는 순환이 생기면 카운트가 0이 되지 않아 그대로 샌다. GC와 달리 참조 카운트는 순환을 못 푼다.
  • 배열 범위를 넘으면 예외가 난다 — C#의 IndexOutOfRangeException을 떠올린 오해다. 검사가 필요하면 vector::at()이 예외를 던지고, 디버깅에는 AddressSanitizer를 쓴다.
  • 참조도 nullptr일 수 있다 — 참조는 초기화 없이 만들 수 없고 대상을 바꿀 수도 없다. 없을 수 있는 값은 포인터로 표현한다.
  • delete와 free는 이름만 다르다 — delete는 소멸자를 부르고 free는 부르지 않는다. 짝을 맞추지 않으면 정의되지 않은 동작이다.
  • 구조체 크기는 멤버 크기의 합이다 — 정렬 때문에 패딩이 들어가므로 선언 순서가 크기를 바꾼다.

현대 C++

값 복사가 기본이라 이동이 필요하고, 코드를 컴파일 타임에 찍어내는 것이 템플릿이다

핵심 개념

C++11 이후 기능은 대부분 C++에서는 값 복사가 기본이라는 사실에서 출발한다. C#은 참조 형식이 기본이라 대입이 참조 하나를 복사하는 것이고 실제 데이터는 GC가 관리한다. C++에서 std::vector<Texture>를 값으로 넘기면 원소 전부가 복사된다. 곧 사라질 임시 객체까지 그렇게 복사하는 것이 아까워 나온 것이 이동 의미론이다.

구분의 기준은 값 범주다. 이름이 있어 주소를 얻을 수 있는 식이 l-value, 리터럴이나 함수가 값으로 돌려준 임시값처럼 이름 없이 곧 사라지는 식이 r-value다. 이동 생성자와 이동 대입 연산자는 T&&(r-value 참조)를 받아 원본이 들고 있던 버퍼 포인터를 그대로 가져오고 원본은 비워 둔다. 복사가 아니라 소유권 이전이라 원소가 몇 개든 비용이 같다.

std::move는 이름과 달리 아무것도 옮기지 않는다. 대상을 r-value 참조로 캐스팅할 뿐이고 실제 이동은 그 결과로 선택된 이동 생성자가 한다. 함정은 이름이 붙은 T&& 변수 자체는 l-value라는 점이라, 다시 이동으로 넘기려면 std::move를 한 번 더 써야 한다. 이동된 원본은 유효하지만 값이 정해지지 않은 상태로 남고 소멸자는 그대로 불린다.

std::vector<int> MakeData();

std::vector<int> a = MakeData();      // 임시값이라 이동(또는 복사 생략)
std::vector<int> b = a;               // 복사: 원소를 전부 옮겨 담는다
std::vector<int> c = std::move(a);    // 이동: 버퍼 포인터만 가져온다
// a는 여전히 유효하지만 내용은 보장되지 않는다. a.clear()로 되돌려 쓴다

템플릿은 C#의 제네릭과 겉모습이 비슷하지만 만들어지는 시점이 다르다. 제네릭은 하나의 IL로 컴파일돼 런타임이 타입을 다루고, 템플릿은 쓰인 타입마다 컴파일러가 코드를 따로 찍어낸다(인스턴스화). 그래서 타입 안전하고 실행 중 형변환 비용이 없는 대신, 실행 파일이 커지고 컴파일이 느려지며 오류 메시지가 길고 읽기 어렵다. 인스턴스화 시점에 정의가 보여야 해서 보통 정의까지 헤더에 둔다.

inline도 이름이 오해를 부른다. 원래 의도는 호출을 없애고 본문을 부르는 자리에 펼치라는 권고였지만 실제 인라인 여부는 컴파일러가 정하고 inline 없이도 한다. 표준에서 이 키워드의 뜻은 여러 번역 단위에 정의가 있어도 된다는 쪽에 가까워, 헤더에 함수 정의를 두고 여러 파일에서 포함해도 중복 정의 오류가 나지 않게 하는 역할이 더 크다. 인라인 자체는 짧은 함수에서 호출 비용을 없애 이득이지만, 본문이 크고 호출 지점이 많으면 코드가 불어나 명령어 캐시 적중률이 떨어져 오히려 느려질 수 있다.

const 정확성은 C#에 대응이 거의 없다. 멤버 함수 뒤의 const는 멤버를 바꾸지 않겠다는 약속이라 const 객체나 const&로 받은 객체에서도 부를 수 있고, 바꾸지 않는 코드가 문서처럼 드러나며 실수는 컴파일러가 잡는다. 캐시 값처럼 예외가 필요하면 mutable로 선언한다. static은 붙는 자리마다 뜻이 다르다. 전역 함수·변수에 붙으면 그 파일에서만 보이는 내부 연결이고(요즘은 익명 네임스페이스를 더 쓴다), 클래스 멤버면 클래스에 하나만 있고 this가 없으며, 함수 안 지역 변수면 처음 호출될 때 한 번 초기화돼 프로그램이 끝날 때까지 값을 유지한다.

면접에서 이렇게 답한다

  • 이동 의미론은 무엇을 해결하나 — C++은 값 복사가 기본이라 곧 사라질 임시 객체까지 내용을 통째로 복사하게 된다. 이동 생성자는 r-value 참조를 받아 원본의 버퍼 포인터만 가져오고 원본을 비워 두므로 원소 수와 무관하게 끝난다.
  • std::move는 무엇을 하나 — 옮기는 함수가 아니라 대상을 r-value 참조로 바꾸는 캐스트다. 그 덕에 이동 생성자가 선택될 뿐이고, 이동된 원본은 유효하지만 값이 정해지지 않은 상태로 남는다.
  • 템플릿의 장단점은 — 타입마다 코드를 찍어내므로 타입 안전하고 실행 중 비용이 없지만 실행 파일이 커지고 컴파일이 느려진다. C# 제네릭과 달리 컴파일 타임에 결정되고 정의를 헤더에 둬야 한다는 점을 같이 말하면 차이가 분명해진다.
  • const를 왜 붙이나 — 바꾸지 않는다는 약속을 타입에 적어 두면 함수의 의도가 드러나고 실수는 컴파일러가 잡는다. const 객체에는 const 멤버 함수만 부를 수 있어, 처음부터 붙이지 않으면 나중에 한꺼번에 고치기 어렵다.

흔한 오해

  • std::move가 실제로 데이터를 옮긴다 — 캐스트일 뿐이다. 이동 생성자가 없는 타입에 쓰면 조용히 복사된다.
  • 이동된 객체는 못 쓰고 소멸자도 불리지 않는다 — 유효하지만 값이 정해지지 않은 상태이고 소멸자는 그대로 불린다. 다시 쓰려면 대입이나 clear()로 상태를 정해 준다.
  • 이름 붙은 T&& 변수는 r-value다 — 이름이 붙는 순간 l-value다. 계속 이동으로 넘기려면 std::move를 다시 써야 한다.
  • inline을 붙이면 반드시 인라인되고 빨라진다 — 강제가 아니라 권고이고, 본문이 크면 코드가 불어나 오히려 느려질 수 있다.
  • 템플릿은 런타임에 타입을 다루느라 느리다 — C# 제네릭과 섞은 오해다. 컴파일 타임에 결정되어 실행 중 비용이 없고, 대신 빌드 시간과 코드 크기를 낸다.

STL

메모리가 이어져 있는지와 정렬을 유지하는지, 두 축으로 컨테이너를 고른다

핵심 개념

STL 컨테이너는 이름이 아니라 메모리 배치로 고르는 것이 빠르다. vector는 원소가 한 덩어리로 이어진 동적 배열이라 인덱스 접근이 O(1)이고 캐시에 잘 맞는다. 용량(capacity)을 넘기면 보통 1.5~2배 크기의 새 버퍼를 잡아 원소를 옮기고 옛 버퍼를 버리는데, 이 순간 기존 포인터·참조·반복자가 모두 무효가 된다. 그래서 push_back은 평균 O(1)이되 개별 호출은 튈 수 있다. 넣을 개수를 알면 reserve로 용량만 미리 잡는다. size는 그대로다.

std::vector<int> v;
v.reserve(1000);      // 용량만 확보한다. size는 여전히 0
v.push_back(1);
int* first = &v[0];   // 재할당이 없는 동안에만 유효하다
v.resize(2000);       // 용량 1000을 넘는 순간 재할당
                      // first는 이제 버려진 옛 버퍼를 가리킨다
컨테이너메모리임의 접근중간 삽입·삭제C# 대응
vector이어진 한 덩어리O(1)O(n) — 뒤를 민다List<T>
list흩어진 노드(이중 연결)없음위치를 알면 O(1)LinkedList<T>
deque여러 블록으로 나뉨O(1)앞뒤 O(1), 중간 O(n)Queue<T>(구현은 다르다)

push_back과 emplace_back은 이미 만들어진 객체를 받아 복사·이동해 넣느냐, 생성자 인자를 받아 컨테이너 안 메모리에서 바로 만드느냐의 차이다. 임시 객체 한 번을 아끼는 것이라 이미 객체가 있으면 비용은 사실상 같다. 대신 emplace_back은 explicit 생성자도 통과시켜 의도치 않은 변환이 조용히 생길 수 있다.

연관 컨테이너는 정렬을 유지하느냐로 갈린다. map은 보통 레드-블랙 트리라 키가 늘 정렬돼 있고 탐색·삽입·삭제가 O(log n)이며, 순서대로 순회하거나 범위 질의를 할 수 있다. unordered_map은 해시 테이블이라 키를 버킷에 나눠 담아 평균 O(1)이지만 순회 순서가 정해져 있지 않고, 해시가 한 버킷에 몰리면 최악 O(n)까지 떨어진다. C#의 Dictionary<K,V>가 unordered_map, SortedDictionary<K,V>가 map 쪽이다. 조회가 잦고 순서가 필요 없으면 unordered_map, 정렬이나 범위 탐색이 필요하면 map을 고른다.

정렬 함수도 메모리 배치를 따라간다. std::sort는 인트로소트라 임의 접근 반복자를 요구해 vector와 배열에는 쓰지만 list에는 쓸 수 없고, 같은 값끼리의 원래 순서를 보장하지 않는다(불안정). list::sort는 값을 옮기는 대신 노드 연결만 바꾸는 병합 정렬이라 안정 정렬이고 반복자도 그대로 유효하다. 같은 값의 순서를 지켜야 하면 std::stable_sort를 쓴다.

면접에서 이렇게 답한다

  • vector는 어떻게 동작하나 — 연속된 메모리를 쓰는 동적 배열이고 용량이 차면 더 큰 버퍼를 새로 잡아 원소를 옮긴다. 그래서 추가는 평균 O(1)이지만 재할당이 일어나면 기존 반복자와 포인터가 무효가 된다. 개수를 알면 reserve로 재할당을 없앤다.
  • vector와 list 중 무엇을 쓰나 — 대부분 vector를 기본으로 둔다. list는 삽입·삭제 자체는 O(1)이지만 위치를 찾으려면 노드를 따라가야 하고 원소가 흩어져 있어 캐시 미스가 많아, 실제 측정에서는 vector가 이기는 경우가 흔하다.
  • map과 unordered_map의 차이는 — map은 균형 이진 탐색 트리라 O(log n)이고 키 순서대로 순회할 수 있다. unordered_map은 해시 테이블이라 평균 O(1)이지만 순서가 없고 충돌이 몰리면 최악 O(n)이다. 순서가 필요한지로 고른다.
  • push_back과 emplace_back은 — emplace_back은 생성자 인자를 받아 컨테이너 안에서 바로 객체를 만들어 임시 객체 하나를 아낀다. 이미 만들어진 객체를 넣을 때는 차이가 거의 없다.

흔한 오해

  • 중간 삽입이 많으면 list가 항상 유리하다 — 삽입 지점을 찾는 비용과 캐시 미스를 빼먹은 비교다. 원소가 작고 개수가 많으면 vector가 빠른 경우가 많다.
  • reserve를 하면 그만큼 원소가 생긴다 — reserve는 capacity만 늘리고 size는 그대로다. 원소까지 만들려면 resize다.
  • emplace_back이 항상 더 빠르다 — 아끼는 것은 임시 객체 한 번이라 이미 있는 객체를 넣으면 사실상 같다.
  • map은 해시로 찾고 unordered_map은 언제나 O(1)이다 — map은 트리라 O(log n)이고, unordered_map의 O(1)은 평균값이라 충돌이 몰리면 나빠진다.
  • std::sort는 안정 정렬이고 list에도 쓸 수 있다 — 안정성을 보장하지 않고 임의 접근 반복자를 요구한다. list는 멤버 함수 sort를, 안정성이 필요하면 stable_sort를 쓴다.

  • cppreference – std::unordered_map
  • cppreference – std::sort

컴파일과 링크

파일마다 따로 컴파일하고 마지막에 묶는 구조를 알면 오류만 보고 원인을 좁힌다

핵심 개념

C#은 프로젝트를 통째로 컴파일해 어셈블리 하나를 만들고 헤더가 없다. C++은 파일 하나씩 따로 컴파일한 뒤 마지막에 묶는다. 이 차이가 헤더, 선언과 정의의 분리, 링크 오류라는 낯선 개념을 전부 설명한다.

순서는 전처리 → 컴파일 → 어셈블 → 링크다. 전처리기가 #include를 그 파일의 내용으로 치환하고 매크로를 펼쳐 번역 단위 하나를 만든다. 헤더는 그 자체로 컴파일되는 단위가 아니라 소스에 펼쳐지는 텍스트다. 컴파일러는 번역 단위 하나만 보고 목적 파일(.o/.obj)을 만드는데, 다른 파일에 있는 함수는 선언만 보이면 통과시키고 주소 자리는 비워 둔다. 링커가 목적 파일과 라이브러리를 모아 그 빈자리를 실제 정의로 채워 실행 파일을 만든다.

그래서 오류 메시지만으로 원인을 좁힐 수 있다. 타입이 안 맞거나 선언을 못 찾는 것은 컴파일 오류, undefined reference나 unresolved external symbol은 선언은 봤는데 정의가 어디에도 없다는 링크 오류다. 대개 .cpp를 빌드 목록에 넣지 않았거나, 라이브러리를 링크하지 않았거나, 선언과 정의의 시그니처가 미묘하게 다르다.

링커는 이름으로 짝을 맞추는데 C++은 이름이 같고 매개변수만 다른 오버로딩을 허용하므로 이름만으로는 구분이 되지 않는다. 그래서 컴파일러가 매개변수 타입·네임스페이스·클래스·const 여부를 섞어 고유한 심볼 이름을 만든다. 이것이 네임 맹글링이다. C에는 오버로딩이 없어 이름이 거의 그대로 남고, 맹글링 규칙은 표준이 아니라 컴파일러마다 달라서 다른 컴파일러로 만든 C++ 라이브러리가 그냥은 링크되지 않는 이유가 된다.

extern "C"는 그 함수만 C 방식으로 이름을 붙이라는 선언이다. 이름을 붙이는 방식만 바꾸므로 함수 안에서는 C++ 기능을 그대로 쓴다. Unity 네이티브 플러그인에서 C# DllImport가 찾을 이름을 고정하려고 쓰는 것이 이것이다.

// plugin.cpp — 구현은 C++이지만 이름은 C 방식으로 내보낸다
extern "C" int AddDamage(int a, int b) { return a + b; }

// C# 쪽 (using System.Runtime.InteropServices;)
[DllImport("plugin", CallingConvention = CallingConvention.Cdecl)]
static extern int AddDamage(int a, int b);

마지막 조각이 호출 규약이다. 인자를 어떤 순서로 놓고 스택은 누가 치우는지에 대한 약속으로, __cdecl은 부른 쪽이 정리해 인자 개수가 달라도 되므로 가변 인자 함수에 쓰이고, __stdcall은 불린 쪽이 정리해 호출 지점마다 정리 코드가 필요 없어 코드가 조금 작아지며 Win32 API가 쓴다. 둘 다 인자를 오른쪽부터 스택에 쌓는다. 양쪽이 서로 다른 규약으로 알고 부르면 스택이 어긋나 함수가 끝난 뒤 엉뚱한 자리에서 죽는다. x64 Windows는 규약이 하나로 통일돼 키워드가 대체로 무시되지만, 32비트 빌드나 DllImport를 맞출 때는 여전히 본다.

면접에서 이렇게 답한다

  • 소스가 실행 파일이 되기까지 — 전처리기가 include와 매크로를 펼쳐 번역 단위를 만들고, 컴파일러가 파일마다 목적 파일을 만들고, 링커가 목적 파일과 라이브러리를 묶어 심볼을 실제 주소로 잇는다. 헤더는 따로 컴파일되지 않고 소스에 펼쳐진다.
  • undefined reference가 나면 — 링크 단계 오류다. 선언은 있는데 정의가 없다는 뜻이라 해당 .cpp가 빌드에 들어갔는지, 라이브러리를 링크했는지, 선언과 정의의 시그니처가 같은지를 순서대로 본다.
  • 네임 맹글링이란 — 오버로딩을 허용하려고 컴파일러가 매개변수 타입 같은 정보를 섞어 링커용 고유 이름을 만드는 것이다. C에는 오버로딩이 없어 일어나지 않고, 규칙이 컴파일러마다 달라 C와 섞을 때는 extern "C"로 끈다.
  • 호출 규약은 왜 맞춰야 하나 — 인자를 놓는 순서와 스택을 치우는 쪽이 다르면 호출이 끝난 뒤 스택이 어긋나 원인을 찾기 어려운 크래시가 난다. Unity에서 네이티브 플러그인을 부를 때 DllImport의 CallingConvention을 플러그인 쪽과 맞추는 이유다.

흔한 오해

  • undefined reference는 컴파일 오류다 — 컴파일은 선언만 보고 통과한다. 정의를 찾는 것은 링커라 링크 단계에서 난다.
  • C에서도 네임 맹글링이 일어난다 — 오버로딩이 없어 이름이 거의 그대로 남는다. 그래서 C 라이브러리는 컴파일러가 달라도 링크가 된다.
  • 맹글링 규칙은 표준이다 — 표준이 아니다. 컴파일러와 버전이 다르면 C++ 라이브러리는 그냥 링크되지 않는다.
  • extern "C"를 붙이면 그 함수에서 C++ 기능을 못 쓴다 — 바뀌는 것은 심볼 이름을 붙이는 방식뿐이고 구현은 C++ 그대로다.
  • 헤더에 함수 정의를 넣어도 상관없다 — 여러 소스가 포함하면 정의가 여러 번 생겨 링크에서 중복 정의가 난다. inline을 붙이거나 정의를 .cpp로 옮긴다.
