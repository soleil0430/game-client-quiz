C# 언어

코드 문제

출력 예측은 기본값과 초기화 순서, 클로저 캡처에서 답이 갈린다

화면에 코드 열 줄이 뜨고 출력을 맞히라고 한다. 문법을 아느냐를 묻는 문제가 아니다. 언어가 언제 무엇을 하는지를 묻는 문제다.

실무에서 버그를 만드는 지점이 그대로 문제가 된다.

초기화하지 않은 DateTime은 null인가

아니다. 참조 형식은 초기화하지 않으면 null이지만, 값 형식에는 null이라는 상태 자체가 없다. 모든 필드가 0으로 채워진 값이 들어 있다.

초기화하지 않은 필드를 null과 비교해 본 코드다:

class A { public string S; public DateTime D; }

var a = new A();
Debug.Log(a.S == null);     // True  - 참조 형식의 기본값은 null
Debug.Log(a.D == null);     // False - 값 형식은 null이 될 수 없다
Debug.Log(a.D == default);  // True  - "설정 안 됨"은 이렇게 본다

함정은 두 번째 줄이 컴파일된다는 데 있다. a.D == null은 DateTime? 비교로 승격된다. 문법은 통과하지만 결과가 언제나 False라 컴파일러가 경고를 붙인다.

값이 들어왔는지를 정말 구분하려면 필드를 DateTime?로 선언한다. 참고로 DateTime의 기본값은 DateTime.MinValue다.

정적 초기화는 타입을 처음 쓸 때 한 번만 돈다

순서는 정해져 있다. 정적 필드 이니셜라이저, 정적 생성자, 인스턴스 필드 이니셜라이저, 인스턴스 생성자. 정적 쪽은 타입을 처음 쓸 때 한 번, 인스턴스 쪽은 객체를 만들 때마다 돈다.

네 자리에 로그를 심어 순서를 눈으로 본 코드다:

class Counter
{
    static int total = Log("1 정적 필드 이니셜라이저");
    int id = Log("3 인스턴스 필드 이니셜라이저");

    static Counter() { Debug.Log("2 정적 생성자"); }
    public Counter() { Debug.Log("4 인스턴스 생성자"); }

    static int Log(string what) { Debug.Log(what); return 0; }
}

new Counter();   // 1, 2, 3, 4가 차례로 찍힌다
new Counter();   // 3, 4만 찍힌다. 정적 초기화는 한 번뿐이다

정적 생성자가 언제 불릴지는 코드로 정할 수 없다. 무거운 초기화를 넣지 않는 이유다.

람다는 변수를 통째로 붙잡는다

람다는 변수의 값이 아니라 변수 자체를 잡는다. for의 반복 변수는 루프 전체에서 하나뿐이다. 그래서 람다 셋이 같은 변수 하나를 보고, 나중에 호출하면 루프가 끝난 뒤의 값을 읽는다.

foreach의 반복 변수는 매 반복 새로 만들어지도록 언어가 바뀌었다. 기대한 대로 나오는 쪽은 이쪽이다.

세 가지 캡처를 한자리에 모아 출력을 비교한 코드다:

var actions = new List<Action>();

for (int i = 0; i < 3; i++)
    actions.Add(() => Debug.Log(i));   // 3 3 3 - i는 루프 전체에 변수 하나다

foreach (var n in new[] { 0, 1, 2 })
    actions.Add(() => Debug.Log(n));   // 0 1 2 - n은 반복마다 새로 만들어진다

for (int i = 0; i < 3; i++)
{
    int captured = i;                  // 반복 안에서 새 변수를 만들어 고친다
    actions.Add(() => Debug.Log(captured));   // 0 1 2
}

캡처는 성능 문제이기도 하다. 변수를 잡는 람다는 그 변수를 담을 클래스를 힙에 만든다. 잡을 것이 없으면 static 람다로 선언해, 실수로 캡처하는 것을 컴파일러가 막게 한다.

짧은 메서드 문제는 경계 조건을 본다

직접 써 보라는 문제도 같이 나온다. 정답 자체보다 경계 조건을 챙기는지를 본다. 음수와 빈 입력, 못 찾은 경우가 단골이다.

음수와 미발견 처리를 각각 담은 두 메서드다:

static int SumEven(int[] numbers)
{
    int sum = 0;
    foreach (int n in numbers)
        if (n % 2 == 0) sum += n;   // n % 2 == 1로 찾으면 음수 홀수를 놓친다
    return sum;
}

static string KeepFirstDollar(string s)
{
    int first = s.IndexOf('$');
    if (first < 0) return s;        // 없으면 원본 그대로
    return s.Substring(0, first + 1)
         + s.Substring(first + 1).Replace("$", string.Empty);
}

면접에서 이렇게 답한다

  • 초기화하지 않은 string과 DateTime을 null과 비교하면 — string은 참조 형식이라 True, DateTime은 값 형식이라 False다. 그 비교는 DateTime?로 승격돼 컴파일은 되지만 결과가 항상 false라 경고가 붙는다고 덧붙인다.
  • 정적 생성자와 인스턴스 생성자 중 무엇이 먼저인가 — 정적 쪽이 먼저다. 타입을 처음 쓰는 시점에 정적 필드 이니셜라이저와 정적 생성자가 한 번 돈다. 이후 객체를 만들 때마다 인스턴스 필드 이니셜라이저와 인스턴스 생성자가 돈다.
  • 루프에서 만든 람다가 전부 같은 값을 출력하는 이유 — 값을 복사하는 것이 아니라 변수를 붙잡기 때문이다. for의 반복 변수는 루프에 하나뿐이라 모두 같은 것을 본다. 버튼을 루프로 만들며 인덱스를 캡처한 콜백을 붙일 때 실무에서 그대로 나온다고 예를 든다.

이런 오해를 한다

  • “값 형식도 초기화 전에는 null이다” — 값 형식에 null 상태는 없다. 0으로 채워진 기본값이 들어 있다.
  • “a.D == null은 컴파일 오류다” — DateTime?로 승격돼 컴파일된다. 경고만 나고 결과는 항상 False다.
  • “정적 생성자는 프로그램이 시작할 때 실행된다” — 타입을 처음 쓰는 시점에 실행된다. 시점을 코드로 제어할 수 없으므로 무거운 작업을 넣지 않는다.
  • “홀짝 판정은 n % 2 == 1로 하면 된다” — 음수에서 -1이 나와 홀수를 놓친다. == 0이나 != 0으로 쓴다.

3줄 정리

  • 참조 형식 기본값은 null, 값 형식은 0으로 채운 값이다
  • 정적 초기화는 타입을 처음 쓸 때 딱 한 번 돈다
  • 람다는 값이 아니라 변수를 잡는다. for에서 갈린다
