자료구조·알고리즘

코딩 테스트와 실기 유형

실기는 정답이 아니라 푸는 과정을 본다. 범위·예외·복잡도를 입으로 말한다

라이브 코딩에서 말없이 10분을 코딩했다. 답은 맞았는데 평가할 근거가 남지 않는다.

보는 것은 결과가 아니라 문제를 좁혀 가는 과정이다.

실기는 세 가지 형태로 나온다

첫째는 라이브 코딩이다. 화면을 공유하며 기본 개념을 변형한 문제를 푼다. 둘째는 풀이 리뷰다. 제출한 코드를 두고 왜 이렇게 풀었는지, 더 줄일 곳은 없는지 묻는다.

셋째는 코드 리뷰 과제다. 일부러 버그를 심은 코드에서 문제를 찾는다. 셋 다 최종 답보다 과정을 본다.

받자마자 하는 순서를 고정해 둔다

순서를 정해 두면 긴장해도 흔들리지 않는다. 네 단계면 충분하다.

  1. 입력 크기와 값의 범위를 되묻는다. N이 10만인지 10억인지에 따라 답이 달라진다.
  2. 빈 배열, 원소 하나, 중복, 음수, 오버플로 같은 예외 케이스를 입으로 짚는다.
  3. 무식한 풀이를 복잡도와 함께 말한 뒤 개선안을 제안한다.
  4. 합의가 되면 짜고, 다 짜면 작은 입력을 손으로 돌려 본다.

단골 문제는 한 번 훑고 끝내는 풀이를 기대한다

대부분 한 번만 훑고 추가 공간을 쓰지 않는 풀이를 본다. 1부터 N 중 빠진 수는 합 공식에서 배열의 합을 빼면 나온다. 다만 N이 크면 합이 넘치므로 XOR이 더 안전하다.

중복 찾기는 HashSet<T> 한 번 훑기, 문자열 뒤집기는 양 끝에서 좁혀 오는 맞바꾸기다. 행렬 90도 회전은 전치한 뒤 각 행을 뒤집는다.

코드로 옮기면 맞바꾸기 두 번이 전부다: 

public static void RotateClockwise(int[,] m)
{
    int n = m.GetLength(0);
    for (int i = 0; i < n; i++)            // 전치: [i, j]와 [j, i]를 맞바꾼다
        for (int j = i + 1; j < n; j++)    // j를 i+1부터 돌려야 두 번 안 바꾼다
            (m[i, j], m[j, i]) = (m[j, i], m[i, j]);

    for (int i = 0; i < n; i++)            // 각 행을 좌우로 뒤집는다
        for (int j = 0; j < n / 2; j++)
            (m[i, j], m[i, n - 1 - j]) = (m[i, n - 1 - j], m[i, j]);
}

라이브러리 없이 문자열을 정수로 바꾸는 문제도 단골이다. 부호·공백·잘못된 문자·오버플로를 어디까지 처리하는지가 평가 대상이다. 실무라면 int.TryParse로 실패를 값으로 받는다고 덧붙이면 좋다.

심어 두는 버그는 목록이 짧다

배열 한 칸 초과, 대입과 비교 혼동, null 접근, 초기화하지 않은 변수, 해제하지 않는 자원. 거의 이 다섯 안에서 나온다. 경계부터 보는 습관이 가장 많이 걸린다.

C#은 if (x = 5)가 컴파일 오류다. 그럼 이 실수는 없어졌나. bool 변수라면 if (isReady = true)가 그대로 통과한다.

클라이언트 면접이라면 이벤트를 구독만 하고 해제하지 않아 객체가 살아남는 누수를 짚는다. 가산점이 붙는 지점이다.

면접에서 이렇게 답한다

  • 문제를 받으면 무엇부터 하나 — 입력 크기와 값의 범위를 먼저 확인한다고 답한다. N에 따라 O(N²)을 써도 되는지가 갈리기 때문이다. 그다음 예외 케이스를 짚고, 무식한 풀이를 복잡도와 함께 말한 뒤 개선안을 제안하고 합의되면 짠다.
  • 빠진 수 하나 찾기 — 1부터 N까지의 합에서 배열의 합을 빼면 O(N) 시간, O(1) 공간에 끝난다. 합이 오버플로할 것 같으면 1부터 N까지와 배열 원소를 모두 XOR해 같은 값을 얻는다고 대안까지 말한다.
  • 이 코드의 문제는 — 경계부터 본다. 조건이 i <= n이면 마지막에 arr[n]을 읽는다. C#은 IndexOutOfRangeException으로 바로 티가 나지만, C/C++라면 조용히 엉뚱한 메모리를 읽어 더 찾기 어렵다.

이런 오해를 한다

  • “답이 맞으면 통과다” — 복잡도와 예외 케이스를 스스로 말하지 않으면 감점이다. 과정이 평가 대상이다.
  • “유효한 인덱스는 0부터 n까지” — n - 1까지다. 한 칸 초과가 가장 흔한 버그다.
  • “합 공식은 언제나 안전하다” — N이 크면 합이 int 범위를 넘는다. long으로 올리거나 XOR을 쓴다.
  • “전치만 하면 회전이 된다” — 전치는 대각선 대칭일 뿐이라 행을 뒤집어야 회전이 된다.
  • “막히면 조용히 생각하는 게 낫다” — 화면에 아무것도 없으면 판단할 근거가 없다. 막힌 지점을 말하면 힌트가 나온다.

3줄 정리

  • 실기는 정답이 아니라 좁혀 가는 과정을 본다
  • 범위 확인 → 예외 케이스 → 복잡도 → 합의 → 구현
  • 심어 둔 버그는 경계·null·해제 누락이 거의 전부다
