DOTS와 최신 기능

ECS는 데이터를 한 줄로 늘어놓아 캐시를 살리는 구조이고, Job과 Burst가 함께 가야 값을 한다

핵심 개념

GameObject 방식이 느려지는 지점은 계산량이 아니라 메모리를 읽는 순서다. MonoBehaviour는 각각 힙에 따로 할당돼 주소가 흩어져 있고, Transform 값을 만질 때마다 C# 쪽에서 엔진 네이티브 쪽으로 넘어간다. 유닛 1만 개를 순회하면 CPU는 매번 캐시에 없는 주소를 기다리게 되고, 이 기다림이 실제 연산보다 몇 배 길다.

ECS는 이 배치를 뒤집는다. 엔티티는 번호일 뿐이고 데이터는 컴포넌트 타입 조합(아키타입)이 같은 것끼리 모아 청크라는 연속 메모리 블록에 저장한다. System은 "LocalTransform과 Velocity를 둘 다 가진 것"을 쿼리해 그 청크들을 앞에서부터 쭉 훑는다. 주소가 순서대로 이어지니 캐시 라인 하나에 여러 개가 같이 딸려오고 프리페처도 다음에 읽을 곳을 맞힌다. 여기에 Job System으로 워커 스레드에 나눠 돌리고, Burst 컴파일러가 그 코드를 LLVM으로 SIMD가 들어간 네이티브로 바꾼다. 셋이 같이 있을 때 값을 한다.

[BurstCompile]
public partial struct MoveSystem : ISystem
{
    [BurstCompile]
    public void OnUpdate(ref SystemState state)
    {
        float dt = SystemAPI.Time.DeltaTime;

        // 두 컴포넌트를 다 가진 엔티티만 골라 청크 단위로 순서대로 훑는다
        foreach (var (tr, v) in SystemAPI.Query<RefRW<LocalTransform>, RefRO<Velocity>>())
            tr.ValueRW.Position += v.ValueRO.Value * dt;
    }
}

대가도 분명하다. 컴포넌트가 struct라 참조 타입을 못 담고, 문자열이나 매니지드 객체를 쓰려면 별도 처리가 필요하다. 엔티티에 컴포넌트를 붙이거나 떼면 아키타입이 바뀌어 데이터를 다른 청크로 옮기는 구조 변경이 일어나므로, 매 프레임 붙였다 떼는 설계는 오히려 느리다. 에디터 워크플로와 디버깅, 기존 플러그인 연동도 전부 다르다. 그래서 현실적인 선택은 전면 전환이 아니라 대량 유닛, 탄막, 군중처럼 개수가 압도적인 부분만 ECS로 돌리는 하이브리드다. Entities 1.0 정식 버전은 Unity 2022 LTS 시기에 나왔고 Unity 6에서 안정화가 더 진행됐지만, 게임의 기본 골격은 여전히 GameObject다.

Unity 6에서 하나만 고른다면 GPU Resident Drawer가 설명하기 좋다. 렌더링이 느린 이유가 GPU 계산이 아니라 CPU가 오브젝트마다 드로우 콜을 준비하는 비용인 경우가 많은데, 이 기능은 BatchRendererGroup API로 메시 데이터를 GPU 쪽에 상주시켜 CPU의 준비 작업을 크게 줄인다. 같이 들어온 GPU Occlusion Culling은 가려진 인스턴스를 GPU에서 걸러낸다. 그 외에 Render Graph 정리, 플랫폼별 빌드 설정을 에셋으로 관리하는 Build Profiles, 멀티플레이 설정을 모은 Multiplayer Center가 있다.

면접에서 이렇게 답한다

  • ECS란 무엇인가 — 엔티티는 식별자, 컴포넌트는 순수 데이터, 시스템은 그 데이터를 처리하는 로직으로 나눈 구조다. 상속으로 기능을 물려주는 대신 어떤 컴포넌트를 가졌느냐로 동작이 정해진다.
  • GameObject 방식보다 왜 빠른가 — 같은 컴포넌트 조합을 가진 엔티티의 데이터를 연속된 메모리에 모아 두고 순서대로 훑기 때문에 캐시 미스가 크게 준다. 여기에 Job System으로 코어를 나눠 쓰고 Burst로 SIMD까지 얹으면 몇 배 차이가 난다.
  • 언제 도입하나 — 유닛 수천에서 수만처럼 같은 처리를 대량으로 반복하는 구간에 먼저 쓴다. 워크플로와 디버깅 방식이 달라 전면 전환은 비용이 크므로 하이브리드로 시작해 효과를 측정한 뒤 넓힌다.
  • Unity 6의 특징 하나를 소개하라 — GPU Resident Drawer를 말한다. 오브젝트마다 CPU가 드로우 콜을 준비하던 비용을 GPU 상주 데이터와 BatchRendererGroup으로 옮겨, 오브젝트가 많은 씬에서 CPU 렌더 스레드 부하를 줄여 주는 기능이라고 설명한다.

흔한 오해

  • ECS를 쓰면 무조건 빨라진다 — 대상 개수가 적으면 구조 변경과 쿼리 오버헤드만 남는다. 수천 개 이상을 같은 방식으로 처리할 때 이득이 나온다.
  • ECS가 곧 멀티스레딩이다 — 별개다. 병렬화는 Job System이 하고, ECS는 그 Job이 읽기 좋은 형태로 데이터를 배치할 뿐이다.
  • Burst를 켜면 모든 C#이 빨라진다 — Burst가 컴파일할 수 있는 것은 값 타입과 NativeContainer만 쓰는 제한된 코드다. 매니지드 객체를 건드리면 빠진다.
  • DOTS가 MonoBehaviour를 대체했다 — Unity 6에서도 기본은 GameObject다. DOTS는 필요한 부분에 골라 쓰는 선택지다.
  • GPU Resident Drawer를 켜면 드로우 콜이 사라진다 — 없어지는 게 아니라 CPU가 준비하던 일이 GPU 쪽으로 옮겨진다. GPU가 이미 한계면 도움이 되지 않는다.
