DOTS와 최신 기능

ECS는 데이터를 연속 메모리에 늘어놓는 구조이고, Job과 Burst가 같이 붙어야 값을 한다

유닛 1만 개를 MonoBehaviour로 돌리면 프레임이 무너진다. 그런데 병목은 계산량이 아니라 기다림이다. ECS는 계산을 줄이는 대신 메모리 배치를 바꾼다.

느린 원인은 계산량이 아니라 메모리를 읽는 순서다

MonoBehaviour는 각각 힙에 따로 할당돼 주소가 흩어져 있다. 1만 개를 순회하면 CPU는 매번 캐시에 없는 주소를 기다린다. 이 기다림이 실제 연산보다 몇 배 길다.

Transform 값을 만질 때마다 C# 쪽에서 엔진 네이티브 쪽으로 넘어가는 비용도 함께 붙는다.

같은 조합끼리 청크에 모아 앞에서부터 훑는다

ECS는 이 배치를 뒤집는다. 엔티티는 번호일 뿐이고, 데이터는 컴포넌트 조합(아키타입)이 같은 것끼리 청크라는 연속 메모리 블록에 담는다.

System은 LocalTransform과 Velocity를 둘 다 가진 것을 쿼리해 그 청크를 앞에서부터 훑는다. 주소가 이어지니 캐시 라인 하나에 여러 개가 딸려온다. 프리페처도 다음에 읽을 곳을 맞힌다.

다음은 속도만큼 위치를 옮기는 시스템이다:

[BurstCompile]
public partial struct MoveSystem : ISystem
{
    [BurstCompile]
    public void OnUpdate(ref SystemState state)
    {
        float dt = SystemAPI.Time.DeltaTime;

        // 두 컴포넌트를 다 가진 엔티티만 골라 청크 단위로 순서대로 훑는다
        foreach (var (tr, v) in SystemAPI.Query<RefRW<LocalTransform>, RefRO<Velocity>>())
            tr.ValueRW.Position += v.ValueRO.Value * dt;
    }
}

ECS와 Job, Burst는 셋이 같이 있어야 값을 한다

ECS는 데이터를 읽기 좋게 놓을 뿐이다. 코어를 나눠 쓰는 일은 Job System이 하고, 그 코드를 SIMD가 들어간 네이티브로 바꾸는 일은 Burst 컴파일러가 한다.

대가도 분명하다. 컴포넌트가 struct라 참조 타입을 못 담고, 문자열이나 매니지드 객체는 별도 처리가 필요하다.

컴포넌트를 붙이거나 떼면 아키타입이 바뀌어 데이터를 다른 청크로 옮긴다. 이 구조 변경이 비싸서, 매 프레임 붙였다 떼는 설계는 오히려 느리다.

그래서 현실적인 선택은 하이브리드다. 대량 유닛, 탄막, 군중처럼 개수가 압도적인 부분만 ECS로 돌린다. Unity 6에서도 게임의 기본 골격은 GameObject다.

Unity 6에서 하나 고르면 GPU Resident Drawer

렌더링이 느린 이유가 GPU 계산이 아니라 CPU의 드로우 콜 준비인 경우가 많다. GPU Resident Drawer는 메시 데이터를 GPU 쪽에 상주시켜 그 준비 작업을 줄인다.

같이 들어온 GPU Occlusion Culling은 가려진 인스턴스를 GPU에서 걸러낸다. 그 밖에 Render Graph 정리와, 플랫폼별 빌드 설정을 에셋으로 관리하는 Build Profiles가 있다.

면접에서 이렇게 답한다

  • ECS란 무엇인가 — 엔티티는 식별자, 컴포넌트는 순수 데이터, 시스템은 그 데이터를 처리하는 로직으로 나눈 구조입니다. 상속으로 기능을 물려주는 대신 어떤 컴포넌트를 가졌느냐로 동작이 정해집니다.
  • GameObject 방식보다 왜 빠른가 — 같은 컴포넌트 조합끼리 데이터를 연속 메모리에 모아 두고 순서대로 훑어 캐시 미스가 크게 줍니다. 여기에 Job System으로 코어를 나눠 쓰고 Burst로 SIMD까지 얹습니다.
  • 언제 도입하나 — 유닛 수천에서 수만처럼 같은 처리를 대량으로 반복하는 구간에 먼저 씁니다. 워크플로와 디버깅이 달라 전면 전환은 비싸므로 하이브리드로 시작해 효과를 재고 넓힙니다.
  • Unity 6의 특징 하나를 소개하라 — GPU Resident Drawer를 말합니다. 오브젝트마다 CPU가 드로우 콜을 준비하던 비용을 GPU 상주 데이터로 옮겨, 오브젝트가 많은 씬에서 CPU 부하를 줄여 줍니다.

이런 오해를 한다

  • ECS를 쓰면 무조건 빨라진다 — 대상 개수가 적으면 구조 변경과 쿼리 오버헤드만 남는다. 수천 개 이상을 같은 방식으로 처리할 때 이득이 나온다.
  • ECS가 곧 멀티스레딩이다 — 별개다. 병렬화는 Job System이 하고, ECS는 그 Job이 읽기 좋은 형태로 데이터를 놓을 뿐이다.
  • Burst를 켜면 모든 C#이 빨라진다 — Burst가 컴파일하는 것은 값 타입과 NativeContainer만 쓰는 제한된 코드다. 매니지드 객체를 건드리면 빠진다.
  • DOTS가 MonoBehaviour를 대체했다 — Unity 6에서도 기본은 GameObject다. DOTS는 필요한 부분에 골라 쓰는 선택지다.
  • GPU Resident Drawer를 켜면 드로우 콜이 사라진다 — 없어지는 게 아니라 CPU가 준비하던 일이 GPU 쪽으로 옮겨진다. GPU가 이미 한계면 도움이 되지 않는다.

3줄 정리

  • ECS는 계산이 아니라 메모리 배치를 바꿔 캐시를 살린다
  • 병렬화는 Job, 네이티브 변환은 Burst가 맡는다
  • 전면 전환 대신 개수가 압도적인 부분만 골라 쓴다
