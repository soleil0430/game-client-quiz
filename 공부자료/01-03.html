델리게이트·이벤트·람다

메서드를 값처럼 넘기는 문법과 거기서 생기는 할당·구독 해제 누수

몬스터가 죽는다. HUD의 킬 수가 오르고, 퀘스트 카운터가 돌고, 사운드가 울린다.

죽는 코드가 이 셋을 직접 부르는 구조라면 반응이 하나 늘 때마다 죽는 코드를 다시 연다. 델리게이트는 그 연결을 실행 중에 갈아 끼우게 해 준다.

메서드를 변수에 담아 실행 중에 갈아 끼운다

델리게이트는 메서드를 담는 변수다. 타입이 맞는 메서드를 담아 뒀다가 나중에 호출한다. 무슨 일이 생겼을 때 누가 처리할지를 컴파일 시점이 아니라 실행 중에 정할 수 있다.

직접 delegate 타입을 선언할 일은 거의 없다. 반환값이 없는(void) 델리게이트가 Action, 있는 쪽이 Func다. Func는 마지막 타입 인자가 반환 타입이다. 둘 다 매개변수 개수별 오버로드가 준비돼 있다.

event는 구독만 열고 발생은 잠근다

event는 새로운 타입이 아니다. 델리게이트에 접근 제한을 거는 키워드이자 필드에 붙는 한정자이고, 외부에서는 +=와 -=만 허용해 대입이나 직접 호출을 막는다.

선언한 클래스만 이벤트를 호출하거나 통째로 바꿀 수 있다. 남이 내 이벤트를 대신 쏘거나 = 한 번으로 다른 구독자를 전부 날리는 사고를 문법이 막아 준다.

이벤트 선언과 안전한 호출을 한자리에 둔 코드다:

static class GameEvents
{
    public static event Action<int> ScoreChanged;   // 밖에서는 +=, -= 만 된다

    // ?. 는 델리게이트를 한 번만 읽어 임시 변수로 호출한다
    // 그래서 검사와 호출 사이에 마지막 구독자가 빠지는 틈이 없다
    public static void Raise(int score) => ScoreChanged?.Invoke(score);
}

대신 구독한 쪽이 수거되지 않는 원인이 된다. 이벤트 쪽이 구독자 메서드와 그 객체를 참조하므로, 해제하지 않으면 구독자 객체가 메모리에서 내려가지 않을 수 있다. 구독한 곳과 대칭이 되는 자리에서 반드시 -= 한다.

if (OnDie != null) OnDie();로는 부족하다. null 검사와 실제 호출 사이에 다른 스레드가 마지막 구독자를 해제하면 그 사이에 델리게이트가 null이 돼 NullReferenceException이 나므로, 델리게이트를 한 번만 읽어 임시 변수에 담고 호출하는 ?.Invoke()를 쓴다.

단일 스레드인 게임 로직에서도 콜백 안에서 구독을 해제하는 경우가 있어, 습관적으로 쓰는 편이 안전하다.

구독은 절반이고, 해제까지가 한 쌍이다.

등록 순서대로 불리고 반환값은 마지막 것만 남는다

델리게이트 하나에 +=로 메서드를 여러 개 담을 수 있다. 이것을 멀티캐스트라 한다. 등록한 순서대로 하나씩 불린다.

여기 함정이 둘 있다. 반환값은 마지막에 실행된 대상의 값만 남고, 중간에서 예외가 나면 그 뒤에 등록된 대상은 호출되지 않는다.

앞의 결과는 그냥 버려지므로, 각각의 결과가 필요하면 GetInvocationList()로 직접 순회해야 한다. 하나씩 try로 감싸 부르면 한 구독자의 예외가 나머지를 막지 못한다. 같은 메서드를 두 번 등록하면 두 번 불린다는 것도 같이 기억해 둔다.

람다가 잡는 것은 값이 아니라 변수다

람다는 그 자리에서 만드는 이름 없는 메서드다. 조심할 곳은 하나뿐이다. 캡처는 변수 자체를 붙잡는다. 값을 복사해 두는 것이 아니다.

for의 루프 변수는 루프 전체에서 하나뿐이라, 그것을 캡처한 람다들은 모두 같은 변수를 본다. 0부터 2까지 도는 루프가 끝나면 그 i는 3이 돼 있고, 람다를 실행하는 시점의 값인 3이 세 번 출력된다.

foreach의 반복 변수는 C# 5부터 반복마다 새로 만들어지므로 foreach였다면 012가 나온다. for에서 012를 원하면 루프 안에서 int copy = i;로 복사한 변수를 캡처한다.

버튼을 루프로 만들며 인덱스를 캡처하는 상황이다:

var actions = new List<Action>();
for (int i = 0; i < 3; i++)
{
    int copy = i;                          // 반복 안에서 새 변수를 만든다
    actions.Add(() => Debug.Log(copy));    // 0 1 2
    // actions.Add(() => Debug.Log(i));    // 3 3 3 - i는 루프에 하나뿐이다
}

캡처는 할당이기도 하다. 캡처가 없는 람다는 컴파일러가 만든 델리게이트 인스턴스를 정적 필드에 캐싱해 재사용하므로 사실상 한 번만 할당된다.

반면 바깥 지역 변수나 this를 캡처하면 컴파일러가 만든 클로저 클래스 인스턴스가 힙에 생겨 호출할 때마다 할당이 쌓인다. 매 프레임 도는 코드에서는 캡처를 피하거나 델리게이트를 필드에 캐싱한다. C# 9의 static 람다는 캡처 자체를 금지해 실수를 막아 준다.

면접에서 이렇게 답한다

  • delegate와 event의 차이 — event는 델리게이트 필드에 접근 제한을 거는 한정자라고 시작한다. 밖에서는 구독과 해제만 되고 발생은 선언한 클래스만 할 수 있다. 알림은 공개하되 통제권은 발행자가 쥐는 구조가 된다고 정리한다.
  • 이벤트로 메모리 누수가 나는 이유 — 이벤트가 구독자 메서드와 그 객체를 참조하기 때문이다. 해제하지 않으면 구독자는 루트에 매달려 수거되지 않는다. 구독한 곳과 대칭이 되는 지점에서 반드시 -= 한다고 답한다.
  • 클로저의 단점 — 캡처한 변수를 담을 객체가 힙에 생겨 할당이 된다. 캡처한 대상의 수명도 람다만큼 늘어난다. 매 프레임 도는 코드에서는 캡처 없는 람다나 미리 만들어 둔 델리게이트를 쓴다.
  • 델리게이트를 안전하게 호출하려면 — OnDie?.Invoke() 한 줄이면 된다. null 검사와 호출 사이에 마지막 구독자가 해제되면 예외가 나는데, ?.는 델리게이트를 한 번만 읽어 호출하므로 그 틈이 없다.

이런 오해를 한다

  • “event는 델리게이트와 별개의 타입” — 타입이 아니라 필드에 붙는 한정자다. 속은 그대로 델리게이트다.
  • “멀티캐스트는 모든 반환값을 받을 수 있다” — 마지막 호출의 결과만 남는다. 전부 필요하면 GetInvocationList()로 하나씩 부른다.
  • “if (e != null) e();면 충분하다” — 검사와 호출 사이에 구독이 해제되면 그대로 NullReferenceException이다. ?.Invoke()가 안전하다.
  • “람다는 가벼우니 할당이 없다” — 바깥 지역 변수나 this를 캡처하면 클로저 객체가 힙에 생긴다. C# 9의 static 람다는 캡처 자체를 막아 이 실수를 컴파일 오류로 잡아 준다.

3줄 정리

  • 델리게이트는 메서드를 담는 변수, event는 그 필드의 한정자
  • 멀티캐스트는 순서대로 불리고 반환값은 마지막 것만 남는다
  • 람다는 변수를 붙잡는다. 캡처하면 힙에 클로저가 생긴다
